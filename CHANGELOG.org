#+TITLE: Changelog
#+STARTUP: showall

What each change guarantees, and what it leaves open.

* A name means what the source says it means

Two ways a program could be compiled into something it did not say, both of
them a C# identifier standing for more than one Bjolang name.

** Two names that mangle alike are two names

~Naming.sanitizeIdent~ is not injective — ~-~ becomes ~sub~, ~?~ becomes
~_QMARK~ — so ~a-b~ and ~asubb~ arrive at C# as one identifier:

#+BEGIN_SRC scheme
(let ((a-b 1) (asubb 2)) (+ a-b asubb))
#+END_SRC

used to declare ~asubb~ twice and fail to compile. The rename pass that already
existed for shadowed locals now counts collisions in the *emitted* spelling
rather than the written one, so the second binder is given a fresh name.
Parameters are covered too, including two parameters of one signature.

Nothing that was already correct changes: a name is renamed only where it
collides.

** A module may declare a binding named after a builtin

#+BEGIN_SRC scheme
(export list)
(: list (List int))
(def list (list 1 2 3))
#+END_SRC

An importer of that module has two ~list~ in scope — this one, and the builtin
— and generated code reaches both through a ~using static~, which is a spelling
C# resolves to neither. ~(list-length list)~ therefore failed to compile with a
CS0411 about a method group. An imported binding whose name is a builtin's is
now qualified to the class that declares it, so the import is what runs.

The rule is the one the language already had: the nearest binding wins. A local
or a definition in the same module always did win — C# lookup sees to that — and
still does; what changed is that an import does too. The builtin is untouched
wherever nothing shadows it.

This is what made ~(def list ...)~ at a REPL prompt unusable from the next entry,
since an entry imports the ones before it.

* A type crosses a module boundary only when it is exported

A module used to publish every type it declared, whatever its ~(export ...)~
said. Now the export list is the whole truth about a module's surface, for types
as much as for bindings:

#+BEGIN_SRC scheme
(export Crate make-crate)
(type (: Crate (Union (MkCrate int))))
#+END_SRC

A type has no signature to be missing — what it publishes is its declaration —
so naming it is the whole of what is required.

*Nothing a module publishes may name a type it withheld.* An exported
signature, a ~(where ...)~, a trait method, an impl target, the field types of
an exported record and the payloads of an exported union are all checked, and
the failure lands where the library is built rather than in somebody else's
module at a call whose author never saw the type.

This is a breaking change for any library that leaned on the old behaviour, and
the fix is always the same: name the type. The metadata format is at version 4,
so everything compiled against an older compiler needs rebuilding — ~build_std.sh~
for the standard library, and a rebuild of anything built against it.

** ~#:opaque~ — a name without its representation

#+BEGIN_SRC scheme
(export Handle)
(type (: (Handle %a) #:opaque (Union (Live %a int) Closed)))
#+END_SRC

The head crosses and the body does not. An importer may write ~(Handle string)~
in a signature, hold one in a ~List~ and pass it back; it may not name ~Live~ or
~Closed~ in an expression or a pattern, and for an opaque ~Record~ it may
neither read a field nor construct one. Inside the declaring module nothing
changes — opacity is a property of the boundary.

*Implementations still travel and still dispatch.* That is what makes an opaque
type usable rather than merely storable: an impl is keyed on the type, and a key
resolves wherever it is read, so a module can say what ~->str~ or ~=~ mean for a
type without saying what it is.

*The pattern matcher needed nothing.* A union case becomes a constructor binding
by walking the cases of a published declaration; an opaque type publishes none,
so a pattern naming one is refused on the path that already refuses a typo. The
same holds for constructor calls, ~record-ref~ and ~record-set~. What was added
is the explanation — the member names travel for the message and nothing is
registered under them:

#+BEGIN_SRC text
Pattern Error: Unknown constructor 'Live' at m.bjo:19. 'Live' belongs to
vault/Handle, which is exported #:opaque: the type's name crosses the module
boundary and its representation does not, so a value of it can be held and
passed on but not taken apart here.
#+END_SRC

~#:opaque~ on an alias is refused: an alias is expanded wherever it is named, so
there is no representation to hold back.

~(std mutable deque)~ is the first user. ~Deque~'s two lists and its count were
already documented as nobody else's business, and a mutable field was already
unwritable from outside; the marker makes them unreadable too, which is what the
comment had been asking for.

* ~(std mutable deque)~

The first thing built on mutable fields, and the reason they were wanted: a
double-ended queue that is written in place.

#+BEGIN_SRC scheme
(def work (deque))
(deque-push-back! work job)
(match (deque-pop-front! work) ((Some j) ...) (None ...))
#+END_SRC

Two lists — ~front~ in order, ~back~ reversed — so a push at either end is a
cons and a pop is a head. When the list at one end runs dry the other is
**split in half** rather than moved across wholesale. Moving all of it is the
textbook queue trick and it is quadratic on a *deque*: pop one end, pop the
other, and every pop hauls the whole structure back again. Half leaves both ends
stocked, so every operation is O(1) amortized. 200k alternating pops on a 200k
deque run in 13ms; the wholesale version would be doing ~10^10~ conses.

It lives under ~std/mutable~ so that reaching for it is a deliberate act, and
the module is the only thing that may write the fields — a mutable field is
writable only in its declaring module, so ~front~, ~back~ and ~size~ are not
somebody else's business.

** Equality is by contents, and it has to be written down

Two deques are equal when they hold the same elements in the same order,
whichever half those elements are sitting in. Pushing three items on the back
and popping one gives a deque ~=~ to one built by three pushes on the front.

The ~Eq~ implementation is not decoration. Without it a deque would fall to the
blanket, which is .NET's equality, which for this record is a field-wise
comparison of ~front~, ~back~ and ~size~ — so two deques holding the same
elements in different splits would have compared unequal, silently.

~eq-hash~ refuses, and that refusal is what keeps the paragraph above true. A
~Map~ keyed on a deque would ask .NET rather than asking the implementation, and
materialization cannot redirect that for a *generic* type. So rather than let
the two disagree, nothing is allowed to ask: the hash throws at the one call
that would have.

** What is still open

- **No transient interface**, which is what ~Readme.org~ originally wanted — a
  persistent deque with a mutable view over it. This is mutable all the way
  down instead. A persistent deque is still worth having and would not conflict.
- **No ~Collector~ implementation**, so a deque is not yet a comprehension
  target the way ~Set~ is.
- **Heap is still missing.**

* Mutable fields in records

#+BEGIN_SRC scheme
(type (: (Queue %a) (Record (: front (List %a) #:mutable)
                            (: back (List %a) #:mutable)
                            (: size int #:mutable))))

(record-set! q (front (list-reverse (record-ref q back))) (back Nil))
#+END_SRC

A field marked ~#:mutable~ is written in place by ~record-set!~. Until now the
language had exactly one mutation primitive — ~def/mutable~ plus ~(set! name
value)~, on a bare identifier — and everything else was persistent, which left
programs that genuinely hold state reaching for ~Array~ and a hand-rolled index
scheme.

~record-set!~ takes a name, writes one or more fields, and is void. All of its
values are evaluated, left to right, *before* any of them is written, so a value
expression that reads the record sees the state before the form rather than one
half way through it. ~record-set~ is untouched and still copies, taking the
mutable fields as they stand.

Four things are deliberately not allowed. A ~Struct~ may not have a mutable
field — it is a value type, so the write would land on a copy — and there is no
~struct-set!~. A union case may not have one, its payload being positional and
so having no name for a write to use. Only the declaring module may write a
field; a module that means its state to be reachable exports functions that
reach it. And constructing a record with a mutable field is not a syntactic
value, so a module-level ~def~ of one is not generalized — the ~make-array~ hole
arriving by a second route.

The emitted C# stays a ~record~. Only a *positional* parameter is init-only, so
the whole field list moves into the body and the constructor is written out:
~with~, ~ToString~ and a synthesized structural ~Equals~ all keep working, and
construction stays positional and in declaration order.

** Equality holds. Hashing does not, and says so.

~=~ is structural over what the fields hold at the moment of the comparison, so
two records equal now may be unequal later. All four paths to equality agree, as
they must: a direct ~=~, a dictionary-dispatched one, a container comparing
elements, and .NET calling ~Equals~.

~eq-hash~ throws. There is no honest number — hashing the mutable field breaks
the rule that a key's hash does not change, hashing only the immutable ones
breaks the rule that equal values hash alike — so a mutable record is not a
~Map~ or ~Set~ key and raises at the point it is asked, rather than being
accepted and then silently lost on the next write.

Closing that properly took two pieces. ~derive~ writes an ~eq-hash~ that calls
the new ~unhashable~ builtin, and codegen writes a throwing ~GetHashCode~ into
any record with a mutable field that materialization did not already write one
for. The second is the one that matters: materialization never fires for a
*generic* type, so ~(Box %a)~ with a mutable ~item~ would otherwise have kept
C#'s synthesized hash over that very field. ~Equals~ is left alone in that case
— the synthesized one compares every field, which is what ~=~ means here, so the
two already agree.

The ~#:mutable~ marker is published in a module's metadata. Not for diagnostics:
an importer never writes a foreign field, but it does *construct* the record,
and one that could not see the marker would generalize the construction and hand
out a single cell at two types.

** What is still open

- **A generic record with a mutable field can never have a working hash**, even
  a hand-written one, because materialization cannot reach a generic type. The
  throw is otherwise a default rather than a property: a non-generic type may
  hash only its immutable fields and mean it.
- **Transitive hash failure is a runtime error.** A record deriving ~Eq~ over a
  field whose type has no hash throws one level down rather than being rejected
  at compile time, which would mean tracking "has no hash" per implementation
  through the registry.
- **Nothing is done about concurrency.** A mutable record shared between fibers
  races, exactly as a ~def/mutable~ does. This is now at least written down.
- ~record-set!~ takes a name rather than an lvalue, so
  ~(record-set! (car xs) (x 1))~ needs a binding first.

* ~Eq~ for the library's collections

Implementations for ~(Set %a)~, ~(OrderedSet %a)~ and ~(OrderedMap %k %v)~, each
in its own module, joining the ~(Map %k %v)~ one already in the prelude.

The two ordered ones were the ones that mattered. ~OrderedSet~ and ~OrderedMap~
are C# classes that had no structural ~Equals~ at all, so ~=~ on two of them
meant *reference identity*: two sorted sets built separately out of the same
elements were not equal, silently. They now compare by a paired walk, which is
what the ordering buys — both trees enumerate in the same order, so keys, values
and elements alike are compared through ~Eq~ in place, and the tree's own
~Comparer~ never has to be trusted to agree with equality. ~(Set %a)~ has to ask
the trie instead, as ~(Map %k %v)~ does, so its element equality is .NET's.

Writing those in Bjolang alone would have *created* a split: ~=~ would have said
two ordered sets were equal while a ~Map~ keyed on one went on failing to find
it. So ~OrderedSet<T>~ and ~OrderedMap<TK, TV>~ gained ~Equals~ and
~GetHashCode~ in the runtime, computing the same paired walk. That is the same
move materialization makes for a type the compiler emits, done by hand for two
it does not.

All four collections now compute ~eq-hash~ and ~GetHashCode~ as the *same
number* — same operation, same seed — rather than each merely agreeing with
itself. ~Set~ and ~Map~ fold with xor, which is what their C# side already did.

** What is still open

- A transient has no implementation and should not: it is mutable and its
  identity is the point.

* A blanket ~Eq~

#+BEGIN_SRC scheme
(def/impl (Eq %a)
  (defun (= a b) (clr-equals a b))
  (defun (eq-hash a) (clr-hash a)))
#+END_SRC

In ~(std eq)~, which the orphan rule already required: a blanket applies at every
type that has none of its own, so one declared elsewhere would change what ~=~
means for modules that never heard of it.

This lands last, and that ordering is the whole of why it is safe. .NET's
equality for a record, struct or union the compiler emitted *is* that type's own
~Eq~ implementation, because ~Equals~ and ~GetHashCode~ are emitted as calls to
it. So the blanket routes to a hand-written implementation wherever one exists,
at any nesting depth — it is "derive, applied automatically" rather than a second
equality. Landed before materialization it would have been the split it exists
to prevent: ~(= p q)~ finding the user's implementation and ~(= (Some p) (Some
q))~ finding .NET's.

** What is guaranteed

- ~=~ works at every type with a head constructor. A record with no
  implementation compares field-wise; a class-backed one compares by identity.
- A tuple of an arity nothing implements — five or more — reaches the blanket
  through its synthetic head key rather than failing.
- A hand-written implementation still wins wherever there is one, including
  through a field whose own type has none.

** What is still open

- *Nothing can opt out.* ~(= p q)~ on two ports, or two fibers, compiles and
  means reference identity. There is no negative-implementation mechanism. The
  lever available, if a type's equality is genuinely meaningless, is to emit an
  ~Equals~ that throws — turning a silent wrong answer into a runtime one.
- *A type with no head constructor is not covered.* Resolution needs a head to
  look up before it can fall back to a blanket, so ~(= f g)~ on two functions is
  a type error. It says so, and names the implementation it was needed by.
- *A generic type still keeps C#'s synthesized equality.* Materialization is
  skipped for it, for the reason in the previous entry. The blanket now makes the
  missing dictionary constructible, so this could be closed; it has not been,
  because a derived implementation agrees with the synthesized one anyway and
  only a hand-written implementation for a generic type can differ.

* ~derive~, and equality that .NET agrees with

Two things, shipping together because both touch record, struct and union code
generation and because either alone is half an answer.

** Materialization

When a record, struct or union has an ~Eq~ implementation, its ~Equals~ and
~GetHashCode~ are emitted as calls to that implementation:

#+BEGIN_SRC csharp
public record Point(int x, int y, string cache) {
    public virtual bool Equals(Point? other) => other is not null && Eq_Point.Instance.eq(this, other);
    public override int GetHashCode() => Eq_Point.Instance.eqsubhash(this);
}
#+END_SRC

C# synthesizes those only when they are not written, and a record's ~==~ calls
~Equals~, so ~EqualityComparer<T>.Default~ *is* the implementation the program
wrote. That closes the gap the previous entry left open, everywhere at once and
in one place:

- ~Map~ and ~Set~ are correct with no dictionary threaded through them and no
  signature changed, because they key on ~Equals~ and ~GetHashCode~.
- Interop is correct: a ~HashSet<Point>~ or a ~Distinct()~ agrees with ~=~.
- An implementation that deliberately ignores a field is ignored by all of them
  too. That is the test worth having, and it is in ~TestFiles/128_derive.bjo~.

The orphan rule is what makes the lookup possible: an implementation for a type
declared here is in this module too, so both are in hand when the type is
emitted.

A union's override goes into every *case* class. A derived record synthesizes
its own ~Equals~, which overrides the base's, so one written on the abstract base
alone would be silently dead.

** ~type/derive~

A macro in ~(std prelude)~:

#+BEGIN_SRC scheme
(type/derive (Eq)
  (: Point (Record (: x int) (: y int))))
#+END_SRC

Records and structs compare their fields in declaration order; unions compare
the case first and then the payload positionally; a type with parameters derives
a conditional implementation. The trait list is a list so that ~Ord~ can join it
without the form changing shape.

It is written in Bjolang rather than in the compiler, which needed the macro
system to reach a little further. Rule 3 — "strip the rename and dispatch" — now
applies to every position that *selects* rather than binds: a type definition's
~Record~/~Struct~/~Union~ tag, the trait in a ~def/impl~ and in each of its
~(where ...)~ constraints, the clause tags inside one, and the name of a method
in an implementation. A method's parameters keep their renames, being binders.

** What is still open

- *A generic type keeps C#'s synthesized equality.* Its implementation is
  conditional, and there is nothing inside ~Box<T>~ that could build the ~Eq<T>~
  dictionary the ~(where ...)~ asks for. A derived implementation is field-wise
  and so agrees; a hand-written one for a generic type can differ from what .NET
  asks. This closes when there is a blanket implementation to use as the
  dictionary.
- *A derived body reports against the ~type/derive~ form, not the field.* Every
  node a macro builds carries the call site's range. The message names the type
  with no implementation and the implementation that needed it, which between
  them say which field.
- *~=~ on a ~Map~ still matches keys by lookup.* That is now correct for every
  key type whose ~Equals~ is its ~Eq~ implementation, which is every record,
  struct and union the compiler emits — so what is left is a key type that is
  neither.
- *There is still no blanket ~Eq~.* A type with no implementation of its own has
  no equality at all.

* Equality is a trait

~=~ is a method of ~Eq~, declared in ~(std eq)~ and re-exported by the prelude:

#+BEGIN_SRC scheme
(def/trait (Eq %a)
  (: = (-> %a %a bool))
  (: eq-hash (-> %a int)))
#+END_SRC

Before this there were three unrelated equalities. ~=~ was typed ~(-> %a %a
bool)~ and emitted as C# ~==~, which does not compile at a type variable, does
not compile on ~Option~ or ~Result~, and silently means *reference* equality on
~List~ and ~Vec~. ~equal?~ was ~EqualityComparer<T>.Default.Equals~. ~eq?~ was
~ReferenceEquals~.

** What is guaranteed

- One equality. ~equal?~ is gone; it *is* ~=~ now. ~eq?~ is unchanged and still
  means object identity — for mutable cells, and silently structural on a value
  type.
- ~=~ at a type with no implementation is a type error naming the trait and the
  type, rather than a C# compile failure or a wrong answer.
- A container compares its elements through *their* ~Eq~ implementation, so
  ~(= (Some p) (Some q))~ reaches whatever ~p~'s type says equality is, at any
  depth. Implementations ship for ~List~, ~Vec~, ~Option~, ~Result~, ~Map~ and
  tuples of two, three and four elements.
- A generic function acquires ~(where (Eq %a))~ from its body. Nothing that
  compared two values has to be annotated.
- ~(= 1 2)~ still emits ~(1 == 2)~. A statically resolved call is spliced, so
  the primitive path costs no dictionary and no allocation — asserted against
  the generated C# in ~TestFiles/codegen/equality.bjo~, because no behavioural
  test can see it.
- ~eq-hash~ lives in the same trait as ~=~ rather than in one of its own,
  because it is derived from the same choice of fields. There are no default
  bodies: the only body a default could have is "ask .NET", which is wrong in
  exactly the case someone wrote an implementation for.
- ~double~ is reflexive on ~NaN~, deliberately: it uses ~Equals~ rather than
  ~==~, because a hash-based container cannot find a key that is not equal to
  itself. IEEE's answer is not available through ~=~.

** What is still open

- *A hand-written implementation and .NET disagree.* C# still synthesizes
  ~Equals~ and ~GetHashCode~ for a record or struct, so ~(def/impl (Eq Point)
  ...)~ governs every ~=~ in Bjolang while ~Map~, ~Set~, ~HashSet<Point>~,
  ~Distinct()~ and every other .NET consumer go on using the synthesized ones.
  Nothing in the language reaches them — every ~=~ is a trait call and the
  container implementations are Bjolang — but a ~Map~ keyed on a type with a
  hand-written implementation is keyed on a different equality from the one ~=~
  answers with.

  This closes when a record's ~Equals~ is emitted as a call to its ~Eq~
  implementation. It is deliberately not papered over by threading ~Eq~
  dictionaries into ~Map~ and ~Set~: that would fix two containers and leave
  interop broken, where emitting ~Equals~ fixes all of it in one place.

- *~=~ on a ~Map~ matches keys by lookup*, so key equality there is the trie's —
  .NET's — while values go through ~Eq~. The same fix closes it.

- *There is no ~derive~.* An implementation over a record's fields is written by
  hand.

- *Tuples reach ~Eq~ through a synthetic constructor key* (~Tuple2~, ~Tuple3~,
  ...); functions and other structural types have no head constructor and so
  cannot have an implementation at all.

** Incidental

- ~clr-eq~, ~clr-equals~ and ~clr-hash~ are builtins private to ~(std eq)~,
  refused by name anywhere else. They are what the primitive implementations are
  written in, and they are shut away against the day a type's ~Equals~ is its
  ~Eq~ implementation — at which point an implementation written with one of
  them calls itself forever.
- ~hash-combine~ is a builtin, for writing an ~eq-hash~ over several fields.
- A trait method's arguments are now all positional, keyword literals included.
  ~(= k #:foo)~ compares a keyword; it is not a call with a keyword argument,
  and no trait declares one.
- ~run_tests.sh~ grew a ~TestFiles/codegen~ stage: each ~;; EXPECT-CS:~ line in
  a fixture is a regex the generated C# has to match.

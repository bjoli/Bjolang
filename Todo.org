Known gaps, written down where they were found. One entry each: what, why it
matters, and the fix where one is known.

* CML: where the remaining speed is

~bench/Cml/Program.cs~ runs the ring at 55 ns/op on the same layer the language
runs at 77-85, and the skewed choose at 90 against 145, so the cost is the seam
between ~sync~ and the layer. Surgical,
separately measurable changes; ~IEvent<T>~ stays the spec. Unmeasured unless
noted.

- *A ~choose~ over sends allocates each send's event.* 32 B per send
  branch: a receive event is the channel, but a send event holds its value
  (157 against 93 B/op for two branches, ~120 ns/op either way). Events are
  values and may be kept and synced again, so the object cannot be reused
  unless the compiler emits a path for a ~chan-send~ written inside
  ~(sync (choose ...))~. Not worth it so far. The larger part of a
  ~choose~'s allocation is its ~SyncState~ (~54 B), on every ~choose~.

* Units

- *Maybe: a unit as the parameter of a type.* F# has
  ~type Body<[<Measure>] 'u> = { Pos: float<'u>; Vel: float<'u/s> }~. Today
  a type's parameters are types, so ~(Vec2 %a)~ at ~(Vec2 (double m))~ works,
  and a field whose unit is computed from the parameter (~%u/s~, ~%u^2~)
  needs a parameter of its own, with the relation said in each signature.
  ~registerTypeDefs~ rejects a unit variable in a field, case, newtype or
  alias. Do it when a program needs it. What it takes:
  - A unit argument as a ~TNum~ over a marker carrier, so that ~unify~'s
    ~TNum~ arms already treat it.
  - A parameter used only in unit positions is a unit parameter; the registry
    and the module metadata record which (~currentVersion~ bump). One used
    both ways is an error.
  - ~(Vec2 m)~ and ~(Vec2 %u)~ in ~TypeSyntax~: a unit expression in a unit
    position.
  - ~instantiateRecord~, the constructor schemes and patterns substitute the
    unit parameters in the field types too: ~substTypeVars~ leaves units.
  - ~eraseUnits~ drops unit arguments; the C# record and union classes have
    no generic parameter for them. About 40 sites zip a type's parameters
    with its arguments, and each has to skip them.

* Source mapping (~#line~)

- Hoisted temporaries inherit the directive of the statement before them; they
  want ~#line hidden~ (~emitStatement~'s prelude, ~hoistToTemp~, two paths in
  ~generateLocalFunction~). Harmless today by luck.
- Directives are emitted even when the line has not changed. A dedup must
  survive scratch buffers being relocated.
- Inlined trait methods keep the impl's ranges, so a trace names the impl and
  not the call site.
- Both build configurations keep a pdb, so its absence no longer tells a ~-d~
  build apart. Nothing depended on it.

* Diagnostics

- Errors from generalization, trait registration and parts of declaration
  checking carry a location only if their call site supplied one. Threading a
  ~Range~ into ~unify~ would close it.
- The numeric-literal message blames the literal when its ~Num~ constraint
  is solved late: ~(map-set m "j" "v")~ on an ~int~-keyed map names a ~1~
  elsewhere (~Traits.fs~).
- A ~loop~'s ~:finish~ value against the loop's result reads as "two
  branches": the message is the expansion's ~if~, not the clause. The common
  case is a loop with no ~=>~ that can also run out: "void" is that exit's
  value, and the message does not say so or suggest ~=>~.
- A named let that only calls itself never returns, so nothing gives its
  result a type, and the type variable stays unresolved:
  #+begin_src bjolang
  (def xs (let more ((i 0)) (more (+ i 1))))
  (println (->str (length xs)))
  #+end_src
  ~length~ then fails with "no implementation of trait 'Collection' for
  '?a' ... no head constructor", which does not say that the loop has no
  exit. Without the ~length~, it compiles, and the C# has
  ~object /* unresolved meta */~ in it. Found through ~(std scan)~, where
  ~'(word (:? int) ...)~ once expanded to such a loop. The fix: report a
  result type that is still open after generalization as "this never
  returns a value", at the expression, or close it to ~unit~ when nothing
  constrains it.

* Pattern matching

- A ~(:is ...)~ clause that no value can reach is not reported. A type test
  covers nothing (~Exhaustiveness.fs~), and it is emitted in the guard, so C#
  does not see it either:
  #+begin_src bjolang
  (match o
    ((:is System.Exception) "exception")
    ((:is System.ArgumentException) "never reached")
    (_ "other"))
  #+end_src
  Before the type test moved to the guard, C# refused the second clause with
  CS8120. The fix: resolve both CLR types and warn when an earlier unguarded
  ~:is~ in the same position tests a type the later one is assignable to
  (~IsAssignableFrom~). A warning, not an error, because it is only a part of
  what C# proved: nulls, interfaces and ~object~ are not modelled.
- The alternatives of a nested ~or~ are not checked for being reachable:
  ~(Tuple (or 1 1) _)~ and ~(Some (or (:at-least 0) 3))~ compile. Only a
  clause's top-level ~or~ is checked (~checkAlternatives~), because only its
  alternatives become ~case~ labels of their own, and C# accepts the nested
  ones as one ~or~ pattern. The fix: expand each nested ~or~ into one row per
  alternative, and check each against the rows above and the alternatives
  before it, as Maranget's algorithm does for or-patterns.

* JSON (~(text json)~, ~(text json-codec)~)

- ~json-codec.bjodoc~ is out of date in two places. "Not here yet" says
  ~(text json)~ has no writer, but ~json->string~ and ~write-json~ are there
  (~363_json_write.bjo~). And it says an error gives no path through several
  levels of records, but a ~(Vec Item)~ field of an ~Order~ reports
  ~Order.items: Item.id: expected an integer~. Found while adding
  ~request-json-as~ to bjoweb.
- There are no instances for ~List~, ~Array~, tuples, ~decimal~, ~float~, the
  date and time types or ~Uuid~, and ~def/json-type~ takes records only. A
  union, such as a status written as ~"open"~, needs its two ~impl~s by hand,
  which is about eight lines.
- Reading an object: half of what it allocates, 376 of about 750 bytes for
  four short fields, is its map, built by ~transientmap-set!~ one key at a time
  and then frozen. A map built from pairs it knows all of, with nodes of the
  size they end at, would help every map built from a collection, not only
  JSON's; the reader would put an object's pairs on its stack, as it does an
  array's elements, and build the map once.
- Reading a float copies its bytes into the builder before parsing them.
  Most of a float's time is .NET's parse, so the copy is a small part.
- ~write-json~ makes the whole text as a string, then writes it, so a large
  response is in memory twice and nothing goes out until all of it is made.
  Writing the builder's chunks to the port needs a port operation that takes a
  builder, with a twin for a bjoroutine, as ~write-string~ has.
- With ~#:ascii~, a string is still written a character at a time: every
  character outside ASCII needs an escape, and ~string-search-any~ takes a
  set of characters, not a range.
- What is left in writing an object, about 240 ns for four fields, is not
  measured further: the entries from ~map->seq~, a search for each key, and
  ~add-newline!~ called per field even without ~#:indent~.

* Characters and strings

- ~char-foldcase~ is ~ToLowerInvariant~: differs from Unicode's simple fold for
  ß, ﬁ and the like.
- Numbers are read and written in the invariant culture only; there is no
  ~Culture~ to ask for ~1,5~. ~string->int~ still uses the ambient culture
  (only the sign can differ).
- *No SIMD over a string's bytes.* ~(std simd)~ loads from arrays and
  ~MutableVec~ only. A load from a string needs a byte index, and a string's
  positions are opaque cursors. ~string->bytes~ copies. When
  ~ReadOnlyMemory<byte>~ is usable from Bjolang, a string can give its bytes
  as one, and ~SimdSource~ can take that without exposing string indexes.
- *Cursor loops: a span in place of the hoisted bounds.* ~hoistStringBounds~
  (Codegen.fs) gets a string's bounds once before a loop where the string does
  not change. A ~ReadOnlySpan<byte>~ local and an index into it would be about
  10-20% faster again: the JIT then knows that the index check covers the
  read. A span is legal only in a loop that runs inline in its method, with no
  closure that captures it, and with no ~await~ or ~yield~ that it must
  survive. Elsewhere keep ~StringBounds~. Cursors are offsets into the whole
  array, so a step reads ~span[c - lo]~ and makes ~lo + i~.
- *Hoisted bounds: what is not done.* A merged loop group (several members in
  one ~while~) does not get bounds. A string that is a module-level binding,
  or that ~set!~ writes anywhere in its declaration, is read again at each
  step.

* Emacs mode (~bjomode.el~)

- A named loop aligns its clauses under the name, not under ~(:for~; needs a
  custom indenter (~lisp-indent-specform~ cannot express it).
- A ~match~ arm's body aligns under the pattern, as Emacs does for ~cond~.
- Library forms that read as bodies (~with-nack~) are not in

* Monomorphisation of constrained generics

Copies are made per ground instantiation, to a fixpoint, bounded by a code-size
budget (module size or ~budgetFloor~). Termination is by key; polymorphic
recursion cannot be written. The stdlib's 22 constrained generics have call
out-degree ≤ 1, so copies grow additively; largest demand 722 nodes
(~139_ord.bjo~). A branching graph would make the floor matter.

- *Every type argument must be ground*, so copies have no type parameters.
  Keeping unconstrained ones needs agreement with ~generalize~ on order. A
  function-typed argument is declined.
- *Suspending functions are not copied.* The twin is generated inside
  ~checkDeclGroup~, out of this pass's reach; ~Naming.specializedCopy~ already
  names it ~f__at_int__bjo~.
- *Mutual recursion is declined*: the group keeps its dictionaries
  (~284_mutual_dictionaries.bjo~).
- *A mention that is not a call is passed over.* Correct via eta-expansion.
- *A body that will not serialize is not published* (~try~, bare list literal,
  tuple destructuring, local function with keyword/rest parameters): calls keep
  their dictionary.
- *Each module makes its own copies.* An importer specialises a published body
  where it calls it, so ~f~ at ~int~ is copied into every module that calls it
  at ~int~. A project should collect its instantiations and monomorphise each
  function once: the copies in one place every module links, rather than one
  per caller. Belongs with evidence structs.

* Reading lines is slower than in C#

A named ~let~ or a ~loop~ is emitted as ~while (true)~. Each iteration copies
each variable into a local, and each jump assigns the new values through a
temporary per variable (~__next__~).

- *The copies and temporaries cost nothing.* Tried and measured: a loop
  without closures emitted with no copies, and a jump that assigns each
  variable directly, with a temporary only where a later argument reads the
  variable. The JIT made the same machine code of the hot loops (revcomp's,
  fannkuch's ~rev~, fasta's ~pick~), with all values in registers. Same-compiler
  A/B: revcomp, nbody, spectral-norm and mandelbrot equal within 1.5%, fasta
  and fannkuch-redux 2 to 2.5% slower by code layout. Not kept.
- *Reverse-complement's loop is as fast as C#'s.* Timed by phase in both
  programs, on the 25,000,000 input: the loop 278 ms in Bjolang, 275 ms in C#.
  Two rewrites of the port's loop (one byte per iteration as the C# does it,
  and one line per step with a counted inner loop) were not faster.
- Its gap to C# was reading standard input, and is closed: see
  ~bench/clbg/README.md~, "Reading standard input".
- *A port over a pipe or a socket refills asynchronously also for a blocking
  caller.* Standard input now reads synchronously for one; a pipe's read half
  (~SmallBufferSize~) and other streams that are not ~ISyncReadable~ still
  pay a task per refill. Measure before changing them: a socket's
  ~ReadAsync~ is a real asynchronous read, unlike standard input's.

* Colourless concurrency

- Two lambda pins (into a .NET ~Func~, into a structure of ground ~->~) get the
  generic ~Unpinned~ message. Unreachable from fixtures today.
- The lazy ~Seq~ functions have no suspending copy. Decided: the copy would
  return ~AsyncSeq~, a different function. ~port->chan~ instead.
- A ~(do ...)~ block cannot suspend: ~:bind~'s lambda colour is fixed. Would
  need ~:bind/bjo~ or a keyword on ~do~.
- *Parsing a string counts as parking.* The bjodat and JSON readers share
  one core for strings and ports, and every function in it reaches the
  ~read-some~ a refill makes, so ~parse-bjodat~ and ~parse-json~ are
  blocking definitions with suspending copies. Reached through an ordinary
  lambda from a bjoroutine, the lint reports the parse, which on a string
  never waits (samizdat's ~generate-docs~ did, fixed there with a loop).
  A port-free copy of the core, or a way for a library to say a function
  does not park, would end it.

* Traits and macros

- *Constraints over an ordinary trait are checked only when code is made.* One
  over a .NET interface is checked during type checking too, so dead code is
  checked; one with implementations is checked in ~Lowering~ when its evidence
  is built, after ~Simplify~ has removed dead branches.
- *A projection only in an impl's associated types.* ~(assoc Iterable elem
  %s)~ can be written in an impl's ~(type ...)~, where the where clause
  guarantees the impl it names. A function's ~where~ cannot constrain one,
  ~(where (->str (assoc Iterable elem %s)))~ fails in Lowering, and a
  function signature naming one at a concrete type fails because signatures
  are read before impls are registered. Both want the same thing as the
  impl case: a projection treated as a type parameter of the function.
  ~(std parallel)~ meets it: a generic function cannot iterate the parts of
  any ~Chunkable~, ~(where (Iterable (assoc Chunkable chunk %c)))~. A pin
  works: ~(where (Chunkable %c #:chunk %p) (Iterable %p #:elem %e))~.
- *A number collector given as a value does not get its type from its
  use.* Passed to a function that pins ~(Collector %k #:elem %x)~ with
  ~%x~ double, ~summing~ is ~(Summing int)~ and the pin fails.
  ~(: summing (Summing double))~ works. Found with ~par-collect~, since
  removed.
- *Pins are matched by the name of a rigid variable.* A body's pins
  (~Registry.PinnedAssocs~) speak of its signature's variables, and a scheme
  read in that body is read without them (~Unification.withoutPins~). A type
  that reaches the body some other way, written over a variable of the same
  name, would be rewritten by them. Renaming a pinned function's variables
  apart when its body is checked would end the question.
- *~chain~ tests its side at every step.* Over two arrays it is 2.8 times
  slower than two loops: the cursor's flag is tested in ~done?~, ~current~ and
  ~next~, and the JIT keeps the bounds checks, which it cannot tie to the
  flag. A loop over a ~chain~ at known types could be lowered as two loops,
  one per side, with the body shared.
- *A copy of an ~#:inline~ constrained function is made even where every
  call to it is then copied.* ~Monomorphise~ checks the copy, ~TraitInline~
  copies its body into each call and drops the copy. The check of the copy
  is work for nothing; marking such a demand would save it.

* Found while writing bjostat's parallel loops

Found in ~bench/parallel.bjo~ of bjostat, where the parts of a loop run on
several cores and their ends are events.

- *The docs of ~spawn/thread~ may be out of date.* They say that for work
  that uses a core ~Task.Run~ "buys nothing at all: it is the same pool".
  Fibers now run on ~Bjoml.Workers~, a pump for each core, so a fiber that
  computes holds its pump, and ~(sync (blocking thunk))~ does not: the
  thunk runs on a pool thread while the fiber is suspended. Measured, the
  sum of 1M rows in 8 parts: 0.52 ms by ~blocking~, 0.49 ms by fibers that
  compute, 1.25 ms by ~spawn/thread~, which makes a thread for each part.
  What ~blocking~ does not show is whether the parts delay the pumps,
  which run on the same pool's threads. If they do not, ~blocking~ (or a
  function of the same body with a name for computing) is the way to run
  short parts, and ~spawn/thread~ is for long ones.

* ~(std parallel)~

- *A map's parts are as even as its hashes.* The trie split weighs a node
  by its level, as spread hashes make it. Keys whose hashes agree in their
  low bits put most entries under a few nodes, and the parts are then far
  from equal. Exact weights would need a size in each node, or a count in
  the split, which cost half of a sequential walk.
- *A walk of a map in parts stops at 2-3x* on 24 threads, against 3.7x for
  a sum of an array: a walk follows pointers. Not examined further.
- *~loop/parallel~.* A ~loop~ whose ~:for~ is over a ~Chunkable~ and whose
  parts' accumulators are joined at the end. ~in-parallel~ with a loop in
  each part does it by hand, combining finished values by ~Combinable~. A
  clause would merge unfinished accumulators: whether that needs a trait
  on collectors, or ~Combinable~ on ~%acc~ is enough, is open.
- *Parts that allocate are bound by the GC.* On 1M elements, 24 threads, a
  vector's ~par-map~ of ~(* 2 x)~ is 0.62x the sequential ~vec-map~ with
  the default settings, and 0.98x with ~DOTNET_GCgen0size=0x4000000~; of a
  sine 2.56x and 5.77x. A map's ~par-filter~ goes from 1.60x to 5.90x. An
  array's ~par-map~, which allocates one array, is 5.5x either way. Server
  GC (~DOTNET_gcServer=1~) did not help the parallel row. Decided: Bjolang
  programs do not set a GC budget of their own; a program that needs one
  sets it (~bench/bjolang/parallel-collections.bjo~).
- *An ordered map's ~par-map~ is 0.75x the sequential one* with the default
  GC settings, 1.9x with ~DOTNET_GCgen0size=0x4000000~, after ~Concat~ and
  ~MapValues~ by leaves. Its parts allocate two arrays of 64 for each leaf,
  and are bound by the GC as a vector's are.
- *A ~par-filter~ of a map sees only the value.* The inline trait is over
  the type constructor, so its method sees ~(Map %k)~'s last argument. An
  inline trait cannot declare associated types, which a predicate type per
  implementation would need.
- *Compute threads delay fibers by keeping the cores busy.* The default is
  now one less than the logical cores. With bjostat's ~bench/latency.bjo~
  on 24 logical cores, a fiber that sleeps 1 ms woke at the median 0.32-0.42
  ms late with 23 compute threads, 0.22 with 18 and 0.14 with 16, at 472-484,
  429-444 and 425-430 loops. Why 24 compute threads gave a maximum of
  7.2-8.6 ms in every run, and 23 one of 1.9-2.7 ms, is not known: the
  calling thread posts one runner fewer and takes parts, so 24 threads
  compute in both. A priority below the run queues' threads is not
  measured.
  - The tail may not be from the compute threads: in the same bench, with
    no compute threads, "fibers that compute" had a maximum of 6.6-7.5 ms
    and "blocking" one of 8.0-10.0 ms. Any load on all cores may delay a
    wake. This machine is a KVM guest (24 vCPUs on a Ryzen 9 5900X), so
    the host's scheduler or vCPU steal can be the cause.
  - To do on a real machine (not a VM): run ~bench/latency.bjo~ with 24,
    23 and 16 compute threads and compare the maximum; read the steal
    column of ~/proc/stat~ during the run; try ~SCHED_BATCH~ or
    ~SCHED_IDLE~ for the compute threads; try fewer run queue threads.
- *A call of 24 empty parts has a tail.* Back to back, 8 us at the median
  and 28 us at p90, 16 us on average: in one call of ten or more the first
  part waits about 20 us, the wake of a thread that sleeps, although the
  compute threads spin 50 us. Not GC (the same with a gen0 of 256 MB). Not
  examined further. After the threads sleep, 26 us: the wake of one thread
  in this KVM guest (~BjolangRuntime/Cml/design.md~, "The cost of a call of
  (std parallel)").
- *The compiler cannot see that a lambda runs on another thread.* The lint
  that a call parks its thread exempts the lambdas of ~blocking~ and
  ~spawn-thunk~ by name (~Prelude.elsewhereBuiltins~). A library function
  such as ~in-parts~ or ~computing-each~ cannot say the same of its
  function parameter, so a nested call in a part, which parks a compute
  thread, is warned of as if it parked a thread that runs fibers. A
  declaration on the parameter would fix it.
- *Parts are not split again.* ~chunks~ makes about k parts at once, so a
  part that is slower than the others is not shared. A recursive split, as
  in Rayon or Java's ~Spliterator~, would let idle workers take half of it.
- *On one core the parallel rows of ~bench/bjolang/parallel.bjo~ are up to
  20% slower than the sequential ones* with tiered compilation on, and
  0.99x with ~DOTNET_TieredCompilation=0~. Not examined. Probably the parts
  call the kernel more often than the sequential row does, so it tiers up
  during the timed runs, and the JIT's background thread competes for the
  one core.

* Packages and projects

- *Build output lands beside the source*, also inside ~.bjo/pkg/...~: two
  projects build one package twice, and a read-only package cannot be built.
  Needs staleness, the resolver table and the build record to know a second
  directory.
- *A relative import still means a path*, even across a package boundary.
- *No ~bjo add~, ~update~, ~remove~*: writing the manifest back would lose its
  comments and layout.
- *No shared clone cache*: it would be shared state, and nothing locks.
- *No registries, commit or branch pins, or pseudo-versions*; an untagged commit
  needs a path source.
- *One version of a package per build*: two copies would be two modules with one
  identity.
- *No ~bjo install~, ~test~ or ~clean~*, and one entry point per package. Tests
  are ~bjo run tests/x.bjo~, which exits 1 after a ~FAILURE:~.
- *Nothing locks ~.bjo~* against two ~bjo~ processes; the second fails loudly.
- *A version requirement on a path dependency is ignored*: a path source is an
  override.

* Benchmarks (~(std bench)~, ~bjo bench~)

- *Allocation is counted on the measuring thread only*
  (~GC.GetAllocatedBytesForCurrentThread~), so a body that spawns fibers or
  hands work to the pool allocates more than ~alloc/op~ says. ~BjoBench~ has
  ~AllocatedInProcess~ (~GC.GetTotalAllocatedBytes(precise: true)~), which
  counts every thread, but also the JIT's background compiles, timers and
  anything else running: noisier, and the precise read is not free. Wants a
  choice per benchmark or run (~#:alloc 'process~, ~--alloc process~), and
  the header saying which was counted.
- *No ~#:teardown~*: a setup that opens a file, a socket or a scope has
  nowhere to close it, and a run of many cases leaks them until the process
  ends. First, run each case in a scope of its own: scopes already track
  open ports (it is how a ~deftest~ fails when it leaves a file open), so
  that may close most of what a setup opens with nothing written. Then
  ~#:teardown~, forms with the setup's names in scope, for what a scope
  cannot see, and ~#:teardown-every~ after each call of a ~#:setup-every~
  benchmark, outside the time. A teardown pairs with a ~prepare~, and a
  case can be prepared more than once: again by ~--compare-within~, and once
  per process by ~--serve~. So ~CaseRun~ gains a ~done~ that whoever
  prepared it calls, also when the body raised; ~--serve~ gets a
  ~(finish i)~ command and finishes what is left on ~(quit)~.
- *Only time per call is reported.* A body that processes n items or bytes
  wants items/s or MB/s, which compare across sizes where ns/op does not:
  ~#:throughput ((bytes (vec-length data)))~, an expression of the setup's
  names giving the work one call does, and a column of it divided by the
  median. With ~--scaling~, the column that should stay flat for a linear
  body.
- *Nothing fails a run on allocation.* Allocation per call is much steadier
  than time, so it is the check a CI job can be strict about: ~--fail-alloc~
  against ~--compare FILE~ or ~--against REF~, exiting 1 when a benchmark
  allocates more by more than a threshold. Not exact, though, so the
  threshold is in bytes and in percent, both: .NET 10's optimized code can
  put objects on the stack, and whether it does can differ between tiers
  and, with profile-guided optimization, between processes; and ~alloc/op~
  is an average over ~k~ calls, so growth now and then (a buffer doubling)
  is a fraction of a byte. The comparison shows the change in ~alloc/op~
  beside the time's.
- *~#:setup-every~ times one call at a time*, with two clock reads around
  each call, so their cost is in every sample and a body under a microsecond
  is marked "below resolution" rather than measured. Measure that cost and
  take it off, as BenchmarkDotNet does with its overhead run: during
  calibration, time an empty body the same way, its setup made before it and
  the clock read around it, and subtract the median of that from each
  sample. Each call still gets a fresh input
  that is hot in the cache, which is what ~#:setup-every~ is for. Batching
  ~k~ inputs made ahead would remove the clock reads too, but it changes
  what is measured: the inputs are cold in the cache by the time the body
  reaches them, and survive collections into older generations, where a body
  that writes into them pays for it. If wanted, an opt-in for a body meant
  to be measured on cold data.

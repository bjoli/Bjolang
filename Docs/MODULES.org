* Modules, imports and includes

Every ~.bjo~ file is one module. Its module name is the file name with ~.~ and
~-~ replaced by ~_~, and it compiles to a C# static class named
~<module>_Module~.

There are three ways to pull in code from elsewhere, and they do different
things.

| Form                     | Creates a module?     | Makes names visible          | Links an assembly |
|--------------------------+-----------------------+------------------------------+-------------------|
| ~(import (std prelude))~ | yes, the imported one | its exports and re-exports   | yes               |
| ~(import "helper.bjo")~  | yes, the imported one | its exports and re-exports   | yes               |
| ~(include "helper.bjo")~ | no — splices into /this/ module | everything in the file       | n/a               |
| transitive ~BjolangDeps~ | no                    | nothing                      | yes               |

"Its exports" means exactly that, and includes its *types*: a type that is not
named in an ~(export ...)~ does not cross an import (see [[*Exporting a
type][Exporting a type]]).

An import may be wrapped in modifiers that decide what its names are called
here and which of them arrive; see [[*Import modifiers][Import modifiers]].

*An import is always a compiled unit.* ~(import "helper.bjo")~ compiles
~helper.bjo~ to ~helper.dll~ and imports that, exactly as if the ~.dll~ had been
there already. So the two spellings of ~import~ differ only in where the file is
looked for, and the choice between ~import~ and ~include~ is a choice about
whether there is a boundary at all:

- an *import* is a boundary. Only exported names cross it, every exported name
  needs a signature *somewhere*, and inlineable bodies cross as metadata — which is lossy,
  since ~Codegen.isSerializableTemplate~ refuses some shapes and those fall back
  to a call.
- an *include* is not. Everything is in scope, nothing needs exporting, and an
  inline template keeps its full body.

Use ~include~ to split one module across files. Use ~import~ when the other file
is a module in its own right.

** Import modifiers

An import may be wrapped in modifiers that decide what the names it brings in
are called here, and which of them arrive at all:

#+BEGIN_SRC scheme
(import (prefix (banan boats) "bb/")
        (postfix (banan rafts) "/r")
        (prefix-defs (util parse) "p/")
        (prefix-types (util geom) "G/")
        (rename (std http) (http-fetcher http-get))
        (only (std json) parse-json)
        (except (std ports) port->lines)
        (prefix (except (std strings) trim) "s/"))
#+END_SRC

They *nest* rather than sit in a list, and are read inside-out: the last line
drops ~trim~ and then prefixes what is left. A modifier belongs to the import
that wrote it, not to the module — the same module imported twice under
different modifiers answers to both sets of names (see [[*Importing one module
twice][Importing one module twice]]).

| Modifier                        | Applies to                                                    |
|---------------------------------+---------------------------------------------------------------|
| ~(only m a b ...)~              | defs and macros: keeps these and drops the rest               |
| ~(except m a b ...)~            | defs and macros: drops these and keeps the rest               |
| ~(prefix m "s")~                | everything but impls                                          |
| ~(postfix m "s")~               | everything but impls                                          |
| ~(prefix-defs m "s")~           | defs and macros                                               |
| ~(postfix-defs m "s")~          | defs and macros                                               |
| ~(prefix-types m "s")~          | types, constructors, traits and trait methods                 |
| ~(postfix-types m "s")~         | types, constructors, traits and trait methods                 |
| ~(rename m (old new) ...)~      | defs and macros                                               |

*** What a modifier may and may not touch

*Whatever types a module exports always arrive.* An imported signature is source
text that has to resolve the types it mentions, so there is no view of a module
in which its own signatures do not typecheck. ~only~ and ~except~ therefore
filter defs and macros only, and naming a type in one is an error rather than a
silent no-op. What decides which types there are to arrive is the exporting
module's ~(export ...)~ (see [[*Exporting a type][Exporting a type]]) — a
modifier narrows the *spelling* of a surface, never the surface.

An ~#:opaque~ type arrives as its name alone, so it is a type here and has no
constructor to be filtered, renamed or prefixed.

*Impls are never filtered, renamed or prefixed.* An implementation has no name
to rename. It travels with its module unconditionally, and a trait method
called by its bare — or prefixed — name still finds it.

*A constructor follows its type.* It is renamed by the ~-types~ variants, never
by the ~-defs~ ones, and ~only~ and ~except~ cannot name it. It is also
published with its type and withheld with it: exporting a union exports its
cases, and marking one ~#:opaque~ keeps them all back.

*Renaming a type is refused*, and points at ~prefix-types~ for a module's worth
of them or a local ~(type (: NewName Old))~ for one. *Renaming an individual
trait method is refused* too: an impl is filed under the name the ~def/trait~
declared, so a bare-name remap would leave the method pointing at nothing.
Prefixing the trait's module renames its methods together and still dispatches,
which is what the error says to do.

*** How a renamed name is compiled

A modifier produces a *spelling*, never a copy. Everything keyed internally —
the implementations, the inline templates, the union cases, the ~Module::name~
qualified reference a macro expansion uses — goes on using the name the
*declaring* module gives it, and the visible name is resolved back to that. For
a def, a macro or a trait, that name is the one its source wrote; for a type or
a constructor it is the key (see [[*How a type is keyed][How a type is keyed]]).

The two halves resolve differently, and the difference matters:

- A *def* stays bound under its visible name, and code generation emits it as a
  qualified reference into the origin's class. So ~(rename (m) (helper h))~
  gives an ~h~ that means ~m~'s ~helper~ even if something else in the program
  also defines ~helper~.
- A *type, constructor or trait* is not bound under anything, so its prefixed
  spelling is resolved away before any registry is consulted. What it resolves
  *to* is the declaring module's own name for it: a trait's bare name, and a
  type's key.

One consequence of the second: a prefixed type does not *hide* the unprefixed
one. ~(prefix-types (m) "T/")~ makes ~T/Crate~ a name; ~Crate~ stays one.

*** What ~prefix-types~ is for

Renaming a module's worth of types, and *disambiguating* two of them.

A type's identity is the module that declared it plus its name. Two libraries
may each declare a ~Banana~, and those are two types: a value of one is not
accepted where the other is wanted. What is left to decide is what each is
*called* here, and that is what the modifier says:

#+BEGIN_SRC scheme
(import (prefix-types "a.bjo" "A/")
        (prefix-types "b.bjo" "B/"))
#+END_SRC

~A/Banana~ and ~B/Banana~ are two names for two types, usable in the same
signature. Passing one where the other is wanted is a type error that names
both modules:

#+BEGIN_SRC text
Type error: these types do not match.
  b/Banana
  a/Banana
  Both are called Banana, and a type belongs to the module that declared it:
  b and a each declared one. Import a module with (prefix-types ...) to give
  its types a spelling of their own.
#+END_SRC

Without the modifier both are still there and still distinct — the bare
~Banana~ simply means the later import's, which is rule 2 of [[*Which name
wins][Which name wins]]. The prefix is how the other one gets a name.

**** How a type is keyed

Internally a declared type — and each of its constructors — is filed under
~<module>__<name>~: ~a__Banana~, ~a__MkBanana~. That string is what the
registries are keyed on and what the generated C# class is called, which is why
two libraries no longer collide there. Source never writes it: the bare name is
registered as a *spelling* of it, exactly as ~prefix-types~ registers ~A/Banana~,
and both resolve to the key before any registry is consulted.

It surfaces in one place, diagnostics, where it is written ~a/Banana~ — the
module, then the name.

The runtime's own types — ~List~, ~Option~, ~Result~, ~Syntax~ and the rest —
are declared by no module and are not keyed. A module declaring a type of one
of those names is not shadowing it so much as declaring its own: ~mine/Option~
and ~Option~ are two types, and mixing them is a type error rather than a
silent substitution.

*** Prefix strings

A prefix or postfix has to lex as part of the name it builds, so a string
containing whitespace, parentheses, quotes or anything else the tokenizer would
break on is rejected at the import. ~/~ is a symbol character and is the usual
separator. ~.~ is also a symbol character but is refused anyway: a dot is how a
.NET member is spelled, and a name that looked like one but was not would be
read as such long before anybody suspected the import.

One quirk worth knowing: a bare symbol is read as a *constructor pattern* only
when it starts with a capital, so a nullary case matched by name needs a prefix
that starts with one. ~(match c (T/EmptyCrate 0))~ matches; ~(match c
(t/EmptyCrate 0))~ binds a variable. Inside a list it is unambiguous either way.

*** Collisions

A spelling that a modifier or an alias *invents* may not be one that something
else already produces. Two renames landing on one name, or two modules prefixed
into the same spelling, is a compile error naming both sources.

This is deliberately narrower than "no two imports may offer one name". A name
that arrives *unchanged* from two modules is the older rule, unchanged: the
later import wins, silently, and a name defined in the importing module wins
over both. Making that an error would reject programs that have always
compiled — the standard library itself relies on it. So the boundary is: what
you asked for by hand is checked, what falls out of import order is not.

*** Importing one module twice

Allowed, and the visible names are the union of what each import produces:

#+BEGIN_SRC scheme
(import (prefix "inc/kitchen.bjo" "k/")
        (only "inc/kitchen.bjo" unwrap make-crate))
#+END_SRC

gives ~k/unwrap~, ~k/make-crate~, ~k/tally-up~ … *and* ~unwrap~ and
~make-crate~, all naming the same compiled members. The collision rule applies
to any overlap.

*** The implicit prelude

Writing any modifier around the prelude's own path suppresses the implicit
import and honours the modifier:

#+BEGIN_SRC scheme
(import (except (std prelude) print))   ;; `print` is really gone
#+END_SRC

The comparison is on the path alone. Were the implicit edge added alongside
this one it would reinstate exactly the name the modifier was written to
remove.

** ~:alias~

#+BEGIN_SRC scheme
(:alias http-get http-get/async+fixed-headers)
#+END_SRC

A second spelling of a binding or a macro already in scope. The alias shares the
original's type scheme, its keyword and rest metadata, and its mutability —
~set!~ through an alias to a mutable def writes the original's cell, because
there is no copy to write instead.

- ~old~ must resolve to a def, a macro, or a ~Module_Module::name~ qualified
  reference. Aliasing a type, a trait or a constructor is an error: a type has
  ~(type (: New Old))~ aliases of its own, and a constructor follows its type.
- An alias of an alias flattens to the ultimate origin rather than hopping
  through the middle.
- An alias is a top-level binding for shadowing and duplicate purposes: two
  aliases producing one name, or an alias taking a name the module defines for
  itself, is an error.
- An alias of a *macro* is registered before the module is parsed. It has to be
  — the parser decides what a head symbol means at the moment it meets it — so
  the alias form is read off the S-expressions alongside the imports.

** The facade pattern

A module may publish names it did not define, under whatever spelling its
callers should write:

#+BEGIN_SRC scheme
;; myapp/net.bjo
(import "net_internals.bjo")

(:alias http-get http-get/async+fixed-headers)

(export http-get)
#+END_SRC

#+BEGIN_SRC scheme
;; a consumer
(import "myapp/net.bjo")

(http-get "https://example.com" #:timeout 30)
#+END_SRC

The exported name needs no signature here, for the same reason ~re-export~ never
did: it already has one where it was defined, and a second copy could disagree.
~rename~ at the import works just as well as ~(:alias ...)~ after it.

*No forwarding method is generated.* ~net~ compiles to a class with nothing in
it; the export metadata carries the *origin* — the module and the name it is
defined under — and the consumer emits a reference straight to
~net_internals_Module~. That assembly is linked because a compiled library's
dependencies are transitive, which is the same mechanism that makes ~re-export~
work (see [[*Linking is not importing][Linking is not importing]]).

The origin recorded is the *ultimate* one, resolved when the facade read its own
imports. So a facade in front of a facade flattens rather than chaining, and two
facades publishing one binding under two names give a consumer two spellings of
one reference — not a conflict.

** ~export~

#+BEGIN_SRC scheme
(export print println Crate)
#+END_SRC

Names a module's public surface — *the whole of it*. A binding, a macro, a
trait, an ~import/extern~ alias, an ~import/class~ alias and a type all cross
only by being named here.

Every exported *binding* must have an explicit signature in the same module:

#+BEGIN_SRC scheme
(: println (-> %a void))
(defun (println x) ...)
(export println)
#+END_SRC

This is deliberate. An exported type is part of a compiled DLL's metadata, so it
has to be written down rather than inferred.

The rule is about names this module *defines*. A name that already carries a
signature from elsewhere is exempt: an ~(:alias ...)~, a name a ~rename~ at the
import produced, and anything else an import brought in. Those are the facade
cases, and writing a second signature for one here would be a copy that could
disagree with the first — which is the same reason ~re-export~ has never
required one.

A *type* is exempt for the opposite reason: it has no signature, and what it
publishes is its declaration. ~(export Crate)~ beside ~(type (: Crate ...))~ is
the whole of it.

*** Exporting a type

A type is visible to an importer only if it is named in an ~(export ...)~. There
are three levels, and the declaration and the export list decide between them
together:

| In ~(export ...)~ | ~#:opaque~ | What an importer gets                     |
|-------------------+------------+-------------------------------------------|
| no                | —          | nothing; the name does not resolve        |
| yes               | yes        | the name and its arity                    |
| yes               | no         | the name, its cases or fields, everything |

*Nothing a module publishes may name a type it withheld.* An exported
signature, a ~(where ...)~, a trait method, an impl target, the field types of
an exported record and the payloads of an exported union are all checked, and a
withheld type in any of them is refused where the library is built:

#+BEGIN_SRC text
Export Error: the exported binding 'make-crate' names the type 'Crate', which
this module declares and does not export. A type crosses a module boundary only
when it is named in an (export ...), so an importer has no way to resolve this.
Write (export Crate), or (export Crate) with the declaration marked #:opaque to
publish the name without its representation.
#+END_SRC

Refused *here* rather than where the type is used, which is the point of
checking it: the alternative is an unresolvable name in somebody else's
signature, failing in the importing module at a call whose author never saw the
type.

Two things are not types in this sense and need no export. A ~(type (: Name
Other))~ *alias* and an ~import/class~ alias are both expanded where they are
named, so a signature mentioning one carries what it expands to and resolves
anywhere — exporting one gives an importer the *spelling*, which is often worth
having and is never required for correctness.

*** ~#:opaque~ — a name without its representation

#+BEGIN_SRC scheme
(export Handle)
(type (: (Handle %a) #:opaque (Union (Live %a int) Closed)))
#+END_SRC

The head crosses and the body does not. An importer may write ~(Handle string)~
in a signature, hold one in a ~List~, pass it back — and may not name ~Live~ or
~Closed~, in an expression or a pattern. For a ~Record~ it is the fields that
stay behind, and the constructor with them, since a record is built by its own
name.

*Implementations still travel and still dispatch.* This is what makes an opaque
type usable rather than merely storable: an impl is keyed on the type, a key
resolves to itself wherever it is read, so ~(->str h)~ finds the implementation
the declaring module compiled with none of the representation crossing.

*The pattern matcher needs no rule for this and has none.* A union case is
registered as an ordinary constructor binding by walking the cases of a
declaration; an opaque type publishes no cases, so there is no binding, and a
pattern naming one is refused exactly as a typo is. The same holds for a
constructor call, a ~record-ref~ and a ~record-set~. All opacity adds is the
explanation:

#+BEGIN_SRC text
Pattern Error: Unknown constructor 'Live' at m.bjo:19. 'Live' belongs to
vault/Handle, which is exported #:opaque: the type's name crosses the module
boundary and its representation does not, so a value of it can be held and
passed on but not taken apart here.
#+END_SRC

The member names travel in the metadata for that message and for nothing else —
nothing is registered under them. No secret is spent on it, since the emitted
C# members are public either way.

*~#:opaque~ on an alias is refused.* An alias is expanded wherever it is named,
so there is no representation to hold back, and an opaque one would be a
different type inside the module from the one outside. A type meant to be its
own is a ~Record~ or a ~Union~.

Inside the declaring module — and inside anything it ~include~s, which is the
same module — an opaque type is entirely ordinary. Opacity is a property of the
boundary, not of the declaration.

** ~re-export~

#+BEGIN_SRC scheme
(re-export print println)
#+END_SRC

Publishes names this module imported from somewhere else. The local-signature
rule does not apply, because a re-exported name already carries a signature from
where it was defined; what is checked instead is that the name is actually in
scope here.

This is how an aggregate module works:

#+BEGIN_SRC scheme
;; std/prelude.bjo
(import (std core) (std list) (std iter))

(re-export print println)
#+END_SRC

Anything importing ~(std prelude)~ sees ~print~ and ~println~ — and nothing else
from ~core~, ~list~ or ~iter~.

** Exporting a trait

A trait travels with its methods. Exporting or re-exporting *any* method of a
trait publishes the whole trait: the ~def/trait~ itself and every implementation
of it known to the compiling module.

#+BEGIN_SRC scheme
;; std/prelude.bjo
(export fold)
(include "Foldable.protobjo")
#+END_SRC

~prelude.dll~ then carries, in its metadata:

#+BEGIN_SRC scheme
(def/trait (Foldable 'col) (type 'item) (: fold (-> (-> 'acc 'item 'acc) 'acc 'col 'acc)))
(def/impl/extern (Foldable (List 'a)) (type 'item 'a))
(def/impl/extern (Foldable (Vec 'a)) (type 'item 'a))
#+END_SRC

~def/impl/extern~ is a ~def/impl~ without method bodies. It says only that the
type implements the trait and what its associated types are — the methods are
already compiled into the assembly that declared it. It exists for metadata;
there is no reason to write one by hand.

Note what a trait method's *signature* alone cannot say. ~fold~'s element type
is the associated type ~%item~, which has no meaning without the trait, so a
trait method is published by its ~def/trait~ and deliberately left out of the
~(: name type)~ list — an entry there would shadow the real binding with a
weaker one. An associated type appearing anywhere else in an exported signature
is written ~(assoc Foldable item 'col)~.

Both halves are needed by an importer. Without the trait, ~%item~ cannot be
resolved to the caller's element type; without the implementations, a call has
nothing to dispatch to.

** Exporting a foreign import

An ~import/extern~ alias may be exported. It is the one kind of name that
crosses as an *import* rather than as a signature:

#+BEGIN_SRC scheme
(export num-max)
(import/extern (num-max (: System.Math.Max)))
#+END_SRC

#+BEGIN_SRC scheme
;; in the metadata
(import/extern (num-max (: System.Math.Max)))
#+END_SRC

The reason is that ~System.Math.Max~ is an *overload set*, not a method. Which
member of it a call means is decided from that call's argument types, so there
is no single type to publish — and publishing one would pick whichever overload
the exporting module happened to use. Sent as the import, the importing module
resolves the overloads against the same .NET metadata, and ~(num-max 3 9)~ and
~(num-max 1.5 2.5)~ are two different methods on its side just as they were on
this one.

An alias is *also* published when an exported body names one — an inline
template, or a trait default. Those are published under a mangled name
(~clr_import__maths__clr-abs~) and the body is rewritten to match, because a
body is re-inferred where it is spliced: under its own name, a definition of it
in the importing module would silently take over the meaning of the library's
method. An alias exported deliberately keeps its own name, since that name is
the one the importer is meant to write.

A name defined in the importing module always wins over an imported alias.

** Which name wins

Three rules, in the order they are decided:

1. A name *defined in the importing module* wins over anything imported. For a
   type that holds wherever the declaration sits in the file: a signature
   written above a ~type~ already means that ~type~.
2. Between two imports offering the same name, the *later import* wins.
   Silently: this is what makes the implicit prelude a background that anything
   can override, and it is what several modules in this repository rely on.

   For a *type* this decides the spelling and nothing else. Both types are
   still there and still distinct, and the one the bare name does not reach is
   reached with ~prefix-types~ (see [[*What ~prefix-types~ is for][What
   ~prefix-types~ is for]]).
3. A spelling a *modifier or an alias produced* may not collide with anything —
   with another such spelling, or with a name the module defines for itself. It
   is a compile error naming both sources.

The boundary between 2 and 3 is deliberate. Rule 2 covers what falls out of the
order imports happen to be written in, where an error would reject working
programs; rule 3 covers a name somebody asked for by hand, where two answers
mean the request was ambiguous.

** Linking is not importing

A compiled library records its dependencies in ~BjolangDeps~. Those assemblies
are *referenced* when you build against the library, because that is where the
code of anything re-exported through it actually lives — but their exports are
not imported. Only what a module explicitly exports or re-exports is visible
through it.

Note the asymmetry that follows: at the C# level a ~using static~ is emitted for
every linked assembly, so all of their static classes are technically in scope.
Visibility is enforced by the Bjolang type checker, not by C#.

#+BEGIN_QUOTE
Historical note: this used to work the other way round. Importing a DLL pulled
in the exports of everything it transitively depended on, which is why
~(import (std prelude))~ gave you ~print~ and ~println~ even though
~prelude.bjo~ re-exported nothing at all and ~prelude.dll~ carried no export
metadata. The names were arriving from ~core~ directly; ~prelude~ was a
dependency bundle rather than a module with a surface.
#+END_QUOTE

** ~include~

#+BEGIN_SRC scheme
(include "inc/math_helpers.bjo")
#+END_SRC

Splices the named file's top-level forms in at that position, as if they had
been typed there. Paths resolve relative to the directory of the file doing the
including, so a chain of includes follows the files.

An include creates *no module*. That has two consequences:

- The included definitions are in scope immediately. They do not need to be
  exported, and they are not visible to anyone importing you unless you export
  them yourself.
- Everything ends up in one generated class.

Includes nest, and an included file's own ~(import ...)~ forms become imports of
the including module.

Cycles, missing files and malformed forms are reported with a file and a line:

#+BEGIN_SRC text
Include Error: 'a.bjo' includes itself at b.bjo:1. Include chain: a.bjo -> b.bjo -> a.bjo
Include Error: cannot find 'nope.bjo' included at m.bjo:1 (looked for /.../nope.bjo)
Include Error: malformed include at m.bjo:1. Expected (include "path")
#+END_SRC

** Building an imported source module

~(import "helper.bjo")~ builds ~helper.dll~ if there is not a current one, and
imports that. "Current" is by timestamp against the whole source closure — the
file itself and everything it ~include~s — so editing any part of a module
rebuilds it. Before this existed, ~resolveImportPath~ preferred any ~.dll~ that
was present, and editing a library then quietly relinked the old one.

The sub-compilation runs in a *process of its own*. The compiler keeps
module-level mutable state that is not stacked — ~Gensym~'s counter, the macro
table, ~Codegen~'s shadowed-builtin set — so a nested compilation would leave
the outer one holding another module's macros and a counter that had moved.

Because the recursion crosses processes, the in-process cycle check cannot see
it. The chain in flight is carried in ~BJOLANG_BUILD_CHAIN~, and a module
imported from something it is itself building is reported rather than spawning
compilers until something gives out.

** The implicit prelude

Every module the compiler loads from source gets ~(import (std prelude))~
prepended to its forms. Writing it by hand is allowed and changes nothing — the
implicit import is suppressed when an explicit one is already there, so the
import graph keeps one edge rather than two.

It is prepended rather than appended, so a later import still shadows a prelude
name: the prelude is the earliest binding there is.

An explicit import wrapped in a modifier counts as importing it, and the
modifier is honoured — ~(import (except (std prelude) print))~ really does
remove ~print~. The comparison is on the path alone, so the implicit edge is not
added alongside the explicit one to put the name back.

Files under ~lib/~ are the exception, and are left exactly as written. The
standard library has to state its own dependencies — ~prelude~ imports ~maths~,
so an implicit ~prelude~ in ~maths~ would be a cycle — and ~build_std.sh~
compiles it in that order.

The point is that where a name happens to live is not the programmer's problem.
~string-append~, ~int->string~, ~file-read-text~ and ~print~ are library
functions written in Bjolang; ~+~, ~vec-ref~ and ~display~ are compiler
builtins. Nothing at a call site should have to know which is which.

** Macros travel as metadata

A module that defines a ~def/macro~ publishes it in a fourth assembly
attribute, ~BjolangMacros~:

#+BEGIN_SRC scheme
(macro "or-else" "macros")
#+END_SRC

The name, and the module that defines it. It is deliberately *not* an entry in
~BjolangExports~: those are signatures, for names an importer may call, and a
macro is not one. It is also read at a different time — before the importing
module is parsed, because the expander has to know a name is a macro at the
moment the parser meets it in head position. That is why dependency discovery
reads ~(import ...)~ off the S-expressions rather than off the parsed
declarations: reading needs no macros, parsing does.

Every macro is published. There is no ~(export ...)~ for them, because a macro
that no other module can reach is unusable — it cannot be used in the module
that defines it. See ~Docs/MACROS.org~.

** What a ~.dll~ says about its types, and the version that says how to read it

Everything a compiled module publishes about itself is one ~BjolangMetadata~
attribute, and the first thing in it is a format version. A mismatch is
reported rather than guessed at:

#+BEGIN_SRC text
'/.../prelude.dll' was built by a different version of the Bjolang compiler
(metadata version 1, this compiler reads 2). Rebuild it with this compiler
version.
#+END_SRC

The version is bumped when a field changes *meaning*; adding one does not need
it. Version 2 is where type names became keys — an older assembly's types would
be read as somebody else's. Version 4 is where the type declarations became the
*exported* ones rather than every one declared: an older assembly offers its
private types as though they were public, and knows nothing of the ~(Opaque
...)~ shape an ~#:opaque~ export is published as.

Two shapes cross the boundary, and the difference is the whole of how a key
travels:

- a type *declaration* travels as the source it was written as, under its bare
  name, and is keyed again by its reader — which knows the module it came from,
  since it is reading that module's own assembly;
- every *other* type name — in a signature, an impl target, a trait's methods —
  is already a key, and a key resolves to itself. That is what a signature
  mentioning a type from a link-only dependency needs (see [[*Linking is not
  importing][Linking is not importing]]): nothing has to be registered for it
  to mean what it meant.

So a module publishes only the types it declares *and exports*. A dependency's
arrive through the dependency, or not at all — and a signature that mentions one
still resolves, because the name in it says where the type lives.

An ~#:opaque~ export is the same mechanism used deliberately. Its declaration is
published as a head with no body, so the name resolves and nothing is registered
that could take a value apart — which is what a link-only dependency's type has
always been, except that here the module meant it.

Rebuilding after a version bump is ~./build_std.sh~ for the standard library,
and a rebuild of anything else compiled against it. A library that still has
its source needs nothing done by hand: the compiler counts itself as part of a
module's source closure, so an out-of-date ~.dll~ beside its ~.bjo~ is rebuilt
at the next import.

** Where a module import resolves

~(import (std core))~ is resolved against the ~lib~ directory of the *compiler
installation* — found by walking up from the compiler binary for a ~lib~ that
contains ~std~ — and not against the working directory. A module path therefore
names the same file wherever you invoke the compiler from. ~BJOLANG_LIB~ (a
~lib~ directory) or ~BJOLANG_HOME~ (its parent) override the search.

This matters more than it sounds. ~resolveImportPath~ prefers a ~.dll~ over a
~.bjo~ of the same name, so as long as the standard library is found compiled,
that is what gets linked. When it was resolved against the working directory,
compiling from anywhere else found no ~std/prelude.dll~, fell back to
~prelude.bjo~, and quietly compiled a second copy of the entire standard
library into the program — with the source-import bug above waiting at the end
of it.

** Building the standard library

~lib/std/*.bjo~ must be compiled to DLLs before anything can import them:

#+BEGIN_SRC sh
./build_std.sh
#+END_SRC

There is exactly one set of these DLLs. Nothing is ever copied next to a
compiled program: a program's manifest names only itself, and its entry point
installs an assembly resolver that loads dependencies from the directories they
were built in. A compiled binary therefore points back at this checkout —
setting ~BJOLANG_LIB~ redirects it at run time.

~BjolangDeps~ stores *absolute* paths, and a dependency that no longer exists
at its recorded path is silently skipped. Moving the checkout therefore breaks
re-exported names with a confusing "Unbound variable" rather than a missing-file
error, and already-built programs stop finding the standard library. Re-run
~build_std.sh~ after relocating the tree, and rebuild anything compiled against
it.

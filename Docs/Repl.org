#+TITLE: The REPL
#+OPTIONS: toc:2

* Running it

: ./bjo/bjo repl

At a terminal the REPL edits its own lines (see "Line editing and completion"
below). Tab completes, Enter with a bracket still open starts a new line, and
entries are kept from one session to the next.

An entry is either a group of declarations or a single expression. An
expression's value is printed; a group of declarations prints the names it
bound. End of input, ~:quit~ or Ctrl-D leaves; ~:help~ prints a summary;
~:show name~ prints a visible name's doc (see "~:show~" below);
~:complete text~ prints what could be written at the end of ~text~.

#+begin_src scheme
bjo> (+ 1 2)
3
bjo> (defun (double (: x int)) : int (* x 2))
double
bjo> (double 21)
42
#+end_src

* Not an interpreter

An entry is compiled by the same ~Pipeline.runFullFrontendPipeline~ a build
runs, emitted by the same ~Codegen~, and published by the same
~Exports.metadata~. The REPL uses the standard compiler pipeline to ensure 
semantics match batch compilation perfectly.

What ~Repl.fs~ decides is a driver's business only: what source an entry
becomes, which earlier entries it links, and how a value is shown.

A tree-walking interpreter over ~TypedAST~ would have to reimplement dictionary
lowering, trait inlining and loop lowering to reach the same answers, and any
divergence between the two would be invisible until someone hit it.

* One assembly per entry

Entry N is written to ~Bjo_Repl_N.bjo~ in a session directory, compiled to
~Bjo_Repl_N.dll~, and loaded. Entry N+1 reaches entry N's bindings by importing
that ~.dll~ — the ordinary module mechanism, needing nothing of its own.

That works because ~Codegen~ already emits a top-level ~def~ as a
~public static readonly~ field on the module class and a ~defun~ as a
~public static~ method, which is what an importing entry links against. No
separate emission path exists for the REPL.

Entries are loaded into a load context of the session's own, a /generation/,
together with the modules they import from outside the standard library. Entry
N+1 holds a hard reference to entry N's assembly, so the two have to be one
identity to the loader. The standard library and the runtime resolve through
the default context, as in a program, so every generation shares one copy of
them, and with it the session scope and the runtime's ports. Nothing is
unloaded until the session is reloaded (see "A module edited during the
session is reloaded"), so a session grows by one small assembly per entry.

Set ~BJOLANG_REPL_DIR~ to keep the generated sources somewhere readable. What an
entry becomes is the whole of what the driver decides, so being able to read one
is the difference between debugging the REPL and guessing at it.

* Which earlier entries an entry links

Every symbol an entry mentions is resolved to the newest earlier entry that
provides it, and only those are imported. Importing all N previous entries
would make entry N re-read N sets of metadata, and per-entry cost would grow
with session length.

The resolution is over the *token stream*, not over parsed expressions:
~AlphaRename.freeNames~ needs an ~Expr~, and parsing needs the imports that are
being computed. Over-approximating costs one assembly reference and changes
nothing — a ~let~-bound ~x~ shadows an import as it shadows anything else — and
under-approximating cannot happen, because every reference to a binding is a
symbol in the text.

Three rules make that correct:

- *A name the entry defines is never imported.* ~(defun (f x) (* x 100))~
  mentions ~f~, so without this it would import an earlier ~f~ alongside
  defining its own — and the import wins. Redefining a name would silently
  produce the old one. In a file the same text is a definition, and a call to
  itself is recursion; here too.
- *Union cases and trait methods count as provided.* Nothing writes ~Shape~; it
  writes ~(Circle 2.0)~. They cannot appear in an ~(export ...)~ list, since a
  case has no signature and travels with the type that declares it — so "what
  an entry provides" and "what an entry exports" are two different sets.
- *An entry declaring a trait or an impl is linked unconditionally.* An impl is
  not a name, so nothing a later entry writes would pull it in.

Imports are emitted in ascending entry order, so when two entries provide the
same name the later one wins. That is the rule ~loadModuleGraph~ gives any two
plain imports, and it is what makes redefinition shadow.

* Signatures at the prompt

~Inference~ requires a signature on every top-level ~defun~ but ~main~, and
~Exports~ requires one on every exported name. At a prompt a complete form is a
complete entry, so a signature and the definition it belongs to arrive
separately unless they are written as one form.

Three mechanisms, all of which keep an entry meaning what the same lines in a
file mean:

- *A ~defun~ writing its own types* needs neither of the others, and is the one
  to reach for. See [[file:Syntax.org][Syntax.org]] for the form, and for what
  it cannot say — keyword and rest parameter types, and ~(where ...)~
  constraints — each of which wants a separate signature.

  #+begin_src scheme
  bjo> (defun (double (: x int)) : int (* x 2))
  double
  #+end_src

- *A signature typed on its own waits* for the entry that defines its name, is
  replayed into that entry's source, and is then forgotten.

  #+begin_src scheme
  bjo> (: double (-> int int))
  bjo> (defun (double x) (* x 2))
  double
  #+end_src

- *An unsignatured ~def~ is compiled twice*: once to infer its type, and then 
  again with the inferred type explicitly annotated. This is necessary because 
  exported bindings require explicit signatures. Since the REPL automatically 
  exports entries, the two-pass compilation ensures the entry behaves identically 
  to a hand-annotated definition in a file.

  This is the only case that incurs a second frontend pass; expression entries 
  remain single-pass.

* How a value is shown

~->str~, the language's own. The prelude gives it a blanket impl over every
type, so there is no value the prompt cannot show, and no printer inside the
compiler to keep in step with the language.

An expression entry becomes:

#+begin_src scheme
(def __bjo_value <what was typed>)
(def __bjo_show (->str __bjo_value))
#+end_src

~def~ rather than ~defun~ because a top-level ~defun~ needs a signature and the
wrapper exists precisely because the type is not known yet. A top-level ~def~
runs its initializer in the class's static constructor, so *reading the field is
what evaluates the entry*.

Two bindings rather than one, so that the type of the value is still readable
off ~env~ afterwards: ~__bjo_show~ is a ~string~ whatever it wrapped, and
whether to print at all depends on what ~__bjo_value~ was. ~void~ and ~Unit~
print nothing — "this was done" is not a value, and echoing ~Bjoml.Unit~ is
noise.

A definition entry is still loaded and its class constructor run, because a
~def~'s initializer is its effect.

* ~:show~

~:show random-int~ prints the doc of the visible name ~random-int~, then a line
for each other visible name containing the text, in any case, with its module
and its summary. When no visible name contains it, nothing is printed.

A name is visible when an entry typed now could write it: a builtin, a name an
import brings in, or one an earlier entry defined. ~random-int~ is not visible
until ~(std random)~ is imported, and after ~(import (prefix (std random)
"r/"))~ it is ~r/random-int~.

The REPL does not work out the scope itself. It compiles an entry holding only
the session's imports and reads what the compiler built, so ~only~, ~except~,
~rename~, ~prefix~ and re-exports mean what they mean in an entry. Each name is
looked up under its original name in the module that defines it, which is
where its doc is published (see ~Documentation.org~, "Where the documentation
goes"). A re-exported name's doc is the defining module's. A doc written at
the prompt, beside its definition, is found in that entry. Builtins have no
docs.

* Line editing and completion

At a terminal an entry is read with a line editor ([[https://github.com/waf/PrettyPrompt][PrettyPrompt]]).

- *Tab* completes the word at the cursor as a shell does: the one candidate
  there is, or as much as all candidates share, is inserted at once, and when
  that would insert nothing a menu opens. Ctrl-Space opens the menu too. In
  the menu the arrow keys choose, Enter or Tab inserts and Escape closes. Beside
  the chosen name is its signature, the summary of its doc, and where it is
  from.
- *Enter* submits a complete entry. With a bracket still open it starts a new
  line, so a long form can be written, and edited, across lines. A command
  (~:show~, ~:complete~) is always complete.
- *History* is kept in ~$XDG_DATA_HOME/bjolang/repl-history~
  (=~/.local/share/...= when that is unset), and the arrow keys bring earlier
  entries back. Ctrl-C abandons the entry being written; Ctrl-D on an empty one
  leaves.

Piped input is read line by line with none of this, which is what the
transcript tests feed. So are Emacs's shell and comint buffers, which say they
are by ~INSIDE_EMACS~ or ~TERM=dumb~. ~BJOLANG_REPL_PLAIN=1~ asks for line by
line reading anywhere, for running under ~rlwrap~ or another wrapper that edits
lines itself.

** What is offered

What the word at the cursor is decides what is offered. A word is a run of
characters the lexer would read as part of a symbol, so ~string-le~ and
~r/random-b~ are one word each.

- *Code*: every visible name, as ~:show~ finds them, then the special forms
  (~let~, ~match~, ~defun~ ...), then the symbols already written earlier in
  the entry. The last are there for the names a ~let~ or a ~fun~ being typed
  binds, which are in no scope yet.
- *A command* at the start of an entry: ~:complete~, ~:help~, ~:quit~, ~:show~.
- *The argument of ~:show~*: the visible names.
- *Inside an import*: the first word of a list is an import modifier
  (~only~, ~prefix~ ...) or a package, and a later word of a module path is the
  next segment, read off the package directories. ~(import (std ra~ offers
  ~random~.
- *Nothing* inside a string or a comment, after ~#:~, or where the lexer cannot
  read the text before the cursor.

The visible names are found by compiling a probe entry, about 90 ms, and kept
until the next entry is evaluated, so only the first Tab after an entry pays
for it.

The special forms are a list in ~Repl.fs~. The parsers recognise them by
matching on the head of a form, so there is no table of them to read, and a
form added to ~Parser.parseExpr~ or ~DeclParser~ is offered once it is added
to that list too.

** ~:complete~

~:complete text~ prints what could be written at the end of ~text~: one name per
line, then a tab, then where it comes from (a module, ~entry 3~, ~builtin~,
~special form~, ~command~, ~module~, ~import modifier~ or ~this entry~). Nothing
is printed when nothing fits.

#+begin_src text
bjo> :complete (random-in
random-int	(std random)
#+end_src

It is the completion the line editor offers, for a tool outside the REPL: an
editor's completion source, until there is a language server. The tool sends
the current entry up to the cursor, on one line, and replaces the run of symbol
characters at its end with the chosen name. A trailing space asks for every
name rather than the ones continuing a word. A command is a line of its own
whatever it holds, so the brackets an unfinished entry leaves open do not make
the REPL wait for more.

* Semantics

** Redefinition shadows

Entry 3's IL holds a hard reference to ~Bjo_Repl_1.f~. Redefining ~f~ does not
update it, and the REPL says so rather than pretending otherwise:

#+begin_src scheme
bjo> (defun (f (: x int)) : int (+ x 1))
f
bjo> (defun (g (: x int)) : int (f (f x)))
g
bjo> (g 10)
12
bjo> (defun (f (: x int)) : int (* x 100))
  note: f shadows the one from entry 1. Anything already compiled against that one still calls it.
f
bjo> (f 10)
1000
bjo> (g 10)
12
#+end_src

Recompiling dependent entries is the alternative and costs more than it is
worth: entry 16 would have to recompile every entry mentioning ~f~,
transitively, and re-emit each — turning a keystroke into a rebuild of the
session, growing with session length, which is the property the import rules
above exist to avoid. It would also re-run every top-level initializer, so a
~(def log (open-file ...))~ four entries back would be silently re-executed.

** An impl reaches forward only

An impl written at entry 9 reaches entries 10 and after, because an entry
declaring one is linked unconditionally. It cannot reach entry 4: ~Lowering~
baked a dictionary choice into entry 4's IL, and that IL is loaded.

#+begin_src scheme
bjo> (type (: Colour (Union Red Green)))
Colour
bjo> (->str Red)
Bjo_Repl_1__Red { }
bjo> (impl (->str Colour) (defun (->str c) (match c (Red "red") (Green "green"))))
bjo> (->str Red)
red
#+end_src

The second line is the failure mode: before the impl exists, the *blanket*
~->str~ impl applies, silently and correctly. Nothing warns, because at that
point nothing is wrong. It only looks wrong in hindsight.

Warning when a new impl overlaps something already compiled would mean keeping,
per entry, the set of ~(trait, type)~ pairs that entry resolved, and reporting
when a new impl would have changed one. That is bookkeeping in ~Repl~ over
information ~Lowering~ already computes, and is not done.

~Exports.metadata~ writes a module's impls only if the module has an export or a
type to hang them on. An entry that is nothing but ~(impl ...)~ has neither,
so the REPL gives it one exported binding — ~__bjo_anchor~ — purely to open the
metadata block. It is not reported as a name the entry defined, because it is
not one anybody wrote. The same is true of a hand-written module: a ~.bjo~ that
exports nothing and declares no type publishes no impls either.

** A binding that may fail needs a body, and an entry is not one

An entry is a top level — a list of declarations — so a pattern in it binds
exactly as one in a module does: every name becomes a definition, and the
pattern has to match every value. A failure part that leaves has nothing to be
the value of and is refused. ~:default~ never leaves, so it is taken.

#+begin_src scheme
bjo> (def* ((Tuple a b) (Tuple 1 2)))
a b
bjo> (def (Some x) (lookup k))
Pattern Error: this def's pattern does not match every value, and at the top level there is nowhere else for one to go.
bjo> (def (Some x) (lookup k) :default 0)
x
bjo> (defun (f (: o (Option int))) : int (def (Some x) o :leave-with 0) (+ x 1))
f
#+end_src

Leaving at a prompt means deciding what the rest of the session is: on a
failure nothing may be bound, and the entries already compiled cannot be the
sequel of an entry typed later. Not done; the workaround above is a function.

** An ambiguous definition is rejected, not defaulted

A top-level ~def~ at the prompt *is* a top-level ~def~ in a module, so the
module value restriction applies and an ambiguous one is rejected with the
language's own diagnostic. Defaulting would make the prompt accept programs a
file rejects.

** ~(import "x.bjo")~ is safe

Imports typed at the prompt are replayed into every subsequent entry rather than
remembered as compiler state, so a macro imported at entry 2 is re-registered at
entry 3 by that entry's own import — the same path a build takes.
~Session.replEntry~ clearing the macro table between entries is what makes
replay the only path, which is what makes it safe.

A relative path means relative to the working directory, not to the temporary
file the entry is written to, so the REPL makes it absolute before writing.

** A module edited during the session is reloaded

An imported module is rebuilt when its source changes, the next time an entry
is compiled, as a build would rebuild it. A load context holds one assembly
per name, though, so once the session has run the old ~m.dll~ the new one
cannot be loaded beside it. When a module the session was compiled against has
been rebuilt, the REPL starts a new generation: it compiles the session's
definition entries again, in the order they were typed, and then the entry
being typed.

#+begin_src scheme
bjo> (import "m.bjo")
bjo> (: g (-> int int))
bjo> (defun (g x) (* 2 (val x)))
g
bjo> (g 1)
4
;; m.bjo is edited: val now adds 100, and val2 is exported as well
bjo> (g 1)
m.bjo changed: reloading the session, and compiling its 3 definition entries again.
202
bjo> (val2 7)
7
#+end_src

What follows from compiling the definitions again:

- Every top-level initializer runs again, including its effects. A
  ~(def x (begin (println "hi") 1))~ prints ~hi~ again.
- The module's own top-level state starts over, as it would in a new process.
- An expression entry is not run again. What it printed or did has happened.
- A definition that no longer compiles against the edited module reports its
  error and is left out, and so is anything that needed it.
- Values made by the old generation and still held somewhere, by a fiber that
  is still running for instance, go on running the old code.

The standard library is not reloaded: it lives in the default context, which
every generation shares.

* Compilation state between entries

~Session.replEntry~ resets everything a compilation owns — the macro table and
its local and expansion sets, ~Parser~'s introduced names, ~Unification~'s
metavariable counter, ~Inference~'s wanted queue — except for ~Gensym~'s counter.

The `Gensym` counter is not reset between REPL entries to prevent name collisions. 
Because each entry is emitted as its own assembly (and later entries reference 
earlier ones), resetting the counter could result in multiple entries defining the 
same generated name (e.g., `tmp__12`), leading to resolution ambiguity.

Determinism is not lost by that. A REPL entry produces an assembly nothing keeps
and no staleness check ever looks at. See ~Session.fs~ for the same state seen
from a batch build's side, where the counter *is* reset so that a module's
~.dll~ does not depend on what was compiled before it.

* Speed

A warm entry costs about 24ms; the first entry of a session costs about 700ms,
most of it waiting for Roslyn's warm-up.

Two things make that possible, both switched on by ~Repl.run~ and off elsewhere:

- ~CSharpEmit.preferInProcess~. Every entry is one Roslyn ~Emit~ in this
  process, against a reference set parsed once. The first emit is expensive and
  every later one is not, which is the case in-process Roslyn exists for — a
  batch build has the opposite shape and uses ~csc -shared~.
- ~Pipeline.cacheLoadedModules~. Every entry imports the prelude, and reading
  the prelude's metadata back into declarations was about a third of what an
  entry cost. It is off for builds because that parse can invent names through
  ~Gensym~, so declarations produced under one compilation's counter and reused
  under another's would make a module's output depend on what was compiled
  first. A REPL entry has nothing to lose by it.

~BJOLANG_TIMING=1~ prints a per-phase breakdown at exit, with one line per
entry-level phase and a count beside it.

* Testing

~TestFiles/repl/*.in~ are scripted sessions, each compared against the
~.expected~ transcript beside it by ~run_tests.sh~. Whole transcripts rather
than a property per line, because what is pinned is the *semantics* — which
value each entry produces, that a redefinition shadows rather than replaces,
that an impl written mid-session reaches the entries after it, and which
diagnostics come out where.

Prompts are stripped and dependency-build narration dropped before comparing:
whether the standard library happened to need rebuilding is not part of a
session.

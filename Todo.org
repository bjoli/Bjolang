* CML: where the remaining speed is

~bench/Cml/Program.cs~ runs the ring at 55 ns/op on the same layer the language
runs at 77-85, and the skewed choose at 90 against 145, so the cost is the seam
between ~sync~ and the layer. Surgical,
separately measurable changes; ~IEvent<T>~ stays the spec. Unmeasured unless
noted.

- *A send carries a ~Unit~ it does not want.* ~ChannelSendEvent : IEvent<Unit>~;
  ~PutOp.ResumeGive~ exists only to avoid a closure (88 of 128 B/op).

* Source mapping (~#line~)

- Hoisted temporaries inherit the directive of the statement before them; they
  want ~#line hidden~ (~emitStatement~'s prelude, ~hoistToTemp~, two paths in
  ~generateLocalFunction~). Harmless today by luck.
- Directives are emitted even when the line has not changed. A dedup must
  survive scratch buffers being relocated.
- Inlined trait methods keep the impl's ranges, so a trace names the impl and
  not the call site.
- Both build configurations keep a pdb, so its absence no longer tells a ~-d~
  build apart. Nothing depended on it.

* Diagnostics

- Errors from generalization, trait registration and parts of declaration
  checking carry a location only if their call site supplied one. Threading a
  ~Range~ into ~unify~ would close it.
- The numeric-literal message blames the literal when its ~Num~ constraint
  is solved late: ~(map-set m "j" "v")~ on an ~int~-keyed map names a ~1~
  elsewhere (~Traits.fs~).
- A ~loop~'s ~:finish~ value against the loop's result reads as "two
  branches": the message is the expansion's ~if~, not the clause.

* Characters and strings

- ~char-foldcase~ is ~ToLowerInvariant~: differs from Unicode's simple fold for
  ß, ﬁ and the like.
- Numbers are read and written in the invariant culture only; there is no
  ~Culture~ to ask for ~1,5~. ~string->int~ still uses the ambient culture
  (only the sign can differ).

* Emacs mode (~bjomode.el~)

- A named loop aligns its clauses under the name, not under ~(:for~; needs a
  custom indenter (~lisp-indent-specform~ cannot express it).
- A ~match~ arm's body aligns under the pattern, as Emacs does for ~cond~.
- Library forms that read as bodies (~with-nack~) are not in
  ~bjo-indent-forms~.
- No completion, imenu or eldoc.

* Monomorphisation of constrained generics

Copies are made per ground instantiation, to a fixpoint, bounded by a code-size
budget (module size or ~budgetFloor~). Termination is by key; polymorphic
recursion cannot be written. The stdlib's 22 constrained generics have call
out-degree ≤ 1, so copies grow additively; largest demand 722 nodes
(~139_ord.bjo~). A branching graph would make the floor matter.

- *Every type argument must be ground*, so copies have no type parameters.
  Keeping unconstrained ones needs agreement with ~generalize~ on order. A
  function-typed argument is declined.
- *Suspending functions are not copied.* The twin is generated inside
  ~checkDeclGroup~, out of this pass's reach; ~Naming.specializedCopy~ already
  names it ~f__at_int__bjo~.
- *Mutual recursion is declined*: the group keeps its dictionaries
  (~284_mutual_dictionaries.bjo~).
- *A mention that is not a call is passed over.* Correct via eta-expansion.
- *A body that will not serialize is not published* (~try~, bare list literal,
  tuple destructuring, local function with keyword/rest parameters): calls keep
  their dictionary.
- *A published body is checked in the importer's scope*, so an importer's
  binding can be checked into the copy.
- *A private helper a published body names becomes public* in the importer's
  scope (~doubled~ in ~193_lib.bjo~).
- *Each module makes its own copies.* An importer specialises a published body
  where it calls it, so ~f~ at ~int~ is copied into every module that calls it
  at ~int~. A project should collect its instantiations and monomorphise each
  function once: the copies in one place every module links, rather than one
  per caller. Belongs with evidence structs.

* Equality and hashing

The collections compare with the key's ~Eq~/~Ord~ (~eq-comparer~), but the
type's own .NET members still disagree with ~=~ in three shapes (documented in
~Docs/prelude.org~, "Writing one by hand"): two cases of a union ~=~ equates, a
specialized target, a ~(where ...)~ of another trait. That reaches any .NET code
handed such a value — a ~Dictionary~ through interop, LINQ's ~Distinct~ — and a
collection the runtime makes from nothing (none today has such keys).

* Found while documenting the prelude

Behaviour the prelude's docs now describe as it is, and that is probably not
what was meant. Confirmed by running it where it says so.

- *~drop-while~ shares its state between walks* (~Iterable~ default in
  ~prelude.bjo~): ~yield?~ is made once per call, not per walk, so the second
  walk of the result drops nothing. Confirmed.
- *~range-by~ checks no step*: a step of 0 makes ~length~ divide by zero, and a
  negative step with ~lo < hi~ counts down until the int wraps. Confirmed.
- *~up-from #:by~ wraps past ~int-max~* instead of stopping, and ~down-from~
  with no ~#:to~ never stops after ~int-min~. Confirmed.
- *~map->str~ does not read back*: it prints ~#map(k1 v1 k2 v2)~, and ~#map~
  wants each entry as ~(k v)~. Docs/prelude.org says it round-trips.
- *~vec-merge/pure~ is ~vec-merge~*: ~RrbList.Merge~ never reads ~pure~.
- *~vecbuilder-ref~ checks no index*: past the end but inside the tail array
  it answers a stale or default element. ~vecbuilder-set!~ does check.
- *The two copies of ~vec-reduce~ and ~vec-for-each/range~ fail differently*:
  on an empty vec the ordinary ~vec-reduce~ raises
  ~InvalidOperationException~ and the suspending one
  ~IndexOutOfRangeException~; the suspending ~vec-for-each/range~ checks no
  range.
- *~stringbuilder-add-code!~ and ~-add-unit!~ truncate silently*: 256 becomes
  byte 0.
- *~cond~ drops what follows ~else~* without an error.
- *~with-shield #:within 0~ has no deadline at all*, though a shield's deadline
  is said to be required.
- *~async-seq->chan~'s pump is not enlisted in the scope*, and its send does
  not race the token, so a pump parked on a send nobody takes never ends.
- *Docs/prelude.org is wrong in places* the bjodoc files now get right:
  ~if-let~ and ~when-let~ written with double parentheses, ~display~ said to
  take any value (it takes a string), a ~Foldable~ trait that does not exist,
  ~(seq-range start count)~ (it is start and stop), ~(Nil)~ for ~Nil~, and
  ~(handler-of open-input-file)~ where the operation is ~open-read-stream~.
  The reference parts of it could now be cut down to what the docs do not
  say.

* Packages and projects

- *Build output lands beside the source*, also inside ~.bjo/pkg/...~: two
  projects build one package twice, and a read-only package cannot be built.
  Needs staleness, the resolver table and the build record to know a second
  directory.
- *A relative import still means a path*, even across a package boundary.
- *No ~bjo add~, ~update~, ~remove~*: writing the manifest back would lose its
  comments and layout.
- *No shared clone cache*: it would be shared state, and nothing locks.
- *No registries, commit or branch pins, or pseudo-versions*; an untagged commit
  needs a path source.
- *One version of a package per build*: two copies would be two modules with one
  identity.
- *No ~bjo install~, ~test~ or ~clean~*, and one entry point per package. Tests
  are ~bjo run tests/x.bjo~, which exits 1 after a ~FAILURE:~.
- *Nothing locks ~.bjo~* against two ~bjo~ processes; the second fails loudly.
- *A version requirement on a path dependency is ignored*: a path source is an
  override.

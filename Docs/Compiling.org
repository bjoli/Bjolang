* Compiling and running

** Building the repository

From a fresh checkout, in this order:

#+BEGIN_SRC sh
git submodule update --init --recursive          # Collections, Map, SchemeList, Bjoml
dotnet build BjolangRuntime/BjolangRuntime.csproj -c Release
dotnet build -c Release                          # the compiler itself
./build_std.sh                                   # lib/std/*.dll, in dependency order
./run_tests.sh
#+END_SRC

The runtime assemblies come first because everything a compiled program links
against lives in ~BjolangRuntime/bin/Release/net10.0~ — see "Runtime assemblies"
below — and the standard library comes before the tests because a missing
~lib/std/*.dll~ is not an error, merely a silent fallback to compiling the whole
library into every program that imports it.

*** Moving the repository

A compiled Bjolang module records the *absolute paths* of its dependencies, so
every ~.dll~ built in the old location is stale the moment the directory moves —
it links against files that are no longer there, and the failure names a missing
module class rather than the cause. After a move, delete the build output under
~lib/std~ and run the sequence above.

~TestFiles~ needs nothing done by hand. Every test binary is rebuilt each run,
and the fixture libraries in ~TestFiles/inc~ — which are *not* — record the
directory they were built from, so a move rebuilds them for the same reason a
changed source does.

** What ~run_tests.sh~ rebuilds

Three things, in this order, and only what is out of date:

- *the compiler*, through ~dotnet build~;
- *the standard library*, when any ~lib/std/*.dll~ is older than its source or
  than the compiler. It has to happen here rather than fall out of the first
  test that notices: an import of a ~.bjo~ rebuilds a stale dependency
  (~ensureLibrary~), so 200 compilations running at once would each rebuild the
  prelude into the same files;
- *the fixture libraries* in ~TestFiles/inc~, in dependency waves — everything
  whose dependencies are already built goes at once. A fixture is rebuilt when
  its ~.dll~ is older than a source it names, than the compiler, or than the
  standard library, and rebuilding one rebuilds everything downstream of it.

The tests themselves are always compiled afresh, in parallel, one job per
three-digit group.

** ~bjo~

The command that runs Bjolang. It is written in Bjolang; ~bjo/bjo~ is a
bootstrap script that compiles ~bjo/bjo.bjo~ if it has to and hands over.

#+BEGIN_SRC sh
./bjo/bjo run Playground/test.bjo        # compile if needed, then run
./bjo/bjo run Playground/test.bjo a b c  # arguments after the file go to the program
./bjo/bjo build --lib lib/std/list.bjo   # compile to a .dll, do not run
./bjo/bjo check src/*.bjo                # errors only; builds nothing
./bjo/bjo repl                           # under rlwrap, where there is one
#+END_SRC

| Command | What it does                                                     |
|---------+------------------------------------------------------------------|
| ~run~   | Compiles if the artefact is behind, then runs it                 |
| ~build~ | The same, without running                                        |
| ~check~ | Reports every error the frontend finds, and writes nothing       |
| ~repl~  | The compiler's REPL, under ~rlwrap~ when one is on PATH          |
| ~help~  | Usage                                                            |

Flags come *before* the source file — ~-d~ for a debug build, ~-c~ to compile
whatever the timestamps say, ~--lib~ for a ~.dll~, and ~--~ to end them.
Everything *after* the file belongs to the program, so ~bjo run prog.bjo -d~
passes ~-d~ to ~prog~.

~main~'s answer is the process's exit code, so ~bjo run~ answers with the
program's and ~bjo check~ with the compiler's.

*** The build record

A build writes ~<source>.bjobuild~ beside the source: the mode it produced, the
artefact, the compiler, every source it read, and every assembly it links —
the runtime among them, since a program is compiled against that API and only
resolves it at run time.

#+BEGIN_SRC text
mode release
output /home/you/prog.exe
compiler /home/you/bjolang/bin/Release/net10.0/Bjolang.dll
source /home/you/prog.bjo
source /home/you/parts/helpers.bjo
dep /home/you/bjolang/lib/std/prelude.dll
dep /home/you/bjolang/BjolangRuntime/bin/Release/net10.0/BjolangRuntime.dll
#+END_SRC

Deciding whether to compile is then a comparison of timestamps against that
list, which is why ~bjo~ can answer in milliseconds where starting a compiler to
ask would cost about half a second.

The compiler writes it because the compiler is the only one that knows what is
in it. An ~include~ is a path inside a form and an import is a module path
resolved against the installation; a driver that works those out from the text
— as ~bjor~ does, with ~grep~ and ~awk~ — is a second answer to a question that
already has one, and the two can disagree. See ~Build.writeBuildRecord~.

A record is written only after a build that succeeded, and never by ~--check~,
which builds nothing.

** ~bjor~

The shell driver ~bjo~ was written to replace. Still here, and still works —
it reads the mode from the first line of the record above, and works the rest
out for itself:

#+BEGIN_SRC sh
./bjor Playground/test.bjo          # compile if needed, then run
./bjor Playground/test.bjo a b c    # arguments after the file go to the program
./bjor -c Playground/test.bjo       # compile unconditionally
./bjor -d Playground/test.bjo       # debug build (see below)
./bjor --lib lib/std/list.bjo       # compile to a .dll, do not run
#+END_SRC

Options come *before* the source file; everything after it is passed to the
compiled program.

*** When it recompiles

Nothing is rebuilt if the binary is newer than everything it was built from.
That means the source file, every ~.bjo~ or ~.protobjo~ it imports or includes
transitively, the standard library, and the compiler itself — a program built by
a different compiler is stale even when nothing you wrote has changed.

Two cases always recompile, under ~bjo~ as well as ~bjor~:

- ~-c~, which is what it is for.
- ~-d~, because the dumps a debug build produces are a product of compiling, and
  because the binary sitting there is almost certainly an optimized one.

Which configuration the binary *is* comes from the record's first line. It used
to be guessed at from a ~.pdb~ beside the binary, which stopped meaning anything
when the compiler began emitting symbols for both — so every binary looked like
a debug build, and the standard library was rebuilt on every invocation.

** Compiler flags

The compiler itself (~dotnet bin/Release/net10.0/Bjolang.dll~) takes:

| Flag           | Effect                                                      |
|----------------+-------------------------------------------------------------|
| ~--lib~        | Compile to a ~.dll~ instead of an executable                |
| ~-d~, ~--debug~ | Unoptimized, with symbols, plus ~ast_dump.txt~ and ~out.cs~ |
| ~--repl~       | Read, evaluate, print, loop. See [[file:Repl.org][Repl.org]] |
| ~--help~       | Usage                                                       |

A file with no ~main~ compiles to a library whether or not ~--lib~ was passed:
an executable without an entry point does not link.

The dumps land in the *working directory*, not next to the source.

*** Environment variables

Diagnostic and escape-hatch settings, all off by default.

| Variable                        | Effect                                                    |
|---------------------------------+-----------------------------------------------------------|
| ~BJOLANG_TIMING=1~              | Print a phase breakdown to stderr at exit                 |
| ~BJOLANG_NO_CSC_SERVER=1~       | Do not hand the C# build to a VBCSCompiler server         |
| ~BJOLANG_OUT_OF_PROCESS_DEPS=1~ | Build each imported module in a compiler process of its own |
| ~BJOLANG_REPL_DIR=<dir>~        | Keep a REPL session's generated sources there             |

~BJOLANG_OUT_OF_PROCESS_DEPS~ resolves issues where builds fail only when modules 
are compiled together. It isolates module-level state by compiling imported modules 
in separate processes, preventing state leakage between them.

~BJOLANG_NO_CSC_SERVER~ is for a VBCSCompiler server that has gone wrong, which
is a failure with no good diagnostic. A build takes several times longer
without it.

** The REPL

: ./bjo/bjo repl

No line editing, no completion, no history of its own — ~bjo repl~ runs it under
~rlwrap~ when there is one on PATH, and says so when there is not. An entry is
a group of declarations or one expression, compiled by the same pipeline a build
runs and emitted as an assembly of its own. [[file:Repl.org][Repl.org]] has the semantics: what
redefinition does, what an ~impl~ written mid-session does and does not reach,
and the three ways a signature arrives at a prompt.

** ~main~

The entry point has one type:

#+BEGIN_SRC scheme
(: main (-> (Vec string) int))
#+END_SRC

and a file gets it whether or not it writes it. A ~main~ with no signature is
given that one, so ~args~ is a vec of strings by declaration rather than by
whatever the body happened to constrain — ~(println (vec-ref args 0))~ on its
own would otherwise leave the element type open, and a generic entry point is
one nothing can call. A ~main~ with no parameter is given one: the arguments
exist whether or not the program wants them, and

#+BEGIN_SRC scheme
(defun (main)
  (println "hi")
  0)
#+END_SRC

is the same function with the parameter left unnamed.

Writing a *different* signature is the one way to get a different type, and it
is rejected:

#+BEGIN_SRC text
Type Error at prog.bjo:15: 'main' is a program's entry point and has one type,
(-> (Vec string) int). This one is (-> (Array string) int). A main written
without a signature is given that one, and a main written without a parameter
is given the arguments anyway — so the way to a different type is a signature,
and there is nothing the entry point could pass it.
#+END_SRC

~main~ may be a ~defbjo~. That is the only way a program gets into fiber-land
today, and the entry point drives the fiber to completion on the process's own
thread; nothing else about its type changes.

The generated ~Main~ builds a ~(Vec string)~ from the process arguments, calls
~main~ with it, and *exits with what it answered*. A ~main~ ending in ~1~ is a
program a shell, a test runner or ~bjo run~ sees fail. This implies that the ~main~ function must strictly adhere 
to the expected signature; unexpected shapes will fail to compile.

** Runtime assemblies

Every compiled program links against a fixed set of support assemblies, named
once in ~Paths.runtimeAssemblyNames~:

| ~BjolangRuntime~ | the builtins — dynamic environment, ~Vec~'s cursor, conversions |
| ~Collections~    | ~Vec~ (RRB tree)                                         |
| ~SchemeList~     | ~List~                                                   |
| ~Map~            | ~Map~ (CHAMP), its builder, transient and cursor         |
| ~BjoSet~         | ~(Set %a)~, bound by =(std set)=                          |
| ~BjoOrderedSet~  | ~(OrderedSet %a)~, bound by =(std orderedset)=            |
| ~BjoOrderedMap~  | ~(OrderedMap %k %v)~, bound by =(std orderedmap)=         |
| ~Bjoml~          | the concurrency runtime: fibers, promises, channels, CML events |

The last four carry no builtin type: their types reach Bjolang through
~import/class~ and their operations through ~import/extern~, ~Map~'s in
=(std prelude)= and the rest in a library of their own.

Each is a submodule with a project of its own, referenced by
~BjolangRuntime.csproj~ and *removed from its compile glob* — without the
removal their sources are compiled a second time into ~BjolangRuntime~, which
for a project with package references of its own simply fails.

Three things follow from that list, and adding an assembly means doing all
three:

1. It is referenced when a program is compiled — by both the fast ~csc~ path and
   the MSBuild fallback, which read the same list.
2. Its directory is on the probe path of the resolver a compiled program
   installs. Nothing is ever copied next to the output: an assembly has one home
   and the program points back at it. A *package* dependency therefore has to be
   copied into that directory, which is why ~BjolangRuntime.csproj~ restates
   Bjoml's ~Microsoft.Extensions.ObjectPool~ reference and sets
   ~CopyLocalLockFileAssemblies~.
3. It is registered with the interop resolver before type checking, so
   ~import/class~ and ~import/extern~ can name types in it. ~Type.GetType~
   searches the core library and the compiler's own assembly and nothing else,
   so without this a linked assembly is reachable at run time but not nameable
   at compile time.

** Optimization

Output is optimized unless you pass ~-d~. The difference is not marginal: a
debug build is marked debuggable, which tells the JIT not to optimize it, and
the same generated C# then runs several times slower. A counting loop over
4×10⁹ iterations measured 0.77 s optimized against 6.9 s unoptimized — the
optimized figure being identical to the same loop written by hand in C#.

Use ~-d~ to read the generated code or to step through it, not to run it.

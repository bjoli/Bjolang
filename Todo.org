Known gaps, written down where they were found rather than in a commit message.


**Make cancellation per-fiber instead of per-sync.** Done — ~FiberWatch~ in
~Concurrency.cs~, one registration per fiber and scope, re-armed per park. The
slot lives on ~DynEnv~, which is already per-fiber-and-scope. See the B7-style
section in ~BjolangRuntime/Cml/design.md~ for the numbers and the hazards.


* The CML layer: where the remaining speed is

The anchor fact for all of these: ~bench/Cml/Program.cs~ uses ~Channel<T>~,
~Cml.Choose~ and ~EventAwaiter~ out of the same assembly the language links, and
runs the ring at 58 ns/op where the language runs it at 112. The layer is capable
of the numbers; what costs is the seam between ~sync~ and the layer. So these are
surgical changes, each independently measurable, and not a rewrite — ~IEvent<T>~
stays the specification the ~Cml/Tests~ suite is written against.

Everything below is unmeasured except where it says otherwise.

** Delivery is a callback where a fiber wants a slot

~IEvent<T>.Publish~ says "call me with the value"; a fiber wants "put the value
here and resume me". ~EventAwaiter~ converts one into the other, at a pooled
object, a delegate hop and an interlocked handover per rendezvous — where the C#
path stores the fiber's resume straight into the ~PutOp~. Measured at ~13 ns, and
tried once already: it regressed the ring badly while the per-park registration
still existed, which it no longer does. Worth another attempt, and the first
thing to try.

** A token cannot unregister

Nothing removes a waiter from a ~Promise~; it prunes amortised instead. That one
fact is why ~FiberWatch~ needs a generation, an abandonment protocol and a
fallback path. A cancellation token with O(1) removal — an intrusive node the
fiber owns and unlinks when the park ends — deletes all three and is *simpler*
than what is there now. Best value per unit of risk on this list.

** A send carries a ~Unit~ it does not want

~ChannelSendEvent : IEvent<Unit>~ puts ~Action<Unit>~ through the whole path, and
~PutOp.ResumeGive~ exists only so publishing a send does not allocate a closure
adapting it to ~Action~ (88 of that row's 128 B/op, per its own comment). A
void-shaped send needs none of it. Allocation, not time.

** Two ~Result~ types meet at every join

~promise-join~ allocates a ~Wrap~ and a mapper per join to turn
~Bjoml.Result<T>~ — which carries an ~ExceptionDispatchInfo~ — into Bjolang's
~Result~. A promise that spoke the language's own failure type would not.
Allocation, not time.

** Event ids are minted with an interlocked increment

Publishing happens on the syncing fiber's thread and nowhere else, so a
~choose~ over eight branches pays eight atomics for a counter with one writer.
Only the readers (~withNack~'s interval close, ~MarkSynchronized~) are on other
threads. Measure before touching; it is a guess.

** Unexplained: the direct-park rewrite regressed the ring

Recorded in ~design.md~ with the six explanations that were ruled out. It wants
~perf~, which is not installed on the development machine. Worth an afternoon
before anyone commits to a larger redesign, because if it is structural the case
for one gets stronger.

* Source mapping (~#line~)

Statement-level directives are emitted from ~generateBlock~, and both build
configurations now carry a portable pdb, so stack traces name ~.bjo~ files and
lines. What is not done:

** Hoisted temporaries are attributed to the statement that produced them
~emitStatement~ builds into a scratch buffer and then prepends a ~prelude~ of
hoisted statements. The hoists are compiler glue with no honest source line, but
they inherit the directive of whatever preceded them. They want ~#line hidden~
around the prelude. Three sibling sites buffer the same way (~hoistToTemp~, and
the two buffered-scratch paths in ~generateLocalFunction~).

Harmless today — the line they inherit is the statement they belong to, which is
close enough to be useful — but it is luck rather than design.

** Directives are emitted unconditionally
No suppression when the line has not changed since the last one, so the
generated C# carries more directives than it needs. Correct, just larger. A
dedup needs care: scratch buffers are relocated after the fact, so a
module-level "last line emitted" would be wrong the moment a buffer moves.

** Column spans are not used
C# 10+ takes ~#line (l1,c1)-(l2,c2) "file"~, and ~Lexer.Range~ already carries
~End~ as well as ~Start~. Using it would give column-accurate squiggles for
nothing beyond the formatting change.

** Inlined trait methods report the impl, not the call site
~TraitInline~ splices an impl body into a caller, and the spliced nodes keep the
impl's ranges. A failure inside an inlined ~fold~ names the ~impl~. That is
defensible — it is where the code is written — but a caller reading the trace
has no way to see which call site reached it.

** The pdb no longer distinguishes a ~-d~ build
Optimized builds used to delete their pdb, and its absence was how a caller
could tell which way a binary was built. Both configurations now keep one.
Nothing depended on the signal, but it is gone.

* Diagnostics

** Errors raised outside ~infer~ depend on their own call site for a location
~infer~ attaches ~file.bjo:N~ to any diagnostic that arrives without one, which
covers type errors. Reports from generalization, trait registration and parts of
declaration checking are outside that wrapper and carry a location only if the
site supplied one. Threading a ~Range~ into ~unify~ would close this, at the
cost of inventing a location at the several call sites that have no natural one.

** ~unify~ reports the two types, not the path to the mismatch
Two large types differing deep inside are printed whole, and the reader finds
the difference. Reporting the innermost disagreeing pair, or marking it, would
be better.

* Characters and strings

** ~char-foldcase~ is simple lowercasing
.NET exposes no simple case-folding table, so ~ToLowerInvariant~ stands in. It
agrees with Unicode's simple fold except for characters like ß and ﬁ, where a
full fold expands — which no char-to-char function can express in any case.

** ~Collection~ is still not implemented for ~(Array %a)~
It has no ~->seq~ to give.

** A number cannot be read or written in a culture
~double->string~ and ~string->double~ now go through ~BjoNum~, which pins both
to the invariant culture. That is the right default — they round-trip, and a
document does not change meaning when it crosses a machine — but it is the
*only* setting on offer, so a program that wants to show a Swede ~1,5~ has
nowhere to ask.

~string->int~ is still ~Int32.Parse~ on the ambient culture. ~NumberStyles.Integer~
allows no group separators, so only the sign differs and nothing has been seen
to break; it is inconsistent rather than wrong.

What is missing is a ~Culture~ the prelude can name, and the overloads that take
one. Until then, formatting for a human means reaching into .NET through
~import/extern~.

* Emacs mode (~bjomode.el~)

Indentation follows Scheme's rules: bodies two, ~if~ four, everything else
aligned under the first argument. Reindenting ~lib/std/prelude.bjo~ and
~TestFiles/008_iterators.bjo~ from scratch reproduces them exactly.

** A named loop aligns under the name, not the first clause
~(loop lp (:for x xs) ...)~ puts the clauses under ~lp~, where the sources put
them under ~(:for~. Standard Lisp alignment gives the former, and the latter
needs a custom indenter that returns the column of the *second* argument —
~lisp-indent-specform~ cannot express it. Named ~let~ is special-cased already
(~bjo-let-indent~) because its body is a body; a named loop's clauses align, so
it needs different machinery for one rarely-used form.

** A ~match~ arm's body aligns under the pattern
~((Ok probe) body)~ is a list with a list at its head, so the body lines up
under ~(Ok probe)~. Emacs does the same for a ~cond~ clause. Some sources
indent it two from the arm's own paren instead.

** Library functions that read as body forms are not known
~with-nack~ takes a function and looks like a body form, but it is an ordinary
call, so its argument aligns under the head. Only forms the parser gives a
meaning to are in ~bjo-indent-forms~; adding library names there would mean
tracking the library from the mode.

** No completion, no imenu, no eldoc
Font lock and indentation only.

* Operators

An unapplied operator is eta-expanded into the lambda it stands for, so its type
comes from the use site. Two things that leaves.

** A local binding that shadows an operator is ignored
~(let ((+ my-add)) (+ 1 2))~ compiles, and prints 3 rather than calling
~my-add~: the operator arms in ~generateApply~ match on the name alone and emit
infix whatever the name is bound to. ~conBaseName~ consults a ~shadowedBuiltins~
set for type constructors; nothing does for operators, and ~Inference~ resolved
the binding correctly before ~Codegen~ threw the answer away.

Silent, which is the bad part. Rejecting the shadowing outright would also do.

** A polymorphic operator value is a C# error, not a Bjolang one
Reachable only by asking for one in a signature —
~(: get-plus (-> (-> %a %a %a)))~ — which emits ~Func<T_a, T_a, T_a>~ with
~a + b~ in the body, and C# says ~Operator '+' cannot be applied to operands of
type 'T_a'~. The other routes are already closed by rules that predate this:
~(def plus +)~ with no signature is caught by the module-level value rule, and a
~defun~ needs a signature at all.

The message is the gap, not the rejection — there is nothing a C# type parameter
could mean here. It is the same wall generic arithmetic hits everywhere else.

* Monomorphisation of constrained generics

~Monomorphise~ copies a constrained function at each ground instantiation the
module calls it with, and the copy takes no dictionary. The body of an exported
one travels in the dll — ~Metadata.ConstrainedBodies~, format version 8 — so the
copy is made in the module that calls it, which is also what lets it resolve
against implementations the library never saw.

What it does not do, written as what was deferred rather than as what was found.

** The budget, and what stops the sweep

The sweep runs to a fixpoint rather than to a depth: each round collects demand
over the copies the round before it made, and it stops when a round asks for
nothing new. There is no depth number, and deliberately — the number that would
have worked when this was written is 3, which is only where the standard
library's chains happen to run out.

Termination is by the key, not by a counter. A copy is keyed by its name and its
ground type arguments, so demanding one that exists is a lookup; new keys can
only run out. What would break that is *polymorphic recursion* — ~f~ at ~T~
calling ~f~ at ~(List T)~, which is why C++ and Rust need a depth cap — and
Bjolang cannot express it: a recursive occurrence is bound monomorphically, the
same fact ~Lowering.Scope.SelfCall~ relies on, and a mutually recursive group is
not a candidate at all.

What bounds it instead is a code-size budget, in typed AST nodes: the module's
own size or ~budgetFloor~, whichever is larger. When it is spent the pass warns,
names the function it stopped at, and leaves the remaining calls dispatching —
always correct, and the same fallback a body that will not re-check takes.

The floor is measured rather than chosen, and the measurement is worth keeping
because it is what makes the fixpoint safe rather than merely terminating. The
standard library has 22 constrained generics and its call graph among them has
**out-degree at most one** — 15 call no other constrained generic and 7 call
exactly one. So copies grow by addition: 1.41 per call site on average, 3 in the
worst case, and depth 8 costs exactly what depth 3 costs. The largest demand
anywhere in the fixtures is ~139_ord.bjo~ at 722 nodes.

A graph that branched would grow by multiplication, and then the floor is what
would matter. Nothing here branches yet.

** Every type argument has to be ground

A call at ~(-> %a int)~ where ~%a~ is still open is passed over, and so is one
where only the *constrained* variables are ground. The copy therefore has no
type parameters at all, which is what lets a call site drop its type arguments
without agreeing with ~generalize~ about the order it put them in. Keeping the
unconstrained ones would give fewer, more general copies and needs that
agreement.

A type argument that is a function type is declined outright: it has no short
spelling for a copy's name, and ~Eq~ and ~Ord~ have no implementation at one.

** Suspending functions are not copied at all

A ~-?->~ signature and a ~defun~ that reaches a ~defbjouble~ both already have a
second body, and it is generated inside ~checkDeclGroup~ — so it is not among
the untyped declarations this pass reads, and it could not copy both halves even
if it wanted to. Copying only the ordinary half would leave ~selectDoubles~
looking up a mangled name in ~DoubleDefs~ and finding nothing, which is not a
wrong answer but is a fiber that blocks where it used to park.

~Naming.specializedCopy~ puts its infix ahead of the colour suffix so that
~f__at_int__bjo~ is what the twin would be called, which is the half of the fix
that is already in place.

** Mutual recursion is declined

Specialising one member of a cycle leaves it calling the generic other, which is
the ~CS7036~ recorded above under "Mutual recursion does not forward
dictionaries". Specialising the whole group together would *fix* that bug at
every ground instantiation, which is the reason to do it and the reason it is a
separate change.

** A mention that is not a call is passed over

~Lowering~ eta-expands one back into call position and supplies its dictionary
there, so it is correct as it stands. Specialising it would remove the
eta-expansion as well as the dictionary, and it is a rewrite at a different node.

** A body that will not serialize is not published

~Codegen.isSerializableTemplate~ decides, and it refuses ~try~, a bare list
literal, a tuple-destructuring binding and a local function with keyword or rest
parameters. Such a function crosses as a signature only, and a call to it keeps
its dictionary — which is what every call did before bodies crossed at all, so
nothing regresses and nothing says so either. The same rule has governed inline
templates since they existed.

** A published body is *checked* in the importer's scope

Qualification rewrites the copy's free names to name the module they came from,
but it is applied after inference: during checking the body still says ~helper~,
and ~helper~ means whatever the importing module calls that. A module that binds
a name the library's body uses would have its own binding checked into the copy
and the library's emitted into it.

Exactly the hazard ~qualifyInlineTemplates~ documents for a splice, with the
same mechanism and the same gap. Closing it means inferring the body in one
environment and emitting from another, which is a change to ~infer~'s ~EApp~
case — see "A resolved call reads its arguments in the resolved name's scope"
above, which is the same seam from the other side.

** A private helper named by a published body becomes public

~autoExports~ already did this for inline templates; there is simply more of it
now. ~doubled~ in ~TestFiles/193_lib.bjo~ is not exported and is published
anyway, because ~width-of~ names it and a copy of ~width-of~ has to be able to
call it. The C# was public either way — what changes is that the name is now in
the importing module's scope, where it can shadow or be shadowed.

* Constraints and numerics

Found while opening ~Ord~ up and making the numeric constraints explicit. All of
them are the same seam: a constraint discharged by *passing a dictionary* rather
than by a C# ~where~ clause. Direct recursion, deriving ~Ord~ and using a
constrained function as a value were three of these and are fixed; what is left
is written as what remains rather than as what was found.

** Mutual recursion does not forward dictionaries

*Direct* recursion does, now: ~Scope.SelfCall~ carries the function's own
dictionary parameters and a call to its own name forwards them. That is correct
by construction rather than by luck — inside its own body a function is bound
monomorphically, so the call is at exactly the enclosing type variables and the
dictionaries it was handed are the right evidence in the right order.

Two constrained functions calling *each other* are still stuck. Neither is its
own callee, so each takes the ordinary route, finds no type arguments recorded —
the mutual bindings are monomorphic for the same reason — and passes nothing.
The result is the ~CS7036~ that direct recursion used to give.

Nothing in the library does this yet, which is the only reason it is written here
rather than fixed. The general answer is to record type arguments for a
monomorphic recursive binding, which is a change to how recursion is typed rather
than a patch to ~Lowering~.

* Incremental builds

** ~bjor~'s staleness check is not covered by the suite

~needs_compile~ decides whether to invoke the compiler at all, and it has been
wrong twice in opposite directions: once rebuilding the whole standard library
on every invocation, once leaving a module stale that a dependency had moved
under. Neither was caught by a test, because the suite compiles fixtures with
the compiler directly and ~bjor~ is only in the path of ~build_std.sh~ and of
running a file by hand.

Testing it means mutating ~lib/std~ mid-run — touching a module and asserting
what the next invocation says — and the tree is left inconsistent between the
touch and the rebuild that follows. The suite already takes a lock against two
runs sharing a working tree for that reason, so this wants to be the last phase
or a script of its own.


* Colourless concurrency

Layers 0–4 ship, and so does trait colour in both shapes. Four things left,
none of which blocks anything.

** A generated copy that never suspends is still emitted

Size only. The copies that gain no yield point are async methods awaiting
nothing. Pruning them needs call sites redirected back to the original *after*
selection, which is a rewrite nothing so far has needed.

** Two lambda pins have no message of their own

A lambda handed to a .NET ~Func<A,B>~, and one stored in a structure whose
element type is a ground ~->~. Both land in ~Unpinned~ and get the generic
message, which is true about them.

Neither is reachable from a fixture: every ~Func~-taking method in the runtime
is generic, and ~Task.Run~ fails overload resolution through ~import/extern~.
A message waiting for a case.

** The lazy half of ~Seq~ has no suspending copy

~seq-map~, ~seq-filter~, ~seq-unfold~. Closed as a decision rather than open
work: the two copies would have different *types* — ~Seq~ against ~AsyncSeq~ —
and a copy that changes its return type is two functions, not monomorphisation.
~port->chan~ shipped instead.

If a suspending sequence is ever wanted it is a separate form producing a
separate type, with an ~AsyncIterable~ trait to consume it. Expressible now that
a trait method may carry a colour; not worth it at two ~seql~ producers in the
whole library.

** A ~(do ...)~ block cannot suspend

~:bind~ desugars to ~bind~ with the rest of the block as ~(fun ...)~, and a
lambda's text is fixed while its colour is not. ~(bind m (bjoroutine (x) ...))~
written by hand does suspend; the macro cannot know which was wanted.

A second definer — ~:bind/bjo~, or a keyword the whole ~do~ reads — would settle
it. Nothing has needed one yet.

* An impl at a concrete instantiation cannot be dispatched to

~(impl (Over (List int)) ...)~ emits ~Over_List~, a non-generic class,
because the impl's fixed prefix is ~int~ and has no type variable in it. A
dictionary built for it is still spelled ~Over_List<int>.Instance~, and Roslyn
answers ~CS0308: the non-generic type 'Over_List' cannot be used with type
arguments~ about a file nobody wrote.

Only the *dispatched* path. A resolved call is inlined or lands on the pad, and
both are fine; ~(impl (Over (List %a)) ...)~ is fine too, which is why this
has not been hit — an impl at one instantiation of a generic type is an unusual
thing to write.

Reproduces with a plain ~->~ method, so it has nothing to do with colour.

* Macros and trait methods

Both found while making a trait method in a template mean the trait. Neither is
reachable from the standard library as it stands, which is why they are written
here.

** A trait a macro's module imports is not among the ones it resolves

The set is read off the macro module's own ~def/trait~ declarations, at the
point where its assembly's macros are registered. Every import edge in the
module graph names a compiled ~.dll~, and a ~.dll~'s node carries its own
declarations and no dependencies, so nothing further is reachable from there.

So ~time-it~ in ~std/stopwatch~ writes ~(->str ...)~ in its template and gets
the old behaviour: the bare name, resolved where the expansion lands. Closing it
means the module's metadata carrying the set, which is where the compiler
genuinely knows it — inference has the whole registry for the module it is
compiling.

** A resolved call reads its arguments in the resolved name's scope

~Inference.unshadow~ puts module level's binding for one name back over what is
in scope, and the ~EApp(EResolved ...)~ case then infers the whole application
in that environment — arguments included. Its docstring says otherwise.

The visible consequence is that a name written by hand *inside* an argument of a
compiler-written call means the compiler's binding rather than the caller's:

#+BEGIN_SRC scheme
(defun (through m bind)
  (do (:bind x m)
      (:return (bind x))))     ;; reaches Monad's bind, not the parameter
#+END_SRC

Fixing it means inferring the callee in one environment and the arguments in
another, which the ~EApp(EIdent ...)~ case is not shaped for: it is one branch
covering trait dispatch, extern resolution and keyword arguments. Renaming the
shadow apart in the arguments instead does not work either — the binder keeps
its spelling into the emitted C#, so only one end of the rename would move.

* A lowercase union case cannot be matched by name

Found while letting a binder shadow a union case constructor, and separate from
it: in *expression* position the two are now told apart by scope, but a pattern
has no such thing to consult.

#+BEGIN_SRC scheme
(type (: Shape (Union blob (dot int) Big)))

(match s
  (blob "a")     ;; binds `s` to `blob` and answers "a" for every shape
  ((dot _) "b")
  (Big "c"))
#+END_SRC

~parsePattern~ reads a bare lowercase symbol as a binder, before any registry
exists to say otherwise — which is right for the overwhelmingly common case and
leaves no way to *test* for a nullary lowercase case. A case with a payload is
fine: ~(dot _)~ is a list, so it reads as a constructor. An uppercase case is
fine for the same reason the binder rule is safe.

Two ways out. Resolve the pattern's constructors after parsing, where the
registry is known — which is where the expression side resolves and would make
the two agree. Or refuse a lowercase nullary case at the ~type~ declaration,
which is smaller and would cost the prelude nothing: its lowercase cases all
carry payloads.

* Equality and hashing

A ~Map~ and a ~Set~ file a key under ~EqualityComparer<T>.Default~ — .NET's
equality — and not under the ~Eq~ impl in ~std/eq~. The two agree today, and
nothing makes them.

What was found: ~RrbList~ had no ~Equals~ or ~GetHashCode~ of its own, so a
~Vec~ key was compared by reference and never found its own entry. It has them
now, and ~Map~, ~Set~ and ~SchemeList~ already did. Separately, ~Map.Clear~,
~Set.Clear~ and both ~Remove~ methods answered with the shared ~Empty~
singleton, which carries the *default* comparer — so a collection built with one
of its own silently reverted to .NET equality the moment it was emptied.
~TestFiles/186_collection_keys.bjo~ pins both.

** A hand-written ~Eq~ is still not what a ~Map~ keys on

The gap the above only papers over. An ~Eq~ impl that departs from .NET's — a
case-insensitive string, a record compared on one field, anything a user writes
over a foreign type — is ignored by every hashed collection, and the symptom is
a lookup that misses rather than anything that can be caught.

The pieces are all in place. The CHAMP is comparer-parameterised end to end:
~TrieOps~ takes an ~IEqualityComparer<TK>~, ~Map<TK,TV>~ stores one and
propagates it through every operation, and ~MapModule.Empty~ already accepts
one. And a ~where (Eq %a)~ compiles to an ordinary interface dictionary:

#+BEGIN_SRC csharp
public static bool same_QMARK<T_a>(Eq<T_a> _dict_Eq_a, T_a a, T_a b) { ... }
// call site: same_QMARK(Eq_System_Int32.Instance, 1, 1)
#+END_SRC

~Eq<T>~ is a public generic interface with a singleton per implementor, which is
nearly an ~IEqualityComparer<T>~ already. Emitting it as one — with default
interface methods forwarding ~Equals~ and ~GetHashCode~ to ~eq~ and ~eqsubhash~
— makes the dictionary itself the comparer: no wrapper, no allocation, no
delegates, one interface call per probe.

The half that is missing is that Bjolang cannot *name* the evidence in scope, so
~map-empty~ has nothing to pass. Either an intrinsic that reads the dictionary
~Lowering~ already threads, or these few constructors become compiler-known.
Only the constructors need it — ~map-empty~, ~mapbuilder-empty~,
~transientmap-empty~, ~seq->map~ and their ~Set~ counterparts — because the
comparer is stored; ~map-set~ and ~map-ref~ keep their signatures. Those
constructors gain ~(where (Eq %k))~, which is the honest cost: it makes "this
key type has Bjolang equality" a checked fact rather than an assumption.

Keep ~null~ meaning "use ~EqualityComparer<T>.Default~", and pass it when the
key's ~Eq~ is the CLR-derived one. Otherwise every ~int~-keyed map loses the
devirtualisation the JIT gives the default comparer, which is a real cost on the
structure whose whole point is speed. With the dictionary as the comparer that
is one check at construction.

The same is true of ~Ord~ and the ordered collections, and worse in one respect:
~orderedmap-empty~ is a bare extern, ~OrderedMap~ keys on ~Comparer<T>.Default~,
and a Bjolang ~Ord~ impl is ignored the same way — which is why ~std/clr-ord~
has to exist at all.

Doing it for one trait and not the other is not worth it: both are one
mechanism, ~evidence-as-comparer~, applied twice.

* Packages: what the roots work left undone

~--roots~ gives a package a name and a directory, and a module its identity from
that name. These are the pieces around it that were deliberately not built at
the same time, each with the reason it could wait.

** An executable names its dependencies by absolute path

~BjolangModulePaths~ in ~Build.fs~ embeds the full path of every module ~.dll~ in
the generated resolver, so a program only runs on the machine that built it:
copy ~app.exe~ to another host and it resolves nothing, however the packages are
arranged there. Deferred because a resolver that searches roots at run time
needs the roots to *be* somewhere at run time — an installed layout, or the
paths written into the executable as a manifest — and that is a decision about
deployment, which no part of this work had to make.

** Build output still lands next to the source

~core.bjo~ compiles to ~core.dll~ beside it, so building the same package in two
projects writes into the fetched copy twice, and a read-only package directory
cannot be built at all. Deferred because moving the output means teaching
staleness, the resolver table and the build record about a second directory, and
none of that is needed to prove that identity no longer depends on location.

** ~lib/text~ is a standard-library root of its own

~(text json)~ is a package named ~text~, beside ~std~, because every
top-level directory of ~lib~ is a root. Moving it under ~std~ would rename every
module in it — ~BjoMod.text.json~ becomes ~BjoMod.std.text.json~ — and every
assembly with it. Deferred as a rename with no technical content; the roots rule
is indifferent to which of the two layouts is chosen.

** A relative import still means a path

~(import "core.bjo")~ resolves against the importing file's directory, as it
always has. What changed is only what the file it finds is *called*: if that
file is inside a package, it is the module the package names, so the two
spellings reach one assembly. Deferred any further change — making a relative
import illegal across a package boundary, say — because nothing yet says what a
package boundary is worth, and a rule refusing programs that work today needs
that.


* Projects: what ~bjo init/fetch/build~ left undone

~bjo~ reads a manifest, resolves a dependency graph, fetches git packages by
version tag, writes ~bjo.lock~ and hands the compiler a roots file. See
~Docs/Projects.org~. These are the pieces around that, each with why it waited.

** ~bjo add~, ~bjo update~ and ~bjo remove~ edit the text, not a tree

Done, in ~bjo/edit.bjo~, and the way it is done is the thing to know: the
bjodat reader gives a value with no positions in it, so the file is scanned for
the *spans* of its forms and only the characters that have to change are
changed. Every edit is parsed before it is kept.

What that leaves: the scanner knows parentheses, strings and ~;~ comments and
nothing else, so an edit is placed by where a form *is* rather than by what it
means. Two things follow. ~bjo update~ replaces a whole constraint, so a
~version-between~ becomes a ~version-at-least~ and the upper bound is gone —
raise it by hand instead. And a comment written *inside* a ~(depends ...)~
clause, between two entries, is left where it is when the entry under it is
removed, so it can end up attached to the wrong one.

** No shared cache in the home directory

Every project clones into its own ~.bjo/git~, so two projects that depend on
~(bjorsec)~ clone it twice. Deferred because a shared cache is shared *state* —
two ~bjo~ processes fetching into one clone at once — and nothing here locks
anything yet.

** Build output still lands beside the source

A fetched package is built inside ~.bjo/pkg/bjorsec@1.2.3/src~, so the
directory has to be writable and two projects that depend on one version build
it twice. Deferred for the reason the roots work deferred it: moving the output
means teaching staleness, the resolver table and the build record about a
second directory.

** No registries, no commit or branch pins, no pseudo-versions

~(source (registry))~ is an error saying there are none; ~commit~ and ~branch~
in a git source are refused. A dependency on an untagged commit — "the fix I
pushed this morning" — has no spelling at all; use a path source. Deferred
because a version is a tag here, and a pin that is not a version would need its
own place in the lock and its own answer to "is this newer than that".

** One version of a package per build

If two packages need ~(json)~ and their constraints cannot both be met, the
build is refused rather than given two copies of ~(json)~. Deferred because a
module's identity is its package name, so two copies would be two modules
called ~(json core)~ — and a value made by one would not be of the type the
other declared.

** No ~bjo install~, ~bjo test~, ~bjo clean~, and one entry point per package

~tests/~ is a directory ~bjo init~ makes and nothing reads: a test is run with
~bjo run tests/whatever.bjo~, which works because a file inside a project is
compiled against the project's packages. A package builds one program, named by
~entry~, so a repository holding both ~myapp~ and ~myapp-server~ needs two
packages. Deferred as conventions that are cheap to add and expensive to
change.

** Nothing locks ~.bjo~ against two ~bjo~ processes

Two builds of one project at the same time can both unpack ~.bjo/pkg/x@1.0.0~,
and the second rename over the first fails. Deferred because a lock file is
easy and the failure mode — one of the two builds stopping with an error — is
loud rather than silent.

** A version requirement on a path dependency is ignored

~(package (name (mylib)) (version (version-at-least "2.0")) (source (path (dir
"../mylib"))))~ builds against ~../mylib~ whatever its manifest says its
version is. Deferred because a path source is an override — "use this copy" —
and refusing it on a version would make the override conditional on the thing
it is overriding.

* Bjolang Prelude

The prelude contains the default environment available to all Bjolang programs. These procedures are automatically in scope.

Nothing here has to be imported. ~(std prelude)~ is linked into every module the compiler loads, so writing ~(import (std prelude))~ is allowed but redundant. (Modules under ~lib/~ are the exception: the standard library says what it depends on explicitly, since ~prelude~ itself imports ~maths~.)

The prelude is nevertheless made of two halves, and it is worth knowing which is which when reading the sources:

- The *builtin* environment (~Prelude.fs~, backed by ~BjolangRuntime~) holds what currently isn't written in bjolang.
- ~lib/std/prelude.bjo~ is an ordinary Bjolang module. It holds everything that *is* just a .NET call — the string, conversion, file, path, directory, environment and port operations below — plus the traits (~->str~, ~Iterable~, ~Collector~, ~Num~) and ~print~/~println~.

Sections below are marked =(std prelude)= where they live in the second.

** Core Values and Constants
- ~void~ (also ~Unit~) : the unit type. Procedures
  documented below as returning nothing return this.

** I/O
- ~(display x)~ : Prints ~x~ to standard output without a newline.
- ~(displayln x)~ : Prints ~x~ to standard output with a newline.
- ~(print x)~ : Generic print utilizing the ~->str~ trait. =(std prelude)=
- ~(println x)~ : Generic println utilizing the ~->str~ trait. =(std prelude)=
- ~(newline)~ : Prints a newline character.

There is no nullary ~read-line~. Standard input is a port like any other, reached through the dynamic environment: ~(read-line (parameter-ref current-input-port))~. current-input-port can be rebound with the parameterize form.

** Math Operators
Standard polymorphic math operators:
- ~(+ a b)~
- ~(- a b)~
- ~(* a b)~
- ~(/ a b)~
- ~(% a b)~

** Comparison
- ~(= a b)~ : Equality. A method of the ~Eq~ trait =(std eq)=, re-exported by the prelude, so it is one operation over the primitives, the containers and a program's own types alike. See *Equality* below.
- ~(< a b)~
- ~(> a b)~
- ~(<= a b)~
- ~(>= a b)~
- ~(eq? a b)~ : Pointer/Reference equality (structural for value types). About mutable cells and object identity, and not a substitute for ~=~.

** Equality =(std eq)=
There is one equality, ~=~, and it is a trait method:

#+BEGIN_SRC scheme
(def/trait (Eq %a)
  (: = (-> %a %a bool))
  (: eq-hash (-> %a int)))
#+END_SRC

Implementations ship for the primitive types (~int~ and its siblings, ~double~, ~bool~, ~string~, ~char~, ~Keyword~, ~Symbol~, ~StringCursor~, ~void~), for ~List~, ~Vec~, ~Option~, ~Result~ and ~Map~, and for tuples of two, three and four elements. A container's implementation compares its elements through *their* ~Eq~ implementation, so ~(= (Some p) (Some q))~ reaches whatever ~p~'s type says equality is.

A generic function that compares two values acquires the constraint without being told to: ~(defun (member? x xs) ...)~ using ~=~ is inferred as ~(where (Eq %a))~.

~eq-hash~ belongs to the same trait as ~=~ rather than to one of its own, because it is derived from the same choice of fields. An implementation that overrode one while inheriting the other would break every hash-based container silently, and there is no supertrait mechanism to keep two traits in step. There are no default bodies for the same reason: the only body a default could have is "ask .NET", which is wrong in exactly the case someone wrote an implementation for. ~(hash-combine a b)~ is what an ~eq-hash~ over several fields folds with.

Two deliberate choices worth knowing:

- ~double~ uses ~Equals~ rather than ~==~, so ~(= x x)~ is true for ~NaN~. Every hash-based container assumes its keys are reflexive; IEEE's answer is the other one, and it is not available through ~=~.
- ~=~ on a ~Map~ matches keys by lookup, so key equality there is the trie's . (FIXME)

*** The blanket
A type with no implementation of its own gets a default equality implementation in ~(std eq)~. 

Two consequences worth knowing. Nothing can opt *out*: ~(= p q)~ on two ports, or two fibers, compiles and means reference identity, and there is no negative-implementation mechanism to say otherwise. And a type with no *head constructor* is not covered at all, because resolution needs a head to look up before it can fall back to a blanket — so ~(= f g)~ on two functions is a type error saying so.

*** Writing one by hand
Writing one by hand is ordinary, and is how a type says its equality is not its fields:

#+BEGIN_SRC scheme
(impl (Eq Point)
  (defun (= a b) (and (= (record-ref a x) (record-ref b x))
                      (= (record-ref a y) (record-ref b y))))
  (defun (eq-hash p) (hash-combine (eq-hash (record-ref p x))
                                   (eq-hash (record-ref p y)))))
#+END_SRC

The implementation *is* the type's .NET equality. A declared type with an ~Eq~
implementation has its ~Equals~ and ~GetHashCode~ emitted as calls to it, so
~Map~, ~Set~ and every other .NET consumer agree with ~=~ without being told
about the trait. ~Ord~ gets the same treatment as ~IComparable<T>~: an
implementation becomes the type's ~CompareTo~, so the ordered collections —
and any .NET code handed the type — sort by ~compare~ rather than throwing. A
parameterized type materializes when its implementation is unconditional; one
with a ~(where ...)~ keeps C#'s synthesized field-wise members, which reach
each field's own implementation anyway.

Two consequences:

- An implementation written in terms of .NET equality would call itself —
  ~Equals~ is the implementation now — which is why ~clr-equals~ is private to
  ~(std eq)~. An implementation that wants "the field-by-field comparison,
  plus one tweak" writes ~(structural-equals a b)~ and ~(structural-hash a)~:
  they compare the fields directly and never consult the receiver type's own
  ~Equals~, while each *field* still compares through its own type's equality,
  so nested implementations are reached.
- The implementation is compiled into the type, so it must live in the module
  that declares the type. An ~Eq~ or ~Ord~ implementation for an imported
  type, an ~import/class~ alias — or, in the REPL, a type from an earlier
  entry — is refused, because ~(= a b)~ would answer through the trait while
  the collections answer through the type, silently disagreeing. The way out
  the message names: the declaring module, the same REPL entry, or a wrapper
  type.

*** ~type/derive~
Writing that out per field is what ~type/derive~ is for. It is a macro in ~(std prelude)~, and a syntactic one — where a declaration is read there is no registry to ask what a type's fields are, only the form that declares them.

#+BEGIN_SRC scheme
(type/derive (Eq)
  (: Point (Record (: x int) (: y int))))
#+END_SRC

- a record or struct compares its fields in declaration order
- a union compares the case first: different cases are unequal, the same case compares its payload positionally
- a type with parameters derives a *conditional* implementation, ~(impl (Eq (Box %a)) (where (Eq %a)) ...)~
- the traits are a list: ~(Eq)~, ~(Ord)~ or ~(Eq Ord)~, each deriving its own methods from the one declaration

~Ord~ reads the same declaration the same way round, and answers with a sign rather than with a ~bool~: a record or struct compares its fields in declaration order and stops at the first that decides, a union compares the case index before the payload. The case order is the declaration order the hash already seeds itself with, so ordering and hashing agree about what a union's cases are without either being told.

#+BEGIN_SRC scheme
(type/derive (Eq Ord)
  (: Version (Record (: major int) (: minor int))))

(list-sort versions)    ;; and every other thing written against Ord
#+END_SRC

Nothing here corresponds to ~eq-hash~'s refusal on a mutable field. Hashing one breaks a law — a key's hash may not change — and ordering has none to break; a sorted collection going stale under a write is the write's doing rather than the comparison's.

A field whose type has no ~Eq~ is reported against the ~type/derive~ form rather than against the field: every node a macro builds carries the call site's range. The message names the type that has no implementation and the implementation that needed it.

** String Operations
- ~(string-append a b)~ : Concatenates strings ~a~ and ~b~. =(std prelude)=
- ~(string-length s)~ : The length of ~s~ in *storage units*. O(1). In current storage units. =(std prelude)=
- ~(string-count s)~ : The number of *characters* in ~s~. O(n), because it walks. The same emoji string counts 1.
- ~(string-empty? s)~ : Returns true if ~s~ has no characters. Builtin rather than =(std prelude)=, so that it sits with ~list-empty?~, ~vec-empty?~ and ~map-empty?~ rather than alone in the library.

~string-length~ and ~string-count~ are two questions with two answers and two costs, which is why neither is called ~size~. Reach for ~string-length~ to size a buffer and ~string-count~ for anything a reader would call "how long is this text".

There is no ~string-ref~, and no other index-based accessor. Indexing UTF-16 by codepoint is O(n), so a loop that looks linear is quadratic; string traversal belongs to a cursor.

*** Searching and rewriting =(std prelude)=
All *ordinal*: they compare storage, not culture. .NET's one-argument overloads compare by the ambient culture instead, which makes ~"e"+U+0301~ and ~"é"~ equal in one place and different in another; nothing here should depend on where it runs. Fold the case first — ~(string-contains? (string-downcase s) needle)~ — for an insensitive answer.
- ~(string-contains? s needle)~
- ~(string-starts-with? s prefix)~ / ~(string-ends-with? s suffix)~
- ~(string-replace s old new)~ : every occurrence; replacing with ~""~ deletes.

The ~char~-taking overloads of these are not wrapped and cannot be: a Bjolang ~char~ is a codepoint and a C# ~char~ a UTF-16 code unit, so they are not the same type at the boundary. ~(char->string c)~ is the way across.

*** Case =(std prelude)=
- ~(string-upcase s)~ / ~(string-downcase s)~

Invariant, for the reason ~char-upcase~ is, and character for character: ß upcases to itself rather than to SS, since the expansion is a German rule and not a Unicode one. These are for normalising before a comparison; what a *reader* expects to see is the locale-dependent answer they avoid.

*** Trimming and padding =(std prelude)=
- ~(string-trim s)~, ~(string-trim-start s)~, ~(string-trim-end s)~ : whitespace, by ~char-whitespace?~'s definition. There is no "trim these characters" form — .NET spells it ~params char[]~.
- ~(string-pad-left s width #:with #\space)~ / ~(string-pad-right s width #:with #\space)~ : to ~width~ *characters*, which is ~string-count~'s count and not ~string-length~'s. Never truncates.

The pad is a ~char~, so it is a codepoint like any other and an astral one counts as the single character it is. That is why these are written in Bjolang rather than wrapping ~.PadLeft~, which counts storage units and takes a UTF-16 code unit it could not be given.

*** Splitting and joining =(std prelude)=
- ~(string-split s sep)~ : the fields between occurrences of ~sep~, as a ~(Vec string)~. Empty fields are kept, which is what makes the two inverses; drop them with ~(vec-filter #(not (string-empty? &1)) parts)~.
- ~(string-join parts sep)~ : the elements with ~sep~ between them, through one buffer.

A ~Vec~ rather than the ~(Array %a)~ .NET answers with, because an array is ~Iterable~ and nothing more — it can be walked, and not measured, mapped or folded.

** Characters
A ~char~ is a Unicode *scalar value* — a codepoint — backed by ~Bjolang.Runtime.BjoChar~, not a C# ~char~. A C# ~char~ is a 16-bit UTF-16 code unit and cannot hold an astral codepoint on its own, so every predicate here classifies by codepoint and an emoji gets a real answer rather than whatever its leading surrogate would have said.



There is no ~char?~. Every other Scheme needs one because a value's type is a runtime question; here it is a static one, and the predicate could only ever answer true.

*** Conversions
- ~(char->int c)~ / ~(char->integer c)~ : The codepoint. =(std prelude)=
- ~(int->char n)~ / ~(integer->char n)~ : The character with codepoint ~n~.
- ~(char->string c)~ : A one-character string. For an astral character that string has ~string-length~ 2 and ~string-count~ 1.

*** Comparison =(std prelude)=
- ~(char=? a b)~, ~(char<? a b)~, ~(char>? a b)~, ~(char<=? a b)~, ~(char>=? a b)~ : Ordering by codepoint.
- ~(char-ci=? a b)~, ~(char-ci<? a b)~, ~(char-ci>? a b)~, ~(char-ci<=? a b)~, ~(char-ci>=? a b)~ : The same, after ~char-foldcase~ on both sides.

These are *binary*, where R6RS's are n-ary. The operators themselves work at ~char~ — ~BjoChar~ has the C# comparison operators — so ~(< a b c)~ chains as it does for numbers, and that is the n-ary route. A named function cannot chain: it would have to become a ~#:rest~ fold, which allocates an array and loses the short-circuit.

*** Case
- ~(char-upcase c)~, ~(char-downcase c)~, ~(char-titlecase c)~, ~(char-foldcase c)~

All four use the invariant culture, because R6RS specifies the locale-independent Unicode mappings — a ~char-upcase~ that answered differently in Turkey would make a program mean different things on different machines. ~char-foldcase~ is Unicode *simple* case folding, which is what a char-to-char function can express; use it rather than ~char-downcase~ when the purpose is comparison. ~char-titlecase~ differs from ~char-upcase~ only for the handful of digraphs Unicode gives a distinct titlecase form.

*** Classification
- ~(char-alphabetic? c)~, ~(char-numeric? c)~, ~(char-whitespace? c)~
- ~(char-upper-case? c)~, ~(char-lower-case? c)~, ~(char-title-case? c)~
- ~(digit-value c)~ : ~(Some n)~ for a decimal digit, ~None~ otherwise. Narrower than ~char-numeric?~ on purpose: ½ is numeric and has no digit value, so the two questions get two answers. An ~Option~ rather than -1, which would be a sentinel the type does not mention.
- ~(char-general-category c)~ : The Unicode general category as a ~Symbol~ — ~'Lu~, ~'Ll~, ~'Nd~, ~'Zs~ and the rest. A symbol because it is a fixed enumeration meant to be compared.

~char-numeric?~ is the Nd/Nl/No categories, not Nd alone, so it answers true for ½ and Ⅶ.

** String Cursors
A cursor represents a position within a string. It replaces traditional index-based access (like ~string-ref~) to ensure $O(1)$ linear traversals without the overhead of computing variable-length character offsets. A cursor is lightweight and costs as much as an ~int~.

*A cursor is opaque.* There are no conversion functions between cursors and indices. This opacity decouples the API from the underlying string encoding (e.g., UTF-16 vs. UTF-8). A cursor is created via ~string-cursor-start~ or ~string-cursor-end~ and moved via ~string-cursor-next~ or ~string-cursor-prev~, guaranteeing it always rests on a valid character boundary.

Every operation takes the string *and* the cursor, because the cursor carries no reference to it — the same bargain ~Iterable~ strikes by passing ~s~ and ~c~ to each method. Comparing cursors from two different strings is meaningless and unchecked, exactly as it is for two ints indexing different arrays.

*** Primitives
- ~(string-cursor-start s)~ : A cursor on the first character.
- ~(string-cursor-end s)~ : The past-the-end cursor. Not a character position; it is the bound a traversal stops at.
- ~(string-cursor-end? s c)~ : Whether ~c~ has reached the end.
- ~(string-cursor-ref s c)~ : The character at ~c~. Throws at the end — guard with ~string-cursor-end?~.
- ~(string-cursor-next s c)~ : The cursor on the next character. Steps over *all* the storage units that character occupies.
- ~(string-cursor-prev s c)~ : The cursor on the previous character. O(1) — it decodes backwards rather than rescanning from the start.
- ~(substring/cursors s start end)~ : The text between two cursors, ~end~ exclusive.

*** Comparison =(std prelude)=
- ~(string-cursor=? a b)~, ~(string-cursor<? a b)~, ~(string-cursor>? a b)~, ~(string-cursor<=? a b)~, ~(string-cursor>=? a b)~

Aliases for the operators, which work at ~StringCursor~ directly. The named forms exist because ~(string-cursor<? a b)~ says what it means where ~(< a b)~ on two opaque values does not.

*** Traversal =(std prelude)=
- ~(string-fold f init s)~ : Left fold; ~f~ receives ~(acc char)~.
- ~(string-fold-right f init s)~ : Right fold; ~f~ receives ~(char acc)~. Walks backwards with ~string-cursor-prev~, so it is a loop rather than n stack frames.
- ~(string-for-each f s)~ : Applies ~f~ to each character for side effects.
- ~(string-index pred s)~ : The first character satisfying ~pred~, as ~(Some cursor)~, or ~None~. A cursor rather than an index is what makes the result usable — it can go straight to ~substring/cursors~, where an integer could not be converted back at all.

*** Conversions =(std prelude)=
- ~(string->list s)~ : ~(List char)~.
- ~(list->string cs)~ : Builds a string from ~(List char)~.
- ~(list->str xs)~ : Formats a list as ~'(1 2 3)~, each element through its own ~->str~. Constrained ~(where (->str %a))~, and what the ~->str~ implementation for lists calls. =(std prelude)=
- ~(string->vec s)~ : ~(Vec char)~.
- ~(string-reverse s)~ : Reverses by *character*, so a string ending in an astral character comes back with that character intact rather than with its two halves swapped.

A string is also ~Iterable~, ~Foldable~ and a ~Collection~, so ~(loop (:for c s) ...)~, ~(fold f init s)~ and ~(length s)~ all work and all deal in characters. See the trait notes below.

** String Builders
The accumulator behind the ~Stringing~ collector, and the same shape as the vector and list builders.
- ~(stringbuilder-empty)~ : Creates an empty builder.
- ~(stringbuilder-add! b c)~ : Appends a character, encoding it however the storage requires.
- ~(stringbuilder-add-string! b s)~ : Appends a string.
- ~(stringbuilder-length b)~ : The length so far, in storage units.
- ~(stringbuilder->string b)~ : Freezes the builder into a string.

Use one — or a ~(:acc out (stringing c))~ clause — rather than ~string-append~ in a loop: appending rebuilds the whole string per element and is quadratic.

Use a builder to construct strings instead of writing to ~(open-output-string)~. Since writing to a port carries an async effect (colour), using a string port would incorrectly force the formatting function to become asynchronous. A builder has no effect, ensuring the operation remains pure and synchronous. See "A string is built with a builder, not with a port" in =Docs/Syntax.org=.

** Conversions
The numeric ones are =(std prelude)=; the keyword and symbol ones are builtin, since ~Keyword~, ~Symbol~ and ~char~ are not .NET types Bjolang can name.
- ~(byte->string b)~
- ~(int->string i)~ (also ~number->string~)
- ~(long->string l)~
- ~(double->string d)~
- ~(string->int s)~
- ~(string->double s)~

~double->string~ and ~string->double~ are *invariant*, for the reason the string comparisons are ordinal: a decimal point is a point everywhere, so the two round-trip and a number written by one machine reads on the next. .NET's own take the ambient culture, under which ~1.5~ writes as ~1,5~ and ~(string->double "1.5")~ throws. There is no way yet to ask for a number in the reader's own culture; see ~Todo.org~.
- ~(keyword->string kw)~ : Returns the string name of a keyword.
- ~(string->keyword s)~ : Interns a string as a ~Keyword~.
- ~(symbol->string sym)~ : Returns the string name of a symbol.
- ~(string->symbol s)~ : Interns a string as a ~Symbol~.

** Files =(std prelude)=
Whole-file operations, for when the contents fit in memory. They throw as the underlying .NET methods do; wrap a call in ~try~ to get a ~Result~ instead. Reach for the ports below when the file is too large to hold, or when the handle is wanted for more than its contents.
- ~(file-read-text path)~ : The whole file, as one string.
- ~(file-write-text path contents)~ : Writes ~contents~, truncating the file if it exists.
- ~(file-append-text path contents)~ : Appends ~contents~.
- ~(file-exists? path)~
- ~(file-delete path)~
- ~(file-read-lines/seq path)~ : The lines, pulled lazily. Builtin rather than =(std prelude)=, because interop cannot equate .NET's ~IEnumerable<string>~ with ~(Seq string)~.
- ~(file-read/seq reader path)~ : The same, pulled through any ~(-> TextInputPort %a)~. Opens the file once per enumeration and disposes it, so the sequence may be walked more than once — which is what ~(std ports)~' ~file->seq~ is built on, and what a ~seql~ over an already-open port cannot do. Prefer ~file->seq~, which reports a missing file as a ~Result~ rather than throwing on the first pull.

** Paths =(std prelude)=
Textual operations on path strings; none of them touches the file system.
- ~(path-absolute path)~
- ~(path-combine part ...)~ : Variadic.
- ~(path-filename path)~ : ~(Option string)~ — ~None~ for a path that ends in a separator, which names a directory.
- ~(path-file-extension path)~ : ~(Option string)~, including the dot. A name that is nothing but a dotted suffix — ~.bashrc~ — counts as one, as it does to .NET.
- ~(path-directory path)~ : ~(Option string)~. Builtin rather than =(std prelude)=: ~GetDirectoryName~ answers null for a root and for a bare filename, and absorbing that needs boundary code in the runtime.

The three that can come up empty answer an ~Option~. .NET reports "no filename here" and "no extension" as ~""~, and neither is a path — an empty string used as one names the working directory, which is a different place from nowhere.

** Directories =(std prelude)=
They throw as the whole-file operations do; wrap a call in ~try~ for a ~Result~.
- ~(directory-exists? path)~
- ~(directory-create path)~ : Creates every missing directory along the path, and does nothing if it is already there — so it needs no guard, which would be a race anyway.
- ~(directory-delete path)~ : An *empty* directory.
- ~(directory-delete-tree path)~ : Spelled differently because it is not a mistake anything can undo.
- ~(directory-files path)~ / ~(directory-subdirectories path)~ : Whole paths, directly in ~path~, as a ~(Vec string)~.

Listing is eager: ~EnumerateFiles~ would pull lazily and comes back as an ~IEnumerable<string>~, which interop cannot equate with ~(Seq string)~. There is no pattern argument either — ~(vec-filter #(string-ends-with? &1 ".bjo") (directory-files dir))~ asks the same question in the language.

** The environment =(std prelude)=
- ~(get-environment-variable name)~ : ~(Option string)~. R7RS's name, and ~None~ where R7RS answers ~#f~.
- ~(set-environment-variable! name value)~ : For this process and its children, not for the shell that started it. Setting a variable to the empty string removes it.
- ~(current-directory)~ / ~(set-current-directory! path)~ : A procedure rather than a value, because it is process-wide mutable state that relative paths follow.

A variable that is not set is ~None~ rather than the empty string .NET's ~null~ arrives as. What this cannot tell you is "unset" from "set to nothing": the test available at the boundary is ~String.IsNullOrEmpty~, there being no ~null~ in the language to compare against.

** Ports =(std prelude)=
Opening a file returns a ~Result~ because a missing file is expected; opening a string cannot fail and returns the port itself. A file port and a string port are the *same type*, so a procedure that reads or writes never learns where the text comes from or goes.

- ~(open-output-string)~ : A port that collects what is written to it. Use this for capturing output in memory (e.g., redirecting ~current-output-port~ in a test harness). To build a regular string, use a ~StringBuilder~ instead, because writing to ports carries an async effect (colour).
- ~(get-output-string port)~ : Everything written to a string port so far. The
  port stays open and keeps collecting, so asking twice with writes in between
  includes the earlier text. *Throws* if called on a non-string port.

Textual ports follow the R7RS shape. Ports directly wrap .NET streams (~TextInputPort~ is ~System.IO.TextReader~ and ~TextOutputPort~ is ~System.IO.TextWriter~). Consequently, file ports and string ports share the same type, allowing functions like ~with-open~ to dispose of either uniformly. Opening returns a ~Result~ to handle missing files, while operating throws exceptions for mid-stream device errors.

Only the *reader-parameterised* drains — ~port->list~, ~port->vec~, ~port->seq~ and ~file->seq~ — are in ~(std ports)~ and have to be imported. Opening, reading, writing and closing are here, since a program that reads a file should not need a header line to do it.

- ~(open-input-file path)~ : ~(Result Exception TextInputPort)~. The ~Err~ carries the real .NET exception, so an arm can say ~(:is System.IO.FileNotFoundException e)~.
- ~(open-input-string contents)~ : A string as an input port. Cannot fail, so no ~Result~.
- ~(open-output-file path)~ : ~(Result Exception TextOutputPort)~, truncating the file if it exists.
- ~(close-input-port p)~ / ~(close-output-port p)~ : Rarely needed — ~with-open~ disposes a port however the body ends. Two functions rather than one, because ~.Dispose~ needs a concrete receiver.
- ~(flush-port p)~
- ~(port-eof? p)~ : Whether the port has no more input. Asking consumes nothing.
- ~(read-line p)~ : The next line, without its newline. *Throws at end of input* — guard with ~port-eof?~.
- ~(read-line/opt p)~ : The next line, or ~None~ at end of input, for when the check and the read want to be one step.
- ~(read-char p)~ : The next character. *Throws at end of input* — guard with ~port-eof?~.
- ~(read-char/opt p)~ : The next character, or ~None~ at end of input.
- ~(read-all p)~ : Everything remaining, as one string. Empty at end of input.
- ~(port->lines p)~ : Every remaining line, as a ~(Vec string)~. The drain to reach for when the shape does not matter; it runs in the runtime, so each line is added once.
- ~(write-string p s)~ / ~(writeln p s)~ : The port comes first, as it does for every operation here.
- ~(write-char p c)~ : One character.

~read-char~ and ~write-char~ deal in *characters* — Unicode scalars — and not in
the UTF-16 code units a .NET port is made of. A character outside the BMP is two
units in the text and one ~char~ to a program, so ~read-char~ puts the pair back
together and ~write-char~ takes it apart. This is the promise walking a ~string~
already makes, and it is what lets ~(port->seq read-char p)~ and ~(read-all p)~
walked as a string agree about what the characters are.

There is no ~peek-char~. Because ports are bare .NET objects without pushback buffers, they cannot safely peek ahead by a full variable-length Unicode character. Use ~port-eof?~ to check for the end of a stream, and ~read-all~ with a ~StringCursor~ when significant lookahead is required.

An ordinary binding wins over an ~import/extern~ alias of the same name, so a module that aliases ~System.Console.WriteLine~ as ~println~ gets the prelude's ~println~ and not the alias. Pick a name the prelude does not bind — ~console-write-line~ say.

** Keywords and Symbols
Keywords (~:foo~ or ~#:foo~) and quoted symbols (~'foo~) are interned first-class types.
- ~(keyword? x)~ : Returns true if ~x~ is a ~Keyword~.
- ~(symbol? x)~ : Returns true if ~x~ is a ~Symbol~.
- Keywords and symbols are interned, so ~(= a b)~ on them *is* $O(1)$ reference equality — as is ~(eq? a b)~. Both are usable as map keys.

** Lists (~SchemeList~)
Built-in functional linked lists.
- ~(Cons head tail)~, ~(cons head tail)~ : Constructs a list.
- ~(Nil)~, ~(list-empty)~ : Returns an empty list.
- ~(list-head lst)~ : Returns the first element.
- ~(list-tail lst)~ : Returns the rest of the list.
- ~(list-empty? lst)~ : Returns true if the list is empty.
- ~(list-length lst)~ : Returns the number of elements. O(n) — a ~List~ stores no count. (There is no ~list-count~: it was the same walk under a second name.)
- ~(list-reverse lst)~ : Reverses the list.
- ~(list-map f lst)~ : Maps function ~f~ over the list.
- ~(list-filter f lst)~ : Filters elements satisfying ~f~.
- ~(list-foldl f init lst)~ : Left fold; ~f~ receives ~(acc item)~.
- ~(list-foldr f init lst)~ : Right fold; ~f~ receives ~(item acc)~.
- ~(list-for-each f lst)~ : Applies ~f~ to each element for side effects.
- ~(list-ref lst index)~ : Gets the element at ~index~.
- ~(list-append xs ys)~ : ~xs~ followed by ~ys~. Written in ~std/prelude~ rather
  than built in, because a builtin of that name is ambiguous to C# at every call
  site — ~,@~'s own append is monomorphic and separate for that reason.

- ~(vec-ref vec index)~ : Gets the element at ~index~.
- ~(vec-set vec index value)~ : Returns a new vector with ~value~ at ~index~.
- ~(vec-add vec item)~ : Returns a new vector with ~item~ appended.
- ~(vec-insert vec index item)~ : Returns a new vector with ~item~ inserted at ~index~.
- ~(vec-remove-at vec index)~ : Returns a new vector with the element at ~index~ removed.
- ~(vec-pop vec)~ : Returns a new vector with the last element removed.
- ~(vec-pop-first vec)~ : Returns a new vector with the first element removed.
- ~(vec-slice vec start count)~ : Returns a sub-vector.
- ~(vec-merge vec other)~ : Concatenates two vectors.
- ~(vec-merge/pure vec other)~ : Concatenates two vectors (pure).
- ~(vec-split vec index)~ : Splits the vector into two vectors at ~index~.
- ~(vec-map f vec)~ : Maps ~f~ over the vector.
- ~(vec-filter f vec)~ : Filters the vector.
- ~(vec-fold f init vec)~ : Left fold; ~f~ receives ~(acc item)~.
- ~(vec-reduce f vec)~ : Reduces the vector.
- ~(vec-for-each f vec)~ : Applies ~f~ for side effects.
- ~(vec-for-each/range f vec start count)~ : Applies ~f~ over a range.

- ~(vec-length vec)~ : Returns the size of the vector. O(1) — a ~Vec~ stores its count.

- ~(vec-contains vec item)~ : Checks if ~item~ is in the vector.

Mutable builders (~SchemeListBuilder~) for efficiently constructing Scheme lists front-to-back in O(1) time per item.
- ~(listbuilder-empty)~ : Creates an empty builder.

** Addable and Addable! — adding to collections
The persistent trait first — ~add~ answers a new collection and touches nothing:

#+BEGIN_SRC scheme
(def/trait (Addable %coll)
  (type %elem)
  (: add (-> %coll %elem %coll))
  (: add-all (-> %coll %s %coll)
     (where (Iterable %s #:elem %elem #:cursor %k))))
#+END_SRC

- ~(add coll elem)~ : One element; a new collection back. ~Vec~ appends at the end; ~Set~ and ~OrderedSet~ are idempotent; ~Map~ and ~OrderedMap~ take a pair, ~(add m (k . v))~, with *set* semantics — a key already there is replaced. That is what the mutable sinks below do on a duplicate, and ~add~ and ~add!~ disagreeing about one would be a trap; ~map-add~, which refuses a duplicate, keeps its own name.
- ~(add-all coll iterable)~ : Everything the source yields, folded in. ~(add-all (set-empty) some-vec)~ is how a collection changes shape.

~List~ has no implementation, deliberately: a cheap add would prepend (reversing what ~add-all~ pours in), an in-order one costs O(n) per element, and a name as plain as ~add~ should not quietly mean either. Build with a ~ListBuilder~ instead.

*** Addable! — the mutable sinks
One trait over every builder and transient, so that filling a collection does not care which one it is filling:

#+BEGIN_SRC scheme
(def/trait (Addable! %coll)
  (type %elem)
  (: add! (-> %coll %elem void))
  (: add-all! (-> %coll %s void)
     (where (Iterable %s #:elem %elem #:cursor %k))))
#+END_SRC

- ~(add! sink elem)~ : One element. For a map-shaped sink the element is a pair, ~(add! mb (k . v))~.
- ~(add-all! sink iterable)~ : Everything an ~Iterable~ holds, in the order it yields. Generic on both sides — the source may be a ~List~, a ~Vec~, a ~Range~, a string, a ~Map~ — and the member-level ~(where ...)~ is what ties the source's element to the sink's (see *Member-level where clauses* in ~Syntax.org~). A mismatch is refused at the call.

Implementations ship for ~VecBuilder~, ~ListBuilder~, ~StringBuilder~, ~MapBuilder~ and ~TransientMap~ in the prelude, and for the set and ordered-collection builders and transients in ~(std set)~, ~(std orderedset)~ and ~(std orderedmap)~ — each beside the type it fills.

** Maps (~Map~)
High-performance immutable CHAMP (Compressed Hash-Array Mapped Prefix-tree) maps.

Not builtins. ~(Map %k %v)~ is an ~import/class~ alias for ~Map.Map~ and the
operations are ~import/extern~ bindings on ~Map.MapModule~, both living in
=(std prelude)= — which every program imports implicitly, so a map is written
exactly as it always was. They are in the prelude rather than a =(std map)= of
their own because ~#map(...)~ reads as a call to ~list->map~, which has to be in
scope wherever the literal is written, and because the prelude implements
~Iterable~, ~Collection~ and ~Collector~ for ~Map~ — a
separate module would have to import the prelude for those while the prelude
imported it back.

- ~(map-empty)~ : Returns an empty map.
- ~(map-ref map key)~ : Returns the value for ~key~; throws if not found.
- ~(map-ref-or map key default-val)~ : Returns the value for ~key~, or ~default-val~ if not found.
- ~(map-try-ref map key)~ : Returns ~(Some val)~ if found, or ~None~ if not.
- ~(map-set map key value)~ : Returns a new map with ~key~ mapped to ~value~.
- ~(map-add map key value)~ : Returns a new map with ~key~ mapped to ~value~.
- ~(map-remove map key)~ : Returns a new map with ~key~ removed.
- ~(map-contains? map key)~ : Returns true if ~key~ is in ~map~.
- ~(map-has-key? map key)~ : Returns true if ~key~ is in ~map~.
- ~(map-length map)~ : Returns the number of key-value pairs in ~map~.
- ~(map-empty? map)~ : Returns true if ~map~ is empty.
- ~(map-clear map)~ : Returns an empty map.
- ~(map-keys map)~ : Returns a lazy sequence (~Seq~) of the map's keys.
- ~(map-values map)~ : Returns a lazy sequence (~Seq~) of the map's values.
- ~(map-merge map other)~ : Merges two maps, with entries in ~other~ taking precedence.
- ~(map-set-all map seq)~ : Sets every entry of ~seq~, through a transient, and returns the new map.
- ~(map-remove-all map seq)~ : Removes every key of ~seq~ and returns the new map.

*** Where an entry is two arguments and where it is one

Every callback below takes the key and the value as **two** arguments, which is
what a walk of the trie produces anyway:

#+BEGIN_SRC scheme
(map-fold (fun (acc k v) (+ acc v)) 0 m)
#+END_SRC

The entry survives as a ~(Tuple %k %v)~ only where a trait signature fixes the
shape. ~Iterable~'s ~%elem~ and ~Foldable~'s ~%item~ are a single element, so a
callback reached through ~fold~ or a ~loop~ sees a pair rather than two
arguments, and the prelude's implementations are what put the pair together:

#+BEGIN_SRC scheme
(fold (fun (acc kv) (def (_ . v) kv) (+ acc v)) 0 m)
#+END_SRC

The pair is also what ~map->list~, ~map->seq~, ~map-cursor-current~, ~map-find~
and the ~#map(...)~ literal deal in — in every one of those an entry is a
*value* crossing the boundary rather than an argument list. A value tuple, so it
costs no allocation.

- ~(map-merge-with f map other)~ : Merges two maps using resolver ~f~ for duplicate keys; ~f~ receives ~(key val1 val2)~ as three arguments.
- ~(map-for-each f map)~ : Applies ~(f key value)~ to each entry for side effects.
- ~(map-iter f map)~ : Iterates with early exit; ~f~ receives ~(key value)~ and returns a boolean.
- ~(map-any? f map)~ : True if ~(f key value)~ holds of any entry.
- ~(map-find f map)~ : ~(Some entry)~ for the first entry where ~(f key value)~ holds, or ~None~. The entry is a pair: it is a value being handed back.
- ~(map-fold f init map)~ : Folds over the map; ~f~ receives ~(acc key value)~.
- ~(map-filter f map)~ : Returns a new map containing only entries where ~(f key value)~ is true.
- ~(map-map f map)~ : Returns a new map whose values are ~(f key value)~. The key is what the result is filed under, so the mapper cannot move it.
- ~(map-map-values f map)~ : Returns a new map with each value replaced by ~(f value)~, keys untouched.
- ~(map->str map)~ : ~#map(key value ...)~, so the literal round-trips. Also the ~->str~ implementation, so ~(println m)~ prints it.
- ~(list->map lst)~ : Constructs a map from a list of ~(key . val)~ pairs/tuples.
- ~(map->list map)~ : Converts the map to a list of pairs/tuples.
- ~(vec->map vec)~ : Constructs a map from a vector of pairs/tuples.
- ~(map->vec map)~ : Converts the map to a vector of pairs/tuples.
- ~(seq->map seq)~ : Constructs a map from a sequence of pairs/tuples.
- ~(map->seq map)~ : Converts the map to a sequence of pairs/tuples.

*** Builders and transients

Two more ways to build a map, in the shape ~(std set)~ and =(std orderedmap)=
use. The builder is the fast way to make a map out of nothing. You put things in it
and call mapbuilder->map. It does not support getting or setting elements. If you add
the same key two times, the last one is used.

The transient is the map's own interface with the writes turned inside out, and
the fast way to make a map out of *another* map: it owns the nodes it has
touched, so ~transientmap->map~ is O(1). The mutators answer nothing.

- ~(mapbuilder-empty)~ / ~(map->mapbuilder map)~ : Creates a builder.
- ~(mapbuilder-add! b key value)~ / ~(mapbuilder-add-all! b seq)~ : Appends.
- ~(mapbuilder-length b)~ : How many entries have been *appended*. Duplicates are resolved when the map is built, last one winning, so this is not the size of the map to come.
- ~(mapbuilder->map b)~ : Builds the map.
- ~(transientmap-empty)~ / ~(map->transientmap map)~ / ~(transientmap->map t)~
- ~(transientmap-set! t key value)~, ~(transientmap-set-all! t seq)~, ~(transientmap-remove! t key)~, ~(transientmap-remove-all! t seq)~, ~(transientmap-filter! f t)~
- ~(transientmap-ref t key)~, ~(transientmap-ref-or t key default)~, ~(transientmap-try-ref t key)~, ~(transientmap-contains? t key)~, ~(transientmap-length t)~, ~(transientmap-empty? t)~

** Sets and sorted collections =(std set)= =(std orderedset)= =(std orderedmap)=

Three libraries rather than builtins, and imported by name:

#+BEGIN_SRC scheme
(import (std set))          ;; (Set %a)        — a CHAMP trie, unordered
(import (std orderedset))   ;; (OrderedSet %a) — a B-tree, sorted
(import (std orderedmap))   ;; (OrderedMap %k %v)
#+END_SRC

Each collection provides three identical interfaces for different usage patterns:

- the collection itself, where every write answers a new one;
- a **builder**, shaped exactly like ~ListBuilder~ — ~empty~, ~add!~,
  ~add-all!~, ~length~, and the conversion each way — and the fast way to make
  one out of nothing, since appends are sorted or scattered into place in a
  single pass at the end;
- a **transient**, which mutates in place.

~(Set %a)~ is ~(Map %k %v)~ with the values left out. Constant time access. Unordered.

~(OrderedSet %a)~ and ~(OrderedMap %k %v)~ are persistent B-trees keyed in the
elements' natural order, by ~Comparer<T>.Default~. 

~(OrderedMap %k %v)~'s api is the prelude's ~map-*~ under an
~orderedmap-~ prefix.

All three implement ~Iterable~, ~Collection~ and ~->str~,
and each publishes a collector — ~setting~, ~ordered-setting~,
~ordered-mapping~ — so a loop can accumulate into one:

#+BEGIN_SRC scheme
(loop (:for x (range 0 10))
      (:when (= 0 (% x 2)))
      (:acc evens (setting x)))
#+END_SRC

** Control =(std prelude)=

Macros, not procedures — which is what lets them take a branch that is not
evaluated. They are written with ~syntax-match~ in ~lib/std/prelude.bjo~; see
~Docs/MACROS.org~ for what that means, and for why they cannot be passed to
anything or stored in a variable.

- ~(cond (test body ...) ... (else body ...))~ : ~if~ at any number of arms. The
  final ~else~ is required. Every arm needs the same return type.
- ~(if-let ((name expr)) then else)~ : ~then~ with ~name~ bound to what ~expr~
  answered, if it answered ~(Some ...)~, and ~else~ if it was ~None~. The
  binding is shaped like a ~let~'s, which should be changed.
- ~(when-let ((name expr)) body ...)~ : the body with ~name~ bound, when there
  was something to bind. 
- ~(some-> value step ...)~ : ~->~ that stops at the first ~None~. Each step
  answers an ~(Option ...)~ and it unwraps every step befor going on.
- ~(try-> value step ...)~ : the same over ~Result~, stopping at the first
  ~Err~. Each step answers a ~(Result ...)~ and receives what the step before
  unwrapped to, so a chain reads in the order it runs rather than inside out.
- ~(let* ((name expr) ...) body ...)~ : sequential binding. 
- ~(parameterize* ((param expr) ...) body ...)~ : the let* version of ~parameterize~
- ~(with-cancel (cancel) body ...)~ : a cancellation scope that owns the fibers
  started inside it and waits for them. See below.
- ~(with-deadline ms body ...)~ : the same scope, with a timer that cancels it.
- ~(with-shield #:within ms body ...)~ : a scope whose token is /not/ linked to
  its parent's, so a ~sync~ in it works after a cancellation. For cleanup.

#+BEGIN_SRC scheme
(cond ((< n 0) "negative")
      ((= n 0) "zero")
      (else "positive"))

(if-let ((half (halve n))) half 0)

(when-let ((line (read-line/opt port)))
  (println line))

(some-> 16 (halve) (halve) (at-least & 3))   ;; (Some 4)

(try-> path (open-input-file &) (read-header &))
#+END_SRC

** Waiting from an ordinary function =(std prelude)=

~sync~ is a yield point, so only a ~defbjo~ may write it. A program whose ~main~
is a plain ~defun~ therefore cannot take a value off a channel, join a promise,
or wait for a timeout — all three are events, and getting a value out of an
event means syncing it.

~(sync/blocking ev)~ is the way out. It takes any event and parks the *calling
thread* rather than suspending a fiber, so ordinary code can reach the whole
concurrent vocabulary:

#+BEGIN_SRC scheme
(sync/blocking (chan-recv ch))
(sync/blocking (promise-join (bjo (work 21))))
(sync/blocking (choose (wrap (chan-recv ch) (fun (v) (Got v)))
                       (wrap (timeout 1000) (fun (u) TimedOut))))
#+END_SRC

No fiber is spawned: the event is published with a continuation that hands the
value over and wakes the parked thread, which is why this is a primitive rather
than something spelled ~(sync)~ inside a ~bjo~ — the spawning version costs a
fiber per value, and on a channel in a loop that is a fiber per element.

It is the mirror of ~blocking~, which carries a thread-parking call *into*
fiber-land; this carries an event *out*.

*Do not call it from inside a bjoroutine.* It parks the thread it is called on,
and inside a fiber that thread belongs to the pool — which is what the events
being waited for need in order to fire. There the answer is ~sync~.

*Nothing withdraws it once parked.* A wait that might not end needs its own way
out composed in first, as in the ~choose~ above. Building an event is pure, so
that composition costs nothing and happens before the thread ever parks.

** Getting work off the fiber pool =(std prelude)=

Two functions, same shape, and the thread pool is what cannot tell them apart.
To the pool, a worker parked on a syscall and a worker halfway through resizing
an image look identical — both are "not coming back soon" — but the programs are
different, and only one of them is helped by moving the work to another pool
thread.

- ~(blocking thunk)~ : for work that *parks a thread*. ~File.ReadAllText~,
  ~Console.ReadLine~, ~Monitor.Enter~. It goes to ~Task.Run~, so the thread that
  parks is one the pool can grow to replace, and the fiber suspends on the
  *result* rather than on the work.
- ~(spawn/thread thunk)~ : for work that *uses a core*. An image resize, a
  compression pass, a search over a big structure. It gets a thread of its own,
  because for compute ~Task.Run~ buys nothing at all — the same pool, the same
  core, a different worker holding it.

#+BEGIN_SRC scheme
(sync (blocking     #(file-read-text path)))     ;; (Result Exception string)
(sync (spawn/thread #(resize image 2048)))       ;; (Result Exception Image)
#+END_SRC

*~spawn/thread~ is a function, not one of the ~spawn~ special forms*, despite
the name. It takes a thunk, so it is ~(sync (spawn/thread #(crunch data)))~ and
never ~(spawn/thread (crunch data))~ — the second is an ordinary application and
a type error. The four spawn forms decide *who owns* a fiber; this decides
*where work runs*, which is a different axis and composes with all four:

#+BEGIN_SRC scheme
;; not cancelled, not waited for, and off the pool
(spawn/detached (crunching data))

(defbjo (crunching data)
  (ignore (sync (spawn/thread #(crunch data)))))
#+END_SRC

A dedicated thread is not free: about a megabyte of stack, created and destroyed
per call. It is worth it for work measured in tens of milliseconds and a loss for
work measured in microseconds. A handful of compute-bound fibers on the pool is
fine and is what a pool is for; this is for when there are more of them than
cores and fibers that care about latency are queued behind them.

*Neither is cancellable*, and neither can be: a thunk is arbitrary code with no
yield point to interrupt. What *is* cancellable is the wait — ~sync~ consults
the ambient token as usual, so a cancelled scope stops waiting while the work
carries on to the end. The scope will not wait for it either; a scope waits for
fibers, and neither of these is one.

Both are guarded, so each ~sync~ starts a fresh run rather than replaying the
first one's answer. Failure is a value in both, as everywhere else that resolves
at sync time.

** Cancellation scopes =(std prelude)=

A scope owns the fibers started inside it. ~spawn~ and ~bjo~ put a fiber in the
current scope, and the scope does not return until every one of them has
finished. So this

#+BEGIN_SRC scheme
(with-cancel (cancel)
  (spawn (process a))
  (spawn (process b)))
#+END_SRC

runs both and waits for both, and when the form returns the work is over.
Stopping early is what the cancel thunk is for:

#+BEGIN_SRC scheme
(with-cancel (cancel)
  (def answer (sync (chan-recv results)))
  (cancel (Requested "got it"))
  answer)
#+END_SRC

*** The forms

- ~(with-cancel (cancel) body ...)~ : makes a token linked to the ambient one,
  installs it as ~current-cancel~ for the body, waits for the children, and
  fires the token on the way out — ~Scope-Ended~ normally, ~(Failed e)~ when the
  body is leaving with an exception. The binding is restored either way, and
  ~cancel~ is bound to the thunk.
- ~(with-deadline ms body ...)~ : the same, with a timer that fires ~Deadline~
  after ~ms~. The timer belongs to the scope rather than to a fiber racing it: a
  watcher fiber would be waiting for a token the scope does not fire until its
  children are done, and its children would include the watcher.
- ~(with-shield #:within ms body ...)~ : a scope whose token is *not* linked to
  its parent's. ~#:within~ is optional and defaults to thirty seconds.

*** The order on the way out

Wait, then cancel. The token fires *first* only when the body is leaving
abnormally — an exception is on its way out, or the body called ~cancel~ itself.
That is what keeps both shapes above writable.

The cost is accepted and worth knowing: a scope whose children never end, and
which never calls ~cancel~, /hangs/ rather than returning. A hang says where it
is. A scope that returned while its children ran on says nothing at all. A child
that is meant to run until the scope ends is a ~spawn/daemon~.

*** A child that fails

The scope fires its token, waits for every remaining child, and only then
propagates — in that order. Reporting the failure straight away would let the
caller carry on while sockets were still tearing down. Several failures at once
are reported together as one ~System.AggregateException~.

A child that stopped because it was *cancelled* has not failed. Being cancelled
is how a worker normally ends, and the record that it happened is the scope's
token.

~bjo~ is the exception, and deliberately: it hands back the promise, so its
failure is the caller's to read and the scope does not raise it a second time.
~spawn~ hands nothing back, so nobody else could be watching and the scope is
what reports it.

*** Shielding cleanup

Every ~sync~ consults the ambient token, so once a scope has been cancelled
every ~sync~ in it raises ~Cancelled~ — including the ones in the code trying to
tidy up. Inside a shield the ambient token is a fresh one that has not fired, so
a ~sync~ works again:

#+BEGIN_SRC scheme
(with-shield #:within (seconds 5)
  (spawn (flush-buffer a))
  (spawn (flush-buffer b)))
#+END_SRC

It is the same object as any other scope with one flag different, which is why
~(current-cancel)~ inside a shield also reads as "not cancelled": a hand-written
~until-cancelled~ agrees with what ~sync~ is doing instead of contradicting it.

~until-cancelled~ itself is for a token that is *not* the ambient one, and that
is a rule rather than a preference. ~sync~ already watches the ambient token, so
handing it to ~until-cancelled~ as well puts two waiters on one promise; they are
woken as two independent pool work items, and whichever commits first decides
whether the sync answers ~None~ or raises. It is deterministic when the token has
already fired, which is what makes the mistake easy to miss.
The deadline is not optional, because a shield is unreachable from outside by
construction and one without a deadline would make the program impossible to
kill.

Naming ~Cancelled~ in a ~#:catch~ is a compile error, and the message points
here. A broad handler that swallows a cancellation and carries on is the classic
bug in every language that made cancellation an exception.

*** Odds and ends

All three are macros over ~scope-open!~, ~scope-push!~, ~scope-canceller~,
~scope-close!~, ~try~ and ~raise~ — nothing the parser knows about, so the
import modifiers reach them like any other binding.

All three *suspend*, because waiting is the whole of what they do. They can only
be written inside a bjoroutine.

~main~ is *not* inside a scope. When it returns the process exits and any fiber
still running is discarded, so a ~(spawn ...)~ at the top level of ~main~ is a
child of nothing and nobody waits for it. Work that has to be waited for goes
inside one of these three forms.

It used to run in a root scope. The cost was that the root scope's token was
live in every program, so every ~sync~ raced a cancellation that could never
fire, and the fast path for "nothing can cancel me" was unreachable.

A bare ~(parameterize ((current-cancel t)) ...)~ stays legal, and is the
deliberate airlock for a token that must outlive its creator — a daemon whose
token lives in a registry. It binds the token without changing which scope a
~spawn~ enlists in.

** Starting a fiber =(special forms)=

Four forms, differing only in what the enclosing scope does about the fiber.

- ~(spawn (f x))~ : a child of the current scope. The scope waits for it and
  reports its failure. Answers ~Unit~, so it needs no ~ignore~. This is the
  common one.
- ~(bjo (f x))~ : the same child, answering its ~(Promise %a)~. The scope waits
  for it but the *failure is yours*, because you are holding the promise. There
  is no ~MustUse~ exemption for it: join it, race it, or say ~ignore~.
- ~(spawn/daemon (f x))~ : cancelled by the scope, but not waited for. A
  heartbeat, a logger, a metrics pump — work that should not hold the scope open
  and should not outlive it either. Its failure is reported, not propagated,
  because by then there is nobody to propagate it to.
- ~(spawn/detached (f x))~ : genuinely outside. Neither the scope nor the token
  is inherited, so nothing waits for it and nothing cancels it. Rare, and the
  name is meant to look uncomfortable.

In all four the operands are evaluated where the form is written and only the
call happens in the new fiber, so ~(spawn (handle (next-job!)))~ runs
~next-job!~ here.

Spawning into a scope that has already started closing does nothing at all: no
fiber, no error, and the spawning code carries on. The scope is unwinding, so
one more error on the way out would be noise rather than information. ~bjo~ has
to answer *something*, and answers a promise that has already failed with
~Cancelled~.

** Options (~Option~)
Optional value type representing presence (~Some~) or absence (~None~).
- ~(Some val)~ : Wraps ~val~ in an option.
- ~None~ : Represents no value.
- ~(some? opt)~ : Returns true if ~opt~ is ~Some~.
- ~(none? opt)~ : Returns true if ~opt~ is ~None~.
- ~(option-ref opt)~ : Returns the unwrapped value; throws if ~None~.
- ~(option-ref-or opt default-val)~ : Returns the unwrapped value, or ~default-val~ if ~None~.

** Results (~Result~)
An answer or the error that stopped it: ~(Ok val)~ or ~(Err e)~. A ~Result~ is
must-use like every other value — it has to be handled, or handed to ~ignore~.
- ~(ok? r)~ : Returns true if ~r~ is ~Ok~.
- ~(err? r)~ : Returns true if ~r~ is ~Err~.
- ~(result-map f r)~ : ~(Ok (f v))~ for an ~Ok~, and the ~Err~ untouched
  otherwise. ~f~ answers a plain value; a step that answers a ~Result~ of its
  own belongs in a ~try->~ chain instead.

~f~ is declared ~-?->~, so it may be either colour — but a lambda's colour is
the keyword it was written with. A step that waits has to be a ~(bjoroutine
(x) ...)~; written ~(fun (x) ...)~ the same call selects the blocking copy and
parks the fiber's thread, which the colour lint reports.

** Sequences (~Seq~)
Lazy, demand-driven sequences.
- ~(seq-empty)~ : Returns an empty sequence.
- ~(seq-empty? s)~ : Returns true if the sequence is empty.
- ~(seq-head s)~ : Returns the first element of the sequence.
- ~(seq-map f s)~ : Lazily maps ~f~ over the sequence.
- ~(seq-filter f s)~ : Lazily filters elements satisfying ~f~.
- ~(seq-fold f init s)~ : Folds over the sequence; ~f~ receives ~(acc item)~.
- ~(seq-unfold generator state)~ : Produces a sequence from ~state~ and a ~generator~ function returning ~(Some (Tuple next-item next-state))~ or ~None~.
- ~(seq-take s n)~ : Takes the first ~n~ elements lazily.
- ~(seq-drop s n)~ : Drops the first ~n~ elements lazily. Dropping more than the sequence holds gives the empty sequence. This is what a ~seq-tail~ would have been: a ~Seq~ has no tail to step to, so walking one element at a time is ~loop~'s job, not a combinator's.
- ~(seq-append s1 s2)~ : Lazily concatenates two sequences.
- ~(seq-for-each f s)~ : Applies ~f~ to each element for side effects.
- ~(seq-length s)~ : Consumes the sequence and returns the count.
- ~(seq-range start count)~ : Returns a lazy integer range sequence.
- ~(list->seq lst)~ : Converts a list to a lazy sequence.
- ~(seq->list s)~ : Consumes a sequence into a list.
- ~(vec->seq vec)~ : Converts a vector to a lazy sequence.
- ~(seq->vec s)~ : Consumes a sequence into a vector.

** Monads =(std monad)=
The ~Monad~ trait, its instances, and the ~(do ...)~ block, none of which is in
the prelude: a file that wants one writes ~(import (std monad))~.

- ~(pure x)~ : ~x~ in the monad. It mentions its constructor only in its
  *result*, so nothing about the call says which instance is meant — the
  expected type does, and where there is none the compiler asks for an
  annotation.
- ~(bind m k)~ : ~m~'s value handed to ~k~, which answers the next ~m~.
- ~(do clause ...)~ : the block, which is ~bind~ and ~pure~ written in
  sequence. See ~Docs/Syntax.org~ for the clauses.

Implemented for ~(List %a)~ — where ~bind~ is a concat-map, so a block over one
multiplies out — ~(Option %a)~ and ~(Result %e %a)~, both of which
short-circuit. The last is what makes a block of fallible steps read as the
happy path: ~%e~ is fixed by the implementation, so the error type is written
once in the signature and never in the block.

~Monad~ is *inline-only*: ~%m~ is a type constructor, which no C# interface can
abstract over, so every call is resolved statically and spliced. Two
consequences follow. A method may not be used at a type that is still a
variable — no function generic in its monad — and whether a block is a loop
depends on the instance: ~bind~ mentioning its continuation once means the
lambda is substituted away, and mentioning it twice means it survives.

Promises and Events do not implement ~Monad~ because concurrency uses direct-style yielding. A call to a ~defbjo~ is the yield point, and suspending inside ~bind~'s continuation would result in a lambda that cannot suspend. Use ~bjo~, ~sync~, and ~with-cancel~ for asynchronous sequencing.

** Walking a collection
The protocol ~(loop ...)~ is built on, and the one ~Iterable~ declares. It is
written out here because a program may use it directly, but it is not what a
program normally reaches for: ~loop~, ~fold~ and the comprehensions are.

The sequence is passed to every method, so a cursor need carry nothing — a
~Vec~'s is a bare ~int~ rather than a pair, and costs no allocation per step.
- ~(iterable-start s)~ : A cursor at the beginning.
- ~(iterable-done? s c)~ : Whether the walk is over.
- ~(iterable-current s c)~ : The element at the cursor.
- ~(iterable-next s c)~ : The cursor after this one.

These methods use long names to prevent collisions with common user variables (like ~next~, ~start~, and ~current~). They are intended to be called by the compiler rather than directly in user code.

** Traits
- ~->str~ : Trait for string representation with method ~(->str x)~. Implemented for ~string~, ~int~, ~double~, ~byte~, ~long~, ~char~, ~Keyword~ and ~Symbol~. A ~char~ prints as itself, not as ~#\a~: ~->str~ is what ~display~ and ~print~ are built on, and those write text rather than a reread-able datum.

  A list prints as ~'(1 2 3)~, through a *conditional* implementation:
  ~(impl (->str (List %a)) (where (->str %a)) ...)~. The where clause is
  what makes each element print through its own implementation rather than
  through the blanket, and it is why ~->str~ over a list of a type you have
  implemented ~->str~ for prints your version.

  Anything with no implementation of its own falls to the blanket, which is
  ~Object.ToString~.
- ~Iterable~ : ~(iterable-start s)~, ~(iterable-done? s c)~,
  ~(iterable-current s c)~ and ~(iterable-next s c)~ —
  how to walk a collection, and what a ~(:for ...)~ clause uses. Implemented for
  ~(List %a)~, ~(Vec %a)~, ~(Map %k %v)~, ~(Seq %a)~, ~Range~ and ~string~. A
  string's ~%cursor~ is a ~StringCursor~ and its ~%elem~ is ~char~, so
  ~(loop (:for c "a😀b") ...)~ runs three times and hands over whole characters.
- ~Foldable~ : ~(fold f init col)~, where ~f~ receives ~(acc item)~. Implemented
  for ~(List %a)~, ~(Vec %a)~, ~(Map %k %v)~ and ~string~. A map's ~%item~ is its
  ~(Tuple %k %v)~ pair; a string's is ~char~, so ~fold~ over one is
  ~string-fold~.
- ~Collection~ : ~(length c)~, ~(empty? c)~ and ~(->seq c)~ — what a collection
  can be *asked*, as opposed to walked (~Iterable~) or consumed (~Foldable~).
  The associated ~%content~ is the element type, and for a ~(Map %k %v)~ that is
  the pair. Implemented for ~(List %a)~, ~(Vec %a)~, ~(Map %k %v)~, ~Range~,
  ~(Seq %a)~ and ~string~; not for ~(Array %a)~, which has no ~->seq~ to give.
  Note that ~length~ is O(1) only where the collection stores a count
  (~Vec~, ~Map~, and ~Range~, which computes it): a ~List~ walks, a ~Seq~
  walks *and* consumes an effectful source, and a ~string~ walks because its
  ~%content~ is ~char~ and so ~length~ must be ~string-count~ rather than
  ~string-length~.
- ~Monad~ : ~(pure x)~ and ~(bind m k)~ — in ~(std monad)~ rather than here.
  See the section above.
- ~Collector~ : ~(collector-init c)~, ~(collector-step c acc x)~ and
  ~(collector-finish c acc)~ — the
  accumulators an ~:acc~ clause names. The stock ones are ~listing~, ~vecing~,
  ~mapping~, ~stringing~, ~summing~, ~counting~ and ~folding~; ~stringing~
  collects ~char~ into a ~string~ through a ~StringBuilder~.

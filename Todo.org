Known gaps, written down where they were found rather than in a commit message.

* Source mapping (~#line~)

Statement-level directives are emitted from ~generateBlock~, and both build
configurations now carry a portable pdb, so stack traces name ~.bjo~ files and
lines. What is not done:

** Hoisted temporaries are attributed to the statement that produced them
~emitStatement~ builds into a scratch buffer and then prepends a ~prelude~ of
hoisted statements. The hoists are compiler glue with no honest source line, but
they inherit the directive of whatever preceded them. They want ~#line hidden~
around the prelude. Three sibling sites buffer the same way (~hoistToTemp~, and
the two buffered-scratch paths in ~generateLocalFunction~).

Harmless today — the line they inherit is the statement they belong to, which is
close enough to be useful — but it is luck rather than design.

** Directives are emitted unconditionally
No suppression when the line has not changed since the last one, so the
generated C# carries more directives than it needs. Correct, just larger. A
dedup needs care: scratch buffers are relocated after the fact, so a
module-level "last line emitted" would be wrong the moment a buffer moves.

** Column spans are not used
C# 10+ takes ~#line (l1,c1)-(l2,c2) "file"~, and ~Lexer.Range~ already carries
~End~ as well as ~Start~. Using it would give column-accurate squiggles for
nothing beyond the formatting change.

** Inlined trait methods report the impl, not the call site
~TraitInline~ splices an impl body into a caller, and the spliced nodes keep the
impl's ranges. A failure inside an inlined ~fold~ names the ~def/impl~. That is
defensible — it is where the code is written — but a caller reading the trace
has no way to see which call site reached it.

** The pdb no longer distinguishes a ~-d~ build
Optimized builds used to delete their pdb, and its absence was how a caller
could tell which way a binary was built. Both configurations now keep one.
Nothing depended on the signal, but it is gone.

* Diagnostics

** Errors raised outside ~infer~ depend on their own call site for a location
~infer~ attaches ~file.bjo:N~ to any diagnostic that arrives without one, which
covers type errors. Reports from generalization, trait registration and parts of
declaration checking are outside that wrapper and carry a location only if the
site supplied one. Threading a ~Range~ into ~unify~ would close this, at the
cost of inventing a location at the several call sites that have no natural one.

** ~unify~ reports the two types, not the path to the mismatch
Two large types differing deep inside are printed whole, and the reader finds
the difference. Reporting the innermost disagreeing pair, or marking it, would
be better.

* Characters and strings

** ~char-foldcase~ is simple lowercasing
.NET exposes no simple case-folding table, so ~ToLowerInvariant~ stands in. It
agrees with Unicode's simple fold except for characters like ß and ﬁ, where a
full fold expands — which no char-to-char function can express in any case.

** ~Collection~ is still not implemented for ~(Array %a)~
It has no ~->seq~ to give.

* Emacs mode (~bjomode.el~)

Indentation follows Scheme's rules: bodies two, ~if~ four, everything else
aligned under the first argument. Reindenting ~lib/std/prelude.bjo~ and
~TestFiles/008_iterators.bjo~ from scratch reproduces them exactly.

** A named loop aligns under the name, not the first clause
~(loop lp (:for x xs) ...)~ puts the clauses under ~lp~, where the sources put
them under ~(:for~. Standard Lisp alignment gives the former, and the latter
needs a custom indenter that returns the column of the *second* argument —
~lisp-indent-specform~ cannot express it. Named ~let~ is special-cased already
(~bjo-let-indent~) because its body is a body; a named loop's clauses align, so
it needs different machinery for one rarely-used form.

** A ~match~ arm's body aligns under the pattern
~((Ok probe) body)~ is a list with a list at its head, so the body lines up
under ~(Ok probe)~. Emacs does the same for a ~cond~ clause. Some sources
indent it two from the arm's own paren instead.

** Library functions that read as body forms are not known
~with-nack~ takes a function and looks like a body form, but it is an ordinary
call, so its argument aligns under the head. Only forms the parser gives a
meaning to are in ~bjo-indent-forms~; adding library names there would mean
tracking the library from the mode.

** No completion, no imenu, no eldoc
Font lock and indentation only.

* Operators

An unapplied operator is eta-expanded into the lambda it stands for, so its type
comes from the use site. Two things that leaves.

** A local binding that shadows an operator is ignored
~(let ((+ my-add)) (+ 1 2))~ compiles, and prints 3 rather than calling
~my-add~: the operator arms in ~generateApply~ match on the name alone and emit
infix whatever the name is bound to. ~conBaseName~ consults a ~shadowedBuiltins~
set for type constructors; nothing does for operators, and ~Inference~ resolved
the binding correctly before ~Codegen~ threw the answer away.

Silent, which is the bad part. Rejecting the shadowing outright would also do.

** A polymorphic operator value is a C# error, not a Bjolang one
Reachable only by asking for one in a signature —
~(: get-plus (-> (-> %a %a %a)))~ — which emits ~Func<T_a, T_a, T_a>~ with
~a + b~ in the body, and C# says ~Operator '+' cannot be applied to operands of
type 'T_a'~. The other routes are already closed by rules that predate this:
~(def plus +)~ with no signature is caught by the module-level value rule, and a
~defun~ needs a signature at all.

The message is the gap, not the rejection — there is nothing a C# type parameter
could mean here. It is the same wall generic arithmetic hits everywhere else.

* Constraints and numerics

Found while opening ~Ord~ up and making the numeric constraints explicit. All of
them are the same seam: a constraint discharged by *passing a dictionary* rather
than by a C# ~where~ clause. Direct recursion, deriving ~Ord~ and using a
constrained function as a value were three of these and are fixed; what is left
is written as what remains rather than as what was found.

** Mutual recursion does not forward dictionaries

*Direct* recursion does, now: ~Scope.SelfCall~ carries the function's own
dictionary parameters and a call to its own name forwards them. That is correct
by construction rather than by luck — inside its own body a function is bound
monomorphically, so the call is at exactly the enclosing type variables and the
dictionaries it was handed are the right evidence in the right order.

Two constrained functions calling *each other* are still stuck. Neither is its
own callee, so each takes the ordinary route, finds no type arguments recorded —
the mutual bindings are monomorphic for the same reason — and passes nothing.
The result is the ~CS7036~ that direct recursion used to give.

Nothing in the library does this yet, which is the only reason it is written here
rather than fixed. The general answer is to record type arguments for a
monomorphic recursive binding, which is a change to how recursion is typed rather
than a patch to ~Lowering~.

* Incremental builds

** ~bjor~'s staleness check is not covered by the suite

~needs_compile~ decides whether to invoke the compiler at all, and it has been
wrong twice in opposite directions: once rebuilding the whole standard library
on every invocation, once leaving a module stale that a dependency had moved
under. Neither was caught by a test, because the suite compiles fixtures with
the compiler directly and ~bjor~ is only in the path of ~build_std.sh~ and of
running a file by hand.

Testing it means mutating ~lib/std~ mid-run — touching a module and asserting
what the next invocation says — and the tree is left inconsistent between the
touch and the rebuild that follows. The suite already takes a lock against two
runs sharing a working tree for that reason, so this wants to be the last phase
or a script of its own.


* Colourless concurrency

Layers 0–4 all ship. Four things left; only the first blocks anything.

** Shape C — ~-?->~ on a trait method's parameter

~Functor.map~ and ~Foldable.fold~ cannot take a colour, so ~(map f xs)~ written
generically stays ordinary even where ~list-map~ suspends. Every concrete name
reaches the suspending copy; the trait is where it stops.

Costs two copies of every implementation and two interface slots to dispatch
between. Shape A — a method declared ~-bjo->~ — is built and is the machinery to
extend.

** A generated copy that never suspends is still emitted

Size only. The copies that gain no yield point are async methods awaiting
nothing. Pruning them needs call sites redirected back to the original *after*
selection, which is a rewrite nothing so far has needed.

** Two lambda pins have no message of their own

A lambda handed to a .NET ~Func<A,B>~, and one stored in a structure whose
element type is a ground ~->~. Both land in ~Unpinned~ and get the generic
message, which is true about them.

Neither is reachable from a fixture: every ~Func~-taking method in the runtime
is generic, and ~Task.Run~ fails overload resolution through ~import/extern~.
A message waiting for a case.

** The lazy half of ~Seq~ has no suspending copy

~seq-map~, ~seq-filter~, ~seq-unfold~. Closed as a decision rather than open
work: the two copies would have different *types* — ~Seq~ against ~AsyncSeq~ —
and a copy that changes its return type is two functions, not monomorphisation.
~port->chan~ shipped instead.

If a suspending sequence is ever wanted it is a separate form producing a
separate type, with an ~AsyncIterable~ trait to consume it. Expressible now that
a trait method may declare ~-bjo->~; not worth it at two ~seql~ producers in the
whole library.

* Macros and trait methods

Both found while making a trait method in a template mean the trait. Neither is
reachable from the standard library as it stands, which is why they are written
here.

** A trait a macro's module imports is not among the ones it resolves

The set is read off the macro module's own ~def/trait~ declarations, at the
point where its assembly's macros are registered. Every import edge in the
module graph names a compiled ~.dll~, and a ~.dll~'s node carries its own
declarations and no dependencies, so nothing further is reachable from there.

So ~time-it~ in ~std/stopwatch~ writes ~(->str ...)~ in its template and gets
the old behaviour: the bare name, resolved where the expansion lands. Closing it
means the module's metadata carrying the set, which is where the compiler
genuinely knows it — inference has the whole registry for the module it is
compiling.

** A resolved call reads its arguments in the resolved name's scope

~Inference.unshadow~ puts module level's binding for one name back over what is
in scope, and the ~EApp(EResolved ...)~ case then infers the whole application
in that environment — arguments included. Its docstring says otherwise.

The visible consequence is that a name written by hand *inside* an argument of a
compiler-written call means the compiler's binding rather than the caller's:

#+BEGIN_SRC scheme
(defun (through m bind)
  (do (:bind x m)
      (:return (bind x))))     ;; reaches Monad's bind, not the parameter
#+END_SRC

Fixing it means inferring the callee in one environment and the arguments in
another, which the ~EApp(EIdent ...)~ case is not shaped for: it is one branch
covering trait dispatch, extern resolution and keyword arguments. Renaming the
shadow apart in the arguments instead does not work either — the binder keeps
its spelling into the emitted C#, so only one end of the rename would move.

* A lowercase union case cannot be matched by name

Found while letting a binder shadow a union case constructor, and separate from
it: in *expression* position the two are now told apart by scope, but a pattern
has no such thing to consult.

#+BEGIN_SRC scheme
(type (: Shape (Union blob (dot int) Big)))

(match s
  (blob "a")     ;; binds `s` to `blob` and answers "a" for every shape
  ((dot _) "b")
  (Big "c"))
#+END_SRC

~parsePattern~ reads a bare lowercase symbol as a binder, before any registry
exists to say otherwise — which is right for the overwhelmingly common case and
leaves no way to *test* for a nullary lowercase case. A case with a payload is
fine: ~(dot _)~ is a list, so it reads as a constructor. An uppercase case is
fine for the same reason the binder rule is safe.

Two ways out. Resolve the pattern's constructors after parsing, where the
registry is known — which is where the expression side resolves and would make
the two agree. Or refuse a lowercase nullary case at the ~type~ declaration,
which is smaller and would cost the prelude nothing: its lowercase cases all
carry payloads.

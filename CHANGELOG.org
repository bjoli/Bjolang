#+TITLE: Changelog
#+STARTUP: showall

What each change guarantees, and what it leaves open.

* Silent failures found by a correctness audit

- *An event synced on its own is nacked when its scope is cancelled.* A
  ~with-nack~, ~spawn-evt~ or ~task->event~ passed straight to ~sync~,
  outside a ~choose~, was judged to have won against the cancellation token,
  so its nack never fired. A cancelled ~(sync (spawn-evt ...))~ left its
  child running and its scope never closed, and a cancelled
  ~(sync (task->event ...))~ never cancelled the .NET call.
- *A ~(std run)~ pipeline ends when a stage stops reading early*, as in a
  shell: ~(pipe (seq 1 200000) (head -n 1))~ answers ~"1\n"~. The upstream
  stage had blocked on a full pipe for good, and the run never returned. A
  process that stops reading is an ordinary end of the copy into it, not an
  error.
- *A ~from-file~ redirect closes its file* once it has been copied into the
  command. Each run had left one descriptor open.
- *The definitions in a body follow ~letrec*~.* A run of ~def~ and
  ~defun~ forms is one scope, and values run in the order they are written.
  A value that reads one written below it, directly or through a local
  function it calls, is refused: "'b' is used before its definition". Such
  definitions had been reordered silently, so effects ran out of the order
  written, and a ~def~ that meant an outer binding of the same name read the
  later one: ~(def y 10) (println "x") (def a y) (def y 20)~ gave ~a~ 20.
  In ~impl~ methods, trait defaults and ~defbjouble~ bodies nothing had
  been ordered at all, so ~(def a (+ b 1)) (def b 41)~ gave ~a~ the value 1.
  A use inside a ~fun~, a ~seq~ or a ~bjo~ may still name a later value,
  and local functions may stand in any order.
- *~(def (: name Type) value)~ at the top level is checked against its type*,
  as ~def/mutable~ and a ~def*~ clause written that way are. The annotation
  had been dropped, so ~(def (: x int) "hello")~ compiled and printed
  ~hello~.
- *~take~ pulls exactly the elements it answers.* It had pulled one more
  before stopping, so ~(take 2 (map f xs))~ called ~f~ three times, ~(take 0 s)~
  forced an element, and taking lines from a ~port->seq~ consumed and lost
  the line after them. Zero or less now gives the empty sequence, as
  ~seq-take~ does; a negative count had answered all of ~s~.
- *Calling the result of a call is a yield point when that result is a
  bjoroutine.* ~((make 1) 1)~, where ~make~ returns a ~-bjo->~ function, had
  been emitted without an ~await~, so a bjoroutine doing it failed in the
  C# compiler, and an ordinary function doing it was accepted and failed
  there too instead of being refused.
- *A tail call to a loop from inside a loop nested in it is a jump.* A named
  let, a ~loop~'s ~=>~ clause or a function's body that calls an enclosing
  named let, an enclosing local function of its group, or the function
  itself from the tail of a nested named let or ~loop~ runs in constant
  stack space. The nested loop is emitted inline and the call jumps out of
  it to the top of the loop it names, in a bjoroutine and in a ~seq~ as
  well. It had been a real call, one stack frame per outer iteration, and a
  million iterations overflowed the stack.
- *A loop nested in tail position of another ends the outer loop when its
  result is the outer loop's.* Both are emitted as ~while~ loops in one
  method, and the inner one's exit left only the inner loop, so the outer
  one ran the same iteration again for ever: a named let that jumps in one
  branch and runs an inner named let or ~loop~ in another, whose result it
  returns, never returned.
- *A fused loop runs its producer as often as the unfused one.* A ~:with~
  end test, ~:while~ or ~:until~ written after the ~:for~ had run before
  the yielded expression was evaluated, so ~(:for e (map f s)) (:with k 0
  (+ k 1) (>= k 2))~ called ~f~ twice where the unfused loop calls it three
  times. One written before the ~:for~ had run after the producer had
  already produced the next element, pulling one more from the source than
  the unfused loop does.
- *A bjodat ~int~ field refuses an integer that does not fit in an int*, in
  both decoders, with "expected an integer that fits in an int", as
  ~(text json-codec)~ does. It had kept the low 32 bits, so ~:n 4294967297~
  read as 1.

* A vec no longer wears down

- *However a vec is edited, it stays close to the shape of a vec built
  from scratch.* ~vec-insert~, ~vec-remove-at~, ~vec-merge~, ~vec-split~
  and ~vec-slice~ could leave a tree taller than its items needed, with
  leaves of a single item and lookups that scanned far through a node. After
  cutting pieces out of a 100,000-item vec and appending them 20,000 times,
  it had gained two levels and four times its leaves, and indexing took
  68 ns against 6 for a fresh vec. It now keeps its height, has within about
  10% of the fewest leaves, and indexes in 19 ns.
- On random edits to a vec that is already in good shape, inserting costs
  20 to 35% more and long runs of small merges about 30% more. Removing,
  slicing and splitting cost what they did.

* vec-merge/pure is gone

- *~vec-merge/pure~ is removed.* It did exactly what ~vec-merge~ does: the
  runtime took the flag and never read it. ~vec-merge~ is the concatenation,
  and ~vec-compact~ rebuilds a vec dense.

* The prelude refuses what it used to get wrong quietly

- *~cond~ refuses a clause after ~else~*, which could never be reached. It
  had been dropped without a word.
- *A map prints each entry in parentheses*, ~#map((a 1) (b 2))~, the shape
  the ~#map~ literal reads, so a map of numbers prints as the literal that
  makes it. An ordered map prints the same way.
- *~vecbuilder-ref~ checks its index* and raises
  ~IndexOutOfRangeException~, as ~vec-ref~ does. Past the length but inside
  the builder's tail it had answered whatever the slot held.
- *~stringbuilder-add-code!~ refuses a number that is not a byte, and
  ~stringbuilder-add-unit!~ one that is not a UTF-16 code unit*, with
  ~ArgumentOutOfRangeException~. They had kept the low bits.
- *Both copies of ~vec-reduce~ and ~vec-for-each/range~ fail alike*: an
  empty vec is an ~InvalidOperationException~ and a run outside the vec an
  ~ArgumentOutOfRangeException~, before the callback is first called, whether
  or not the callback suspends. A count of -1 is refused rather than read as
  "to the end".
- *~with-shield #:within~ refuses zero or less*, which to a scope means no
  deadline, so a shield could be written that nothing could end.
- *The pump of ~async-seq->chan~ ends with its scope*: its send races the
  scope's token, so a pump parked on an item nobody takes stops when the
  scope ends, and its promise fails with ~Cancelled~. It had stayed parked
  for good.

* The REPL finds foreign imports, and re-exported traits where they live

- *Tab and ~:complete~ offer a module's published ~import/extern~ names*, such
  as the prelude's ~sqrt~, with their docs in ~:show~. They had been left out.
- *A re-exported trait and its methods are attributed to the module that
  declared them*: ~Num~, ~abs~ and ~even?~ are ~(std maths)~'s, which is where
  their docs are, rather than the prelude's, which has none for them.
- *Module metadata is version 18*: it records the declaring module of each
  trait a module re-exports. Every library is rebuilt by this compiler.
- *A REPL entry after the first keeps what the prelude says about its
  bodies*: which exports park a thread, which have a suspending copy, and the
  constrained bodies an entry may specialise. The cached read of a library
  had dropped all three.

* (std maths): integer division, gcd and powers, and its docs

- *Racket's integer division*: ~quotient~ and ~remainder~ (what ~/~ and ~%~
  do at an integer type, named), ~modulo~ (the sign of the divisor:
  ~(modulo -7 2)~ is 1) and ~quotient/remainder~, at every integer type.
- *~gcd~, ~lcm~, ~expt~ and ~integer-sqrt~* at every integer type, signed and
  unsigned. ~expt~ squares, ~integer-sqrt~ is exact and cannot overflow, and
  both refuse a negative argument.
- *~sqr~, ~positive?~ and ~negative?~* at every numeric type. Zero is neither,
  unlike .NET's ~IsPositive~.
- *Doubles*: ~nan?~, ~infinite?~, ~finite?~, ~pi~, and ~exact-floor~,
  ~exact-ceiling~, ~exact-truncate~ and ~exact-round~, which answer an ~int~ and
  refuse NaN, the infinities and what does not fit.
- ~even?~ and ~odd?~ are in the export list, where they had been missing.
- *The module is documented*, in ~maths.bjodoc~, so its exports are what
  ~:show~ and Tab describe and a new one without a doc is a warning.

* drop-while walks again, and range-by refuses a step it cannot take

- *Every walk of a ~drop-while~ starts over.* Its flag lived outside the
  sequence and was shared by every walk, so a second walk dropped nothing.
- *~range-by~ refuses a step of zero or less* with a panic, as ~up-from~ does:
  a range counts up, and such a step never reached ~hi~ (zero made ~length~
  divide by zero). ~down-from~ counts down.
- *A range's ~length~ no longer overflows* for a step near ~int-max~.
- Kept as it was: a walk stepping past ~int-max~ or ~int-min~ wraps rather
  than stopping. Checking would cost every step of every walk.

* The prelude and the builtins are documented

- *Every name the prelude offers has a ~(:doc ...)~*, 583 of them: its own
  definitions, its traits and their methods, its macros and reader
  extensions, and the builtins compiled into the runtime. They are in
  ~lib/std/prelude.bjodoc~ (the module's own doc) and eleven
  ~prelude-<area>.bjodoc~ files, written from Docs/prelude.org, the source
  comments and the runtime, and checked against the code.
- *A builtin is documented in the prelude* and checked against its type in
  ~Prelude.fs~: the doc names the arguments, and their number, the rest
  parameter, whether it returns anything and its type parameters are checked.
  Its doc is published in ~prelude.dll~ with its kind and signature, so
  ~:show~, Tab's menu, ~(janitor docs)~ and samizdat's ~@generate-docs~ find
  it.
- *The prelude has a module doc*, so an export, a macro or a builtin added
  without a doc is a warning when the standard library is built.
- *A function whose parameters the compiler named* — ~defeffect~'s wrapper
  takes ~effect-arg0__164~ — is documented as one without parameter names: the
  doc names them, as for a builtin. An ~import/extern~'s ~(out T)~ parameters
  are not counted as arguments, since a call passes nothing for them.
- *~:show~ finds traits, trait methods and types*, and prints a call made of
  the doc's argument names for a function with no definition to show.
- Docs/prelude.org is unchanged and now wrong in a few places the docs get
  right; Todo.org lists them, with the bugs found on the way.

* Lists print without a quote; mutablevec-sort! is stable; hash collisions stay local

- *A list prints as ~(1 2 3)~*, not ~'(1 2 3)~. A nested list was printed as
  ~'('(1) '(2 3))~, which is no literal; it is now ~((1) (2 3))~, and the empty
  list stays ~()~. Output that matched the quote has to drop it.
- *~mutablevec-sort!~ and ~mutablevec-sort-by!~ are stable*, as ~list-sort~ is:
  equal elements keep their order. They used .NET's introsort.
- *A hash collision node holds only keys with one full hash.* It used to take
  in every later key that shared its hash prefix, turning 1/32 of a map's or
  set's keys into a linear scan after one real collision.
- *Merging two maps or sets with different key comparers* adds the right
  side's entries through the left one's comparer. The result used to keep the
  right side's layout under the left comparer, and lookups failed.
- Tested in ~291_collection_edges.bjo~ and the Map and Set test suites.

* One clock, in the prelude, and a program can make its own

- *~Clock~ is the prelude's, and a record of functions*: ~read-monotonic-ms~,
  ~read-utc-ticks~, ~read-zone~ and ~advance-ticks~. ~(make-clock ...)~ takes
  any of them as a keyword and fills in the rest from the system clock.
  ~(std datetime)~'s clock used to be a closed union of three cases.
- *~current-clock~ and ~system-clock~ moved from ~(std datetime)~ to the
  prelude.* ~current-clock~ is cold. A program that imports both sees one of
  each, so no call site changes.
- *The ~MonotonicClock~ effect is gone.* ~(monotonic-ms #:clock c)~ reads the
  clock, defaulting to ~current-clock~. A test that installed
  ~(with-handler ((monotonic-ms f)) ...)~ binds
  ~(parameterize ((current-clock (make-clock #:monotonic-ms f))) ...)~ instead,
  and ~op/monotonic-ms~ is no longer exported.
- *Binding ~current-clock~ moves ~now~ and ~monotonic-ms~ together.* A fixed
  clock's monotonic reading stands still. A manual clock's starts at 0 and
  moves on a forward ~clock-advance!~ only, so a stopwatch over it never reads
  a negative time when the wall clock is stepped back.
- *~(clock-in c z)~* is ~c~ with ~today~ in ~z~, for a clock of one's own;
  ~(system-clock-in z)~ is ~(clock-in system-clock z)~.
- *~clock-advance!~ calls the clock's ~advance-ticks~*, so a clock of one's
  own made with ~#:advance~ can be moved too. On one without, it raises
  ~ArgumentException~ as before.
- *~now~ checks the reading*: ticks outside the calendar raise
  ~OverflowException~.
- Tested in ~210_prelude_effects.bjo~ and ~245_datetime.bjo~.

* The reader refuses brackets that do not pair

- *A form left open at the end of a file is an error*, at the bracket that was
  never closed. The end of the file used to close every open form.
- *A bracket closed by another kind is an error*, naming both: ~[1 2 3)~ was
  read as a vec.
- *A closing bracket with nothing open is an error.* At the top level it used
  to end the file, so that every form after it was silently not compiled.
- Code that relied on any of this stops compiling. One extra ~)~ at the end of
  ~TestFiles/assets/jsonbench/formatbench.bjo~ is gone; the published samizdat
  releases up to 0.8.0 end ~src/lightweight.bjo~ with one too, and need a
  release without it.

* The REPL edits its own lines, and completes on Tab

- *At a terminal an entry is read with a line editor* (PrettyPrompt, a new
  package reference of the compiler). Tab inserts the one candidate or the
  part all candidates share, and opens a menu showing each one's signature,
  doc summary and origin when that inserts nothing. Enter with a bracket open
  is a newline. History is kept in ~$XDG_DATA_HOME/bjolang/repl-history~.
- *What is offered depends on where the cursor is*: visible names (as ~:show~
  finds them), special forms and the symbols written earlier in the entry in
  code; commands at the start; package and module segments inside an import;
  nothing in a string, a comment or after ~#:~.
- *~:complete text~* prints the same candidates, one per line with their origin
  after a tab, for an editor's completion source. Every line starting with ~:~
  is now a complete entry, so a command is never held back by an open bracket.
- *~bjo repl~ no longer runs the REPL under ~rlwrap~.* Piped input, Emacs
  (~INSIDE_EMACS~, ~TERM=dumb~) and ~BJOLANG_REPL_PLAIN=1~ get the line-by-line
  reader as before; the transcript tests are unaffected.
- Not offered yet: the keyword arguments of the function at the head of a
  form, the names a module exports inside ~(only ...)~, and .NET members.
- PrettyPrompt brings ~Microsoft.Extensions.DependencyInjection.Abstractions~
  7.0 along, and it is kept out of the compiler's directory. A copy there
  answered ASP.NET Core's request for its own version 10, so every type that
  needs it failed to load and a package naming ~WebApplicationBuilder~ (bjoweb)
  stopped compiling. The shared-frameworks package test names that type now.

* (cancelled ct) and a with-nack's nack wrap nothing

- *~(cancelled ct)~ is the token's value as an event of its own*, delivered
  through a waiter rather than through ~Cml.Wrap~, and committed on the spot
  once the token has fired. The nack ~with-nack~ hands its generator is built
  the same way. ~(sync (cancelled ct))~ on a fired token: 57 -> 11 ns/op,
  168 -> 24 B/op; a worker choosing between a receive and ~(cancelled ct)~:
  180 -> 160 ns/op, 408 -> 304 B/op.
- No change of meaning: the event carries the token's reason, loses a
  ~choose~ without leaving anything behind, and fires once the token has.

* promise-join is the promise, and a landed one is joined on the spot

- *~(promise-join p)~ returns ~p~.* A promise is the join event in Bjolang's
  shape as well as BjoML's, and converts its outcome to ~(Result Exception a)~
  as it delivers. The ~Cml.Wrap~ a join used to build, and the closure and
  delegate the wrap built at every publish, are gone.
- *A promise that has landed is available*, so ~(sync (promise-join p))~ on one
  commits without a ~SyncState~ or a publish. Joining a landed promise:
  74 -> 12 ns/op and 168 -> 0 B/op. Starting a fiber and joining it:
  362 -> 230 B/op.
- No change of meaning: the outcome, the failure as ~(Err e)~, a join as a
  branch of a ~choose~, and the ambient token's race are as before. A landed
  promise skips the race because an available event already beats the token.

* chan-put and chan-get: a send and a receive without an event

- *~(chan-put ch v)~ is ~(sync (chan-send ch v))~ and ~(chan-get ch)~ is
  ~(sync (chan-recv ch))~*, as Guile fibers has ~put-message~ beside
  ~put-operation~. They are yield points like ~sync~, race the ambient token
  as ~sync~ does, and are cancelled the same way.
- *No event value is built*, so a rendezvous through them allocates nothing,
  and the type tests ~sync~ makes on an event are skipped. On the ring
  benchmark 80-92 -> 63-73 ns/op (minimum over six runs) and 32 -> 0 B/op.
  A choose whose sender uses ~chan-put~ goes 72 -> 40 B/op; its time is set
  by the receiving ~choose~ and does not move.
- ~bench/bjolang/cmlbench.bjo~ has a ~put~ twin of the ring row and of the
  skewed-choose row, so the overhead of syncing an event is on the table.
- The event forms are unchanged and are what ~choose~, ~wrap~ and anything
  that passes an operation around still take.
- Each channel keeps one object that parks its sends, made the first time a
  send parks.

* A watched park costs one compare-exchange, and a fiber's cell is its own

- *A spawned fiber never shares its parent's park cell.* ~Bjo.Spawn~ starts
  every child with ~FiberContext.ForChild()~, which ~DynEnv~ answers without
  the cell, and ~blocking~ / ~spawn/thread~ hand their thread the same copy.
  ~Scope.Start~ and ~spawn/daemon~ no longer do it themselves.
- *So the cell needs no claim before a park.* The owner fills it in with plain
  stores and arms it with one compare-exchange, before the op is handed to
  the channel. The claim, the re-read of the token after the park, and the
  fallback for a fiber that could not claim the cell (~CancelWatch~, the
  ~ITakeable~ link on ops, ~CancellableEvent~ for a ~choose~) are gone.
- *Cancellation keeps its guarantees.* A value a partner took is never thrown
  away, a token that fires during a park is never missed, and the fiber is
  resumed once: whether the op was on the channel's list when the token
  withdrew it decides, under the channel's lock, who resumes it.
- A park that finds its cell already armed raises instead of overwriting
  another fiber's park.
- Ring 86 -> 80 ns/op at the first quartile, nested ring 77 -> 72, skewed
  choose 148 -> 144; spawn burst within its noise. Interleaved runs of the two
  runtimes, in ~Cml/design.md~.
- Tests: each order of the race on the op driven by hand, including the token
  withdrawing before the op is parked and the owner matching inline; a spawned
  child starts without its parent's cell.

* :show at the REPL: the docs of what an entry could write

- *~:show name~* prints the doc of the visible name, and lists every other
  visible name containing it, in any case, with its module and summary. A name
  from a module the session has not imported is not visible, so
  ~:show random-int~ prints nothing before ~(import (std random))~.
- *Visible is what the compiler says it is*: the REPL compiles the session's
  imports and reads the scope back, so modifiers and re-exports need no rules
  of their own. A renamed or prefixed name is looked up under its original name
  in its defining module. Earlier entries' definitions and builtins are
  visible too; builtins have no docs.
- *An import modifier's strings other than its path are left as written at
  the prompt.* ~(import (prefix (std random) "r/"))~ used to turn ~"r/"~ into
  an absolute path, as though it named a file.
- Left open: only the REPL has it. A compiled program cannot ask what is in
  scope where it was written.

* A partner takes a parked channel operation without touching the other fiber

- *The claim a partner and the cancellation token race for is on the parked
  op*, not on the parked fiber's registration. A partner takes it with a plain
  store under the channel lock it already holds; the token takes the same lock
  to withdraw it. A rendezvous under a scope no longer pays an interlocked
  instruction and an interface call on the partner's side, or moves the other
  fiber's cell to the partner's core. Ring 85 -> 80-81 ns/op (minimum), nested
  ring 74 -> 70; spawn burst and skewed choose unchanged.
- *A value a partner took is still never thrown away by a cancel*, and a token
  that fires while a fiber is parking still reaches it. The op mints a
  generation per watched park and keeps it across recycling, so a token
  holding a stale op cannot withdraw another fiber's park.
- New test driving each order of the race by hand (partner first, token
  first, stale generation); the ping-pong cancel race now also checks that
  every send that returned was received.
- Left open: the owner still pays two compare-exchanges on its own cell per
  watched park. One of them exists only because two fibers can share a cell.

* A collection compares keys the way = does

- *What makes a ~Map~, ~HashSet~, ~OrderedMap~ or ~OrderedSet~ out of nothing
  asks for the key's ~Eq~ or ~Ord~ and compares with it*: the ~-empty~
  functions, the conversions from lists, vecs and seqs, the collectors, and
  ~hashset-map~ into a new element type. Three lookups that silently missed now
  find their key: two cases of a union that ~=~ equates, a specialized target
  such as ~(Eq (Pair %a %a))~, and an implementation with a ~(where ...)~ of
  another trait. An ordered collection of the last two threw at its second
  element; it is now ordered by the ~Ord~.
- *No signature changes.* The constraint is inferred where a signature leaves
  it out, and reaches callers as any ~(where ...)~ does.
- *Ordinary keys run the same code.* Each ~Eq~/~Ord~ dictionary is also a .NET
  comparer and says whether the type's own members give the same answer; where
  they do, which is every primitive, std container of such and compiled-in
  implementation, the collection keeps the default comparer and the shared
  empty map. 1M ~map-set~/~map-ref~ on ~int~ keys measured the same before
  and after.
- A collection made from another keeps its comparer, also through a builder or
  transient left empty, ~map-map~ and ~map-map-values~, and the suspending
  halves of the walking functions. These used to fall back to the default.
- ~eq-comparer~ and ~ord-comparer~ are builtins: the comparer that agrees with
  ~=~ or ~compare~ at a type, for handing to .NET.
- ~(compare a b)~ on strings compares code points without converting to
  UTF-16: the order an ~OrderedMap~ of strings keeps, and no allocation.

* A suspending copy that awaits nothing is not emitted

- *An inferred copy whose body awaits nothing is dropped after selection*, and
  its calls go to the ordinary body. ~vec->list~ reaches ~vec-for-each~, a
  ~defbjouble~, but hands it an ordinary lambda: its copy was an ~async~
  method with no ~await~, awaited by every bjoroutine calling it.
- *A dropped copy is not published as a double*, so an importer calling it is
  not copied in turn. That was how one such copy spread through every module
  above it (samizdat's HTML writer; glasnost's ~folder-page~ needed ~#:sync~).
- Copies that only call one another go together; a copy referenced as a value
  is kept, since its delegate type was settled where it was handed over.
- The blocking lint then reports the bjoroutine that calls the ordinary body,
  rather than a copy nobody calls.

* A type error says what is wrong with what, and where inside

- *A mismatch inside two types names the innermost pair and the way down to
  it*: ~They differ inside the Option, inside the List: string against int.~
  under the two whole types, rather than the two types alone.
- *An argument, a return value, a field, a list element and a keyword default
  are named in the message*, with the expected type above the one found:
  ~the 1st argument to 'k' has the wrong type.~, ~what 'f' returns has the
  wrong type.~ The location is the argument's, not the call's.
- Two ~if~ branches that disagree are shown as one and the other, since
  neither is the expectation.
- A call with the wrong number of arguments to a known function says so
  before any type is compared: ~'h' takes 2 arguments, and is given 1
  argument here.~

* A rendezvous costs a quarter less

- *A single channel operation parks with the fiber's own resume in the op*,
  as the C# twin's awaiter does, rather than through a pooled ~EventAwaiter~
  and a delegate hop. ~bench/bjolang/cmlbench.bjo~: the ring from 117 to
  about 90 ns/op, the nested-scope ring from 100 to about 80, against the C#
  twin's 55-65.
- *A ~choose~'s cancellation branch is the fiber's one registration on the
  token*, committed through the sync's own ~SyncState~, rather than an event
  and a waiter built per park: the skewed-choose row from 112 to 72 B/op and
  a third of its collections, at about the same time.
- What remains of the token's cost is the claim on a direct park, measured in
  ~design.md~; event ids as a plain increment were measured and gave nothing.

* A call the compiler writes reads its arguments in the caller's scope

- *A local named like the head of a compiler-written call means the local in
  that call's arguments.* ~#"[${str}]"~ with a parameter ~str~ read it as the
  prelude's ~str~, and ~(:return (bind x))~ in a ~do~ with a parameter ~bind~
  as Monad's: type errors about types nobody wrote. The arguments' own
  mentions are renamed out of the head's way while it is inferred, and back.
- A compiler-written call inside another one's arguments, such as an
  interpolation inside an interpolation, is spelled qualified when a local has
  its name, so C# does not call the local.

* bjo does not recompile a program whose imports kept their interfaces

- *After a body edit in a dependency, ~bjo run~ rebuilds the module and runs
  the program as it was compiled.* ~bjo~ builds the imports first, then reads
  the program's build record the way the compiler reads a library's: every
  newer file must be a linked module whose interface digest is the one the
  record names, or a source such a module was built from. A changed numeric
  keyword default, which C# copies into the caller, still recompiles it.
- A build record now carries its ~written~, ~interface~ and ~interface-of~
  lines into ~bjo~'s ~BuildRecord~, with the ~source~ lines apart.

* A rebuilt runtime makes the libraries stale

- *A library older than the runtime assemblies is rebuilt*, as one older than
  the compiler is. A runtime rebuilt on its own (~dotnet build
  BjolangRuntime~) left every library compiled against its old API, and the

* A string's ~(:for ch s)~ is a walk

- *~Iterable string~ walks with a ~StringWalk~*, not a ~StringCursor~. It
  takes the string's array and bounds once and decodes each character as it
  steps onto it, so the loop asks nothing of the string again. Since
  strings and slices became one type, every cursor step has checked which
  of the two it has, and the JIT does not hoist that out of a loop: a loop
  over ASCII text had lost a quarter of its speed. ~(:for ch s)~ is now
  about twice what it was, and faster than a ~string-cursor-ref+next~ loop.
- ~string-walk~, ~string-walk-done?~, ~string-walk-current~ and
  ~string-walk-next~ are exported, because an inlined impl body reaches
  them. A walk's fields are private, and only those functions make one, so
  it is always on a character boundary of its own string; it is a type of
  its own, so no cursor function takes it; and a default one is at the end.
- Explicit ~string-cursor-*~ loops are as they were.

* Slices

- *A slice is a string that shares its source's bytes.* ~substring/slice~,
  ~string-trim/slice~, ~string-trim-left/slice~, ~string-trim-right/slice~
  and ~string-split/slice~ make one; every other operation copies as
  before. A slice equals, hashes and orders by its text, and its cursors
  are its source's, regex positions included.
- *~(string-copy s)~* gives a slice bytes of its own, so that holding it no
  longer holds its source.
- A string is still one reference wide: BjoString keeps a slice's bounds in
  a small object beside the array, so only a slice costs anything — 32
  bytes when it is made, and a slower path when a cursor walks it.

* Faster string walks

- *~string-reverse~ is BjoString's ~Reverse~*, which reverses the bytes and
  then puts each multi-byte character back in order: about 4× faster on
  mostly-ASCII text. Characters are reversed as before, not grapheme clusters.
- A cursor step decodes a two-byte character (Latin, Greek, Cyrillic) inline,
  which makes walking such text about 20% faster.

* ~(std rx)~ runs on BjoRx

- *The engine is BjoRx*, a translation of Rust's ~regex~ crate, linked as the
  submodule ~BjolangRuntime/BjoRx~. It matches the string's UTF-8 in linear
  time, so match positions are the string's cursors with no conversion. The
  API is unchanged: leftmost-first, ~:bos~ only at the start of the string,
  only ~$~ and ~=>~ groups capture, an empty match moves the next search one
  character on, and ~rx-split~ skips empty separators.
- *A character set may hold any scalar*: ~(in #\😀)~ and ~(/ #\😀 #\🙏)~
  compile, where they were an error.
- *~#rx(...)~ compiles to BjoRx's tree as text* (~(s (A) (l 61) (z))~), which
  is what ~rx-pattern~ answers and ~rx-compile~ takes.
- Where .NET's engine and this one disagree, this one follows Rust's: a group
  inside a loop whose body can match empty, like ~(* ($ (* "a")))~, reports
  the last non-empty iteration, and nested loops such as ~(+ (** 2 4 "x"))~
  are not merged into one.

- A pattern whose only group is unnamed, ~(seq "=" ($ (+ :digit)))~, has that
  group; ~rx-group/n~ answered ~None~ for it.

* Strings are UTF-8

- *~string~ is BjoString's ~Utf8String~*, an immutable UTF-8 string that is
  always valid. A submodule, ~BjolangRuntime/BjoString~, linked like the
  collections. ~StringCursor~ and ~StringBuilder~ are BjoString's too.
- *Storage units are bytes.* ~string-length~, ~string-code-ref~,
  ~stringbuilder-length~, ~stringbuilder-code-ref~ and
  ~stringbuilder-add-code!~ count and move UTF-8 bytes; ~string-count~ and
  the cursors are unchanged. Bytes from ~add-code!~ are checked when the
  builder becomes a string, which throws if they do not form whole
  characters. ~(stringbuilder-add-unit! b n)~ takes a UTF-16 code unit, for a
  reader of a text port, and pairs surrogates into their character.
- *Order is codepoint order*, which differs from the old UTF-16 ordinal order
  only between a character above U+FFFF and one in U+E000–U+FFFF.
- *.NET's ~System.String~ is a separate type.* A .NET member taking or
  returning one, or an array of them, is converted at the call; ~null~
  becomes ~""~. An import declaring ~System.String~ as its result keeps it.
  A method ~string~ lacks is called on the converted string, so
  ~(.Substring s 1)~ still works in .NET's terms. Strings inside other types
  are not converted: ~(string->clr-string s)~ and ~(clr-string->string s)~.
  ~(:is string s)~ tests for a Bjolang string.
- *String literals are hoisted*, one static field per distinct text, and a
  literal in a pattern is a guard rather than a C# constant label.
- *~(std rx)~ still runs on .NET's engine*, through UTF-16, with match
  positions turned into byte cursors; its API is unchanged.

* Hoisting, paths, and two renames

- *~(please-hoist-i-promise-i-am-not-naughty expr)~* evaluates ~expr~ the first
  time the form is reached and keeps the value. A throw keeps nothing, so the
  next evaluation tries again; identical forms share one value. A form that
  cannot be hoisted is one error listing every reason: a local, a def of its
  own module or a ~def/mutable~, a type variable of the function around it, an
  await, a ~yield~, a ~with-return~ escape, a void form, or a value that can be
  written in place. Purity and independence from dynamic context are promised,
  not checked.
- *~#rx(...)~ is hoisted*, in expressions and in ~Rx~ / ~RxIn~ patterns alike.
  It no longer hashes its pattern on every evaluation; a search with
  ~(+ :alpha)~ is about eighteen times faster.
- *~(try ... #:catch ...)~ and calls imported with ~#:exceptions~* compile to
  a ~try~ / ~catch~ statement rather than an immediately invoked lambda, so
  they allocate no closure, and an ~#:async~ one no extra state machine.
- *~get~, ~try-get~, ~set~ and ~update~* read and copy along a path of
  ~.field~ steps and keys. Keys go through ~Refable~ to read and the new
  ~Settable~ (~ref-set~, for ~Vec~ and ~Map~) to write. Errors in a step are

- *~(std set)~ is ~(std hashset)~*: ~Set~ is ~HashSet~ and ~set-*~ is
  ~hashset-*~, and the collector is ~hash-setting~. *~(std http)~'s ~get~ and
  ~post~ are ~http-get~ and ~http-post~.* Both free the names for the path

* ~loop~: ~:finish~, ~:abandon~, ~:while~, ~:until~ and the ~:subloop~ form

- *~(:finish test [value])~* ends the whole loop. With a value, that is the
  result and ~=>~ does not run; the value must have the loop's result type.
  ~:break~ is a deprecated spelling, and warns. ~:break-let~ is renamed
  ~:finish-let~ the same way.
- *~(:abandon test)~* ends the current level. ~:end-subloop-if~ is a
  deprecated spelling, and warns. At the outermost level it is an error.
- *~(:while test)~ and ~(:until test)~* are drivers that bind nothing, grouped
  and opening levels as a ~:for~ does. The test runs before every iteration and
  may read the variables of the drivers before it in its group.
- *~(:subloop clause ... [=> (name expr)])~* is a nested loop whose
  accumulators, or ~name~, are bound for the clauses after it.
  ~(:finish-subloop test)~ ends it, ~(:abandon-subloop test)~ drops it and the
  rest of the iteration holding it. A bare ~(:subloop)~ still only separates
  levels.
- *A clause may not bind a name the loop carries*: an accumulator, a ~:with~
  variable of its own or an enclosing level, or a variable of an enclosing
  level. Such a binding used to be carried in place of the outer one, so
  ~(:with i 0 (+ i 1) (= i 3)) (:subloop) (:for i ys)~ never ended.
- *A type error between an ~if~'s branches is reported at the ~if~.*

* ~bjo publish~: a program that runs from anywhere

- *~bjo publish [-o dir] [file]~* makes a release build of a program and copies

* Graph builds, a ReadyToRun compiler, and ~bjor~ removed

- *The compiler builds a set of libraries in parallel.*
  ~--build-graph PATH...~ reads the imports of every ~.bjo~ under the given
  paths, sorts them, works out which modules are out of date, and builds each
  one in a ~--worker~ process as soon as everything it imports is built. A
  module that fails skips everything that imports it; an import cycle is
  refused and printed as a chain. ~-j N~ limits the workers, and ~--dry-run~
  prints the plan. The out-of-date rule is the one ~ensureLibrary~ uses
  (~Pipeline.upToDateAgainst~), and imports resolve through the same function
  (~resolveImport~), so the plan matches what the compiler would build. A
  worker emits through the same C# backend as a single ~--lib~ compile, so its
  output is byte-identical. Checked by a new phase in ~run_tests.py~.
- *~build_std.sh~ is one graph build over ~lib/~.* It no longer lists modules
  or their order, so a module added under ~lib/~ is built without being named
  there. The fixture libraries in ~TestFiles/inc~ are built the same way.
- *The compiler is a ReadyToRun publish in ~bin/compiler~,* built by
  ~build_compiler.sh~, which is also the only place that knows that path.
  ~bjo~, ~build_std.sh~, ~run_tests.py~, ~run_bjo_tests.py~ and
  ~bench/run.sh~ ask it. ~bjo~ treats a build record naming a different
  compiler as stale, so moving the compiler rebuilds everything once.
- *~bjor~ is gone.* Use ~bjo~, or the compiler directly. The leftover
  ~lib/bjor~ build output, whose source moved to ~bjo/manifest.bjo~, is gone
  with it, which frees the package name ~(bjor)~.
- *~run_tests.py~ runs more of itself in parallel:* codegen and warning tests
  in batches, REPL sessions at once, and the package tests alongside the test
  groups. ~TestFiles/172_http.bjo~'s slow handler sleeps 1.2 s instead of 4.

Left open: ~bjo~ still builds project libraries with ~--batch --if-stale~
rather than ~--build-graph~, and nothing stops a graph build and an unrelated
compile from writing the same ~.dll~ at the same time. The first build of the
compiler on a new machine downloads the ReadyToRun crossgen package for its

* bjodat writes a double so that it reads back as one

~bjodat->string~ wrote a ~BjoFloat~ as .NET writes a double, so ~1.0~ came
out as ~1~ and read back as a ~BjoInt~. A double is now always written with a
fraction or an exponent: ~1.0~, ~-2.0~, ~0.5~, ~1E+20~, the shortest form that

NaN and the infinities are spelled as Scheme spells them: ~+inf.0~,

written ~Infinity~ and ~NaN~, which read back as symbols. Only those exact
names are doubles: ~+inf~ and ~inf.0~ are still symbols.

documented, so each builds without a warning, and an export added without a
doc is warned about. A manual page is ~@defmodule[(std fmt)]~ and ~@defdocs~.

Pointers to the old files in source comments, ~Docs/Projects.org~ and
~bjo/manifest.bjo~ now point at the docs.

~bjor~ did not rebuild a module whose ~.bjodoc~ had changed: it followed only
string literals naming a ~.bjo~ or ~.protobjo~. It follows ~.bjodoc~ too.

Writing the docs found these, none fixed here:
- A ~(:doc ...)~ form the compiler accepts need not be bjodat: a lone ~:~ in a
  ~(form ...)~ compiles, and the published docs then do not read back. The
  compiler should refuse it.
- A trait and its method with the same name (~->bjodat~) share one doc, which
  is checked as the method's; the trait has none of its own and is not warned

- ~by-lines~ in ~(std run)~ reads all of the output before it hands over the

- bjodat writes ~2.0~ as ~2~, which reads back as an integer, and NaN and the
  infinities as symbols.
- ~fmt.org~ described ~str*~, which ~(std fmt)~ does not export.

* ~(std random)~ is documented with ~(:doc ...)~

Every export of ~(std random)~ has a doc, in ~lib/std/random.bjodoc~, and the

* ~(janitor docs)~: published docs, read back as records

A new top-level package, ~janitor~, holds what tools need from the compiler's
side of things. It is a directory of ~lib~, so the name is reserved, and it is
not ~std~: a program has no reason to import it.

- ~(janitor modules)~ finds a module by name the way ~Paths.fs~ does: the
  installed ~lib~ (~lib-directory~, ~standard-roots~, which first try the
  ~lib~ that ~janitor/modules.dll~ itself was loaded from, so a program run
  from outside the installation finds it), a project's packages
  from its roots file (~read-roots-file~), and the longest package name that
  is a proper prefix of the module's (~find-module-source~,
  ~find-module-assembly~, which answers the dll beside the source).
- ~(janitor docs)~ reads a module's ~BjolangDocs~ into ~Doc~ records:
  ~module-docs~ by name, ~assembly-docs~ by path, ~parse-docs~ from the text.
  A ~Doc~ has its subject, its kind, a function's signature and ~defun~ head
  as the compiler added them, and its clauses as ~DocClause~ values in the
  order written. A clause or kind this version does not know is kept as
  ~DocOther~ / ~KindOther~, so docs from a later compiler still read.
- The attribute is read with ~System.Reflection.Metadata~, by a new runtime
  helper ~Bjolang.Runtime.BjoAssemblyMetadata.Read~, so the assembly is never
  loaded: a tool can read the docs of a module it links itself, or of the
  whole library, and keep none of it loaded.

Both modules are documented with ~(:doc ...)~, so they are also the first
modules of ~lib~ to carry docs. ~TestFiles/265_janitor_docs.bjo~ reads its own
exe's docs and ~(janitor docs)~'s by module name, and covers each failure: no
package, no module, an uncompiled one, a file that is not an assembly, a
malformed clause, and a roots file that is wrong or missing.

Left open: the samizdat commands for the manual and the REPL's ~:doc~, which
are what this is for; and a match guard that calls a function in some
positions fails in codegen ("this ~match~ guard needs statements to
evaluate"), which ~read-clauses~ works around by matching on the head first.

* Documentation: ~(:doc ...)~, checked against what it documents

A definition is documented with ~(:doc name clause ...)~ in the module that
defines it, and the compiler checks the doc against the definition: a renamed
parameter, a removed function, a field nobody documented or a ~(see ...)~ of
nothing is an error where the doc is. ~Docs/Documentation.org~ is the whole of
it; the short version:

- Clauses: ~summary~, ~arg~, ~rest~, ~key~, ~returns~, ~raises~, ~see~,
  ~example~, ~reference~, and ~field~, ~case~, ~tparam~, ~form~ and ~literal~
  for the kinds that have them. Every text is a string, raw ones included, with
  samizdat markup in it.
- The compiler works out what a name is. A function documents each argument
  without a default in order, its rest parameter, and what it returns unless
  that is ~void~; a keyword is optional. A record documents every field unless
  it is ~#:opaque~. A union's cases are optional. A macro shows how it is
  written with ~(form ...)~, and documents each variable in it. A trait method,
  an ~import/extern~ and a ~def~ of a function have no parameter names, so their
  doc gives them and the compiler counts them.
- ~(:doc name #:reader ...)~ documents the reader extension ~#name(...)~;
  ~(:doc #:module ...)~ the module; ~(:doc #:file "x.bjodoc")~ reads docs from
  another file, which then counts as a source of the module.
- A module with a module doc is documented, and the compiler warns about each
  export, trait method, macro and reader extension of it that has no doc.

The forms never reach the parser: ~Pipeline~ takes them out once includes are
spliced, and ~Docs.check~ runs after type checking, before the gate that stops
the build on an error. The docs are published in the assembly under a metadata
key of their own, ~BjolangDocs~, as one bjodat vec of the forms as written plus
~(kind ...)~, a function's ~(signature ...)~ and its ~(definition ...)~ head, so
that an importing compilation, which reads ~BjolangMetadata~, never parses them.

~TestFiles/264_docs.bjo~ documents one of every kind, part of it from
~264_docs.bjodoc~, and reads its own published docs back with bjodat. Each rule
has an error test, ~errors/doc_*.bjo~, 26 of them; the warnings are in
~warnings/doc_undocumented.bjo~ and ~warnings/doc_quiet_without_module_doc.bjo~,
and ~repl/docs.in~ is the prompt: a doc is checked against what its own entry
defines.

What it leaves open:

- Builtins from ~Prelude.fs~ have no definition a doc can be checked against,
  and cannot be documented yet.
- Nothing reads the published docs yet but the test: the REPL has no ~:doc~
  command, and there is no samizdat command for the manual.
- A list's range ends at the token after it, which is the reader's doing, so
  publishing finds a form's end by counting brackets in the file's tokens.

* Raw strings: ~"""..."""~

Three or more quotes open a string and the same number close it, and nothing
in it is an escape. On one line the text is what lies between the quotes:
~"""say "hi" """~. Over several lines, the opening quotes end their line, the
closing ones stand on a line of their own, and the whitespace before them is a
margin that comes off every line, so the text indents with the code around it.
A line with text that does not begin with the margin is refused rather than
cut, and a run of quotes as long as the delimiter is refused anywhere in the
text. Line breaks are ~\n~ whether the file has ~\n~ or ~\r\n~.
~Docs/Syntax.org~, "Raw strings", has the rules.

They are for text that is mostly quotes and backslashes: markup, SQL, regexes,
Windows paths, and the documentation that ~(:doc ...)~ will hold.

Both readers read them: the compiler's lexer, and bjodat's reader in
~lib/text/bjodat-core.bjo~, so a ~.bjodat~ file can hold one. They are two
implementations of one rule, and ~263_raw_strings.bjo~ keeps them together:
its cases live in ~263_raw_strings.in~, which the compiler reads through
~include~ and bjodat reads as the program's input, and every case is checked
against its escaped spelling and bjodat's reading against the compiler's.
The compiler's six refusals are in ~errors/raw_string_*.bjo~, and bjodat's,
with ~\r\n~, are in the same test.

What it leaves open:

- bjodat's writer still writes every string escaped and on one line. A raw
  string written back would need a margin that fits the text around it, and
  ~bjodat->string~ writes a value on its own.
- There is no raw interpolated string. ~#"""~ is refused, where before it read
  as an empty interpolated string followed by the start of another string. No
  file in the tree wrote ~"""~ before this.
- A raw string inside an interpolation hole is skipped whole, so
  ~#"${(f """}""")}"~ works.

~bjomode.el~ fences a raw string so Emacs sees one string, inner quotes and
semicolons included, and ~C-M-f~ steps over it. textmate-bjolang's grammar has
a ~string.quoted.triple.bjolang~ scope, which is how samizdat highlights one.

* A bjoroutine call that does not suspend allocates nothing

Every call to a bjoroutine allocated its promise, a ~FiberCore~ of about 88 B,
before its body ran, and a box for its state machine if it suspended. Now a
call allocates nothing until it suspends, as ~ValueTask~ does: a call that
returns without suspending carries its value back in the ~Fiber<T>~, and a
call that suspends makes one ~CalledFiber~, which is both its promise and its
box. A spawned fiber is unchanged, because its promise is handed out before its
body runs: it is still a ~FiberCore~ and a separate box.

What it costs: ~Fiber<T>~ now holds a ~T~ beside its reference, so a result is
copied through the fiber, its awaiter and the builder instead of through the
heap. For a 32-byte result, the size of an ~Option~ of a ~Result~, a single
call that does not suspend is about 4 ns slower. A chain of eight is still 10%
faster, because the allocation it saves is worth more than the copies.

Measured with ~bench/Diag --mode calls~, old and new alternated, per call chain:

| Shape                                  | Before          | After           |
|----------------------------------------+-----------------+-----------------|
| one call, ~int~, no suspension         | 18 ns, 88 B     | 8 ns, 0 B       |
| eight nested calls, ~int~              | 162 ns, 704 B   | 49 ns, 0 B      |
| one call, 16 B result                  | 20 ns           | 15 ns           |
| eight nested calls, 16 B result        | 174 ns          | 114 ns          |
| one call, 32 B result                  | 20 ns           | 24 ns           |
| eight nested calls, 32 B result        | 222 ns          | 199 ns          |
| ~Colour.Lift~ call                     | 20 ns, 88 B     | 8 ns, 0 B       |
| eight nested calls that all suspend    | 4364 ns, 1776 B | 3811 ns, 1520 B |
| eight inline helpers and one suspension | 1668 ns, 1192 B | 1431 ns, 416 B  |

In bjoweb's ~examples/hello.bjo~ about half of the bjoroutine calls a request
makes never suspend. Each ~GET~ allocates about 545 B less (~7.0 KB~ to
~6.4 KB~) and an echo about 990 B less; requests per second are unchanged
within the noise of ~bench/bjoweb.sh~.

~default(Fiber<T>)~ is now a call that returned ~default~ rather than a fiber
that cannot be awaited. ~AsPromise~ on a call that did not suspend makes a new,
completed promise each time it is asked. The runtime tests in
~BjolangRuntime/Cml/Tests~ gain a section for called bjoroutines: no
allocation without a suspension, one and two suspensions, the caller's and the
callee's contexts kept apart, a failure before and after the first suspension,
and a spawn whose body never took its promise.

* ~string-split~ gives its fields to the vec without copying them

~string-split~ added each field of .NET's ~Split~ to a ~VecBuilder~, which
copied them into its tail and copied the tail again when it froze. The runtime
now does the split itself, and hands the array ~Split~ made to the vec: up to
32 fields it becomes the vec's tail as it is, and past that it goes into leaves
in one pass. This is safe only because nothing else ever holds that array, so
it is done in ~BjolangRuntime.SplitToVec~ and not offered to Bjolang code: an
array a program could still write to would change the vec under it. Measured
on one machine, per call:

| Split                       | Before         | After          |
|-----------------------------+----------------+----------------|
| ~"a,b,c"~ on ~","~          | 96 ns, 576 B   | 51 ns, 168 B   |
| ~""~                        | 45 ns, 472 B   | 12 ns, 80 B    |
| a path of five segments     | 120 ns, 672 B  | 79 ns, 248 B   |
| 32 fields                   | 553 ns, 1712 B | 445 ns, 1352 B |
| 200 fields                  | 3700 ns        | 3115 ns        |

The fields are the same, empty ones included. ~067_chars_and_strings.bjo~
adds the empty string, separators at both ends and nothing else, 32 and 33
fields, and adding to and setting in a split's vec.

* A vec builder costs what its vec needs

Every ~VecBuilder~, and so every ~vecing~, ~vec-filter~ and string split,
allocated a 512-slot array for leaves and a 32-slot tail before its first
item, and copied the tail when it was frozen: about 4.4 KB for a vec of any
size, three items or none.

The runtime's ~RrbBuilder~ (the ~RrbList~ submodule) now allocates when it has
to. The tail, a leaf's worth, is made with the first item; the array of full
leaves is made with the first leaf and grows up to 512. A frozen vec's tail
is still exactly as long as its count, so a vec is no larger than before:
the builder copies its tail down, or hands it over when it is exactly full
and copies it before changing it again. Measured on one machine, per build,
medians of three runs:

| Vec                 | Before           | After           |
|---------------------+------------------+-----------------|
| empty               | 146 ns, 4418 B   | 47 ns, 80 B     |
| 3 ints              | 136 ns, 4424 B   | 36 ns, 320 B    |
| 32 ints             | 196 ns, 4536 B   | 49 ns, 280 B    |
| 100 ints            | 437 ns, 5424 B   | 308 ns, 1376 B  |
| 1000 strings        | 3760 ns          | 2108 ns         |
| a million ints      | 2.13 ms          | 1.82 ms         |

A bjoweb server answering a short text went from 49 900 to 52 700 requests a
second over 32 connections, and from 100 900 to 112 300 over 128.

A tail that grew 4, 8, 16, 32 was tried as well: it saved 3 to 10 ns on one
to four items, and cost as much again for every vec of five to 32, copied
three times on its way to a leaf.

What a builder holds and gives did not change. ~BuilderGrowthTests~ checks
the sizes around every step of the leaf array's growth, vecs that must stay
as they were while their builder goes on, and a seeded mix of adds, ranges,
sets and freezes against a ~List<int>~.

Left open: setting an item in a leaf the builder did not make still clones
that leaf every time, not once.

* ~(text xml)~: XML, read as signals, folds or a tree, and written

Three modules over ~System.Xml~ and ~System.Xml.Linq~, with no shim.
~(text xml)~ is an opaque ~Node~ and ~Document~ whose constructors keep every
tree to four rules (adjacent text merged, no empty text, no attribute twice,
no namespace declaration as an attribute), the views and helpers later modules
are to be built on, ~node=?~, and a printer in SXML's look. ~(text xml read)~
is a pull stream of signals, Kiselyov's SSAX fold, a tree fold where the
caller picks the tree type, ~parse-xml~, and ~xml-for-each~, which holds one
element at a time. ~(text xml write)~ writes through ~XmlWriter~, chooses the
prefixes names do not carry, refuses what ~XmlWriter~ would silently change,
and indents without touching mixed content.

The defaults are the safe ones: a DOCTYPE is refused, nothing external is ever
resolved, entities expand to at most 10 000 000 characters, and nesting deeper
than 512 is an error. Nothing recurses per level of nesting, so a tree 100 000
deep reads, compares, prints and writes, and a flat document of a million
elements folds, in a loop.

See ~Docs/std/xml.org~. Tests: ~252_xml_nodes.bjo~ to ~258_xml_print.bjo~.

Left open: ~#:dtd 'ignore~ loses the doctype, because ~XmlReader~ does not
report it then; ~#:dtd 'parse~ refuses a DOCTYPE that names an external DTD,
an XHTML one say; a DOCTYPE refused or a limit reached has no position, since
.NET gives none; and ~xml-skip-element!~ does not check what it skips against
~#:max-depth~.

* A lambda's result is what its context expects of it

A lambda checked against an expected function type had its parameters pinned
and its body inferred on its own. Two things went wrong with that.

A literal it ended in was not elaborated: ~(pick (fun (x) 'fast))~, with a
~(-> bool Mode)~ parameter, was a type error, ~Mode~ against ~Symbol~. The body
is now checked against the expected result, as a ~defun~'s body is against its
declared one, so ~(fun (x) (if x 'fast 'safe))~ and ~(fun () '(a "b"))~ are
elaborated into the union the result names. An unsolved result expects nothing.

A body ending in a call to a .NET method returning void has ~System.Void~ for a
type, and a lambda with that result was emitted as an ~Action~. Passed to a
~(-> int void)~ parameter, which is a ~Func<int, Unit>~, it was C# error CS0126
when written inline and CS1503 when bound first. Such a lambda now returns the
unit, and so does a local function with no return type written. The one
exception is a lambda whose expected type comes from a .NET parameter that
really is an ~Action~. ~(twice (fun (n) (sb-length! sb n)))~ no longer needs a
~unit~ at the end.

Tested in ~259_lambda_results.bjo~.

* A keyword argument is checked against its parameter's type

~(f #:mode 'fast)~ was a type error, ~Mode~ against ~Symbol~, where
~(g 'fast)~ elaborated the literal into the ~Fast~ case. A keyword argument
was inferred on its own; it is now checked against the type the callee
declares for it, as a positional argument is. So a quoted symbol or list, and
an ~if~ or ~let~ ending in one, elaborates into the union the keyword names,
and a lambda passed by keyword has its parameter types before its body is
checked, so it can read a field that two record types share.

A top-level function's keyword *default* is checked against the keyword's
declared type the same way, so ~(defun (run #:mode 'safe) ...)~ works, as the
body is already checked against the declared result.

A lambda's *result* is checked too, by the entry above.

Tested in ~250_keyword_literals.bjo~.

* A type variable only keyword parameters mention is written out at the call

~(: f (-> (#:seed %a) %a))~, and a case analysis whose handlers are all
keywords, ~(: shape-case (-> Shape (#:else (-> Shape %r)) ... %r))~, compiled
and then failed in C# with CS0411. A generic keyword parameter is an ~Option~
in C#, reached through an implicit conversion that C# type inference does not
look through, and an omitted keyword is no argument at all. Such bindings are
now in ~TraitRegistry.KeywordOnlyGenerics~, and a call to one gets its type
arguments written out, as a call to a ~ReturnOnlyGenerics~ one does. The set
is separate because ~MustUse~ reads ~ReturnOnlyGenerics~ as "never returns".

For the same reason keyword arguments no longer switch off the guess that
writes type arguments for a call whose positional arguments are all lambdas:
~(f (fun (x) (+ x 1)) #:seed 41)~ gave C# nothing to infer from.

A keyword parameter named like a module-level function is a local inside the
function that declares it. ~AlphaRename~ does not rename keyword parameters,
their spelling being the calling convention, and ~(circle r)~ in a function
with a ~#:circle~ parameter was emitted as a call to the module's ~circle~.

Tested in ~251_keyword_only_generics.bjo~, across a module boundary through
~inc/kwgeneric.bjo~.

* A union case with a payload is written ~(: Case type ...)~

~(Union (Circle double) (Rect double double) Empty)~ is now
~(Union (: Circle double) (: Rect double double) Empty)~, the way a record
field is written. A parenthesized form in a type is then always a type
applied to arguments. A case that carries nothing is still its bare name, and
markers follow the types as before: ~(: FPipe (List Form) #:tag pipe #:rest)~,
~(: Asc #:tag asc)~.

The old spelling is an error that names the rewrite, and so is ~(Empty)~ for a
case that carries nothing. Published metadata writes cases the new way, so
its version is now 14 and every library has to be rebuilt.

~type/derive~ reads a case's payload up to its first marker, so a case with a
~#:tag~ no longer counts the tag's name as a payload type.

* A bare field name in a record pattern binds that field

~(Car brand year)~ is ~(Car (brand brand) (year year))~, and the two forms
mix: ~(Car brand (colour Red))~. So ~(def (Point x y) p)~ destructures a
struct. A bare name that is not a field is an error naming the fields there
are.

Left open: ~(loop (:for ...))~ still accepts only a name or a ~Tuple~.

* The prelude documentation covers the new file functions

~Docs/prelude.org~ describes ~file-info~ and ~FsInfo~, ~file-copy~ and its
default, the bytes and lines functions, ~file-move~'s ~MoveMode~,
~directory-walk~ with examples of ~#:into?~, ~filter~ and ~find~, and that
~directory-delete-tree~ removes a link to a directory rather than entering it.
The ~FS~ table has ~fs-info~ and ~fs-move~'s mode, and ~with-fake-fs~'s entry
the fake's clock and ~fake-fs-set-modified!~.

It also says in one place that the lazy ones never suspend: ~file-read/seq~,
~file-read-lines/seq~, ~directory-walk~, and ~(std ports)~' ~port->seq~ and
~file->seq~ are ~Seq~s, and a bjoroutine pulling from one parks its thread on
every pull; ~file-read-lines~ or ~port->chan~ is the way in a bjoroutine. The
examples were run.

* A lambda can be passed to a keyword parameter whose default is not a constant

~(directory-walk "." #:into? (fun (d) ...))~ was C# error CS1660. A keyword
parameter whose default C# cannot hold as a constant is an ~Option~ in C#, and
a value reaches it through the runtime's implicit conversion; a C# lambda has
no type until one is given, so there was nothing to convert from. A named
function worked, because it is emitted cast to its delegate type. A lambda
passed by keyword is now cast the same way, as one passed to ~Colour.Lift~
already was.

Tested in ~115_kwarg_const_defaults.bjo~ (a function-typed keyword defaulted,
given a named function, a lambda and a ~#(...)~ shorthand) and
~249_files.bjo~ (~#:into?~ given a lambda).

* ~directory-walk~ walks a tree, and ~directory-delete-tree~ no longer follows links

~(directory-walk dir #:into? pred)~ is the files under ~dir~, depth first, as
a lazy ~Seq~.

- Each directory's entries are taken in ordinal order, so a walk is the same
  on every OS and on a fake: a tool that hashes files in walk order gets the
  same hash everywhere.
- ~#:into?~ is asked about each directory before the walk goes into it:
  ~(directory-walk "." #:into? (fun (d) (not (= (path-filename d) (Some ".git")))))~.
- A directory that is a symbolic link is not entered, so a link back up the
  tree cannot loop the walk.
- Nothing is listed until the walk, and a walk that stops early lists nothing
  more: ~(find pred (directory-walk dir))~ stops at the first match. The
  handler installed where the sequence is walked is the one that answers.
- No glob patterns: ~(filter #(string-ends-with? & ".bjo") (directory-walk "src"))~
  asks the same question in the language.

~directory-delete-tree~ followed symbolic links to directories since it was
rebuilt from the ~FS~ operations, and so deleted what they pointed at: a link
to the home directory inside a build directory would have emptied the home
directory, and a link back up the tree never ended. A link to a directory is
now removed as a link and never entered, including when it is the path given.

Tested in ~249_files.bjo~: the walk's order, ~#:into?~, ~filter~ and an empty
directory on the fake and on the disk; on the fake, counting listings, that
making a walk lists nothing and stopping early lists only what was passed, and
that the handler at the walk answers; on the disk, a link back up the tree not
entered, and a tree holding a link out of it deleted without what the link
points at.

* Files can be copied, and read and written whole as bytes or as lines

- ~(file-copy from to #:mode CreateNew)~. The mode is how ~to~ is opened:
  ~CreateNew~, the default, fails if it exists, so a copy never loses a file by
  accident; ~Truncate~ replaces it; ~Append~ adds to it. The default differs
  from ~open-output-file~'s on purpose, and is ~File.Copy~'s. The source is
  opened first, so a missing one leaves ~to~ as it was. A copy onto its own
  path is refused before anything is opened, because opening the target would
  empty the source; the check is on the path's text, so two names for one
  file are not caught. A directory as the source fails. The copy is a new
  file, with a modified time of its own.
- ~(file-read-bytes path)~ → ~(Array byte)~, ~(file-write-bytes path bytes)~
  and ~(file-append-bytes path bytes)~.
- ~(file-read-lines path)~ → ~(Vec string)~ and ~(file-write-lines path
  lines)~. Writing puts ~"\n"~ after every line, the last one too, on every
  OS, so the same lines are the same bytes everywhere. Reading takes ~"\n"~
  and ~"\r\n"~, a last line with no line end, and makes no empty line after
  a final one, so what was written reads back unless a line held a line end
  of its own.

All of them open through the ~FS~ effect, so a fake answers for them, and
each has a suspending copy: in a bjoroutine a copy awaits the disk rather
than parking its thread.

The fake filesystem kept a written file as text when it was read back or
appended to, so bytes that are not UTF-8 came back changed: 256 bytes read
back as 515. It keeps bytes now.

Tested in ~249_files.bjo~: copies, bytes and lines on the fake and on the
disk, each run once through the ordinary copies and once more from a
bjoroutine through the suspending ones.

* ~file-move~ can replace a file

~(file-move from to #:mode MoveReplace)~ replaces a file at ~to~, in the one
rename that moves the new file there, so nothing ever sees ~to~ missing. That
is what writing a file safely is built from: write a temporary file, then move
it over the old one. ~MoveNew~, the default, fails when ~to~ exists, as
~file-move~ always has.

A directory is never replaced, and never replaces a file: ~MoveReplace~ onto a
directory, or of a directory onto a file, fails and changes nothing.

*Breaking.* The ~FS~ operation ~fs-move~ takes the ~MoveMode~ as a third
argument; a handler for it takes three.

Tested in ~249_files.bjo~, the same eleven checks on the fake and on the disk:
~MoveNew~ refusing, ~MoveReplace~ replacing, neither replacing a directory or
with one, a missing source failing even when replacing, and a move to a free
path.

* ~file-info~ says how big a file is and when it was written

~(file-info path)~ answers ~(Option FsInfo)~: the ~kind~ (~FsFile~ or
~FsDirectory~), the ~size~ in bytes (0 for a directory), the last write as
~modified-ms~, Unix milliseconds in UTC, and ~link?~. A script can now skip a
download that is still being written, or a build step an output that is newer
than its input.

- Milliseconds because ~(std datetime)~'s ~unix-milliseconds->instant~ takes
  them; the prelude cannot name an ~Instant~. Two writes in the same
  millisecond look equally old.
- A symbolic link's size and time are those of the file it leads to, which is
  what reading it reads, and ~link?~ says it is one. A link to nothing keeps
  its own.

*Breaking.* The ~FS~ operation ~fs-kind~ is gone. ~fs-info~ takes its place and
answers the whole record, so a handler cannot say a path is a file and forget
to say how big it is. A handler for ~fs-kind~ is now one for ~fs-info~;
~fake-fs-kind~ is ~fake-fs-info~.

The fake filesystem has a clock of its own. It starts at
2000-01-01T00:00:00Z, which is every seed's time; each write opened and each
directory created moves it one second on and stamps the path, so something
written later is always newer, however fast the test runs. A move keeps the
times it moves, as a rename does on a disk. ~(fake-fs-set-modified! fs path
ms)~ sets one by hand.

Tested in the new ~249_files.bjo~ (kind, size in bytes, times and the clock on
the fake; the same on the disk, a path that is no path, and a symbolic link
where the system allows one) and ~214_fake_filesystem.bjo~.

* Records and structs can be matched by field

~(match car ((Car (brand b) (colour Red)) ...))~ matches a record or struct by
naming its type and the fields to look at. Fields may be written in any order,
and a field left out matches anything. A bare ~Car~ matches every value of the
type. The fields are checked for exhaustiveness like a constructor's
arguments, and an ~#:opaque~ record can only be matched in the module that
declares it.

Left open: a field whose name is also a pattern macro, ~or~ or ~and~ is read
as that form, not as a field, since the parser does not know which names are
records. Punning, where ~(Car brand)~ binds the ~brand~ field to ~brand~, is not
supported.

* Everything that reaches the disk goes through the ~FS~ effect

~FS~ had two operations, ~open-input-file~ and ~open-output-file~, and
everything else went straight to .NET. Under ~with-fake-fs~ a program read the
fake and wrote the real disk: ~file-write-text~, ~file-append-text~,
~file-exists?~, ~file-delete~, the directory functions and ~(std ports)~' byte
openers all bypassed it.

~FS~ is now eight operations, and nothing in the prelude or ~(std ports)~
reaches the disk any other way:

- ~(open-read-stream path)~ and ~(open-write-stream path mode)~, answering
  ~(Result Exception Stream)~;
- ~(fs-kind path)~, answering ~(Option FsKind)~ — ~FsFile~ or ~FsDirectory~;
- ~fs-list~, ~fs-create-directory~, ~fs-delete-file~, ~fs-delete-directory~
  and ~fs-move~, answering a ~Result~.

Each has a ~/raw~ default that does what the .NET call does, so a program
that installs no handler behaves as before.

The openers answer a ~Stream~, not a port. ~open-input-file~,
~open-output-file~, ~open-byte-input-file~ and ~open-byte-output-file~ are
ordinary functions that build the port over it and register it on the ambient
scope. One handler therefore serves text and bytes, and a ~MemoryStream~ a
handler made is owned exactly as a file is. That was what ~#:adopt~ did for
the string ports the old handlers answered; ~FS~ no longer uses it, and
~adopt-input~ and ~adopt-output~ are gone.

An output file has a mode, ~WriteMode~: ~Truncate~, ~Append~ or ~CreateNew~.
~open-output-file~, ~call-with-output-file~ and ~open-byte-output-file~ take it
as ~#:mode~, defaulting to ~Truncate~, so existing calls are unchanged.
~CreateNew~ fails with an ~IOException~ when the file exists, in the same
system call that would create it.

Over the operations: ~file-write-text~ and ~file-append-text~ open, write,
flush and close a port, and so now have suspending copies — a bjoroutine that
writes a whole file awaits it, and the blocking lint no longer reports it.
Like ~file-read-text~ they now need an ambient scope. ~directory-delete-tree~
deletes one entry at a time, so a handler sees every deletion. ~file-move~ is
new.

*Breaking.* A handler installed for ~open-input-file~ or ~open-output-file~
has to be installed for ~open-read-stream~ or ~open-write-stream~ instead, and
answer a ~Stream~. ~fake-fs-reader~ and ~fake-fs-writer~ are now handlers for
those.

~with-fake-fs~ installs all eight. A seeded path is a file and every directory
above it exists; directories can be created, listed, emptied, deleted and
moved; a failure is the exception type the .NET call raises. ~with-fake-fs-of~
installs an existing ~FakeFs~, which replaces writing the ~with-handler~ out.

~file-read/seq~ and ~file-read-lines/seq~ were builtins, with bodies in the
runtime that opened the file by path. They are now ~(std prelude)~ functions: a
~seq~ that opens through ~open-input-file~ inside a ~with-open~, so each walk
opens the file afresh, a walk that stops early closes it, and ~file->seq~,
built on the first, reads a fake like everything else. The file is opened when
the sequence is walked, so the handler installed at the walk is the one that
answers. The builtins, their runtime bodies and their entries in the compiler's
blocking list are gone; the blocking lint still reports a bjoroutine that pulls
from one, since a ~seq~ body cannot await.

~stream->byte-input-port~ and
~stream->byte-output-port~ are deliberately outside the effect: a stream
somebody handed over is not a filesystem access.

Tested in ~214_fake_filesystem.bjo~: each mode faked and on the disk; the
whole-file functions, the byte openers, the lazy readers and the directory
functions under a fake; a lazy walk that stops early leaving the scope's list
as it was; a real move, listing and tree delete. The two warning tests that used
~file-write-text~ as their blocking leaf now use ~Thread.Sleep~. bjoweb's
~tests/html.bjo~ and ~tests/demo.bjo~ pass, and its two examples build.

* A value of a union is no longer wrapped in one of its own cases

Where a list, vector or array literal's element type is a union, an element
that is not a literal is wrapped in the one case whose payload could hold it.
A value that already had the union's type could be wrapped too, if a case's
payload was a bare type variable or the union itself:

#+BEGIN_SRC scheme
(type (: Tree (Union (Leaf int) (Wrap Tree))))
(list-map depth (list a b))   ;; two leaves: was '(0 1), now '(0 0)

(type (: (Opt %a) (Union Nothing (Just %a))))
(list-length (list (Just 7) (Just 8)))   ;; was a type error, now 2
#+END_SRC

The first was silent. Now a value whose type is already the union is an
element as it stands; to wrap one, write the case.

Tested in ~100_literal_elaboration.bjo~ (both unions, and a ~Wrap~ written by
hand staying as written). ~248_generic_materialization.bjo~ no longer works
around it.

* The documentation says where ~=~ and a ~Map~ can still disagree

~Docs/prelude.org~, "Writing one by hand", said a generic type's
implementation keeps C#'s members. It now says the implementation is compiled
in, with the undirected ~Edge~ as the example, and lists the three cases where
~=~ and a collection still part ways: a ~(where ...)~ of a trait other than
~Eq~ and ~Ord~, a specialized target such as ~(impl (Eq (Pair %a %a)))~, and
two different cases of a union, with ~(Cents 100)~ and ~(Dollars 1)~ as the
example and normalizing as the way out. "~type/derive~" says a derived generic
type is a ~Map~ and an ~OrderedMap~ key. The comments in ~Codegen.fs~ and
~128_derive.bjo~ that said otherwise are rewritten.

* A generic type's ~Ord~ is what ~OrderedMap~ and ~OrderedSet~ order by

~OrderedMap~ and ~OrderedSet~ compare keys through ~IComparable<T>~, which C#
never writes. A generic type's ~Ord~, derived or written by hand, was not
compiled into it, so ~(type/derive (Eq Ord) (: (Pair %a) ...))~ as an
~OrderedMap~ key compiled and crashed at the first comparison: "At least one
object must implement IComparable".

Now it is compiled in as a generic ~Eq~ is: the type implements
~IComparable<T>~, and its ~CompareTo~ calls the implementation, built once per
closed type from a stand-in that compares ~T~ through its own ~CompareTo~ —
and a string ordinally, as ~(Ord string)~ and the ordered collections do, so
~(Pair "B" ...)~ comes before ~(Pair "a" ...)~ in both ~compare~ and an
~OrderedSet~, where the machine's culture would put it after.

It costs nothing measurable: adding 100 000 shuffled keys to an ~OrderedSet~
takes 757 ns per key for a derived ~(Pair int)~ and 753 ns for the same
record written without a type parameter.

Tested in ~248_generic_materialization.bjo~ (a derived ~(Pair %a)~ in an
~OrderedMap~ and an ~OrderedSet~; strings inside it; a hand-written ~Ord~ on
~(Job %a)~ that ignores the label, in both collections and agreeing with
~list-sort~; a generic union), and in the codegen test ~materialization.bjo~
(a generic record, record struct and union base).

* A generic type's ~Eq~ is what ~Map~ and ~Set~ key on

~Map~ and ~Set~ are .NET collections: they never call ~=~, only the key
type's ~Equals~ and ~GetHashCode~. The compiler writes a declared type's ~Eq~
into those two members, but it skipped a generic type's, because that
implementation is conditional, ~(where (Eq %a))~, and nothing inside
~Edge<T>.Equals~ is handed the ~Eq~ of ~T~. So an undirected ~(Edge %a)~,
whose ~=~ says (1 2) is (2 1), made a set of both with 2 elements and a map
that missed the lookup.

Now the type builds that dictionary itself, once per closed type, in a static
field: from a stand-in that answers through ~T~'s own ~Equals~ and
~GetHashCode~, which is what ~T~'s ~Eq~ is for every type (compiled in for a
declared type, native for a primitive, and a delegation to those members for
what ~lib/std~ implements). This holds when every ~where~ is ~Eq~ or ~Ord~ on
one of the type's own parameters. A ~(where (->str %a))~ has nothing .NET
could answer it with, so such an implementation keeps C#'s field-wise
members, as before.

- A derived ~Eq~ on a generic type means what it did, field by field, but its
  hash is now the derived ~eq-hash~, as a non-generic type's already was.
- A generic record with a mutable field and a derived ~Eq~ still cannot be a
  key: the refusal now comes from the derived ~eq-hash~.
- ~(Deque %a)~: its ~Equals~ is now its ~=~, the same elements in the same
  order. Before, it compared the ~front~ and ~back~ lists, so two equal deques
  split differently were unequal to .NET. It is still not a key.
- Two *different* cases of a union that ~=~ equates, such as ~(Cents 100)~
  and ~(Dollars 1)~, are still two keys: C# writes each case's ~Equals~
  itself, and it answers false for another case before any implementation
  runs. Pinned by a test.

The hash changes speed where keys are small consecutive numbers. C#'s hash
of a record is a straight line in its fields, which fills the map's tree
perfectly for 0, 1, 2, ...; ~hash-combine~ scatters it. Nanoseconds per
element, on one machine:

| Keys, ~type/derive (Eq)~                                  | Before | After |
|-----------------------------------------------------------+--------+-------|
| ~map-set~ and ~map-try-ref~ of 100 000 ~(Pair int)~, 0..n | 288    | 401   |
| the same, a ~Struct~                                      | 240    | 310   |
| ~list->set~ of 1 000 000 ~(Pair int)~, shuffled 0..n      | 144    | 154   |
| the same, a ~Struct~                                      | 72     | 90    |
| ~map-set~ and ~map-try-ref~, random ints                  | 397    | 393   |
| ~list->set~, random ints                                  | 111    | 105   |
| a non-generic derived record, 0..n, unchanged             | 411    | 381   |

Tested in ~248_generic_materialization.bjo~ (an edge in a ~Set~ and a ~Map~,
as a record, a record struct and a union's same-case values; nested in a
derived ~Pair~; derived ~Eq~ unchanged; the ~->str~ exception; a mutable
generic record; the deque; the union rule), and in the codegen tests
~materialization.bjo~ (a generic record, record struct and union, the
stand-in's parameter for a ~where~ on the second variable, the ~->str~
exception) and ~mutable_fields.bjo~ (the generic ~Box~ now hashes through its
implementation; the direct throw moves to the ~->str~ case).

* ~(std datetime)~ reads back what it writes, and allocates nothing doing it

What a writer writes with a format that can be read, the reader of the same
type reads back with that format: the value, or what the format keeps of it,
such as the minute when it has no seconds. ~245_datetime.bjo~ checks this for
3000 seeded values in each of 23 formats, 69 000 round trips over every type,
across the whole range and in Stockholm, New York, Kathmandu (+05:45) and
Chatham (+12:45).

Outside the tests, a mutation run wrote random values with 32 formats,
changed each text at random (a character replaced, inserted, deleted, swapped
with the next, or the rest cut off, with digits, signs, letters and a
character outside the BMP), and fed 160 370 texts to every reader with every
format: 5 933 690 calls, 77 194 answered ~Some~, 5 856 496 ~None~, none
raised, and every value answered came back when written and read again.

Reading measured 1219 ns for an RFC 3339 instant at first. The fields read
are kept in a struct, which held a reference, the zone, so .NET cleared every
copy of it a function might make on each call: 5.6 KB of stack each time a
field was stored. The zone is now kept as the span of text its id was read
from and looked up once at the end, so the struct holds no reference. Per
call, on one machine:

| Operation                                  | Time    | Allocated |
|--------------------------------------------+---------+-----------|
| ~iso8601->instant~                         | 51 ns   | 0 B       |
| ~text->instant~, RFC 3339 with a fraction  | 591 ns  | 0 B       |
| ~iso8601->date~                            | 27 ns   | 0 B       |
| ~text->date~, ~(year 4) "-" (month 2) ...~ | 252 ns  | 0 B       |
| ~text->date~, with names                   | 432 ns  | 0 B       |
| ~iso8601->moment~                          | 211 ns  | 56 B      |
| ~text->moment~, with offset and zone       | 951 ns  | 56 B      |
| ~->str~ of an instant                      | 86 ns   | 192 B     |
| ~instant->text~, RFC 3339                  | 188 ns  | 232 B     |

A reader walks its format part by part and checks it on every call, about a
third of the time, so the ISO 8601 readers stay the fast path.

Tested in ~245_datetime.bjo~ (23 round-trip checks, and a zone read twice).

* ~(std datetime)~ reads instants and moments with formats of your own

~(text->instant s format)~, ~(text->moment s format)~ and
~(text->moment/resolver s format resolver)~ read what ~instant->text~ and
~moment->text~ write, so every writer now has a reader.

- An instant is its ~unix~ or ~unix-ms~ time, or a date and a time, which are
  UTC's unless the format has an ~offset~. That is the writer's own rule, so
  ~'((year 4) "-" (month 2) "-" (day 2) "T" (hours 2) ":" (minutes 2) ":"
  (seconds 2) offset)~ reads RFC 3339 both with ~Z~ and with an offset.
- A moment needs a ~zone~ in its format, and a zone is never guessed: a text
  with an offset and no zone is read as an instant and put in a zone with
  ~instant->moment~. An offset read beside the zone has to be one the zone
  has then, so both offsets of Stockholm's 2026-10-25 02:30 read and a July
  +01:00 does not. Without an offset, a gap or an overlap is ~None~, and
  ~text->moment/resolver~ resolves it as ~datetime->moment~ does, but answers
  ~None~ where that raises, at the ends of the range.
- ~unix~ reads an optional minus and up to 12 digits, ~unix-ms~ up to 15, and
  outside the years 1 to 9999 either is ~None~. ~offset~ reads ~Z~ or
  ±hh:mm with optional seconds, and ~zone~ the longest run of an IANA id's
  characters, looked up with ~timezone~.

A moment's format without ~zone~, and a Unix time beside any other field of
the instant but a moment's zone, raise an ~ArgumentException~ when used to
read: ~'(unix " " zone)~ reads, ~'(unix " " (year 4))~ does not. ~zone~,
~unix~ and ~offset~ join the parts that can be of more than one length, so
~'(zone unix)~ is refused as a text that reads two ways.

Tested in ~245_datetime.bjo~ (34 checks: RFC 3339 with ~Z~, an offset and
offset seconds, UTC without an offset, Unix time at both ends of the range
and one past each end in seconds and milliseconds, both offsets of the
overlap and an offset Stockholm does not have, the overlap and the gap
without an offset and resolved, a zone the machine does not know, a Unix
time placed in a zone, the ends of the range in New York and Stockholm, a
moment written and read back, and each refused format).

* ~(std datetime)~ reads times and datetimes with formats of your own

~(text->time s format)~ and ~(text->datetime s format)~ read what
~time->text~ and ~datetime->text~ write, with the rules ~text->date~ has.

A time is ~hours~, or ~hours12~ with ~am-pm~, where 12 AM is the hour 00 and
12 PM the hour 12; minutes, seconds and the fraction left out are 0, and a
datetime without any time field is midnight. ~(fraction n)~ reads exactly
~n~ digits, dropping those past the seventh, and a bare ~fraction~ reads
ISO 8601's: nothing, or a point or a comma and at least one digit. ~am-pm~ is
matched exactly, as names are, and has to agree with ~hours~ beside it.

A time's format without hours, a datetime's with minutes, seconds, a
fraction or ~am-pm~ but no hours, and ~hours12~ without ~am-pm~ raise an
~ArgumentException~ when used to read. A bare fraction can be of more than
one length, so a digit, a point or a comma after it is refused as a text
that reads two ways.

Tested in ~245_datetime.bjo~ (31 checks: no 24:00 and no leap second, the
twelve-hour clock at 12 AM, 12 PM, 0 and 13, ~am-pm~'s case and Swedish
words, ~am-pm~ against ~hours~, both kinds of fraction, two fractions that
agree and disagree, a datetime with and without its time, and each refused
format).

* ~(std datetime)~ reads dates with formats of your own

~(text->date s format)~ reads a text with the format ~date->text~ wrote it
with, and answers an ~(Option Date)~; it takes ~#:names~ as the writers do.

#+BEGIN_SRC scheme
(text->date "Sunday, 25 October 2026" '(weekday-name ", " day " " month-name " " year))
(text->date "2026-W43" '((week-year 4) "-W" (week 2)))    ;; 2026-10-19, the Monday
#+END_SRC

Numbers are ASCII digits, from their width (or one) up to their most digits,
read greedily. Names match exactly, case included, the longest when two do.
Roman numerals are read only as they are written, so ~MDCCCC~ is not 1900.
The date is made from year, month and day, from year and ~yday~, or from
~week-year~, ~week~ and ~weekday~, and a field left out is its first value,
which reads HTML's month and week inputs. Every other field read has to be
the date's own: a wrong weekday name is ~None~. Text that does not fit is
~None~, never an exception.

A format that cannot be read raises an ~ArgumentException~ when used to
read, whatever the text: a date without a year; month, day or ~yday~ with
~week-year~ in place of ~year~, or ~week~ with ~year~ in place of
~week-year~, since ~'((year 4) "-W" (week 2))~ would read ~2026-W01~ as
January 1, a Thursday; and a part of more than one length followed by a part
that can begin with a character it could take, as in ~'(year month day)~,
where ~2026111~ is January 11 and November 1 both.

Tested in ~245_datetime.bjo~ (53 checks: widths and none, ASCII digits only,
the whole text, names in English and Swedish, the longest name, Roman years
and a numeral in another form, a Roman and a numeric year that agree and
disagree, ordinal and week dates, HTML's month and week inputs, fields
checked against the date, and each refused format).

* ~(std datetime)~ writes Unix time and instants with formats of your own

~(->unix x)~ is the Unix time in seconds of an instant or a moment, as a
~long~, rounded toward the past as ~instant->unix-seconds~ rounds: half a
second before 1970 is -1. The four functions that were there keep their
names.

A moment's format has two more fields, ~unix~ and ~unix-ms~, rounded the same
way. An instant has a format of its own, ~InstantPart~: the fields of a
~DateTimePart~, ~offset~, ~unix~ and ~unix-ms~. ~(instant->text i format)~
writes the date and time in UTC, and the offset as ~Z~, so the format
~'((year 4) "-" (month 2) "-" (day 2) "T" (hours 2) ":" (minutes 2) ":"
(seconds 2) offset)~ writes what ~->str~ writes for a whole second. Writing
an instant's time of day used to mean ~(datetime->text (instant->utc-datetime
i) ...)~, which could not write the ~Z~.

Tested in ~245_datetime.bjo~ (~->unix~ at the epoch, half a second before it,
the first and the last second of the range, on an instant and on a moment;
~unix~ and ~unix-ms~ written for both, negative ones included; an instant
written as ~->str~ writes it) and in ~errors/datetime_text_zone_in_instant.bjo~.

* ~(std datetime)~ writes formats of your own, Roman years included

A format is a quoted list of field names, strings and characters, which the
language's tagged literals elaborate into one union per kind of value:

#+BEGIN_SRC scheme
(date->text d '(weekday-name ", " day " " month-name " " (roman year)))
;; Sunday, 25 October MMXXVI
#+END_SRC

~date->text~, ~time->text~, ~datetime->text~ and ~moment->text~ take a
~Date~, ~Time~, ~DateTime~ and ~Moment~. A number after a field is a width
filled with zeros. The fields are the date's numbers (~year~ to
~week-year~), ~(roman year)~, ~(roman month)~ and ~(roman day)~, month and
weekday names and abbreviations, the hours on a 24- or 12-hour clock with
~am-pm~, minutes, seconds, ~(fraction n)~ digits, and a moment's ~offset~ and
~zone~, which also writes RFC 3339's ~2026-10-25T02:30:00+01:00~. Names come
from ~#:names~ or the parameter ~current-date-names~: ~english-names~,
~swedish-names~, or a ~DateNames~ of your own. Roman numerals go on adding
~M~ past ~MMMCMXCIX~, so 4000 is ~MMMM~.

A field a value does not have (~hours~ in a date's format, ~offset~ in a
datetime's), a misspelled field, or a width on a numeral is a compile error
naming the fields there are. Two widths on one field, or a names table
without twelve months or seven weekdays, raises an ~ArgumentException~ when
it is used. Formats are written, not read.

Tested in ~245_datetime.bjo~ (33 checks, from widths and names through
Roman years from I to 9999, week dates, the twelve-hour clock, fractions, and
both offsets of an overlap) and in ~errors/datetime_text_hours_in_date.bjo~,
~errors/datetime_text_offset_in_datetime.bjo~ and
~errors/datetime_text_roman_width.bjo~.

* A definition takes its name over from a ~defbjouble~, in a bjoroutine too

Which names have a suspending copy, and which park a thread, was decided by
name alone. A module that defined its own ~read-all~, or imported a plain
~read-line~ from another module, still had the prelude's entries for those
names, so:

- a bjoroutine's call to it was pointed at the prelude's ~read-all__bjo~,
  and the C# compile failed;
- so did the call inside the suspending copy a ~defun~ was given for calling
  it, which is how it first showed: a ~void~ function called as a statement;
- a bare reference to it, passed on in a bjoroutine, was the prelude's copy
  too;
- a library that exported its own ~read-all~ published it as a pair, so its
  importers failed the same way;
- the blocking lint said a bjoroutine calling it parked its thread.

A module's own definitions now drop the imports' entries for their names, as
they already dropped the import-table entries, and a module's own
~defbjouble~ keeps its pair. An imported claim holds only while the name ends
up bound to the definition the claim is about, so an import that takes a name
over from the prelude takes it over here as well. The imported pairs are no
longer joined into the registry a second time after inference, which put
back what the module had taken over.

Tested in ~247_own_def_over_defbjouble.bjo~ and
~warnings/own_def_over_blocking.bjo~, both of which fail the C# compile
without the fix.

* ~(std datetime)~ reads text without allocating, and writes it into one buffer

The readers turned their input into a list of characters, one cell per
character, and the writers joined a dozen small strings per value. Reading an
instant cost 640 bytes and writing one 1288.

The readers walk the string with a ~StringCursor~, and answer through
~Option~ and ~Tuple~, which are structs, so they allocate nothing but a
moment's zone id. The writers append digits one at a time into a single .NET
~StringBuilder~ sized for the text. Measured on one machine, per call:

| Operation            | Before          | After         |
|----------------------+-----------------+---------------|
| ~iso8601->instant~   | 165 ns, 640 B   | 51 ns, 0 B    |
| ~http-date->instant~ | 475 ns, 1824 B  | 124 ns, 0 B   |
| ~->str~ of an Instant | 231 ns, 1288 B | 87 ns, 192 B  |
| ~->str~ of a Moment  | 371 ns, 1736 B  | 155 ns, 296 B |

What is read and written did not change: a program that prints random values
of every type, reads them back, and runs every reader on edge cases and on
random mutations of those texts printed the same 108 670 lines before and
after. ~245_datetime.bjo~ adds a character outside the BMP, the longest
period, and a zone id longer than the builder's first guess.

* A system clock can be in a zone of its own: ~system-clock-in~

~system-clock~ is always in the machine's zone, and no other clock read the
real time, so on a machine set to UTC, as most containers are, ~(today)~ was
UTC's date unless every call remembered ~#:tz~: in Stockholm, yesterday's
until 01:00, or 02:00 in summer. ~(system-clock-in zone)~ reads the same time
in ~zone~, and a program binds ~current-clock~ to it once around everything it
runs. It cannot be advanced, like ~system-clock~.

The documentation no longer shows ~(option-value (timezone ...) utc)~, which
falls back to UTC without a word on exactly the machines that lack zone data,
and says to stop there instead.

Tested in ~245_datetime.bjo~: the clock's zone, the zone of ~now/moment~, a
binding of ~current-clock~ carrying it, its reading lying between two of the
system clock's, and ~clock-advance!~ refusing it.

* Elapsed time is measured between instants only

~hours-between~ and the other exact differences took two values of one
~Timeline~ type, and on two ~DateTime~ values they answered the wall-clock
difference: 2026-10-25 00:00 to 2026-10-26 00:00 was 24 hours, where 25
passed in Stockholm. Stored local times look like timestamps, so the answer
was easy to take for the time that passed, and code generic over ~Timeline~
could not tell which it had.

The ~Timeline~ trait is gone. ~duration-between~, ~hours-between~,
~minutes-between~, ~seconds-between~ and ~milliseconds-between~ take any two
~HasInstant~ values, so a moment and an instant now mix, and two ~DateTime~
values are a compile error. The wall-clock difference is still there, written
as a reading in UTC: ~(hours-between (utc-datetime->instant a)
(utc-datetime->instant b))~.

Tested in ~245_datetime.bjo~ (25 hours between Stockholm moments, a moment
against an instant, and 24 on the wall clock read as UTC) and in
~errors/datetime_hours_between_datetimes.bjo~.

* Calendar differences between moments read both in one zone

~days-between~ and the other calendar differences read each argument's own
local date, so one instant as a New York moment and as a Tokyo moment was a
day apart from itself: 2026-10-25T20:00Z is the 25th in one and the 26th in
the other. The second argument is now read in the first one's zone, as
java.time does, through a new trait ~DateDiff~ on ~Date~, ~DateTime~ and
~Moment~. Across zones, swapping the arguments swaps the zone too.

The two arguments now have one type. ~(days-between some-date some-moment)~
compiled and read the moment's local date without saying so; it is a type
error, and ~(days-between some-date (->date some-moment))~ says it.

Tested in ~245_datetime.bjo~ (one instant in New York and Tokyo is 0 days
apart either way round, and a ~months-between~ that reads New York's
2026-02-28 rather than Tokyo's 2026-03-01) and in
~errors/datetime_days_between_date_and_moment.bjo~.

* ~(std datetime)~ has ISO week numbers

~(->week x)~ is the ISO 8601 week, 1 to 53, of anything with a date, and
~(->week-year x)~ the year that week belongs to: the year its Thursday is in,
which differs from ~->year~ in up to three days at either end of a year
(2027-01-01 is in week 53 of 2026). ~(weeks-in-year y)~ is 52 or 53, and
~(week-date y w d)~ is the date of day ~d~, Monday being 1, of week ~w~, or
~None~ for a week the year does not have. Day 6 of the last week of 9999 is
10000-01-01, outside the range, so it is ~None~ too; ~weeks-in-year~ raises
outside the years 1 to 9999.

The week text of ISO 8601, ~2026-W43-7~, is still neither written nor read.

Tested in ~245_datetime.bjo~: known weeks on both sides of a new year, 71
years of 53 weeks in a 400-year cycle, the two ends of the range, and every
day of a 400-year cycle and of the range's first and last ten years agreeing
with .NET's ~System.Globalization.ISOWeek~ and coming back from ~week-date~.

* ~(std datetime)~ numbers weekdays as ISO 8601: ~->weekday~, Monday 1 to Sunday 7

~->wday~ counted from Sunday as 0, as C and .NET do, while everything else in
the module follows ISO 8601, where the week starts on Monday and Sunday is 7.
It is replaced by ~->weekday~, which counts the ISO way; ~(% (->weekday d) 7)~
gives the old numbering. The new name is on purpose: under the old one, a
check such as ~(= (->wday d) 0)~ would still compile and would never be true,
while now it fails to compile. The HTTP date code uses the same numbering.

Tested in ~245_datetime.bjo~: a Sunday is 7 and a Monday 1, 0001-01-01 was a
Monday and 9999-12-31 a Friday, a moment's weekday is its local one (the first
moment of Samoa's 2011-12-31 is a Saturday there and a Friday in UTC), and a
week of HTTP dates carries the day names Mon to Sun.

* Every duration can be negated, printed and read back

A ~Duration~ built by ~duration~ or read by ~iso8601->duration~ stayed within
±(2^63 − 1) ticks, but adding two was ~TimeSpan.Add~, which goes one tick
further to −2^63: the one ~TimeSpan~ with no negation. A sum could land there,
and then ~->str~ raised ("Negating the minimum value of a twos complement
number is invalid"), inside a ~Period~ too, and so did ~duration-negate~ and
~-duration~.

~+duration~ on two durations checks the sum against ±(2^63 − 1) and raises the
module's own ~OverflowException~ at either end, so no duration reaches −2^63.
It is ~duration+duration~, exported beside the other trait methods at one type
because the impl's copied body calls it. Tested in ~245_datetime.bjo~: the
longest and shortest durations print and read back, and one tick past either
raises.

* ~(std clr-ord)~ no longer names the .NET time types

~(std clr-ord)~ exported the names ~DateTime~, ~DateTimeOffset~, ~TimeSpan~,
~DateOnly~ and ~TimeOnly~ for the .NET types it orders. ~(std datetime)~ exports
a ~DateTime~ of its own, so in a module importing both, the later import
decided what a bare ~DateTime~ meant, and a signature written for one type
met the other as "these types do not match".

It exports ~Guid~ and ~Version~ only. The five time types keep their ~Ord~
implementations, which apply whatever the type is called; code that names the
.NET type writes ~System.DateTime~ or declares an alias of its own. Tested in
~246_clr_ord_with_datetime.bjo~, which fails against the old export list.

* A manual clock counts every advance

~clock-advance!~ read the manual clock's instant and wrote it back with nothing
between two threads doing the same, so steps were lost: eight threads
advancing one clock 10 000 ms each ended between 27 and 42 seconds in rather
than at 80. A ~now~ on another thread had no promise of seeing an advance
either. The clock now holds a ~System.Threading.Lock~ and takes it to advance
and to answer ~now~, so every advance counts and the next ~now~ sees it.
Tested in ~245_datetime.bjo~ with those eight threads.

Also in ~(std datetime)~, from a review of the first version:

- *Changes of a whole day are tested.* Samoa skipped 2011-12-30 and it is a
  gap; Alaska had 1867-10-18 twice and it is an overlap. The offset search
  finds a jump of any size, as long as every offset is under a day.
- *Time-of-day arithmetic is documented as modulo 24 hours*, with tests: whole
  days drop out, so 12:00 plus 3 days and 2 hours is 14:00, and 01:00 minus 3
  hours is 22:00.
- *A ~Duration~ is described as a fixed length of time.* Between two
  ~DateTime~ values it is the difference on the local clock, which is the time
  that passed only when no change of offset lies between them.
- *Two more limits are documented.* .NET caps offsets at ±14:00, so nine zones
  before 1845 or 1867 (Alaska, Manila, Guam, Saipan, Palau) are off by up to
  two hours; and on Windows, IANA ids map onto Windows' own zone data, which
  keeps little history.

* ~(std datetime)~ reads its clock from ~current-clock~

The functions that read the time took the clock as an argument, ~(now clock)~,
so every function between ~main~ and a timestamp had to pass one along, and a
test could only fix the time for code that took a clock.

- *~#:clock~, defaulting to ~current-clock~.* ~now~, ~now/moment~, ~today~ and
  ~clock-timezone~ take ~#:clock~, which defaults to the parameter
  ~current-clock~ read at that call. The parameter starts as ~system-clock~, so
  ~(now)~ is the time, and ~(parameterize ((current-clock c)) ...)~ fixes it for
  everything inside that names no clock of its own.
- *The zone travels with the clock.* ~now/moment~ and ~today~ take ~#:tz~,
  defaulting to the clock's zone, in place of ~now/zone~ and ~today/zone~.
  There is no current-zone parameter, so a fixed clock fixes ~today~ too,
  wherever the test runs.
- *A manual clock for tests.* ~(manual-clock instant zone)~ stands still until
  ~(clock-advance! clock duration)~ moves it, backwards too for a negative
  duration. Advancing the system clock or a fixed one raises an
  ~ArgumentException~.

Everything else is pure, as before. A program written against the first
version replaces ~(now clock)~ with ~(now #:clock clock)~ or ~(now)~, and
~(now/zone clock z)~ with ~(now/moment #:clock clock #:tz z)~. Tested in
~245_datetime.bjo~.

* The prelude's clock effect is ~monotonic-ms~

The prelude's ~Clock~ effect had one operation, ~(now)~: milliseconds on a
monotonic clock from an unspecified start, which ~(std stopwatch)~ measures
with. ~(std datetime)~ also has a ~now~, ~(now clock)~, which answers an
~Instant~ on the wall clock. So ~(now)~ meant a count of milliseconds in one
module and ~(now clock)~ a point in time in the next, and importing
~(std datetime)~ hid the prelude's ~now~.

The effect is ~MonotonicClock~ and its operation ~(monotonic-ms)~, with the
same default, and a test installs a fake as ~(with-handler ((monotonic-ms
...)) ...)~. Only the name changed: the two clocks stay apart, because the wall
clock can step backwards when the machine's time is corrected, and a stopwatch
reading it could then report a negative elapsed time.

A program that performed ~(now)~ or installed a handler for it has to use the
new name. ~210_prelude_effects.bjo~ does so; ~243_imported_def_shadow.bjo~ now
shadows ~getenv~ where it shadowed ~now~, so that it still takes a name over
from the prelude.

* ~(std datetime)~: dates, times, instants and zones

One model for time in place of the .NET types imported one by one: ~Date~,
~Time~, ~DateTime~, ~Instant~, ~TimeZone~, ~Moment~ (a local time with its
offset and zone), ~Duration~, ~DatePeriod~, ~Period~ and ~Clock~. The model is
the one java.time, NodaTime and Racket's Gregor share. See
~Docs/std/datetime.org~.

- *The types refuse what means nothing.* Six one-method traits (~HasDate~,
  ~HasTime~, ~HasInstant~, ~DateArith~, ~TimeArith~, ~Timeline~) decide what
  each type can do, so ~(+days some-instant 1)~ and ~(+hours some-date 2)~ are
  compile errors: a day on an instant needs a zone, and a date has no hours.
- *Every value was checked.* The value types are opaque single-field structs
  over ~DateOnly~, ~TimeOnly~, ~DateTime~, a ~long~ of UTC ticks, ~TimeZoneInfo~
  and ~TimeSpan~, and cost what those cost. A moment's offset is always one its
  zone has at that time. No .NET time type is in a public signature.
- *Gaps and overlaps are the caller's choice.* ~datetime->moment~ takes a
  resolver (~GapPush~ or ~GapNextValid~, ~OverlapEarlier~ or ~OverlapLater~),
  and ~datetime->moment/opt~ refuses both. A local time finds its offsets from
  ~GetUtcOffset~ on instants alone, since .NET's ~IsInvalidTime~ misses the gap
  a change of standard time leaves (Brussels, 1914-11-08).
- *The clock is an argument.* ~now~, ~today~, ~now/zone~ and ~today/zone~ take
  a ~Clock~, ~system-clock~ or ~(fixed-clock instant zone)~, and nothing else
  reads the time. Importing the module hides the prelude's ~(now)~ there.
- *Nothing leaves the range quietly.* Every value lies in the years 1 to 9999.
  A result outside raises an ~OverflowException~, or is ~None~ from a
  constructor, a reader or an ~/opt~ function, and the checks come before any
  arithmetic that could wrap. The lookups a day either side of a local time are
  clamped to the range, since 0001-01-01 minus a day is not a ~DateTime~.
- *ISO 8601 both ways*, and IMF-fixdate for HTTP, written and read digit by
  digit with no culture involved.

Tested in ~245_datetime.bjo~, which covers the required Stockholm cases and the
edges of the range and prints a ~FAILURE~ naming the tz database when the
machine has none, and in ~errors/datetime_days_on_instant.bjo~ and
~errors/datetime_hours_on_date.bjo~.

* A call to a constrained function with no implementation is one error

A call such as ~(double-area 3)~, where ~double-area~ requires ~(Shape %a)~ and
~int~ has no ~Shape~, is an error that dictionary lowering reports at the call.
The specialiser ran first and made a copy of ~double-area~ at ~int~, and the
copy's check failed on the same missing implementation. So the one mistake was
reported twice, first as a warning at the callee's definition, which for an
imported function is ~lib.dll:1~.

~Monomorphise~ now asks for no copy of an instantiation where a constraint, or
a constraint of the implementation that would discharge it, has no
implementation. Tested in ~errors/constraint_without_impl_no_copy.bjo~.

* A library's bodies may use its ~#:opaque~ types where they land

A body a library publishes is checked again in the module that uses it: an
impl's inline template where it is spliced, a constrained generic where a copy
is specialised, a macro template where it expands. When that body built, read
or matched one of the library's own ~#:opaque~ types, the check failed, because
opacity was the importer never seeing the representation at all:

- a specialised copy that read a field crashed the compiler ("Poisoned") after
  reporting a type error at ~lib.dll:1~, a line nobody wrote;
- an inlined impl that built one fell back to a call, with a warning at every
  use site in the importing module.

So a library had to route every use of its own representation through small
helper functions to keep its generic code specialisable.

- *Opacity is decided by whose code it is.* Every range now carries the key of
  the module whose code it is (~Lexer.Range.Module~): the module's own forms,
  the files it includes, a published body's module when an importer reads it
  back, and a macro's module for what its template wrote, while the pieces
  written at the call site keep theirs. Construction, field access, patterns,
  exhaustiveness and literal elaboration ask whether that module may see the
  representation. A piece of the call site inside a macro expansion is
  therefore refused, although it lands inside code that is allowed.
- *The representation is published.* An ~#:opaque~ type is published whole,
  ~#:opaque~ included, and registered in every importer like any other.
  Each type carries an access scope, the code that may use it. Today that is
  always the declaring module. It is stored rather than assumed, so that a type
  can later name more of its code, such as a companion module or a package.
- *A published body keeps who wrote what.* A part of it another module wrote,
  such as a macro's expansion, is marked ~(%origin "module-key" ...)~, so that
  it keeps that module's access where the body is read back.
- *A failed copy falls back again.* Checking a specialised copy used to report
  its errors as the program's and poison its name, so the specialiser's own
  fallback to the dictionary call never ran. The check is now all or nothing
  (~Diagnostics.speculate~): a copy that does not check is dropped with a
  warning, and the call keeps its dictionary.
- *Published field types are resolved.* A record field or union payload is
  published as the type it resolves to, as a signature is. Written as source had
  it, a field of an ~import/class~ alias type that the library does not export
  meant nothing in the importer, so an inlined body that built one failed there.

The metadata version is 13; everything built against an older one has to be
rebuilt. The error messages for a refused use name the type, the module that
may use it, and say what was refused rather than calling the name unbound.
Tested in ~244_opaque_bodies.bjo~, ~codegen/opaque_bodies.bjo~,
~warnings/opaque_bodies_splice.bjo~ and ~errors/opaque_macro_argument.bjo~.

* An imported definition takes its name over from the prelude

An import shadows a name the prelude also exports, and inference always agreed.
Code generation did not. A module that defined its own ~list-append~ still had
the prelude's entry for that name in its import table, so its metadata said the
definition lived in the prelude. An importer's call was then emitted as
~prelude_Module.listsubappend~: at the prelude's own type it compiled and ran
the prelude's function, and at any other type the C# compile failed. A module
exporting ~now~ could not be used at all, since the prelude's ~Clock~ effect
exports one too.

- *A module's own definition drops the import's entry* for that name before the
  module is checked, so the metadata publishes no foreign origin for it. The
  same stale entry made an ~(:alias ...)~ of the name, and the blocking lint,
  look at the import instead of the definition.
- *A name that more than one module binds is always qualified* in the generated
  C#, to the module inference chose. Each module is a ~using static~, so a bare
  call reached all of them: two imports of one name at one type were a CS0121
  ambiguity rather than the later import winning, as MODULES.org says it does.

Tested in ~243_imported_def_shadow.bjo~.

* A call handed to a waiting receiver is taken

A ~Call~ made with a token (~inbox-call/token~, ~inbox-try-call/token~) is
either still queued or taken, and the token does different things to each: a
queued call is cancelled, and a taken one is left pending while
~call-abandoned~ fires for the receiver. A call was marked taken only when a
receive took it from the queue. A call that found a receiver already waiting
was handed straight over and never marked. When its token fired, the call was
cancelled as though still queued, under a receiver that was answering it, and
~call-abandoned~ never fired.

In a web server the idle workers are all waiting, so this was the usual path.
A client that went away mid-request made Kestrel finish the request and recycle
its ~HttpContext~ while the handler could still be using it. The handler never
heard that the client had gone.

~inbox-post!~ and ~inbox-send~ now mark a call taken before handing it to a
waiting receiver, and mark it queued again when that receiver's ~choose~ was
won elsewhere, as a receive from the queue does. A call whose token fired
before it could be handed over is not handed over. Tested in
~229_inbox_calls.bjo~.

* ~utf8~ writes no byte order mark

~utf8~ in ~(std ports)~ was ~System.Text.Encoding.UTF8~, which starts every
text port over bytes with a byte order mark: ~(write-string t "a")~ through
~byte->text-output-port~ wrote four bytes. Browsers skip it; ~curl~ shows it,
and Python's ~json.loads~ refuses JSON text that starts with it. The JSON RFC
forbids adding one to JSON sent over a network.

- *~utf8~ never writes one.* It is ~UTF8Encoding(false)~, the encoding .NET
  itself uses when none is given.
- *~byte->text-input-port~ skips one* leading byte order mark with any UTF-8
  encoding, whether or not that encoding writes one. It did so before only
  because ~Encoding.UTF8~ writes one.

This is what OCaml's Uutf, Python's ~utf-8~ and Haskell's ~utf8~ do: a BOM is
never written unless asked for, and one is dropped when reading. Tested in
~231_byte_ports.bjo~.

* Closing a byte output port writes only what is pending

Closing a byte output port used to flush the stream under it every time, with a
blocking call, even when nothing had been written. A stream that refuses
blocking I/O, as Kestrel's do, made every such close raise.

- *A close writes only what is pending*: bytes still in the port's buffer, or
  bytes the stream was given since its last flush. After ~flush!~ a close does
  no I/O, so ~with-open~ and a scope's release are safe over such a stream.
- *~close-byte-output-port!~ suspends on a fiber.* It is a ~defbjouble~ now,
  like ~flush!~ and ~shutdown!~: the pending bytes are written asynchronously
  and then the port is released. The port is released even when that write
  fails or the fiber is cancelled, and the failure is raised afterwards.
- *A text port over a byte port* closes without I/O after an asynchronous
  flush as well. ~StreamWriter.Dispose~ always flushes its stream, and that
  flush now reaches the stream under the byte port only when something is
  pending.

Still open: a port closed by ~with-open~ or released by its scope while bytes
are pending, over a stream that refuses blocking I/O. A release cannot suspend,
so the write is blocking and raises. The failure is reported, and the handle
is released anyway. ~flush!~ first, or close with ~close-byte-output-port!~ on
the fiber.

Tested in ~BjolangRuntime/Cml/Tests~, over a stream that refuses blocking I/O
the way Kestrel's do, and in ~231_byte_ports.bjo~.

* ~stream->ports~ in ~(std net)~

~(stream->ports s #:peer "")~ makes the two ports over a duplex ~Stream~ that
something else connected — the stream an HTTP server hands over after ~101~, or
a ~NetworkStream~. The stream is shared the way ~tcp-connect~ shares its socket:
disposed when both halves are closed or the ambient scope ends, where
~stream->byte-input-port~ and ~stream->byte-output-port~ would each own it and
the first close would take it from the other. ~peer~ is what ~peer-address~
answers; ~""~, the default, answers ~None~.

It is what the ~(net websocket)~ package (github.com/bjoli/websocket) runs on
under ~bjoweb~. Tested in ~232_net.bjo~, over .NET's own ~TcpClient~.

Found on the way: closing a byte output port over a stream that refuses
synchronous I/O, as Kestrel's do, raised from ~Dispose~, which flushed the
stream synchronously. Fixed in the entry above.

* ~def~ failure parts are named, and ~:default~ is new

Every failure part of a ~def~, ~def*~ clause or ~cond~ ~:def~ now starts with a
keyword. Where a failure goes has not changed.

| Before                      | Now                           |
|-----------------------------+-------------------------------|
| ~(def p e value)~           | ~(def p e :leave-with value)~ |
| ~(def p e :fail (arm ...))~ | ~(def p e :leave arm ...)~    |
| ~(def p e :propagate)~      | unchanged                     |
| —                           | ~(def p e :default value)~    |

- *A bare value is an error.* It read as a default and meant leaving the body.
  The error shows both ~:leave-with~ and ~:default~ and says what each does.
- *~:leave~* comes last, and its arms are not wrapped in a list. ~:fail~ is
  gone, not an alias.
- *~:default value~* binds the pattern's one name to ~value~ when the pattern
  does not match, and the next form runs either way. The value has the name's
  type and is evaluated only on failure. A pattern binding no name or several
  is an error, and so is one that cannot fail. It is allowed at the top level
  and in the REPL, since it never leaves. In a ~def*~ it never short-circuits.

Migration is mechanical: every bare value becomes ~:leave-with value~, every
~:fail (arms)~ becomes ~:leave arms~. All of ~bjo/~, ~lib/~ and ~TestFiles/~ are
converted. Tested in ~220_def.bjo~, ~226_cond_clauses.bjo~ and the ~def_*~ files
in ~TestFiles/errors/~.

Also fixed: a name bound by a ~def~'s pattern was not renamed when it collided
with another local in the same C# method, such as ~(def n (begin (def (Some n)
o :leave-with 0) n))~, which failed with CS0128. ~:default~ is written that way.

* ~(:match pattern expr body ...)~ in ~cond~

A ~cond~ clause that answers when ~expr~ matches ~pattern~ and an optional
~#:when guard~ holds, and falls through to the next clause otherwise. It is the
bracketed counterpart of ~:def~: what it binds is in scope in its guard and
body only, and a failed match means "next clause", not a value for the rest
of the ~cond~. It covers what Haskell's pattern guards and Rust's ~if let~ do,
without an exit that is not visible where it is written.

It expands to one ~match~ whose fallback arm is the rest of the ~cond~, so
nothing is duplicated. Tested in ~226_cond_clauses.bjo~ and
~errors/cond_match_scope.bjo~.

* Four backend fixes found by writing bjosql and bjosqlite

- *A generic call whose type arguments only a lambda argument mentions* now
  writes them out: ~(make-namer "x" (fun (c) ...))~ was C#'s CS0411. Calls where
  another argument fixes the lambda's parameters, like ~(list-map (fun (n) ...)
  xs)~, are emitted as before. Test: ~239_lambda_type_args.bjo~.
- *Two linked modules with the same name*, such as ~(bjosql core)~ and
  ~(bjosqlite core)~, or ~(bjoweb core)~ and ~(bjorsec core)~, made a qualified
  reference to either ~core_Module~ ambiguous in C#. A module-qualified name now
  includes its namespace, and the namespace is written out only where the class
  name is ambiguous in the file. Test: ~240_same_basename_qualified.bjo~.
- *A .NET member re-declared with ~new~*, such as ~SqliteCommand.Parameters~,
  ~SqliteConnection.CreateCommand~ or ~Exception.GetType~, was reported as
  ambiguous, or crashed the compiler for a property. As in C#, the most derived
  member is the one used. Test: ~241_hidden_members.bjo~.
- *An impl at a type with fixed arguments*, ~(impl (ToSql (Array byte)))~, is a
  class with no type parameters. Its dictionary was written ~ToSql_Array<byte>~
  wherever it was built in another module's specialised body. Test:
  ~242_impl_fixed_args.bjo~.

Also documented in ~Docs/MACROS.org~: a type or constructor name that a
transformer builds for the caller has to be built with ~inject~.

Not fixed: a union case with the same name as its union, such as ~(type (:
(Select %c) (Union (Select ...))))~, still fails in the C# compile (CS0542)
instead of being reported by the front end.

* Tag delegation: a tag found through an untagged case

An untagged case whose one payload is a union now passes on the tags the
expected union does not have. With ~(Leaf %leaf)~ in a generic ~(Cond %leaf)~,
~'(id 3)~ at ~(Cond UserTest)~ is ~(Leaf (TId 3))~. A frame such as a condition
language can be written once, generic over its leaves, rather than repeated in
every union that needs ~and~ and ~not~. Documented in ~Docs/Syntax.org~ under
Delegation.

What it guarantees:
- A tag of the expected union itself always wins.
- It works through any number of levels, and a union already on the path is not
  entered again.
- Two cases offering the tag is an error naming both.
- It needs no metadata of its own, so it works across modules.

What it changes: a delegated tag is looked up before shape, as a direct tag is.
Before, no literal could reach a case whose payload is a union, so the only
programs that change are ones where a literal's head happened to be a tag of
such a union and an untagged list or symbol case took it as data. None of the
tests or the standard library have one.

Two diagnostics came with it:
- A tag that is not found lists the tags on offer through delegating cases as
  well as the union's own.
- When a list whose head is not a tag is taken as data by an untagged list case
  and then fails, the error has a note saying the head is not a tag either, and
  which tags there are. ~(select (id) (form users))~ used to report only that
  ~form~ is not a column.

* NuGet packages: ~(packages ...)~ in the manifest

A project's manifest may name NuGet packages, ~(packages (nuget (id "Npgsql")
(version "9.0.3")))~, and its modules may then use their types through
~import/class~ and ~import/extern~. ~bjo~ restores them with the .NET SDK and
hands the compiler the result with a new ~--nuget <dir>~ flag: the type checker
loads the packages' runtime assemblies, the C# compile references their compile
assemblies (all three backends), and the executable's assembly resolver finds
the runtime assemblies by name. Documented in ~Docs/Projects.org~ under NuGet
packages.

What it guarantees:
- A version is NuGet's, passed through as written; ~bjo~ never interprets one.
- ~packages.lock.json~ is written at the project root and should be
  committed. ~bjo build --locked~ fails with ~NU1004~ rather than change it.
- What a package contributes is decided by the SDK's own resolution, including
  conflicts with the shared frameworks in ~(frameworks ...)~: with ASP.NET
  declared, its copy of a package it contains wins.
- A project with no packages starts no ~dotnet~ for them and builds exactly as
  before, and a build whose packages, frameworks and lock file have not changed
  does not run the restore again. The standard library's artefacts never depend
  on a project's packages.
- Removing the packages from the manifest makes the program stale, although no
  file it read changed.
- A ~Directory.Build.props~, ~Directory.Build.targets~ or
  ~Directory.Packages.props~ above the project does not affect the restore.
- A dependency may declare packages. Each gets a generated project that the
  root project references, so NuGet resolves versions across the graph, and the
  project's own declaration of a package wins.
- Native assets work. The ones for the building machine's RID are picked, with
  the portable RIDs as fallback (Fedora's .NET reports ~fedora.43-x64~), and the
  executable's entry point installs a ~ResolvingUnmanagedDll~ handler that
  loads them from the NuGet cache. The REPL installs the same in its own
  process. Microsoft.Data.Sqlite works.

Left open: the built executable loads the packages from the NuGet cache, so it
runs only on the machine that built it until there is a ~bjo publish~; and the
compiler loads package assemblies into its own process with ~Assembly.LoadFrom~
rather than a ~MetadataLoadContext~.

* ~#:tag~ and ~#:rest~: a quoted literal can name the case it means

A union case may be marked ~#:tag name~, and then a quoted list whose head is
that name *is* that case — the tag is consumed, so what the case declares
describes the form's arguments. ~#:rest~ on such a case says its arguments are
its payload, any number of them. Both markers are in ~Docs/Syntax.org~ under
~#:tag~.

Selection for a quoted literal used to go by the payload's *head* constructor
and nothing else, so a union carried one case per shape and a grammar with two
productions that are both lists could not be written at all. That is why
~(std run)~'s tags are symbols read at run time, and why its documentation has
to say that a misspelled one is an ~Err~ rather than a type error. A tag is a
name the declaration chooses, so how many cases a literal can reach is now the
declaration's to decide.

Three consequences are not just more cases:
- A case whose payload is itself a union is reachable. No shape could ever
  select one — a union's head is never ~List~ or ~string~ — so a clause taking a
  sub-grammar was dead as far as a literal was concerned.
- A case may declare several payload types, which a literal could not build
  before.
- The head symbol stops being data. ~'(from users)~ used to be a ~Symbol~
  element beside the payload; now it is the case.

Two more came with it, and each stands on its own:
- A literal written where a union is expected is elaborated at the *top* of a
  form and not only in an element position, so ~(f 'x)~ and
  ~(def (: x T) 'hello)~ behave the way ~Docs/Syntax.org~ always said they did
  and were type errors before.
- A tagged case takes no part in shape selection, which is what leaves every
  program written before this meaning what it did: the untagged case for a list
  still takes the literals it always took.

Left open: a tag is looked up in the expected type, so a literal still cannot be
inferred from its own head and a generic parameter still expects nothing. A tag
lives in the head of a list, so a vec- or array-shaped clause is still selected
by shape, and arguments are positional with no labels. The payload types of a
tagged case are substituted with the union's type arguments but not instantiated
per use, so two positions sharing one declared variable are not tied together.

* ~(out T)~: .NET out parameters in ~import/extern~

An ~import/extern~ signature may declare a parameter ~(out T)~ where C# has an
~out~ parameter. It is not an argument; the outs come back in the result, as
~(Option ...)~ for a ~bool TryXyz~ method or as the return value followed by the
outs otherwise. Both forms, and the rules the declaration is checked against,
are in ~Docs/Syntax.org~ under ~(out T)~.

Before this, no method with an ~out~ parameter could be imported, and the
runtime answered its partial lookups with ~(bool, T)~ tuples that the standard
library wrapped into ~Option~ by hand. On a miss such a tuple carried
~default(T)~, which is ~null~ for a reference type, so a value Bjolang does not
have reached Bjolang code. The runtime now answers with ~bool TryXyz(..., out
...)~, the outs marked ~[MaybeNullWhen(false)]~, and the library imports those
with the Option form: the out is read only when the call returned true.

What changed for a program:
- ~map-try-find~ answers ~(Option (Tuple %k %v))~ rather than
  ~(Tuple bool %k %v)~. It is now the same as ~map-find~.
- Every other exported lookup keeps its type. ~map-try-ref~, ~orderedmap-min~,
  ~mutableheap-pop!~ and their neighbours are now the import itself, so a call
  compiles to the runtime call and a conditional, with no wrapper in between.
- A method whose overloads all take ~out~ or ~ref~ parameters now says so, and
  says how to declare the out or that a ~ref~ needs a C# shim.

Left open: ~ref~, ~in~, pointer and span parameters, and constructors with
outs. Only an import with outs can name an instance method of a generic .NET
type by the type's plain name.

* ~inbox-try-call~, for the caller who cannot look at a faulted task

A refusal has two shapes in ~(std inbox)~ because there are two kinds of
caller. ~inbox-post!~ answers ~#f~; ~inbox-call~ faults its task with
~InboxFullException~. The fault is the right answer for anyone who awaits the
task, and no answer at all for anyone who does not — and the caller the whole
module exists for is exactly that: a .NET callback that hands its task straight
back and returns.

An HTTP middleware is the case. It never awaits, so it never sees the fault,
which escapes as an unhandled exception: the client is told *500* when the
truth was *503*, and the server logs a stack trace per rejected request under
precisely the load that filled the queue. Measured on a one-worker,
one-slot server with six requests at once, before this: ~500 500 500 200 500
200~, and four traces.

So there is a third form, and it is ~inbox-post!~'s ~#f~ for a call:

#+BEGIN_SRC scheme
(match (inbox-try-call/token requests ctx (request-aborted ctx))
  ((Some answering) (cast Task answering))
  (None (set-status! (response-of ctx) 503) completed-task))
#+END_SRC

~None~ means nothing was posted — full under ~DropNewest~, or closed — and it
is an answer the callback holds *before* it returns, which is the only moment
it can still say anything. Under ~DropOldest~ the answer is ~(Some ...)~: this
call went in and an older one's task faulted, which is what ~inbox-post!~
means by ~#t~ in the same situation.

What it leaves open: the distinction ~inbox-call~ draws between full (faults)
and closed (cancels) is one this form deliberately drops — the caller asked
whether the item went in, and it did not. A caller that needs to tell the two
apart should ask ~inbox-closed~, or use the faulting form and await it.

* A ~defbjo~ with a keyword or a rest parameter is still a ~defbjo~ to its importers

An exported signature carries its colour on the arrow head, because that head is
all an importing module has to read it off. The path that writes the *keyword*
form of a signature wrote ~->~ outright and dropped the effect on the floor, so
a suspending function with a keyword or a rest parameter was published as an
ordinary one.

Nothing said so. The importer's ~callSuspends~ answered no, the call was emitted
without its ~await~, and what the author saw was Roslyn refusing a file nobody
wrote:

#+BEGIN_EXAMPLE
error CS0029: Cannot implicitly convert type 'Bjoml.Fiber<Server>' to 'Server'
#+END_EXAMPLE

The same function called from its own module was fine, which is what made this
hard to place: the shape that failed is a library's API, and only across the
module boundary.

~Exports.signatureText~ now writes ~arrowHead eff~ like every other serializer.
Nothing about a call site changed; what changed is that the metadata says what
the declaration said.

What it leaves open: a ~.dll~ built before this carries the wrong head, and
nothing detects that beyond the C# error it already caused. Rebuild libraries
that export a keyword-taking bjoroutine — a compiler change makes everything
stale anyway.

* A ~(:is T name)~ that shadows an imported name compiles

~uniquifyProgram~ renames a local that would shadow an enclosing one, and it
renames the binders as well as the uses. It handled ~TPIdent~ and ~TPAs~ and not
~TPTypeTest~ — while ~typedPatternBinders~, which decides what gets renamed,
listed all three. So a type test's designation was renamed everywhere it was
*read* and left alone where it was *bound*:

#+BEGIN_SRC scheme
(match (cast Object s)
  ((:is System.String str) str)     ;; in a module that imports `str`
  (_ ""))
#+END_SRC

became C# that binds ~str~ and returns ~str__1~. Fixed by rewriting the
designation with the same substitution as the rest of the pattern.

* A package may name types from a shared framework it declares

~Microsoft.AspNetCore.App~ and its neighbours are not part of the base runtime,
and until now nothing in Bjolang could name a type out of one. A manifest says
which it wants:

#+BEGIN_SRC scheme
(package
  (name (shop web))
  (frameworks "Microsoft.AspNetCore.App"))
#+END_SRC

Three sets, and keeping them apart is the whole design.

- *You may name what you declare.* Writing ~Microsoft.AspNetCore.Http.HttpContext~
  in an ~import/class~, an ~import/extern~, a ~(:is ...)~ or a type annotation is
  checked against the declaring *package*, not the module — so a package that has
  not declared ASP.NET is told so, by name, even when some other package in the
  build has already loaded the assembly.
- *You may use values that reach you.* The check is about names. A package that
  calls a function returning an ~HttpContext~ and hands it to another function
  taking one declares nothing, because it writes nothing.
- *A program's runtime needs follow what its modules actually used.* Each module
  records the frameworks its types were really resolved from, plus its imports',
  and the executable's runtimeconfig is built from that — so a module importing
  only the pure half of an ASP.NET library gets a runtimeconfig without ASP.NET
  in it. With only ~Microsoft.NETCore.App~ the file is byte-for-byte what it was.

Types are found lazily and by *file*: namespace guessing does not work for split
assemblies — ~HttpContext~ lives in ~Microsoft.AspNetCore.Http.Abstractions~, not
~Microsoft.AspNetCore.Http~ — so the first miss reads the type names out of every
assembly in the framework with ~System.Reflection.Metadata~, loading none of
them, and then registers the one file that has the type. Indexing
~Microsoft.AspNetCore.App~ costs about 8 ms, once per process.

A name that is nowhere gets a hint rather than a shrug:

#+BEGIN_EXAMPLE
  hint: Microsoft.AspNetCore types live in the shared framework Microsoft.AspNetCore.App.
  Add (frameworks "Microsoft.AspNetCore.App") to the manifest of package (shop web).
#+END_EXAMPLE

Each module's build record carries one ~framework~ line per declaration, so
*removing* ~(frameworks ...)~ recompiles the modules that used it and they fail
with the naming error rather than staying quietly built. ~bjo~ writes the
declarations to ~.bjo/frameworks~; a lone file can say ~--framework <name>~.

What it leaves open. The framework has to be installed wherever the program
*runs*, not only where it was built — the ~dotnet/runtime~ image does not have
ASP.NET and ~dotnet/aspnet~ does; an unknown framework, or one not installed, is
an error listing the ones that are. Four type names in
~Microsoft.AspNetCore.App~ are defined in two assemblies each, so the index reads
them shortest-assembly-name-first for a deterministic answer rather than a
correct one, and naming such a type from ~import/extern~ gets CS0433 out of the
C# compiler anyway, because every reference in the framework is passed to it; an
~extern alias~ would be the fix and is not here. Visibility is per-package for
framework type *names* and nothing else. The REPL has no framework support.

* The inbox: what a .NET thread knocks on when it wants a fiber

A thread that is not a fiber has no effect handlers, no parameters and no
cancellation scope. Kestrel's thread, a ~System.Threading.Timer~ callback, a
~FileSystemWatcher~: each arrives from outside holding a value, and running
Bjolang on it would be running Bjolang with none of the things that make it
Bjolang. ~(std inbox)~ is the door they knock on instead — a bounded queue whose
receive side is an ordinary CML event, so the handover is a rendezvous like any
other.

#+BEGIN_SRC scheme
(def requests (make-inbox 1000 DropNewest))

;; On Kestrel's thread, and the whole of what runs there.
(use! app (fun (ctx next) (cast Task (inbox-call/token requests ctx (request-aborted ctx)))))

;; An ordinary fiber, with its whole environment.
(defbjo (worker)
  (def c (sync (inbox-recv requests)))
  (try (handle (call-request c))
    #:finally (ignore (call-reply! c unit))))
#+END_SRC

*The one rule for a lambda .NET calls: it may call this module's functions and
nothing else.* Every one of them is a plain ~defun~ that reads no parameter and
no handler, because the caller has none. A ~(log ...)~ written there does not
fail — it quietly goes to the default handler from inside a ~with-handler~,
which is the sort of bug found in production. It is also why a post from a
thread with no fiber context *enqueues* the woken receiver rather than running it
inline: the posting thread may hold a lock, and a fiber resumed under it runs
arbitrary code there.

Three ways in, for three kinds of producer. ~inbox-post!~ and ~inbox-call~ never
wait and let the inbox's ~WhenFull~ decide; ~inbox-send~ hands back a ~Task~ that
stays pending until there is room, which is real backpressure rather than a
policy; ~inbox-send-evt~ is the fiber's form, and it is an event and not that
task because a task cannot be withdrawn — a losing ~choose~ branch would queue
the item anyway, later, with nobody expecting it. Capacity is mandatory:
~DropNewest~ refuses the new item, ~DropOldest~ evicts the oldest, and both count
what they threw away.

~inbox-close!~ is the graceful end, ~inbox-fail!~ the same with an exception kept
*beside* the queue where no full policy can drop it, and ~inbox-abort!~ the hard
stop. ~inbox-closed~ fires once the inbox is closed and empty.

A ~Call~ is request and reply. With ~inbox-call/token~ the caller's token means
two different things: *still queued*, the call is removed and its task cancelled,
so no fiber sees a call nobody waits for; *already taken*, the task is *not*
completed — only ~call-reply!~ and ~call-fail!~ complete it, and
~call-abandoned~ fires instead. The reason is concrete: completing the task hands
the ~HttpContext~ back to Kestrel, which recycles it into the next request while
the handler is still writing into it. So a fiber that takes a ~Call~ must answer
it, and ~#:finally~ is where that belongs.

No lock in ~Bjoml.Inbox~ is ever held across a commit, a resume or a task
completion, and one settle loop matches queued items with waiting receivers
rather than pump and admit recursing into each other — so stack depth does not
grow with the number of waiting producers.

~(cast Task t)~ needed no change to work for the upcast a middleware signature
wants; ~Task~ is now one name at two arities, as in C#.

What it leaves open. There is no inline mode, so every hand-over costs a
thread-pool hop even for a caller known to hold no locks. An inbox can only be
fed by APIs taking ~Func~, ~Action~, ~IObservable<T>~ or ~IProgress<T>~ — other
delegate types and .NET events are a separate piece of work. And a ~Task<T>~'s
value is still not readable from Bjolang, which is the whole reason
~inbox-call~ exists rather than an await.

* Every fold hands the element to its callback first

~(fold f init col)~ called ~f~ with the accumulator first and the element
second; ~list-foldr~ and ~string-fold-right~ called theirs the other way round.
Both orders were defensible and having both was not: which one a given fold
wanted was something you looked up rather than knew.

They are now all SRFI-1's: **the element comes first and the accumulator last**,
so the right fold's order is the left fold's order and the two differ only in
direction.

#+BEGIN_SRC scheme
(fold (fun (x acc) (+ acc x)) 0 xs)
(list-foldl (fun (x acc) (string-append acc x)) "" xs)
(string-fold (fun (ch n) (+ n 1)) 0 s)
(map-fold (fun (k v acc) (+ acc v)) 0 m)        ;; the entry first, both halves of it
#+END_SRC

Changed: ~fold~ (the ~Iterable~ method), ~list-foldl~, ~vec-fold~, ~vec-reduce~,
~seq-fold~, ~string-fold~, ~map-fold~, ~set-fold~, ~orderedset-fold~,
~orderedmap-fold~ and ~deque-fold~. Unchanged, because they were already this
way: ~list-foldr~, ~string-fold-right~ and ~port-fold~.

A map fold keeps handing the key and the value as two arguments rather than a
pair, so its callback takes ~(key value acc)~. The runtime's own ~Fold~ entry
points were flipped with it rather than wrapped, so nothing pays a delegate per
element for the new order.

What it leaves open: this is a silent break for callers whose accumulator and
element have the *same* type — ~(fold (fun (acc x) (- acc x)) 0 xs)~ still
compiles and now means something else. Nothing in the type system can catch
that, and there is no deprecation window; a subtraction or a string-append fold
wants reading. ~Collector~'s ~(collector-step c acc x)~ is a different protocol
and keeps its shape.

* A ~def~ that may fail has to say so, and ~:propagate~ is how it says "pass it on"

A bare clause used to propagate. That made the quietest thing you can write —
a pattern and a scrutinee — the one that silently added a second exit from the
body, and it read as a plain destructuring bind right up until the types
disagreed somewhere else.

So there is no default any more. ~(def (Some x) e)~ is an error naming the value
that reaches nothing; the pattern in a bare clause has to match every value, as
one at the top level always has. A clause that may fail writes a failure value,
~:fail~ arms, or the new ~:propagate~:

#+BEGIN_SRC scheme
(def pattern scrutinee)                     ;; must match every value
(def pattern scrutinee value-expr)
(def pattern scrutinee :fail (arm arm ...))
(def pattern scrutinee :propagate)
#+END_SRC

~:propagate~ stands alone and takes nothing: it rebuilds every case the pattern
left out at the *body's* type, which is what the bare clause did.

**It is no longer only ~Option~ and ~Result~, and no longer only one case.** The
rebuilt case is checked against the body like any other failure value, so the
rule is the general one: a type argument the leftover case carries has to be the
same on both sides, and one it does not carry is free. ~None~ carries nothing,
so ~(Option string)~ still propagates into ~(Option int)~; an ~Err~ is rebuilt
around its payload, so the error types still have to be one type. A three-case
union with one case matched now passes the other two through, and a user union
does it without being named in the compiler.

~:propagate~ on a pattern that cannot fail is refused, like any other failure
part on one. What is left over has to be *whole cases*: a nested or literal
pattern leaves part of a case behind, there is no constructor to rebuild that
with, and it says so rather than guessing.

What it leaves open: the leftover cases are rebuilt, never the scrutinee handed
back, so propagation still cannot widen an error type or convert one. ~From~-style
conversion remains something to write out.

* ~bjo rebjo~ builds the compiler, and nothing else does

~bjo~ used to ask whether the compiler was behind its own sources on the way to
every command it ran. Twice, in fact — once in the bootstrap script and once in
~bjo.bjo~ — and each asking cost a walk of every ~.fs~ and every ~.cs~ in the
tree, to be told "no" nearly every time. When the answer was "yes" it was worse:
a ~dotnet build~ in the middle of running something else, which is not what the
command was for.

So it is a command now. ~bjo rebjo~ builds the compiler and ~bjo.exe~, and
nothing else builds either. An up-to-date ~bjo build~ answers in about 40 ms.

Programs are still rebuilt after one. That question was never this one: the
build record names the compiler among a program's inputs, so a fresh
~Bjolang.dll~ makes every artefact stale by timestamp exactly as an edited
source does.

~rebjo~ is answered by the bootstrap script rather than by ~bjo.bjo~, and has to
be — it rewrites ~bjo.exe~, which ~bjo.bjo~ is running from. Reaching the
command any other way says so instead of doing it.

What it leaves open: ~bjor~ still asks the old question, and is still what
~build_std.sh~ runs on.

* ~def~ and ~def*~ replace ~def+~, and a bare clause propagates

The form is no longer spelled apart from the binding it is. A ~def~ takes a
pattern and a third slot saying what the body produces when the pattern does not
match, and ~def*~ is several of those in a row:

#+BEGIN_SRC scheme
(def pattern scrutinee)                     ;; propagate
(def pattern scrutinee value-expr)          ;; the body evaluates to value-expr
(def pattern scrutinee :fail (arm arm ...)) ;; the arms decide

(def* clause clause ...)
#+END_SRC

~def~ is to ~def*~ what ~let~ is to ~let*~, and nothing here jumps: a failure
value simply becomes the value of the enclosing body.

**A bare clause propagates.** The case the pattern leaves out is rebuilt at the
*body's* type — a fresh ~None~, or an ~Err~ around the payload that came in — so
the value type is free and the error type is not. ~which~ in ~bjo.bjo~ is the
shape this was written for: two lookups, each answering ~None~ by itself, and no
failure written down at all.

The restriction is one check over the constructors the pattern leaves
uncovered: exactly one, belonging to ~Option~ or ~Result~. It sits where the
general rule would — uncovered constructors mentioning only type parameters
shared by scrutinee and body — so relaxing it later is a condition and not a
path.

**Three failure shapes, one of them new, and the third slot is never arms.** The
pattern is unparenthesised at the head, so nothing is disambiguated by shape;
arms go after ~:fail~, and a list of arms written without it is answered with
the keyword rather than with a type error about a call to a list.

**~def*~ short-circuits and scopes sequentially**, because it is parsed as one
clause nested inside the next. A failing clause evaluates no later scrutinee,
and binder names must be distinct across clauses — they share the sequel's
scope, so shadowing there would be silent.

**The extent is the innermost body, and it now says so.** A refutable ~def~ in a
~when~ body leaves the ~when~, not the function, and the code after the ~when~
still runs. Where that value then goes nowhere in silence, the compiler warns
and names the body it resolved to. Where the body carries a value, the must-use
rule was already reporting it.

**A pattern that cannot fail may also stand at the top level.** There is no body
there for a failure to be the value of, so that is exactly what the top level
takes: a pattern that matches every value, and no failure part. Each name it
binds becomes a definition of its own — one evaluation of the scrutinee, one
destructuring — which is what `(def (a b) ...)` already did for tuples, asked of
any pattern. A `def*` there is its clauses spliced into the declaration list,
because with nothing able to fail its ordering *is* declaration order.

A REPL entry is a top level, so it takes the same: `(def (Tuple a b) ...)` binds
at the prompt now.

What it leaves open: the refutable case at a prompt, which is the one people
want there. It means deciding what the rest of the session is — on a failure
nothing may be bound at all, and the entries already compiled cannot be the
sequel of an entry typed later. Refused with a message saying so, rather than
given an answer the language does not have.

* ~(std rx)~: regular expressions, compiled while your file is

Patterns are s-expressions in SRE notation, read and compiled to a .NET pattern
by a hash macro:

#+BEGIN_SRC scheme
(def phone #rx(seq :bos (=> :area (** 3 3 :ascii-digit)) (lit "-")
                   (=> :line (** 4 4 :ascii-digit)) :eos))

(match line
  ((Rx phone (Some m)) (rx-group m :area))
  (_ None))
#+END_SRC

Four things follow from doing the reading at compile time rather than at
construction.

**A bad pattern is a compile error naming the sub-form.** ~'bos' is a symbol,
and an rx that takes no argument is a keyword. Did you mean :bos?~ — pointing at
the ~bos~, not at the whole call.

**Character-set algebra costs nothing at run time.**
~(- :ascii-alpha (in "aeiou"))~ is one flat class by the time the program
exists, and a set that came out empty is refused here rather than becoming a
complaint from .NET about ~[]~.

**The meaning is in this repository.** The emitter writes no ~.~, ~^~, ~$~,
~\d~, ~\w~, ~\s~ or ~\p{...}~. Each of those is .NET's decision and the Unicode
ones move when the runtime's tables are updated; the named sets are explicit
range tables generated from ~CharUnicodeInfo~ and checked in, so ~:alpha~ and
~char-alphabetic?~ agree and neither drifts under a compiled program.

**One atom consumes one scalar.** The engine works in UTF-16 code units, so
~:any~ and every complemented set are emitted as an alternation that takes a
surrogate pair as one unit. ~(rx-match? #rx(:any) "😀")~ is true and
~(rx-match? #rx(seq :any :any) "😀")~ is false, and a cursor a match hands back
is therefore always on a character boundary.

What it leaves open. Matching is ~NonBacktracking | ExplicitCapture |
CultureInvariant~, and the emitted pattern stays inside the subset that mode
accepts — which refuses backreferences, lookarounds, atomic groups and
conditionals. Those are out on purpose: they are what would tie the language to
a backtracking engine, and nothing here can emit one. Also absent: a string
syntax, patterns built at run time (~,x~ inside ~#rx(...)~ is reserved and says
so), case-insensitive matching, ~bol~/~eol~ and the word boundaries. A character
set is limited to U+0000–U+FFFF, because a .NET class cannot name a scalar above
it; matching one as a literal is unaffected.

One compiler change went with it. ~DotNetInterop.clrToNullary~ held only ~char~,
so a .NET method returning a ~Bjolang.Runtime.StringCursor~ came back as a type
that unified with nothing and no such method could be imported. ~StringCursor~
is now the second entry, on the same grounds the comment there already gave for
the first: its constructor is internal and it has no public members, so there is
no ~import/class~ alias for it to disagree with.

* ~def+~ replaced ~def/else~ and ~def/else*~, and its arms were checked

A binding that may fail now names what happens when it does, as arms over the
same scrutinee:

#+BEGIN_SRC scheme
(def+ ((Ok n) (parse-int s))
      ((Err why) (str "refused: " why)))
(str "n = " (int->string n))
#+END_SRC

Three things follow from arms that a single else body could not give.

**An arm can bind what the failure carried.** The else body ran because *some*
clause failed and could not say which, so nothing it carried was reachable —
that was an error test of its own. An arm matches the scrutinee, so ~why~ is an
ordinary binding.

**The form is checked for coverage.** The binder and the arms are a match over
one value, so ~Exhaustiveness~ asks the ordinary question and names the
counterexample. A two-case type needs no wildcard: ~Cons~ and ~Nil~ are the
whole of ~List~, and writing both is what says so.

**A binder that cannot fail is refused.** It was a warning, and a narrow one —
it fired for a bare variable and said nothing about a pattern irrefutable by
construction, so ~(def/else ((Tuple n s) pair) ...)~ compiled with an else body
nothing could reach. The question is now asked of the pattern rather than of its
spelling, and answered with an error: a binding that cannot fail is a ~def~.

~def/else*~ is gone rather than ported. Its shared else body existed so that one
message could serve several binds, and it had no uses outside its own tests;
what replaces it is a chain of ~def+~, which costs a message per failure and is
the better trade — "key did not exist or wasn't dollar" was the form's
limitation talking.

The lowering follows the shape: one scrutinee named once, then an ~if~ / ~else
if~ chain with the sequel as the first branch. No shared label and no ~goto~,
because there is no longer one body with many ways to reach it. The final
~else~ throws, unreachable, for the reason a switch statement's ~default:~ does:
C# cannot see that the chain always takes a branch, and without it a ~def+~ in
return position is CS0161.

What it leaves open: an arm still cannot say *which* of several chained binders
failed, because each ~def+~ knows only its own. And the sequel is still
invisible at the form — what the binder binds scopes over "the rest of the
body", and nothing on screen says how far that runs. That is what buys the flat
indentation, and it is the one thing arms do not address.

* A build writes down what it was built from, and ~bjo~ reads it

Deciding whether to compile means knowing a file's whole source closure and
every module it links. Only the compiler knows those — an ~include~ is a path
inside a form, an import is a module path resolved against the installation —
and until now the only thing asking was a shell script, which worked them out
again with ~grep~ and ~awk~. That approximation was wrong in both directions.
It followed a module import one edge deep, so editing ~eq.bjo~ left
~prelude.dll~ claiming to be current and the next compilation linked metadata
describing a module that no longer existed; the symptom was a SIGBUS in an
unrelated file.

So a build that succeeds now writes ~<source>.bjobuild~: the mode it produced,
the artefact, the compiler, every source it read and every assembly it links.
All of that is what the compilation already had — the source closure is what
~expandIncludes~ reports and the assemblies are ~linkedAssemblies~ — so what
changed is that they stop being thrown away.

The runtime is in that list for a reason of its own. A program is compiled
against ~BjolangRuntime~'s API and resolves it at run time from where it was
built, so a rebuilt runtime under an unrebuilt program is a missing method at
run time rather than a failed build.

~bjo~ is the command built on it, written in Bjolang, with ~run~, ~build~,
~check~ and ~repl~. Its staleness check is a comparison of timestamps against a
list, and it keeps only the two questions the record cannot answer: whether the
compiler is behind its own sources, since a stale compiler would answer as the
compiler it used to be, and what to exec afterwards. An up-to-date ~bjo run~
answers in about 150 ms, where starting a compiler to ask would cost about half
a second before it did anything.

What it leaves open: ~bjor~ still works the rest out for itself, and now reads
only the mode from the record's first line. The two drivers therefore still
hold two different answers to the same question, and the loose one is still the
one ~build_std.sh~ runs on.

* ~main~'s answer is the process's exit code

The entry point's type has been ~(-> (Vec string) int)~ throughout, and a file
that wrote a different one was refused in those terms. The ~int~ meant nothing:
the generated ~Main~ called ~main~ and discarded what came back, so every
Bjolang program exited 0 — including one whose ~main~ ended in ~1~ precisely to
say it had failed.

Both runtime entry points, ~RunMainSync~ and ~RunToCompletion~, already handed
the value back. It is now returned rather than assigned to a discard.

What it leaves open: a program that returned non-zero by accident now fails in
the eyes of whatever started it. Nothing in the test suite judged by exit code,
so nothing there changed, and ~run_tests.py~ still reads output text.

* A cancelled ~task->event~ always raises, and never returns a value

The rule was already written down: an ~(Err e)~ from a ~task->event~ means the
request *failed*, and cancellation raises ~Cancelled~ instead, so that a caller
never has to tell the two apart by looking at the exception type. It held for a
scope cancelled *before* the sync. It did not hold for one cancelled while the
call was in flight, about one sync in fifty.

The ambient token was linked into the call's own ~CancellationTokenSource~, so
the token firing woke two branches from a single cause: the call faulted and
its branch became ready, and the ambient branch ~sync~ publishes became ready,
by a different path. Two ready branches race and the first commit wins — and a
task branch that won handed back ~(Err TaskCanceledException)~, which is exactly
the representation the rule forbids. The comment in ~TaskEvent~ asserted the
opposite, that "the token's branch in ~sync~ commits first", and nothing
enforced it.

The fix is to give the call the nack's token and nothing else. Cancelling a
scope is then an ordered sequence rather than a race: the token fires, the
ambient branch is the only one that *can* become ready because the call is
still running, it commits, ~sync~ raises, the commit withdraws the task branch,
and the nack cancels the call. The call still stops, and stops because the sync
was abandoned rather than alongside it.

Nothing is lost by dropping the link. ~sync~ omits the ambient branch only for
~RootCancel~, and ~AmbientCancellation~ returns ~None~ for that same token, so a
call with no ambient branch never had a linked source either. It is also a
little cheaper: the linked source and the continuation that disposed it are
gone, per sync.

Direct ~#:async~ calls are untouched. They still take the ambient token as a
trailing argument and still surface cancellation as ~TaskCanceledException~ up
the fiber, which is what ~079_dotnet_async.bjo~'s last case pins.

What it leaves open: the general rule that cancellation loses a race and never
undoes a commit is unchanged, and should be — a rendezvous that happened
delivered a message, and discarding it would lose data. ~task->event~ could be
fixed locally precisely because there is no delivered message there: the result
*was* the cancellation. Any other event that can be completed by the same token
that cancels the scope has the same shape of bug, and there is no check that
would find one.

** The test that could not see it

~079_dotnet_async.bjo~ tried this once and passed forty-nine times in fifty, so
the bug read as flakiness in a timing test for as long as it existed.
~221_task_event_cancel.bjo~ is the regression test and runs the cancellation a
thousand times; against the broken runtime it reports eighteen or so leaks every
run. A race needs a loop, and a single-shot assertion about one is a placebo.

Separately, ~bjor~ decided the compiler was stale by looking at ~*.fs~ in the
project root and nothing else, so editing ~BjolangRuntime/*.cs~ and running a
program ran the *old* runtime — and a bare ~dotnet build~ produces Debug while
~bjor~ runs Release, so a rebuild did not fix it either. A fix could be applied
and a test could pass against code that was no longer on disk. The staleness
check now covers the runtime's C# as well.

* A ~def/else~ else body is an arm, not a jump

~def/else~ no longer needs an enclosing ~with-return~. Its else body produces
the value of the whole form, exactly as the else arm of an ~if~ does, and the
form is once again just a definition:

#+BEGIN_SRC scheme
(defun (label s)
  (def/else ((Ok n) (parse-int s))
    "unparseable")
  (fmt "n = {}" n))
#+END_SRC

What it replaces: the else body used to be typed against the *enclosing
block's* result and compiled to an escape. That implicit jump was the only
thing the form needed a block for, so a ~def/else~ with nothing blocklike about
it — the one above — had to be wrapped in a ~with-return~ that existed solely
to be jumped out of, and the wrapping was invisible at the point of use.

Leaving a block is still available and is now simply written:

#+BEGIN_SRC scheme
(with-return ret
  (def/else ((Ok n) (parse-int s))
    (ret (Err "bad input")))
  (Ok (+ n 1)))
#+END_SRC

~(ret ...)~ sits in tail position of the else body, which is where
~checkEscapeUses~ already allowed it, so this compiles to what it always did —
one unreachable ~return~ shorter, the old lowering having emitted the escape's
own return after the one the ~ret~ had already taken.

The optional block name is gone with the implicit jump: ~(def/else outer (p e)
...)~ named the block to leave, and there is nothing left for it to name. Write
the escape instead, which is what every other form does.

~InnermostEscape~ is gone from the inference environment with it. ~def/else~ was
its only consumer, and "the nearest enclosing block" is no longer a thing the
form has an opinion about.

** What it lowers to

The sequel and the else body are the two arms, so both are generated into the
same target. In the method's ~return~ position each ends in a ~return~ of its
own and nothing else is emitted. Anywhere else the value goes to a local,
declared *once* ahead of the construct and assigned by each arm, with the
~goto~ and the label that let them meet afterwards — the shape ~TIf~ has, with
the ~default!~ that ~TWithReturn~ and ~TThrow~ carry and ~TIf~ omits.

The clause-failure label and the nested-~if~ lowering are unchanged: a
~def/else*~ still emits one else body with every failing clause jumping to it,
which is still why it is a node of its own rather than nested matches.

** What is unchanged

Clauses still bind sequentially, so a later scrutinee sees what an earlier
pattern bound. The else body still stands outside every clause's bindings — it
runs because a clause failed, so which bindings would exist is not known. The
sequel is still the rest of the enclosing body, supplied by position.

Left open: the ~default!~ on that declaration is defensive rather than load
bearing. It guards an arm that never assigns, and none can be written today,
because ~checkEscapeUses~ will not let a ~ret~ stand where the form's value is
wanted. It costs one store, usually elided, and stays correct if that check is
ever relaxed.

Also left open, and older than this change: a ~def/else~ clause pattern that
shadows a name an enclosing scope already bound emits C# that does not compile
(CS0128) — the clause binder and the outer local collide, where a ~match~ arm
in the same position renames and does not. It is a lowering bug, not a scoping
one, and it predates this work.

* ~with-return~ and ~def/else~

A named early-exit block, and a refutable binding that leaves it. The part
below about the else body *leaving* the block is superseded by the entry above:
it is an arm now, and says so with a ~ret~ when it means to leave.

#+BEGIN_SRC scheme
(with-return ret
  (def/else ((Some cfg) (map-ref opts 'config))
    (Err "no config"))
  (loop (:for h (record-ref cfg hosts))
        (:do (when (blocked? h) (ret (Err "blocked host")))))
  (Ok (listen cfg)))
#+END_SRC

The name is required and there is no implicit ~return~: ~:return~ already means
~pure~ in ~(do ...)~ notation, and a second meaning for that word would be a
trap. ~ret~ is bound in the *ordinary value namespace*, and that is not a claim
but a mechanism — ~addBinding~ drops the name from the escape table exactly as
it drops one from ~TraitMethodNames~, so shadowing an escape needs no rule of
its own.

~def/else~ is in the ~def~ family and consumed by ~parseBody~ beside
~def/mutable~, because it *is* a definition: what its pattern binds scopes over
the rest of the body. That is ~def~'s scoping and not ~let~'s, which opens a
nested scope with a body of its own — which is why this is not spelled
~let/else~ however well Rust's version reads.

It was ~guard~ while it was being written, and could not stay. ~guard~ already
names a match clause's ~#:when~ test all through the pattern machinery —
~TMatchClause.Guard~, ~generateClauseGuard~ — and separately names CML's event
combinator, which ~http.bjo~ calls. A third meaning, in the middle of the
subsystem that already owns the first, is worse than a longer word. The plural
lost its ~#:else~ marker with the rename: that existed to keep a bare ~else~
from colliding with a pattern macro of that name, and once the clauses are one
parenthesised group there is nothing left for it to disambiguate.

** What it lowers to

Two shapes, and which one a block gets is not something a program can see.

**When the block is the function's value, nothing is emitted for the block at
all**: the body is generated straight into the method's ~return~ position and
every escape becomes a ~return~. No slot, no label, no definite-assignment
question, and nothing for a relocated scratch buffer to strand. Anywhere else
the value goes to a slot and control jumps past the body — the slot declared,
and the label emitted, in the block the form *stands in* rather than in one of
its own, since a ~goto~ whose label lands in a sibling block is CS0159.

~def/else~ is a node of its own rather than a ~match~ with a ~ret~ in its
fallback arm. A single clause would go that way exactly, but a ~def/else*~ has
one else body and many ways to reach it, and nesting matches would emit that
body once per clause. ~TestFiles/codegen/with_return.bjo~ pins the difference:
three jumps, one copy. It lowers to nested ~if~ s rather than a ~switch~,
because a switch section scopes its pattern bindings to the section and the
sequel lives after it.

No local function is generated anywhere in this, which is what makes the
lowering colour-blind: the sync and suspending copies of a body get the
identical rewrite.

** Where an escape may go

Only where the path to its block crosses no function boundary — refused inside a
lambda, inside a ~seq~ (a C# iterator may not be jumped out of, which is the
platform's rule rather than a taste), inside a ~#:finally~ cleanup, and inside a
spawned call. Leaving a ~try~ *body* is legal and correct: C# runs the
~finally~ on a ~goto~ as it does on a ~return~, so resources unwind either way.

**A loop is not a function boundary, however it is spelled.** ~loop~, ~for~ and
a named ~let~ all desugar to a letrec whose body immediately calls one of its
own members, which is exactly what ~LoopLowering.flatLoopEntry~ recognises in
order to emit a ~while~ rather than a local function — so an escape crossing one
is leaving a loop, and the loop's own ~ExitLabel~ already jumps out of it.

Every one of these is decided syntactically, in ~Parser.checkEscapeUses~, before
the body is typed: they are all questions about shape, and inference would
otherwise have to invent a type for a form that never yields a value.

Left open: ~(ret e)~ is admitted as a statement or in tail position and nowhere
else. As a proper subexpression it would have to interact with the hoisting of
statement-shaped operands and would need a bottom type to have one at all;
relaxing it later is a codegen change only. And the boundary check reads the
loop shape off the untyped AST, so a loop that ~LoopLowering~ later declines to
inline would strand a ~goto~ inside a local function — a C# error rather than
wrong behaviour, but the check would be better placed after that pass.

* A record may be written as a tagged form

~(: Package (Record #:tag package (: name (List Symbol)) ...))~ reads and writes
~(package (name (bjolang http)) ...)~ instead of ~{:name ... }~. The head symbol
names the type and each clause names a field. It diffs a line at a time and it
is what a person writes a manifest in.

**The format did not change.** ~(package (name ...))~ was already a ~BjoList~
headed by a ~BjoSym~ and still is; what ~#:tag~ settles is which shape a
*record's codec* reads and writes. The rule underneath is that **the expected
type picks the shape, and the shape never picks the type** — a ~(...)~ headed by
a symbol is a tagged record, a union case or a plain list according to the field
that wanted it. That is what lets a module name be ~(std run)~, the spelling
~import~ uses, with no ambiguity against a ~(git ...)~ in the next clause.

~#:rest~ answers the question a tagged list otherwise leaves open, which is
which clauses may repeat. It is answered per *field*, by the type, because
nothing else knows: ~(: depends (List Dep) #:rest)~ takes every value of its
clause, and ~(: version Version)~ takes one. A field is marked; a clause is not
repeated. ~(depends a) (depends b)~ takes the first, because the first entry
under a key wins for a map and one rule is better than two.

Reading costs what the parenthesised map form already cost: the tag and every
field name are matched against the reader's buffer by ~key=?~, so no string is
built and nothing is interned for either. A ~#:rest~ field reads its values
through ~read-value~, which carries the depth budget — so a manifest nested five
hundred deep is refused by ~bjodat-max-depth~ rather than by the stack. A
~#:rest~ that recursed into a generated decoder would have had no budget at all,
and that is the reason it does not.

An unknown *clause* is read and ignored at any arity, where an unknown key was
one value and done. A clause may hold none, one or five, and refusing every
arity but one would make each new clause a breaking change for every older tool.

~(bjor manifest)~ is the first user: the package types ~bjor~ reads, with module
names as ~(List Symbol)~ and version constraints as the forms
~(version-at-least "1.2")~, ~(version-at-most "2.0")~ and ~(version-between
"1.2" "2.0")~ — all three inclusive. A constraint inside a string would have
been a small language smuggled past the reader, with a parser, an error
vocabulary and a notion of position all its own, all of which the reader has.

Left open: writing a nested form back out puts it on one line, because
~bjodat->string~ is the canonical spelling. A manifest wants an indented writer,
which is a second writer and not a second format; nothing needs it in order to
read. And a record holds its fields and nothing else, so a manifest that
round-trips through one loses the clauses that version of the tool did not know
— a tool that edits a manifest in place has to work on the tree. That is the
same fact as the paragraph about unknown clauses, seen from the other side.

* A module may re-export a type

~(re-export SomeType)~ publishes a type this module imported. It is *one* type:
what crosses is the declaring module's declaration under the declaring module's
key, with a spelling of this module's pointing at it, so a value built through
either name unifies with one built through the other. No declaration of this
module's is made and none is published — the difference from ~(export ...)~,
which in a module that only imported the type declares a second one.

A union comes with its cases, in an expression and in a pattern, and a record
with its own name. They are not written in the list: exporting a union exports
its cases, and this is that rule one module further along. ~#:opaque~ survives
the trip for the reason it needs no rule — what crossed the first boundary was
a head, and a head is what is passed on. An import modifier reaches a
re-exported type like any other name, so ~(prefix-types (m) "M/")~ spells it
~M/Thing~ and its cases with it. Three things are refused at the form that
wrote them: a type this module declares, a trait, and an ~import/class~ alias.
Metadata is version 10, so every ~.dll~ rebuilds.

~(text bjodat)~ is what this was for. It re-exports ~Bjodat~, ~Reader~ and the
one-pass driver, so a program that declares records with ~def/bjodat-type~ — or
writes a ~->bjodat~ instance by hand, naming ~BjoInt~ — needs one import rather
than two. The reason generated code needs this at all is that it cannot choose
its imports: a template is spliced into somebody else's module and every type it
names has to resolve *there*.

A bug fell out of it that had been there all along. A macro template naming a
binding its own module *re-exported* resolved to ~Facade_Module::name~, and a
facade generates no member, so the expansion failed with "Unbound variable".
Nothing had reached it because no macro's module re-exported a name its
templates used. ~Macro.MacroBinding.Exports~ now carries the module each name is
defined in.

Left open: an implementation does not cross a facade. A re-export publishes a
spelling and the declaration behind it, and an ~impl~ reaches a consumer through
the module that wrote it — so a facade hands on a type and not its ~->str~,
~Eq~ or ~Ord~ instances, and a program that wants those imports that module too.
Which trait would have to travel beside a republished impl is the question that
kept it out.

* Hash macros, and the operators fold in the prelude

A third macro table. ~(def/hash-extend (name form inject compare) body)~ is
called as ~#name(args...)~ or ~#name[args...]~, and ~#name~ is a namespace of
its own: the prelude's ~#map~ sits beside its ~map~. The lexer makes a ~#name~
token only when a bracket follows it, so nothing that read before reads
differently now; ~t~ and ~f~ are the two names a hash macro cannot take. A
~#~ head is never renamed, is expanded before any special form is tried, is
refused in a pattern and in a quoted list, and a miss is a syntax error at the
parser rather than an unbound name later. ~prefix~ and ~postfix~ reach it;
~only~, ~except~ and ~rename~ do not see it, so a module's hash macros arrive
with every import of it. Metadata is version 9, so every ~.dll~ rebuilds.

The prelude defines four: ~#fl~ folds left, ~#fr~ right, ~#ch~ chains
comparisons, ~#map~ is the map literal. The parser now hands an arithmetic,
bitwise or comparison operator with three or more operands to ~#fl~ or ~#ch~
instead of folding it itself, and reads only arities 0–2 on its own. The
surface is unchanged — ~(+ a b c)~ still works and is still binary by the time
inference sees it — and the generated C# of every library module and Example
is byte-identical except where a chained comparison bound a temporary, whose
name is now the template's ~t~/~u~ instead of ~cmp~.

One change of meaning. ~(< a (f) (g) d)~ used to evaluate ~(f)~ and ~(g)~
both before testing anything; it now binds each right before its first use,
so once ~a < (f)~ fails, ~(g)~ does not run. A middle operand still runs
exactly once.

~#map(...)~ used to be rewritten by the reader into a ~list->map~ call; it is
now a prelude macro whose expansion reaches ~list->map~ by rule 2, so a local
binding of that name at the call site no longer matters. The reader's
~desugarMapLiteral~ is gone with it.

Left open: ~def/hash-extend~ at the REPL prompt fails as ~def/macro~ does
there, and an import modifier is not honoured by the REPL for any kind of
name; both are the REPL's, not the tables'. A ~#name~ written in a template is
looked up by spelling where the expansion lands, as an ordinary macro's head
is — a caller that imported the macro's module under a prefix has to have
written the prefixed spelling.

* ~sync~ costs what a rendezvous costs

Three changes, no change of meaning in any of them. Against raw BjoML on the
same box, a Bjolang rendezvous was 15x and is now about 2x.

~sync~ is no longer an ~async~ method. It was ~async Fiber<T>~, and ~Fiber<T>~ is
backed by a promise, so every rendezvous was: the event completes, that wakes
~sync~'s state machine, which completes ~sync~'s promise, which wakes the caller.
Two scheduler hops and a promise where one direct resume would do, and it threw
away the inline dispatch that makes a ring fast in the first place. A control
that does nothing but ~await ev~ inside an ~async Fiber<T>~ measured the same
cost, so that was all of it. ~sync~ now returns a ~SyncOp<T>~ struct whose
awaiter forwards to the event's own. Possible without touching the compiler
because ~sync~'s type is written down in ~Prelude.fs~ rather than read off the
C# signature. Ring, 1,000,000 messages: 870 ns/op to 130.

A rendezvous that can commit immediately no longer runs the cancellation race.
~chan-send~ and ~chan-recv~ answer whether the partner is already there; if it
is, the send or receive happens with no ~SyncState~, nothing published and no
token branch. This is not a relaxation: the token is published second and
publish order is priority, so an available event already won that race.

The race itself is one purpose-built event instead of a ~choose~ over two
~wrap~s. The combinator spelling allocated seven objects per parked rendezvous;
the event branch now passes its continuation straight through and only the token
branch needs a closure.

One difference worth writing down: calling ~sync~ and discarding the result no
longer starts the synchronisation, because an async method body runs to its
first await and a struct does not. Every call site in the language awaits, so it
is unreachable from Bjolang, and "building an event is pure" is the better
reading anyway.

Enlisting a spawn in a scope takes no lock either. The closed flag is the sign
bit of the outstanding count, so counting a child in *is* the test for whether
the scope is still open, and a spawn that arrives too late puts the count back.
Deliberately an unconditional increment rather than a compare-exchange loop:
every landing decrements that same word from every pool thread at once, and a
CAS that has to match what it just read spends a spawn storm retrying — worth
occasional 2-4x spikes on a million spawns, where an increment has none.

Measured and rejected: reading the ambient environment with an unchecked cast
instead of ~as~. ~DynEnv~ is sealed, so ~as~ is one method-table compare, and the
two measured identical. It would have bought nothing for an invariant BjoML
explicitly declines to make — the fiber context slot is documented as opaque,
and the language is not promised to be its only writer.

What is left: a fiber parked in a scope registers a waiter on the scope's token,
and that list is one object shared by every fiber in the scope. It is pruned on
an amortised threshold now rather than scanned on every registration — which is
what took a 4,000-fiber ring from 20,000 ms to 1,650 — but the push still takes
a lock. Topologies with thousands of fibers parked at once (a 4,000-node ring,
200,000 senders convoying on one channel) still pay for that and are the rows
furthest from BjoML. A lock-free waiter list would close it.

* A scope closes in one wait

A scope used to keep one entry per child and, at close time, wait on every entry
still running at once, rebuilding that wait each time one of them landed.
Children usually land one at a time, so n children cost about n²/2 waiter
publications — 4,000 children measured 8,002,000 of them. A child now decrements
a counter and whoever takes it to zero completes a single promise, so closing is
one wait and a child is O(1). 100,000 trivial ~spawn~ calls in one ~with-cancel~:
30 ms before, 16 ms after.

The counter starts at one, and that one is the body. Otherwise ~(spawn (quick))~,
a sleep, ~(spawn (slow))~ would end the scope the moment ~quick~ landed.

A landing that has no failure to report takes no lock, only an interlocked
decrement. Children land on every pool thread at once, and one shared lock per
landing measured slower than the per-child list it replaced.

Three behaviour changes:

- A child that failed while the body was still running now fires the token once
  the body ends. Nothing did before, so a body that returned normally, with one
  failed child and one child parked on a channel nobody writes to, hung in
  ~with-cancel~ forever. A child's failure still does not interrupt the body.
- Whether a child was cancelled or failed is decided when it lands, not after
  the drain. A genuine ~OperationCanceledException~ — an ~HttpClient~ timeout —
  raised before the scope's token fired used to be classified after it had
  fired, and dropped. It is reported now.
- Several failures come out of the ~AggregateException~ in landing order.

* ~(and p q ...)~ in pattern position

Every conjunct against the same value. Each may bind — two of them binding one
name is refused at the parser — so this is how a value is kept whole and taken
apart at once:

#+BEGIN_SRC scheme
(match o
  ((and whole (Some n)) (log whole n))
  (None                 (skip)))
#+END_SRC

It is emitted as C#'s own ~and~, so a conjunction of ordinary patterns is a
label and the clause stays in the jump table. A conjunction of views is one
~&&~ chain in the guard, which is the reason to write them under an ~and~
rather than to pack the results into a tuple: a later step is not evaluated when
an earlier one has already failed, and nothing is allocated for the packing.

Both combinators are now emitted parenthesised. C#'s ~and~ binds tighter than
its ~or~, so ~(and (or 1 2) x)~ emitted bare read as ~1 or (2 and var x)~.

For exhaustiveness a conjunction covers the intersection of its conjuncts, which
the matrix has no head constructor for. A conjunct that cannot fail is dropped;
one that can and stands alone is the whole of what the conjunction matches; two
that can means the clause covers nothing.

~and~ makes ~:as~ redundant — ~(and name p)~ is what it would have been — so the
unimplemented ~TPAs~ can go rather than be finished.

Found on the way: ~AlphaRename~'s pattern walk inside ~TMatch~ was written out
by hand with a ~leaf -> leaf~ fallback, so it dropped every node it had no case
for. It goes through ~TypeVisitor.mapPatternChildrenWith~ now.

* ~match~ is checked for exhaustiveness

A clause list that does not cover its scrutinee is a compile error at the
~match~, with one value that gets through printed as a pattern; a clause nothing
can reach is a compile error at that clause. Both come out of Maranget's
usefulness algorithm, run over the typed patterns after inference in the new
~Exhaustiveness.fs~.

A union is covered by its cases, ~bool~ by its two values, a tuple by its one
shape, a list by ~Nil~ and ~Cons~, a ~Vec~ or ~Array~ by the lengths written
plus a rest pattern for everything longer. ~int~, ~string~, ~char~, keywords,
symbols, .NET types and anything imported ~#:opaque~ have no listable set of
values, so only a binder covers them. An ~(or ...)~ covers each alternative.

Three things cover nothing: a clause with a ~#:when~ guard, a ~(:view ...)~ and
a ~(:is ...)~. Each decides by running code or by testing something with no
enumerable set behind it. Such a clause is still checked for being reachable, so
a guarded clause after ~_~ is as dead as any other, but a clause list made of
them has to end in a binder.

Pattern macros expand before this runs, so they are invisible to it: a macro
that rewrites to a covering set covers, and a counterexample is printed in
expanded form with the macro's name gone.

What this leaves open: nothing reasons about what a view returns, and no view
call is shared between clauses. A run of consecutive clauses over one
argument-free view, exhaustive over the view's result type, could be one call
with an inner switch — "total views". Not implemented; the note is in
~Exhaustiveness.fs~.

~Codegen.liveClauses~ no longer drops the clauses after an irrefutable one. It
asserts there are none, since reaching it with one now means a pass built it.
Three test files had a match the old ~default: throw~ was standing in for.

* ~match~ is extensible: ~(:view step p)~ and ~def/pattern~

Two layers. ~(:view step p)~ hands the value to ~step~ and matches what comes
back against ~p~ — the only pattern that runs code:

#+BEGIN_SRC scheme
(match n
  ((:view even? #t) "even")                          ; a predicate
  ((:view halve (Some k)) (int->string k))           ; a partial view
  ((:view (orderedmap-try-ref & "port") (Some p)) p) ; extra arguments, no lambda
  (_ "none"))
#+END_SRC

The step is written like a ~->~ step and read by the same code: a bare name is
applied to the value, and ~&~ says where the value goes in a form. A ~(fun
...)~ is accepted too. It is emitted into the clause's ~case ... when~ with the
value bound by a designation in the label, so the call is direct, nothing is
allocated for it, and a clause *without* a view keeps its constant labels and
its jump table.

~def/pattern~ is ~def/macro~ in a second table: the transformer runs when its
name heads a pattern, and what it answers is read as one. A name can be an
ordinary function in expression position and a pattern macro in pattern
position, the way ~Cons~ is already both, and a pattern macro shadows a
constructor of the same name in pattern position. Hygiene is the expander's and
unchanged — a binder a template writes is not the name the clause body reads,
so a macro that binds a caller's name takes it out of the input form. ~(std
orderedmap)~ ships the worked example, ~(om-has key p)~.

The step is inferred against the arrow it has to have, so ~&~ stands at the
scrutinee's type before the call around it is inferred. That is what lets a
trait method with an associated type be a step: ~(:view (try-ref & "port") (Some
p))~ resolves ~Refable~'s ~%index~ through the receiver.

What a view cannot do. It cannot suspend: a C# ~when~ has no ~await~, so a
~-bjo->~ step is a type error. It cannot need a statement to evaluate, exactly
as a ~#:when~ cannot. It cannot appear in an ~(or ...)~, because only one
alternative runs. And it runs once per clause that tries it — three clauses
each viewing ~parse-int~ call it three times, so a step that costs something
belongs in front of the ~match~. A view sees a ~#:opaque~ type only through a
view function that type's own module exported.

Module metadata is version 9: a ~.dll~ built before this publishes no pattern
macros and has to be rebuilt.

* Four mutable collections, over the .NET ones

~(std mutable vec)~, ~(std mutable map)~, ~(std mutable set)~ and ~(std mutable
heap)~ — a ~List<T>~, a ~Dictionary<K,V>~, a ~HashSet<T>~ and a
~PriorityQueue<T,P>~ respectively, joining the ~Deque~ already under
~std/mutable~. The value each hands back *is* the .NET collection, so one may
be passed straight to any other ~import/extern~ that takes one.

What they fill: ~VecBuilder~ and ~ListBuilder~ are append-only and
~TransientMap~ and ~TransientSet~ are a persistent collection being built and
frozen. None of those can be written at an index, sorted, or have an entry
removed and go on being used. ~MutableHeap~ has no counterpart at all.

Each is reached through a static module in ~BjolangRuntime/BjoMutable.cs~
rather than by importing the BCL type's members directly, because three things
the interop cannot reach are needed to use one: ~import/class~ declares no
constructor for a generic class, an accessor import takes no index so there is
no indexer, and a method with an ~out~ parameter is filtered out of overload
resolution. Every method in that file is one of those three or a one-line
forward.

~MutableVec~, ~MutableMap~ and ~MutableSet~ implement ~Refable~, ~Iterable~,
~Collection~, ~Addable!~, ~Eq~ and ~->str~. ~=~ is structural and ~eq-hash~
throws ~unhashable~, which is the pair ~Deque~ already carries: there is no
honest number for a value whose elements move. ~MutableHeap~ has ~Collection~
and ~->str~ only — its walk is unordered, so an ~Iterable~ would hand a caller
an order it had every reason to think was the heap's, and its ~add!~ takes a
priority as well as an element.

What this leaves open: keys are filed under ~EqualityComparer<T>.Default~ and
priorities ordered by ~Comparer<P>.Default~, which is .NET's answer and not the
~Eq~ or ~Ord~ implementation in ~std/eq~. That is the same hole
~TestFiles/186_collection_keys.bjo~ documents for ~Map~ and ~Set~, so the
collections agree with each other; a hand-written ~Eq~ that departs from .NET's
is still not consulted. ~mutableheap-by~ is the way out for an ordering, and
there is no equivalent for equality. Stack and queue are deliberately absent —
~Deque~ is both — as are ~SortedDictionary~ and ~SortedSet~, which would need
an ~Ord~-to-~IComparer~ bridge that does not exist yet.

* A trait member may carry a ~where~ of its own, and ~add-all!~ exists

A member of an interface trait can now be constrained, with every associated
type of the constrained trait pinned by keyword — the grammar ~dyn~ already
uses, for the same reason:

#+BEGIN_SRC scheme
(def/trait (Addable! %coll)
  (type %elem)
  (: add! (-> %coll %elem void))
  (: add-all! (-> %coll %s void)
     (where (Iterable %s #:elem %elem #:cursor %k)))
  (defun (add-all! coll xs) ...))
#+END_SRC

~#:elem %elem~ is the point: the element the source yields *is* the element
the sink takes, an equation neither a function's ~where~ nor an impl's could
state. An impl-level constraint over a trait with associated types stays
refused — an impl is one class, and its constraints' associated types would
have to be class parameters fixed before any call site exists. A *method* has
no such problem: the C# interface slot takes one generic parameter per
member-level variable and a leading dictionary argument, each call site
supplies the evidence, and a pin that fails is reported at the call that
raised it, naming the pin and both types.

What this bought immediately: ~(add-all! sink iterable)~ in the prelude, one
default body walking any ~Iterable~ into any ~Addable!~ sink — every builder
and transient, filled from a ~List~, a ~Vec~, a ~Range~, a string or a ~Map~,
with the element types agreeing by construction. The sink impls live beside
their types in ~(std set)~, ~(std orderedset)~ and ~(std orderedmap)~ as well
as the prelude.

And its persistent twin: ~Addable~, with ~add~ and ~add-all~ over ~Vec~,
~Map~, ~Set~, ~OrderedSet~ and ~OrderedMap~ (plus a new ~vec-add~). For a
map-shaped collection ~add~ replaces on a duplicate key — the mutable sinks
do, and ~add~ and ~add!~ disagreeing about one would be a trap — while
~map-add~ keeps the refusing behaviour under its own name. ~List~ is left
out on purpose: a cheap add would prepend, an in-order one is O(n), and a
name as plain as ~add~ should promise neither.

The edges, decided rather than left:
- an implementation writing a constrained member by hand repeats the clause
  as ~(: name (where ...))~ beside its ~defun~, and is refused without it;
- a constraint over a trait with a ~-bjo->~ method is refused — the call
  would be a yield point the member's own arrow never declares;
- ~(dyn ...)~ over a trait with a constrained member is refused for now: the
  box does not yet forward the dictionary;
- exported traits serialize their members' clauses and are written in
  dependency order, so an importer re-derives the constraint before the trait
  that carries it.

* ~Ord~ materializes too, and equality's last holes are closed

An ~Ord~ implementation for a declared type is now emitted into the type as
~IComparable<T>~ and its ~CompareTo~, the way an ~Eq~ implementation already
became ~Equals~/~GetHashCode~. ~Comparer<T>.Default~ finds the interface, so
the ordered collections — =(std orderedset)=, =(std orderedmap)=,
~SortedSet~, ~PriorityQueue~ — move from "compiles, throws at the first
comparison" to sorted by ~compare~. A union's ~CompareTo~ goes on the abstract
base, the opposite corner from ~Equals~, which goes into every case:
~Comparer~ asks the base type for the interface, and — unlike ~Equals~ —
nothing synthesized in a case class displaces ~CompareTo~, so one member on
the base serves every case and is dead on none.

A parameterized type with an *unconditional* implementation materializes now
too: ~(impl (Eq (Keyed %a)))~ with no ~(where ...)~ has a class that abstracts
over exactly the type's parameters, so it is instantiated at them. A
conditional implementation still keeps C#'s synthesized members, which compose
through each field's own override — refusing it is not a hole.

New to write: ~structural-equals~ and ~structural-hash~, the field-by-field
comparison by name. They are what an implementation writes when it wants "what
C# would have synthesized, plus one tweak" — written with ~clr-equals~ that
shape would emit an ~Equals~ that calls the impl that calls ~Equals~, forever,
which is why ~clr-equals~ stays private to ~(std eq)~ and its message now
names these. They never consult the receiver type's own ~Equals~; each *field*
still compares through its own type's equality, so nested implementations are
reached.

And one hole is refused rather than left silent: an ~Eq~ or ~Ord~
implementation for a type the module did not declare — an ~import/class~
alias, a type imported from another module, in the REPL a type from an earlier
entry. Every one of them passes the orphan rule and works for ~(= a b)~, and
none of them can reach the type's already-compiled ~Equals~ and ~CompareTo~,
so ~Map~, ~Set~ and the ordered collections would disagree in silence. The
message names the fix: the declaring module, the same REPL entry, or a wrapper
type. ~lib/std~ is carved out — its implementations for .NET types delegate to
the very members .NET consults, so its two answers cannot part ways, which no
compiler check could establish of an arbitrary body.

* A scope owns its fibers, and ~sync~ watches the token

~with-cancel~ used to hold a cancellation token and nothing else, so every
program wrote its own shutdown: keep the promises, cancel by hand, join them one
at a time. And every channel operation needed three combinators to say "receive,
or give up if we were cancelled".

#+BEGIN_SRC scheme
;; before
(def crew (hire jobs answers 8))
(def feed (bjo (feeder jobs urls)))
...
(cancel (Requested "enough"))
(ignore (sync (promise-join feed)))
(reap crew)

;; after
(hire jobs answers 8)
(spawn (feeder jobs urls))
...
(cancel (Requested "enough"))     ;; the scope drains on the way out
#+END_SRC

Two changes, which fit together.

*A scope waits for what it started.* ~spawn~ and ~bjo~ put a fiber in the
current scope, and ~with-cancel~ does not return until every one of them has
finished. When the form returns, the work is over.

*~sync~ consults the ambient token by itself.* A ~sync~ under a cancelled scope
raises ~Cancelled~, so a worker loop is written as if cancellation did not
exist. The token is offered as one more branch of a ~choose~ and it is published
*second*, so an event that is already available still wins: a rendezvous that
happened is not undone by a token that fired while the value sat on the run
queue.

** What is new to write

- ~(spawn (f x))~, ~(spawn/daemon (f x))~ and ~(spawn/detached (f x))~ beside
  ~bjo~. A daemon is cancelled by the scope but not waited for; a detached fiber
  inherits neither the scope nor the token. ~bjo~ keeps its promise and keeps
  ~MustUse~ — a second form is cheaper than a hole in a rule with no other
  exceptions.
- ~(with-shield #:within ms body ...)~, a scope whose token is not linked to its
  parent's, so cleanup after a cancellation can still ~sync~. Thirty seconds by
  default, because a shield with no deadline cannot be reached from outside at
  all.
- ~seconds~, ~minutes~ and ~millis~, which answer milliseconds.
- ~(spawn/thread thunk)~, for long CPU work. A *function* taking a thunk, like
  ~blocking~ and not like the spawn forms: the pool cannot tell a parked thread
  from a computing one, ~blocking~ answers the first case with ~Task.Run~, and
  this answers the second with a thread of its own — because for compute
  ~Task.Run~ is the same pool, the same core and a different worker holding it.
  It decides *where* work runs, so it composes with all four spawn forms, which
  decide *who owns* it.

** What changed under existing code

- ~until-cancelled~ takes the token to watch: ~(until-cancelled tok ev)~. The
  ambient token is ~sync~'s business now, and two mechanisms watching it — one
  raising, one answering ~None~ — would be two answers to one question. Every
  *other* token still composes under ~choose~, which is what keeps the CML layer
  intact.
- A cancelled ~task->event~ raises ~Cancelled~ instead of answering
  ~(Err TaskCanceledException)~. There is now one representation of
  cancellation, so a ~(Result Exception string)~ from a fetch means the request
  failed and nothing else.
- ~with-cancel~, ~with-deadline~ and ~with-shield~ *suspend*, because waiting is
  what they do. Only a bjoroutine may write them.
- ~main~ runs inside a root scope, so a top-level ~spawn~ is a child of
  something.
- ~deadline-watch!~ is gone. A deadline is a timer the scope owns; a watcher
  fiber would wait for a token the scope does not fire until its children are
  done, and its children would include the watcher.
- Naming ~Cancelled~ in a ~#:catch~ is an error, and the message points at
  ~with-shield~.

** What it leaves open

A scope whose children never end, and which never calls ~cancel~, hangs instead
of returning. That is the trade: a hang says where it is, and a scope that
returned while its children ran on says nothing at all.

A scope does not wait for a daemon to acknowledge its cancellation, so a daemon
can still be finishing its last write when the scope returns.

A scope owns fibers and nothing else. Eio's switches own file handles too, and
~with-response~ does the same job for one type; unifying them is worth doing
later, and the closing path leaves somewhere for a release action to go.

* The parking warning says when the fix is a keyword

The lint that reports a bjoroutine reaching a call which parks its thread used
to prescribe one repair: ~(sync (blocking (fun () ...)))~. That is the wrong
advice when the parking was chosen by a lambda, which is a common way to arrive
here — a lambda takes its colour from ~fun~ or ~bjoroutine~ and never from the
body around it, so an ordinary one selects the parking copy of everything it
reaches.

Two shapes now get told so: a parking call *inside* an ordinary lambda written
as an argument, and one that *is* what such a lambda was handed to. Both are one
keyword away from suspending, and the message says which keyword and where.

The first is asked for a suspending copy before the advice is offered, since
without one the keyword changes nothing. The second cannot be — that copy is
generated in the module declaring the ~-?->~ and is not published — so the
message names the condition instead, and following it where it does not hold
costs a rejected compile rather than a wrong program.

* ~:when-let~ and ~:break-let~ in a loop

#+BEGIN_SRC scheme
(loop (:for x xs)
      (:when-let (Some h) (halve x))      ;; no match: next iteration
      (:acc out (vecing h)))

(loop (:for n (up-from 0))
      (:break-let (Some job) (next-job q)) ;; no match: leave the loop
      (:do (handle job)))
#+END_SRC

A ~:let~ destructures and its pattern must always match, because a pattern that
could fail has nowhere to send the failure. These are the two versions that say
where it goes, and together they replace the three-clause spelling of a filter:
a ~:let~, a ~:break~ or ~#:when~ on a predicate, and a second ~:let~ to unwrap.

The pattern is what selects, so neither clause is about ~Option~ in particular —
a ~Result~, or a union of the program's own, works the same way, and no
per-type unwrapper is needed. Both are ordinary clauses, so comprehensions and
~seql~ take them.

Two clauses rather than one with a modifier, because neither edge is the
default. A ~chan-recv~ that answers ~None~ answers it forever, so a skip where a
break was meant is a loop that spins rather than one that stops.

* ~try->~ and ~result-map~

#+BEGIN_SRC scheme
(try-> path (open-input-file &) (read-header &) (parse &))

(result-map (fun (r) (read-all (response-port r))) response)
#+END_SRC

~try->~ is ~some->~ over ~Result~: each step answers one, receives what the step
before unwrapped to, and the first ~Err~ ends the chain with the steps after it
unrun. ~&~ says where the value goes when it is not the first argument, since
the threading is ~->~'s.

~result-map~ is the single step, for a function that answers a plain value —
it puts the ~Ok~ back on and passes an ~Err~ through. A step that answers a
~Result~ of its own belongs in a ~try->~ chain, where the wrapping is already
right.

Both are in the prelude, beside ~ok?~ and ~err?~. ~(std monad)~'s ~bind~ and
~(do ...)~ still exist and are still the general answer; these are the concrete
ones, the way ~list-map~ is concrete beside ~Iterable~'s ~map~ — and they are
reachable from the modules below ~(std monad)~ in the build, which ~bind~ is
not.

* A ~Result~ can be ignored

#+BEGIN_SRC scheme
(ignore (sync (promise-join fiber)))    ;; was a compile error, is now a discard
#+END_SRC

Must-use had a third level: a set of head constructors that ~ignore~ could not
satisfy, holding exactly ~Result~. It is gone, along with the ~NoDiscard~ field
and the check that read the argument of an ~ignore~ to enforce it.

A ~Result~ is level 1 now — the blanket ~Discard~ impl drops it. The ordinary
rule still applies, so a ~Result~ that goes missing without a word is the same
error every other value gets. What no longer happens is the compiler refusing
the word.

The rule is now universal with no exceptions at all, which is what ~MustUse~'s
header claimed for it already.

* ~main~ takes a ~(Vec string)~

#+BEGIN_SRC scheme
(: main (-> (Vec string) int))
(defun (main args)
  (println (vec-ref args 0))
  0)
#+END_SRC

The entry point still has exactly one type, and a ~main~ written without a
signature is still given it. What changed is the collection: the arguments
arrive indexable, which is what reading the third of them wants, and the
generated ~Main~ builds the vec directly from the ~string[]~ instead of consing
a list back to front.

A ~main~ that declares ~(-> (List string) int)~ is now the rejected shape,
with the same message the other way round.

* A lambda argument is inferred after the arguments that pin its parameters

#+BEGIN_SRC scheme
(vec-for-each (fun (r) (println (record-ref r url))) kept)
#+END_SRC

~url~ is a field of more than one record, so reading it off ~r~ needs ~r~'s
type — and ~kept~ is what says it. A call site now infers its positional
arguments in two passes, everything that is not a lambda first, unifying each
against the parameter it fills; the lambdas follow, with their parameters
pinned from the callee's arrow before their bodies are inferred.

Only the parameter types are pinned, never the effect: a ~fun~ passed to a
~-bjo->~ parameter is still an ordinary function that ~Colour.Lift~ bridges,
and ~ColourCheck~ still sees the colour the lambda was written with.

Arguments are still *evaluated* left to right — this is the order they are type
checked, not the order they run — and a parameter that is a bare type variable
still expects nothing, so ~(map spawn-thunk thunks)~ is unchanged.

What it leaves open: two lambda arguments that each need the other's type. That
still needs field access to become a deferred constraint.

* ~&~ is ~&1~ in a lambda shorthand

#+BEGIN_SRC scheme
#(+ & 5)                 ;; (fun (&1) (+ &1 5))
(seq-for-each #(println &) xs)
#+END_SRC

One hole has no number to tell it apart from another, and the Readme has
described it this way for a while. The reader rewrites `&` to `&1` before it
collects the parameters, so the two spellings are one form from there on and
mixing them is not a case anyone has to think about: ~#(- &2 &)~ takes two
arguments and subtracts the first from the second.

A nested shorthand needs no exception either. The inner ~#(...)~ is already a
~fun~ of its own by the time the outer one looks, which is also what keeps a
~&~ inside a ~#(...)~ inside a ~->~ the lambda's rather than the thread's.

* Iterators for part of a collection, backwards, and for a bare count

~(:for x xs)~ walks all of ~xs~ forwards. Nine names now say something else:

#+BEGIN_SRC scheme
{summing x (:for x (in-array row #:from 2 #:to 20))}
{listing x (:for x (in-reverse-vec v))}
(loop (:for i (up-from 0)) (:for line (in-port p read-line/opt)) ...)
(loop (:for tail (over-list xs)) ...)             ;; '(1 2 3), '(2 3), '(3)
#+END_SRC

~in-array~, ~in-reverse-array~, ~in-vec~, ~in-reverse-vec~, ~over-list~,
~in-port~, ~up-from~, ~down-from~ — and ~int-max~/~int-min~, which is what a
walk with no ~#:to~ runs to. ~#:from~ is inclusive and ~#:to~ exclusive, as
~range~ has them, and a reverse form takes the *same* slice as the forward one
and walks it the other way.

~down-from~ is the one exception, and deliberately: its ~#:to~ is inclusive, so
~(down-from n #:to 0)~ counts down to zero and says zero. Each spells the bound
it stops at, which is what either is written for.

They live in ~lib/std/iterators.protobjo~, which the prelude ~include~s after
its port section — an implementation belongs with the trait, so a module of its
own would have to import the prelude it is part of. The prelude keeps the
implementations for the collections themselves.

Each is a struct plus an ~Iterable~ implementation, so a loop allocates nothing
for one — it lands in the prologue, and what the loop compiles to is what the
hand-written one compiles to. That is also why they are ordinary iterables:
~fold~, ~map~, ~enumerate~, ~any?~ and the rest come with them.

A vec slice walks by ~RrbList~'s own range and reverse *enumerators* rather
than by ~vec-ref~ per index, which would descend the tree for every element.
Two bugs in the reverse one were in the way, both reachable only through the
range overloads nothing had used: its hot path stopped at the leaf's start
rather than at the range's, so a walk ending inside a leaf yielded elements
outside the range; and a walk that left the tail for the tree advanced a stack
that had never been built, because "am I in the tree" was asked as "are there
items", and a tail is items.

A slice that is not one is a panic naming the bounds, raised once where the
walk is built rather than as an index failure inside the loop.

What it leaves open: ~in-port~ blocks. ~Iterable~'s methods are synchronous, so
the reader's sync copy is what runs even inside a bjoroutine, and a port that
should suspend still wants ~port->seq~ or ~port-fold~. And there is no
~in-string~: a string is walked by cursors, which is a different protocol.

* ~#[1 2 3]~ — an array literal

~[...]~ builds a ~Vec~ and ~#[...]~ a .NET array: mutable, of a fixed length,
and exactly what ~make-array~ allocates.

#+BEGIN_SRC scheme
(def ys #[1 2 3])
(array-set! ys 0 42)
(array-length ys)              ;; 3
#+END_SRC

It is a reader rewrite to ~(array-literal ...)~, the way ~[...]~ is one to
~(vec-literal ...)~, and it lands on the node a call already packs its rest
arguments into — so the emitted C# is the array initializer and nothing else.
A literal that needs a statement to build an element hoists it ahead, as an
argument to any other call does.

Everything a vec literal takes part in, an array literal takes part in: it is
elaborated into the union case whose payload is an ~(Array %a)~, it spreads
through ~apply~ — into a rest parameter, which *is* an array, without a copy —
and it is a pattern as well, with ~...~ for the rest. The rest of an array
pattern is an array of its own, a slice being a copy.

It is not a syntactic value, for the reason ~make-array~ is not: it allocates a
cell. So a module-level ~(def ys #[])~ is one array, and the first write decides
what it holds.

What it leaves open: nothing says the length at the type level, so ~#[1 2 3]~
and ~(make-array 3)~ are the same type and an out-of-range index is still a
runtime failure.

* A panic ends the entry at a prompt, not the session

~panic!~ still writes to the error port and calls ~Environment.Exit~ in a built
program: a panic says the program cannot go on, and a program that cannot go on
should stop. A session is not a program, so at a prompt it raises instead, and
what it raises is caught where every other entry failure is caught:

#+BEGIN_SRC text
bjo> (g -1)
panic: negative
bjo> (+ kept 1)
42
#+END_SRC

The switch is a parameter, ~currently-in-repl~, false everywhere except inside a
REPL, which binds it once for the session. A *cold* parameter: it is read on one
path and bound at most once in the life of a process, which is not what the 31
ids that stay cheap under load are for.

What it raises is ~PanicException~, a type of the runtime's own, deriving
straight from ~Exception~ so that nothing catching a BCL type catches it by
accident. It carries the message and not the exit code — a code is what a
process leaves for whoever started it, and nobody started an entry.

What it leaves open: a panic raised on a fiber, which the promise machinery
still converts into an ~(Err e)~ value like any other failure. Rethrowing it
where the conversion happens is not safe — that code runs inside the sync
callback, where a throw lands in a channel's matching loop rather than on the
fiber that synced.

* ~case~ takes a lone datum, and requires an ~else~

#+BEGIN_SRC scheme
(case sym
  ('ticks (stopwatch-ticks sw))
  ('ms    (stopwatch-ms sw))
  ('s     (/ (stopwatch-ms sw) 1000L))
  (else   (raise (cast Exception (ArgumentException. "not a unit")))))
#+END_SRC

A clause groups data, and a group of one is now written without the bracket
around it: ~('ms body)~ rather than ~(('ms) body)~. Unambiguous because a datum
is an atom — a clause whose head is a list is a group, one whose head is not is
the datum itself — and the two spellings mix inside one form. ~else~ is still
read as itself rather than as a symbol datum, being matched before either.

The fallback is no longer optional. A clause's data are literals, so the arms
name a handful of values and say nothing about the rest: without an ~else~ the
key fell out of the ~match~ the form becomes, and the program died at runtime
naming neither the value nor the form it fell out of. ~(std stopwatch)~ shipped
exactly that — ~(ref sw 'seconds)~ answered with a bare
~TargetInvocationException~ — and now answers with the symbol and the three that
would have worked.

Refused, and this is the same rule rather than an exception to it: an ~else~
after both ~#t~ and ~#f~. Those are the whole of ~bool~, so the arm can never
run, and the language already refuses a duplicate datum and a clause after
~else~ on exactly that ground. Nothing else in the language can be exhausted by
listing values, so ~bool~ is the only key that may leave the ~else~ out. C#
reported this one as CS8510 against generated code before.

Alongside it, the REPL unwraps what it catches. An entry is invoked by
reflection, so anything raised arrived inside a ~TargetInvocationException~
whose message is that a target threw; only the ~TypeInitializationException~
around a ~def~ was being unwrapped. A raise from an ordinary call — the common
case — printed the wrapper and nothing of itself.

* ~def/impl~ is spelled ~impl~

#+BEGIN_SRC scheme
(impl (->str Money)
  (defun (->str m) (str (int->string (record-ref m kr)) " kr")))
#+END_SRC

The ~def/~ prefix is for the forms that *define* something — ~def~, ~defun~,
~def/mutable~, ~def/macro~ — and an implementation defines nothing. Every name in
one is already there before it is read: the trait, the method names under it,
and the type. It says only that the three meet. The methods are still written
with ~defun~, which is where the defining happens.

The bodyless form a library's metadata carries follows it: ~def/impl/extern~ is
now ~impl/extern~. Nothing has to be done about existing ~.dll~ files, since a
module's source closure counts the compiler, so every library rebuilds itself
against the new spelling on the first build after this.

A hard rename, with no alias: ~(def/impl ...)~ is refused as an unknown
declaration.

Untouched, and not as a compromise: ~def/trait~. A trait *is* defined. It
introduces the trait's own name and a method name for every signature under it,
and afterwards those names dispatch where before they meant nothing — which is
exactly what an implementation never does. The prefix was wrong on ~def/impl~
and is right on ~def/trait~, so the two spellings differing is the rule being
applied rather than a tidy-up left half done.

* A trait method takes a callback of either colour

~-?->~ on a trait method's parameter. ~Monad.bind~ declares one, so ~(bind m k)~
written generically suspends when ~k~ does:

#+BEGIN_SRC scheme
(defbjo (lines ports)
  (bind ports (bjoroutine (p) (Cons (read-line p) Nil))))
#+END_SRC

The trait derives a second method from the arrow, every implementation gets a
second body from the one it was written with, and the call site picks by the
callback it was handed. For an interface trait the two are two slots, so a
receiver that is still a type variable picks at the dictionary; for an inline
trait they are two static methods on the impl's class.

Before, every concrete name reached its suspending copy and the trait was where
it stopped: ~list-map~ took a colour and ~map~ could not.

What it leaves open: a ~(do ...)~ block still cannot suspend. ~:bind~ desugars to
~bind~ with the rest of the block as an ordinary ~(fun ...)~, and a lambda's text
is fixed while its colour is not — which is the same limit that keeps a callback
out of an implementation's body. ~Monad~'s ~List~ instance hands its continuation
to ~list-map~ rather than calling it inside a fold's lambda, for that reason.

Refused: a method that is both ~-bjo->~ and ~-?->~, since the two leave the
callback nothing to decide, and a ~-?->~ on a trait standing for a .NET
interface, which has one member per method and no second one to derive into.

* ~case~ dispatches on a jump table

~(case key ((datum ...) body ...) ... (else body ...))~. A clause's data become
one ~(or ...)~ pattern, so the form is a C# ~switch~ with a label per datum and
a section per clause — the shape Roslyn lowers to a jump table. Written as a
~cond~ of comparisons it would have been a chain of tests down the clauses.

The data are literals of the key's type. A bare name is *refused* rather than
read as a binder: ~((red orange) ...)~ means "the symbols red and orange" to
anyone writing Scheme, and would have meant "bind red to the key and match
everything" — silently, in the clause that then swallowed all the others. A
datum listed twice is refused too, because C# refuses a repeated ~case~ label
and the error would arrive against generated code.

What it leaves open: ~(else => proc)~ is not a clause, and neither is a datum
that is not a literal. Both are rejected with a message rather than accepted at
another meaning.

~(or p q ...)~ is available in ~match~ on its own. No alternative may bind,
since only one of them runs.

* Draining a port no longer parks the fiber

~port->list~ and ~port->vec~ take their reader as ~-?->~, so a bjoroutine can
drain a port at the suspending colour:

#+BEGIN_SRC scheme
(defbjo (slurp p)
  (port->list (bjoroutine (q) (read-line q)) p))
#+END_SRC

That emits ~await portsubgtlist__bjo(async (q) => ...)~, awaiting both the
drainer and each read. Before the reader was declared this was not merely slow,
it was *inexpressible*: a suspending lambda handed to a parameter typed
~(-> ...)~ is a type error, so there was no way to write it at all.

It matters more than the shape suggests, because the failure it replaces was
*silent*. A reader is called through a parameter, and the blocking lint does not
treat that as an edge — so a fiber parking on every line of a file said nothing
at all. The declaration is what makes the parameter something the compiler can
see.

~port->seq~ and ~file->seq~ keep ordinary ~(-> ...)~ readers, and the reason is
worth stating rather than leaving as an omission: their bodies are sequences,
a sequence is emitted as a C# iterator, and an iterator may not await.
Declaring ~-?->~ there would promise a copy that cannot be built, and the
compiler would rightly refuse it.

*What it leaves open.* The reader is written as a lambda rather than passed as
the bare name. ~(port->list read-line p)~ still selects the ordinary reader and
parks, because a name with two copies has the ordinary one's type when it is
referenced as a *value* rather than called. Fixing that means giving such a name
a polymorphic effect on reference and defaulting the unconstrained case to the
enclosing member's colour — which is what ~groundEffect~ was shaped for and does
not yet do.

* A procedure that mentions no colour suspends anyway

This is the one the rest was for. A ~defun~ whose call graph reaches a
~defbjouble~ is given a suspending copy too, without declaring anything:

#+BEGIN_SRC scheme
(: drain (-> TextInputPort int))
(defun (drain p)
  (let loop ((n 0))
    (if (port-eof? p) n (let () (ignore (read-line p)) (loop (+ n 1))))))
#+END_SRC

Called from a ~defun~ that is ~drain(p)~ and ~PortEof~. Called from a ~defbjo~ —
the same two words at the call site — it is ~await drain__bjo(p)~, and inside
that copy ~await portsubeof_QMARK__bjo(p)~. Nothing in either the definition or
the call says which.

~-?->~ is written down because it changes what a procedure *accepts*. This
changes nothing about the type, only which of two bodies runs, so there is
nothing for an author to say and no reason to make them say it.

The graph is over names, on the untyped declarations, because generation has to
precede inference while the real graph in ~EffectGraph~ needs types. It
over-approximates in the two safe directions: a free name counts as a call even
when the value is only passed around, and a call *through* a parameter is not
counted at all — the same approximation the blocking lint already makes. Both
cost at most a copy nobody calls, and neither can produce a wrong one, because a
copy is only ever *chosen* by selection, which reads the real types.

**A generated copy always type-checks, so nothing has to detect a bad one.** The
original is a ~defun~, so it contains no yield point anywhere or it would not
have compiled; the copy is the same body, and the only yield points it can gain
are the ones selection puts there, which it only does where an await is legal.
What that buys is graceful degradation rather than a diagnostic: a ~defun~ whose
call to the leaf sits inside a ~(seq ...)~ still gets a copy, the call inside the
sequence stays on the ordinary body, and the copy simply awaits nothing. It
still parks, and the lint still says so.

Which is the other half of the news: *the blocking warning went quiet.* What it
reported was never a mistake in the program — it was the compiler declining to
generate a body. It now fires only where the generated body cannot be reached,
and ~warnings/blocking_in_bjoroutine~ was reshaped around that, since the case it
was built on is the case that now works.

*What it leaves open.* A copy that gains no yield point is still emitted, so a
handful of async methods await nothing and pay for a state machine they do not
use. Pruning them means redirecting their call sites back to the original after
selection, which is a rewrite this change did not need. Trait methods still
carry no colour at all, and ~seql~ still has no suspending form, because an
async iterator does not exist to emit.

* Both copies of a ~-?->~ procedure are generated

~-?->~ declared that a parameter may be given a callback of either colour, and
then refused the suspending instantiation, because the second body it asks for
did not exist. It exists now, so the declaration means what it said.

#+BEGIN_SRC scheme
(: apply-twice (-> (-?-> int int) int int))
(defun (apply-twice f x) (f (f x)))

(apply-twice (fun (x) (* x 2)) 3)          ; ordinary
(apply-twice (bjoroutine (x) (+ x 1)) 3)   ; suspending, awaited
#+END_SRC

One body written, two emitted: ~applysubtwice(Func<int,int>, int)~ and ~async
applysubtwice__bjo(Func<int,Fiber<int>>, int)~, whose body is ~return (await
f((await f(x))))~. The prelude's ~port-fold~ is the one that matters — a fold
over a port whose reader may suspend, which is the question the arrow was
introduced for.

**Which copy a call means is decided by the argument, not by the caller.** The
two take unrelated C# delegate types, so exactly one of them fits; an ordinary
lambda passed from inside a bjoroutine still reaches the ordinary copy. Choosing
by the enclosing colour instead would emit C# handing a fiber-returning delegate
to a parameter that takes a plain one.

The copy is generated as *source*, before anything is checked, and re-checked
against the signature with its ~-?->~ repainted. The alternative — copying the
checked tree and substituting the effect — has to replace a value that lives in
every type on every node, and each occurrence it missed would be silent, since
~Codegen~ grounds a stray effect variable to the ordinary colour and emits a
body of the wrong one. Re-checking cannot miss one, and it is what ~defbjouble~
already did with a body written by hand.

It crosses a module boundary on the published signature alone. ~-?->~ is part of
the type, and the copy's name is derived from the written one at both ends, so
nothing new is serialized and no metadata version moved.

*What it leaves open.* A ~defun~ gets a second copy only when its signature says
~-?->~. One that merely reaches a ~defbjouble~ through its call graph does not,
so a port read reached through an undeclared ~defun~ still parks and the lint
still reports it. That is the remaining distance to the Guile-fibers model, and
closing it means inferring the copies rather than declaring them — which is the
thing the design keeps choosing not to do, because inference would double every
higher-order function in the library for callbacks nobody will ever suspend.

A copy that cannot be coloured is a compile error against the definition it was
copied from, since the two share their source ranges. The message says whose
copy it is, because otherwise it reports a yield point at a line where, as
written, there is none.

* A refused yield point says which construct refused it

There are six ways to be somewhere a yield point cannot live — an ordinary
~defun~, a module-level initializer, a ~(fun ...)~, a ~(seq ...)~ body, a
body-local function, and a loop that is used as a value — and from inside the
program they look identical. A call that would be fine one line out is refused
here, and nothing on the page says what objected.

The pass has always known exactly which, because the seal is set at the
construct that causes it. It used to throw that away and print a paragraph
listing all six for the reader to narrow down by hand.

#+BEGIN_EXAMPLE
Type Error at outer.bjo:6: calling 'fetch' is a yield point, and a yield point
is not allowed here.
  It is inside 'helper', a body-local function, which is emitted as a C# local
  function — and a local function inside an async method is not itself async.
  Inline 'helper' into the bjoroutine's body, or lift it out to a top-level
  (defbjo ...) and call it.
#+END_EXAMPLE

Named constructs are named. ~helper~ and the escaping loop ~go~ are things the
reader wrote and can see; reporting an anonymous ~(fun ...)~ for either would
send them looking for a lambda they never wrote. Where the constraint is a
parameter, the message names the callee and the arrow it is declared with,
because that declaration is what would have to change.

The old message ended by recommending ~-?->~ on that parameter. Following it
landed you in ~copies are not generated yet~ from ~unifyEffect~ — advice that
produces a second error is worse than none — so ~-?->~ is now offered as the
eventual answer and says what it does not yet do. The fix that works is the
loop, which is why a promoted loop being allowed to suspend matters: it is the
one workaround the higher-order restriction has.

*What it leaves open.* A lambda handed to a .NET ~Func~ parameter is pinned for
a third reason — a delegate's colour is part of its type — and has no case of
its own, because no fixture can currently reach one: every ~Func~-taking method
in the runtime is generic, and ~Task.Run~ does not resolve through
~import/extern~. Such a lambda gets the ordinary ~(fun ...)~ message, which is
true about it.

This is the diagnostic half of declaration checking. The other half — warning
that a ~defbjo~ never suspends, so it pays for a state machine it does not use —
waits for monomorphisation, because today it would fire on correct code with no
available fix: ~run.bjo~ declares ~Filter~ and ~Reader~ as ~-bjo->~ types, and a
filter that happens not to suspend must still be written ~defbjo~ to have one.

* A procedure is written once and works in both colours

~port-eof?~, ~read-line~, ~read-char~, ~read-all~ and ~flush-port~ each have two
bodies now, and no call site knows. Inside a ~defbjo~ they await; anywhere else
they are ordinary method calls. The source is the same source:

#+BEGIN_SRC scheme
(let go ((n 0))
  (if (port-eof? p) n (let () (ignore (read-line p)) (go (+ n 1)))))
#+END_SRC

Written in a ~defun~ that loop calls ~PortEof~ and ~ReadLineOrThrow~ and parks
the thread it is on. Written in a ~defbjo~ — the same characters — it calls
~PortEofAsync~ and ~ReadLineOrThrowAsync~, hands its thread back to the
scheduler, and honours the ambient cancellation token. Nothing in it mentions a
colour, and there is no suffix to choose.

Three pieces make that work, and each ships on its own.

*** ~BjoPort~ owns a buffer, so eof is answerable without waiting

~port-eof?~ was ~(= (.Peek p) -1)~, and ~TextReader~ has no async peek. That is
not an oversight in .NET: *eof on a stream is a read* — you cannot know whether
a socket is finished without waiting for a byte or a FIN, and peek is "read one
and put it back" with the read being the part that waits.

So ~open-input-file~ now hands back a ~BjoPort~: a ~TextReader~ that keeps the
characters it has read. Eof costs nothing whenever anything is buffered, which
reading a line at a time is all but one call in a bufferful, and
~ReadLineValueAsync~ can return a ~ValueTask~ where ~TextReader.ReadLineAsync~
must allocate a ~Task~. Standard input is wrapped too, once, shared — it is the
port every program touches.

~open-input-string~ is deliberately *not* wrapped. The text is already in
memory, so there is nothing to buffer and nothing to wait on, and a string port
correctly takes the ordinary path with no task and no allocation.

Nothing in the type surface moved: ~TextInputPort~ is still
~System.IO.TextReader~, so ~with-open~, ~(cast TextInputPort ...)~, ~(.Peek p)~
and handing a port to a .NET API all go on working.

The way this bites is *silent*. If any inherited read reached the underlying
reader while the buffer held characters, those characters would be skipped —
wrong output rather than an exception. So every virtual read is overridden, and
~152_port_buffer~ interleaves all of them against one port with the buffer
boundary placed inside a line, inside a ~\r\n~ and inside a surrogate pair.

*Opening still blocks.* ~new StreamReader(path)~ is synchronous and .NET has no
async constructor — ~FileOptions.Asynchronous~ affects reads, not the open. One
call parks wherever it is made; everything done to the port afterwards need not.

*** ~defbjouble~ is where the second body is written by hand

One name, one signature, two bodies. It is the *only* place two bodies are
written out, and the reason is specific to a leaf: its two colours call
different .NET methods, which is the one thing no inference derives.

#+BEGIN_SRC scheme
(: read-line (-> TextInputPort string))
(defbjouble (read-line p)
  (#:sync (clr-line p))
  (#:bjo  (clr-line-await p)))
#+END_SRC

Both bodies are checked against the one written signature, recoloured for each
half, so neither gets to disagree with the declaration — arity and type drift
is most of what rots between two hand-written bodies. What is *not* checked is
that they agree about failure: nothing compares what two .NET methods do when
they fail, so "both throw the same exception at end of input" is a promise the
docstring makes and the author keeps.

Leaves only, and mechanically: the ~#:bjo~ body must contain a yield point the
~#:sync~ body does not. Two bodies differing only in which ordinary functions
they call are a ~defun~, and writing them out by hand is two things that will
drift for nothing.

*What it leaves open.* Selection is by the *enclosing member's* colour, so a
~defun~ that a bjoroutine calls keeps its ordinary copy — generating a second
one is monomorphisation, which is a later layer. Until then a procedure that
must suspend is written ~defbjo~ and says so, and the lint below reports the
ones that do not.

*** ~-?->~ says a parameter may be given either colour

~-?->~ is to effects what ~%a~ is to types: one anonymous variable per
signature, shared by every occurrence in it, freshened at each use the way a
~%a~ is. One rather than one-per-arrow is what keeps it cheap — a signature has
exactly two instantiations however many function parameters it has, so there is
no 2^k of copies, and the mixed case is written by leaving the ordinary
parameters ~->~.

#+BEGIN_SRC scheme
(: port-fold (-> (-?-> TextInputPort %a %a) %a TextInputPort %a))
#+END_SRC

It is refused everywhere it would mean nothing, each with its own message: as a
definition's own arrow, where ~defun~ is already colour-polymorphic and the
writer probably wants ~defbjouble~; as a return type or a record field, where a
function value's colour *is* its type and always will be; and warned about on a
parameter the body never calls, where the two copies would be identical.

*What it leaves open.* The suspending instantiation is refused too — the second
body it asks for needs monomorphisation. The declaration is accepted, checked
and published, so a module compiled now will not need rewriting; it is the use
that waits. The collection functions are deliberately not converted: until the
copy is generated, ~-?->~ on ~list-map~ would buy a doubled emitted size for no
program that can yet use it.

* The compiler says which bjoroutines hold a thread

A fiber that waits gives its thread back to the scheduler. A fiber that calls
something which *parks* does not — it sits on a pool thread for the duration,
and every other fiber has one fewer to run on. That is legal, occasionally
deliberate, and invisible: nothing goes wrong until the pool is empty, at which
point the program stops for reasons nothing in it explains.

#+BEGIN_EXAMPLE
Warning: 'parked' is a bjoroutine, and calling 'port-eof?' at p.bjo:15 parks the
thread it runs on.
  parked -> drain -> port-eof?
#+END_EXAMPLE

~#:blocking~ on an ~import/extern~ clause is how a call says it parks;
~Prelude.blockingBuiltins~ is how the compiler's own primitives do, having no
clause to say it on. The lint is a fixpoint over the call graph — nodes are
bodies, an edge is a call, and the constraint is ≤ rather than equality, since
equality would force every caller of ~map~ to supply a suspending callback the
moment ~map~'s body yielded.

Two things it is careful about. The fact crosses a module boundary, which is
what makes it useful at all: the whole port surface lives behind one, so a graph
that stopped there would stop at every call worth reporting. And a lambda handed
to ~blocking~ or ~spawn-thunk~ runs somewhere else and is not walked into —
reporting ~(sync (blocking (fun () ...)))~ would be reporting the advice the
warning itself gives, and a lint that fires on its own recommendation is one
nobody leaves switched on.

* A vector literal is the array it looks like

~[1 2 3]~ used to open an ~RrbBuilder~, ~Add~ each element as a statement of its
own, and call ~ToImmutable~. It is now one array handed to ~RrbBuilder.FromArray~,
which chunks straight into leaves — so a literal costs one array and one walk of
it rather than an ~Add~ per element with the tail overflow check each one carries.
Up to 32 elements, which is every literal anyone writes by hand, it is the array
and nothing else: the vector's tail *is* that array, un-copied.

That last part is the only thing worth knowing. ~FromArray~ is asked to reuse the
array rather than copy it, which is sound here and nowhere else: the array is
allocated by the literal, reaches no other name, and a ~Vec~ is immutable from
there on. ~151_vec_literals~ asks the two questions that would catch it being
wrong — a persistent write through the vector, and two evaluations of one
literal.

A literal is also an *expression* now rather than a statement, so it no longer
forces a hoist where it appears. An element that needs statements of its own is
still hoisted ahead of it, left to right, exactly as an argument to any other
call is.

* A name means what scope says it means

A trait method's name, and a union case constructor's, are ordinary bindings.
Every binder shadows one — a parameter, a ~let~, a lambda parameter, a
definition — and inside the shadow the name means what the binder said.

Neither did. A call dispatched on the *name*, before the environment was
consulted at all, so nothing a program wrote could intercept one:

#+BEGIN_SRC scheme
(defun (pick less? a b) (if (less? a b) a b))   ;; the parameter was dead
(let ((counting 7)) (int->string counting))     ;; int against (prelude/Counting ?a)
#+END_SRC

The first was accepted, ignored, and reported as an arity error against the
programmer's own line. The second could not be written at all, so ~listing~,
~vecing~, ~mapping~, ~stringing~, ~summing~, ~counting~ and ~folding~ were seven
words no program could use as variables. And call position and value position
disagreed: ~(m a b)~ meant the trait and ~(def f m) (f a b)~ meant the local,
three lines apart.

What this does *not* touch is what the compiler writes for you. A ~loop~ calls
~iterable-next~, a comprehension constructs a ~folding~, an interpolated string
calls ~->str~, a derived ~Eq~ calls ~=~, and a macro template's method call means
the trait it belonged to where the template was written. Each of those is a
resolved reference rather than a lookup in your scope, so none of them can be
captured — which is what made shadowing safe to allow.

Two shadows now say so. A top-level definition over a method name warns and
suggests ~def/impl~, which is what someone writing ~(defun (= a b) ...)~ almost
always meant; this is also what makes a definition of ~sign~ — a ~Num~ method by
~#:clr-member~, and until now silently dead — work and be mentioned. An *import*
that lands on a method name warns too: the nearest binding wins, so a module you
did not write can decide what ~sign~ means here, and ~(except ...)~ or
~(rename ...)~ is the answer. A local shadow is silent, being a decision in a
scope its reader can see the whole of.

A module may now export a shadow, and an importer gets it. It used to publish
the *trait* instead — a module exporting a function called ~sign~ grew a
~def/trait (Num ...)~ it had never declared — and to drop the binding as
"already published by that trait", so an importer got neither and nothing said
so.

What it leaves open: ~Codegen~ still emits an operator infix on the name alone,
so a local binding named ~+~ is ignored after inference resolved it correctly.
That one is in ~Todo.org~ and predates all of this.

* A trait method in a macro template means the trait

A macro's template that *calls* a trait method now gets the method, whatever the
module the expansion lands in has bound that name to. Before, the name was
handed to the call site's scope, so this quietly derived nonsense:

#+BEGIN_SRC scheme
(defun (= a b) "not equality at all")

(type/derive (Eq Ord)
  (: Point (Record (: x int) (: y int))))
#+END_SRC

~type/derive~ compares two ~int~ fields with ~=~, and that ~=~ was whichever one
was in scope where the derivation landed. It could not arise until a trait method
name became an ordinary binding; once it could, hygiene had a hole in it exactly
where hygiene is for.

This is the third of the three renaming rules changing: a trait method has no
qualified spelling for rule 2 to use, and stripping the mark — rule 3 — was the
old answer for want of one. The compiler now writes such a reference as a
*resolved* name, the same node behind the ~->str~ of a string interpolation and
the ~iterable-next~ of a ~loop~.

What it does not cover: a trait the macro's own module merely *imports* rather
than declares, and the arguments of such a call, which are read in the resolved
name's scope as well. Both are in ~Todo.org~. Nothing about calling a macro
changes, and code that shadows a trait method for its own use goes on meaning its
own — resolving a template's name is not un-shadowing the name.

* The Iterable and Collector methods are namespaced

*Breaking.* ~start~, ~done?~, ~current~ and ~next~ are ~iterable-start~,
~iterable-done?~, ~iterable-current~ and ~iterable-next~. ~init~, ~step~ and
~finish~ are ~collector-init~, ~collector-step~ and ~collector-finish~. The
~Cursor~ methods already read this way and are unchanged.

These are methods the compiler calls on your behalf. A ~(loop ...)~ is written in
terms of all seven, and almost nobody writes one by hand — but they sat in the
prelude under the plainest words there are, where an import cannot rename them
away. ~lib/std/fmt.bjo~ binds a local called ~start~; the test suite has
functions called ~start~ and ~step~ that were dead, being shadowed by a trait
method they had nothing to do with. Those three now mean what they say.

Nothing about the protocol changed, only what it is called. A program that walks
a collection by hand needs the new names; one that uses ~loop~, ~fold~ or a
comprehension needs nothing.

* A boolean is a literal

*Breaking: ~true~ and ~false~ are no longer booleans.* Write ~#t~ and ~#f~. The
two names are ordinary identifiers now and a program may use them for anything.

They were bindings. ~#t~ lexed as the *symbol* ~#t~, the parser rewrote it to the
name ~true~, and ~true~ was an entry in the prelude's environment — so a boolean
was a variable, and anything that bound that name redefined it:

#+BEGIN_SRC scheme
(let ((true #f))
  (if #t "t" "f"))        ;; "f"
#+END_SRC

Not only the literal. ~and~, ~or~, ~not~ and every chained comparison ~(< a b c)~
are written in terms of these, so all of them inverted too. A loop level with two
~:for~ clauses joins its termination tests through the same name, so with the
shorter sequence first the walk was told it had not finished, ran off the end,
and died inside the runtime with "Car is not defined on an empty list" — a crash
in C# with nothing in it naming the cause, from a program whose only unusual act
was a variable called ~true~.

Nothing defends against this now, because there is nothing left to defend: a
literal is not a name and no environment is consulted. What used to guard it was
a comment in the code generator arguing that a shadowing binding could not be
mistaken for the prelude's, which was true and beside the point.

*A boolean pattern works.* It never had. ~(match b (#t "y") (#f "n"))~ read ~#t~
as a *binder* — matching everything, and reaching the generator as a name, which
spelled it into the C# as written and produced a preprocessor directive. It is a
constant pattern now, ~case true:~.

*A quoted boolean is a boolean.* ~'(#t #f)~ is a list of booleans as ~'(1 2)~ is
a list of ints. A symbol in a quoted list is still a symbol, which is what lets
~'(true)~ name the program of that name to ~(std run)~.

** ~#~ introduces a reader form and is not part of a name

The reader used to fall back to reading anything after a ~#~ as a symbol. That
is where ~#t~ came from, and it did not stop there: ~#banana~ was an ordinary
identifier, accepted by the whole of Bjolang and refused by C#, where ~#~ begins
a preprocessor directive. The diagnostic named a generated file and a rule of
another language.

What may follow ~#~ is now enumerated — ~#t~, ~#f~, ~#\c~, ~#:keyword~,
~#'template~, ~#(...)~, ~#[...]~, ~#map(...)~ and ~#"..."~ — and anything else is
refused where it is written.

The two booleans are a token of their own rather than a symbol, and that is what
makes them unbindable rather than merely undefined: every binder position matches
a symbol, so there is no shape a boolean fits. ~(let ((#t 1)) ...)~ used to be
accepted — the binding was made, and nothing could refer to it, a use of ~#t~
being the literal.

A boolean still crosses into a macro as the symbol it is spelled with, since
~Syntax~ has no boolean node, and comes back as the token the reader would have
produced. Nothing a template can write has changed.

* A changed module is rebuilt, however far down it is

Staleness used to be judged against a module's own source closure — the file and
its ~include~s — and the compiler. Its *imports* were not part of that, and what
crosses an import is metadata, read once, when the importer was compiled. So a
chain of three:

#+BEGIN_SRC scheme
;; app.bjo   imports middle.bjo
;; middle.bjo imports leaf.bjo
#+END_SRC

with an edit to ~leaf.bjo~ left ~middle.dll~ looking current — its own source was
untouched — and the program went on being built against the module leaf used to
be. The failure was a silence rather than an error: no diagnostic, no rebuild,
and an edit that simply did not happen.

An import is now part of what a module is judged against, and *resolved* rather
than stat-ed: resolving a dependency builds it if it is itself behind, so a
change reaches everything above it one edge at a time. The implicit
~(import (std prelude))~ counts as an edge like any other.

A build with nothing changed still rebuilds nothing — the walk remembers what it
has decided for as long as that build lasts, so a diamond in the import graph is
visited once, and a cycle stops there rather than recurring. An illegal cycle is
still reported as one, in terms of the import chain.

* A name means what the source says it means

Two ways a program could be compiled into something it did not say, both of
them a C# identifier standing for more than one Bjolang name.

** Two names that mangle alike are two names

~Naming.sanitizeIdent~ is not injective — ~-~ becomes ~sub~, ~?~ becomes
~_QMARK~ — so ~a-b~ and ~asubb~ arrive at C# as one identifier:

#+BEGIN_SRC scheme
(let ((a-b 1) (asubb 2)) (+ a-b asubb))
#+END_SRC

used to declare ~asubb~ twice and fail to compile. The rename pass that already
existed for shadowed locals now counts collisions in the *emitted* spelling
rather than the written one, so the second binder is given a fresh name.
Parameters are covered too, including two parameters of one signature.

Nothing that was already correct changes: a name is renamed only where it
collides.

** A module may declare a binding named after a builtin

#+BEGIN_SRC scheme
(export list)
(: list (List int))
(def list (list 1 2 3))
#+END_SRC

An importer of that module has two ~list~ in scope — this one, and the builtin
— and generated code reaches both through a ~using static~, which is a spelling
C# resolves to neither. ~(list-length list)~ therefore failed to compile with a
CS0411 about a method group. An imported binding whose name is a builtin's is
now qualified to the class that declares it, so the import is what runs.

The rule is the one the language already had: the nearest binding wins. A local
or a definition in the same module always did win — C# lookup sees to that — and
still does; what changed is that an import does too. The builtin is untouched
wherever nothing shadows it.

This is what made ~(def list ...)~ at a REPL prompt unusable from the next entry,
since an entry imports the ones before it.

* A type crosses a module boundary only when it is exported

A module used to publish every type it declared, whatever its ~(export ...)~
said. Now the export list is the whole truth about a module's surface, for types
as much as for bindings:

#+BEGIN_SRC scheme
(export Crate make-crate)
(type (: Crate (Union (MkCrate int))))
#+END_SRC

A type has no signature to be missing — what it publishes is its declaration —
so naming it is the whole of what is required.

*Nothing a module publishes may name a type it withheld.* An exported
signature, a ~(where ...)~, a trait method, an impl target, the field types of
an exported record and the payloads of an exported union are all checked, and
the failure lands where the library is built rather than in somebody else's
module at a call whose author never saw the type.

This is a breaking change for any library that leaned on the old behaviour, and
the fix is always the same: name the type. The metadata format is at version 4,
so everything compiled against an older compiler needs rebuilding — ~build_std.sh~
for the standard library, and a rebuild of anything built against it.

** ~#:opaque~ — a name without its representation

#+BEGIN_SRC scheme
(export Handle)
(type (: (Handle %a) #:opaque (Union (Live %a int) Closed)))
#+END_SRC

The head crosses and the body does not. An importer may write ~(Handle string)~
in a signature, hold one in a ~List~ and pass it back; it may not name ~Live~ or
~Closed~ in an expression or a pattern, and for an opaque ~Record~ it may
neither read a field nor construct one. Inside the declaring module nothing
changes — opacity is a property of the boundary.

*Implementations still travel and still dispatch.* That is what makes an opaque
type usable rather than merely storable: an impl is keyed on the type, and a key
resolves wherever it is read, so a module can say what ~->str~ or ~=~ mean for a
type without saying what it is.

*The pattern matcher needed nothing.* A union case becomes a constructor binding
by walking the cases of a published declaration; an opaque type publishes none,
so a pattern naming one is refused on the path that already refuses a typo. The
same holds for constructor calls, ~record-ref~ and ~record-set~. What was added
is the explanation — the member names travel for the message and nothing is
registered under them:

#+BEGIN_SRC text
Pattern Error: Unknown constructor 'Live' at m.bjo:19. 'Live' belongs to
vault/Handle, which is exported #:opaque: the type's name crosses the module
boundary and its representation does not, so a value of it can be held and
passed on but not taken apart here.
#+END_SRC

~#:opaque~ on an alias is refused: an alias is expanded wherever it is named, so
there is no representation to hold back.

~(std mutable deque)~ is the first user. ~Deque~'s two lists and its count were
already documented as nobody else's business, and a mutable field was already
unwritable from outside; the marker makes them unreadable too, which is what the
comment had been asking for.

* ~(std mutable deque)~

The first thing built on mutable fields, and the reason they were wanted: a
double-ended queue that is written in place.

#+BEGIN_SRC scheme
(def work (deque))
(deque-push-back! work job)
(match (deque-pop-front! work) ((Some j) ...) (None ...))
#+END_SRC

Two lists — ~front~ in order, ~back~ reversed — so a push at either end is a
cons and a pop is a head. When the list at one end runs dry the other is
**split in half** rather than moved across wholesale. Moving all of it is the
textbook queue trick and it is quadratic on a *deque*: pop one end, pop the
other, and every pop hauls the whole structure back again. Half leaves both ends
stocked, so every operation is O(1) amortized. 200k alternating pops on a 200k
deque run in 13ms; the wholesale version would be doing ~10^10~ conses.

It lives under ~std/mutable~ so that reaching for it is a deliberate act, and
the module is the only thing that may write the fields — a mutable field is
writable only in its declaring module, so ~front~, ~back~ and ~size~ are not
somebody else's business.

** Equality is by contents, and it has to be written down

Two deques are equal when they hold the same elements in the same order,
whichever half those elements are sitting in. Pushing three items on the back
and popping one gives a deque ~=~ to one built by three pushes on the front.

The ~Eq~ implementation is not decoration. Without it a deque would fall to the
blanket, which is .NET's equality, which for this record is a field-wise
comparison of ~front~, ~back~ and ~size~ — so two deques holding the same
elements in different splits would have compared unequal, silently.

~eq-hash~ refuses, and that refusal is what keeps the paragraph above true. A
~Map~ keyed on a deque would ask .NET rather than asking the implementation, and
materialization cannot redirect that for a *generic* type. So rather than let
the two disagree, nothing is allowed to ask: the hash throws at the one call
that would have.

** What is still open

- **No transient interface**, which is what ~Readme.org~ originally wanted — a
  persistent deque with a mutable view over it. This is mutable all the way
  down instead. A persistent deque is still worth having and would not conflict.
- **No ~Collector~ implementation**, so a deque is not yet a comprehension
  target the way ~Set~ is.
- **Heap is still missing.**

* Mutable fields in records

#+BEGIN_SRC scheme
(type (: (Queue %a) (Record (: front (List %a) #:mutable)
                            (: back (List %a) #:mutable)
                            (: size int #:mutable))))

(record-set! q (front (list-reverse (record-ref q back))) (back Nil))
#+END_SRC

A field marked ~#:mutable~ is written in place by ~record-set!~. Until now the
language had exactly one mutation primitive — ~def/mutable~ plus ~(set! name
value)~, on a bare identifier — and everything else was persistent, which left
programs that genuinely hold state reaching for ~Array~ and a hand-rolled index
scheme.

~record-set!~ takes a name, writes one or more fields, and is void. All of its
values are evaluated, left to right, *before* any of them is written, so a value
expression that reads the record sees the state before the form rather than one
half way through it. ~record-set~ is untouched and still copies, taking the
mutable fields as they stand.

Four things are deliberately not allowed. A ~Struct~ may not have a mutable
field — it is a value type, so the write would land on a copy — and there is no
~struct-set!~. A union case may not have one, its payload being positional and
so having no name for a write to use. Only the declaring module may write a
field; a module that means its state to be reachable exports functions that
reach it. And constructing a record with a mutable field is not a syntactic
value, so a module-level ~def~ of one is not generalized — the ~make-array~ hole
arriving by a second route.

The emitted C# stays a ~record~. Only a *positional* parameter is init-only, so
the whole field list moves into the body and the constructor is written out:
~with~, ~ToString~ and a synthesized structural ~Equals~ all keep working, and
construction stays positional and in declaration order.

** Equality holds. Hashing does not, and says so.

~=~ is structural over what the fields hold at the moment of the comparison, so
two records equal now may be unequal later. All four paths to equality agree, as
they must: a direct ~=~, a dictionary-dispatched one, a container comparing
elements, and .NET calling ~Equals~.

~eq-hash~ throws. There is no honest number — hashing the mutable field breaks
the rule that a key's hash does not change, hashing only the immutable ones
breaks the rule that equal values hash alike — so a mutable record is not a
~Map~ or ~Set~ key and raises at the point it is asked, rather than being
accepted and then silently lost on the next write.

Closing that properly took two pieces. ~derive~ writes an ~eq-hash~ that calls
the new ~unhashable~ builtin, and codegen writes a throwing ~GetHashCode~ into
any record with a mutable field that materialization did not already write one
for. The second is the one that matters: materialization never fires for a
*generic* type, so ~(Box %a)~ with a mutable ~item~ would otherwise have kept
C#'s synthesized hash over that very field. ~Equals~ is left alone in that case
— the synthesized one compares every field, which is what ~=~ means here, so the
two already agree.

The ~#:mutable~ marker is published in a module's metadata. Not for diagnostics:
an importer never writes a foreign field, but it does *construct* the record,
and one that could not see the marker would generalize the construction and hand
out a single cell at two types.

** What is still open

- **A generic record with a mutable field can never have a working hash**, even
  a hand-written one, because materialization cannot reach a generic type. The
  throw is otherwise a default rather than a property: a non-generic type may
  hash only its immutable fields and mean it.
- **Transitive hash failure is a runtime error.** A record deriving ~Eq~ over a
  field whose type has no hash throws one level down rather than being rejected
  at compile time, which would mean tracking "has no hash" per implementation
  through the registry.
- **Nothing is done about concurrency.** A mutable record shared between fibers
  races, exactly as a ~def/mutable~ does. This is now at least written down.
- ~record-set!~ takes a name rather than an lvalue, so
  ~(record-set! (car xs) (x 1))~ needs a binding first.

* ~Eq~ for the library's collections

Implementations for ~(Set %a)~, ~(OrderedSet %a)~ and ~(OrderedMap %k %v)~, each
in its own module, joining the ~(Map %k %v)~ one already in the prelude.

The two ordered ones were the ones that mattered. ~OrderedSet~ and ~OrderedMap~
are C# classes that had no structural ~Equals~ at all, so ~=~ on two of them
meant *reference identity*: two sorted sets built separately out of the same
elements were not equal, silently. They now compare by a paired walk, which is
what the ordering buys — both trees enumerate in the same order, so keys, values
and elements alike are compared through ~Eq~ in place, and the tree's own
~Comparer~ never has to be trusted to agree with equality. ~(Set %a)~ has to ask
the trie instead, as ~(Map %k %v)~ does, so its element equality is .NET's.

Writing those in Bjolang alone would have *created* a split: ~=~ would have said
two ordered sets were equal while a ~Map~ keyed on one went on failing to find
it. So ~OrderedSet<T>~ and ~OrderedMap<TK, TV>~ gained ~Equals~ and
~GetHashCode~ in the runtime, computing the same paired walk. That is the same
move materialization makes for a type the compiler emits, done by hand for two
it does not.

All four collections now compute ~eq-hash~ and ~GetHashCode~ as the *same
number* — same operation, same seed — rather than each merely agreeing with
itself. ~Set~ and ~Map~ fold with xor, which is what their C# side already did.

** What is still open

- A transient has no implementation and should not: it is mutable and its
  identity is the point.

* A blanket ~Eq~

#+BEGIN_SRC scheme
(def/impl (Eq %a)
  (defun (= a b) (clr-equals a b))
  (defun (eq-hash a) (clr-hash a)))
#+END_SRC

In ~(std eq)~, which the orphan rule already required: a blanket applies at every
type that has none of its own, so one declared elsewhere would change what ~=~
means for modules that never heard of it.

This lands last, and that ordering is the whole of why it is safe. .NET's
equality for a record, struct or union the compiler emitted *is* that type's own
~Eq~ implementation, because ~Equals~ and ~GetHashCode~ are emitted as calls to
it. So the blanket routes to a hand-written implementation wherever one exists,
at any nesting depth — it is "derive, applied automatically" rather than a second
equality. Landed before materialization it would have been the split it exists
to prevent: ~(= p q)~ finding the user's implementation and ~(= (Some p) (Some
q))~ finding .NET's.

** What is guaranteed

- ~=~ works at every type with a head constructor. A record with no
  implementation compares field-wise; a class-backed one compares by identity.
- A tuple of an arity nothing implements — five or more — reaches the blanket
  through its synthetic head key rather than failing.
- A hand-written implementation still wins wherever there is one, including
  through a field whose own type has none.

** What is still open

- *Nothing can opt out.* ~(= p q)~ on two ports, or two fibers, compiles and
  means reference identity. There is no negative-implementation mechanism. The
  lever available, if a type's equality is genuinely meaningless, is to emit an
  ~Equals~ that throws — turning a silent wrong answer into a runtime one.
- *A type with no head constructor is not covered.* Resolution needs a head to
  look up before it can fall back to a blanket, so ~(= f g)~ on two functions is
  a type error. It says so, and names the implementation it was needed by.
- *A generic type still keeps C#'s synthesized equality.* Materialization is
  skipped for it, for the reason in the previous entry. The blanket now makes the
  missing dictionary constructible, so this could be closed; it has not been,
  because a derived implementation agrees with the synthesized one anyway and
  only a hand-written implementation for a generic type can differ.

* ~derive~, and equality that .NET agrees with

Two things, shipping together because both touch record, struct and union code
generation and because either alone is half an answer.

** Materialization

When a record, struct or union has an ~Eq~ implementation, its ~Equals~ and
~GetHashCode~ are emitted as calls to that implementation:

#+BEGIN_SRC csharp
public record Point(int x, int y, string cache) {
    public virtual bool Equals(Point? other) => other is not null && Eq_Point.Instance.eq(this, other);
    public override int GetHashCode() => Eq_Point.Instance.eqsubhash(this);
}
#+END_SRC

C# synthesizes those only when they are not written, and a record's ~==~ calls
~Equals~, so ~EqualityComparer<T>.Default~ *is* the implementation the program
wrote. That closes the gap the previous entry left open, everywhere at once and
in one place:

- ~Map~ and ~Set~ are correct with no dictionary threaded through them and no
  signature changed, because they key on ~Equals~ and ~GetHashCode~.
- Interop is correct: a ~HashSet<Point>~ or a ~Distinct()~ agrees with ~=~.
- An implementation that deliberately ignores a field is ignored by all of them
  too. That is the test worth having, and it is in ~TestFiles/128_derive.bjo~.

The orphan rule is what makes the lookup possible: an implementation for a type
declared here is in this module too, so both are in hand when the type is
emitted.

A union's override goes into every *case* class. A derived record synthesizes
its own ~Equals~, which overrides the base's, so one written on the abstract base
alone would be silently dead.

** ~type/derive~

A macro in ~(std prelude)~:

#+BEGIN_SRC scheme
(type/derive (Eq)
  (: Point (Record (: x int) (: y int))))
#+END_SRC

Records and structs compare their fields in declaration order; unions compare
the case first and then the payload positionally; a type with parameters derives
a conditional implementation. The trait list is a list so that ~Ord~ can join it
without the form changing shape.

It is written in Bjolang rather than in the compiler, which needed the macro
system to reach a little further. Rule 3 — "strip the rename and dispatch" — now
applies to every position that *selects* rather than binds: a type definition's
~Record~/~Struct~/~Union~ tag, the trait in a ~def/impl~ and in each of its
~(where ...)~ constraints, the clause tags inside one, and the name of a method
in an implementation. A method's parameters keep their renames, being binders.

** What is still open

- *A generic type keeps C#'s synthesized equality.* Its implementation is
  conditional, and there is nothing inside ~Box<T>~ that could build the ~Eq<T>~
  dictionary the ~(where ...)~ asks for. A derived implementation is field-wise
  and so agrees; a hand-written one for a generic type can differ from what .NET
  asks. This closes when there is a blanket implementation to use as the
  dictionary.
- *A derived body reports against the ~type/derive~ form, not the field.* Every
  node a macro builds carries the call site's range. The message names the type
  with no implementation and the implementation that needed it, which between
  them say which field.
- *~=~ on a ~Map~ still matches keys by lookup.* That is now correct for every
  key type whose ~Equals~ is its ~Eq~ implementation, which is every record,
  struct and union the compiler emits — so what is left is a key type that is
  neither.
- *There is still no blanket ~Eq~.* A type with no implementation of its own has
  no equality at all.

* Equality is a trait

~=~ is a method of ~Eq~, declared in ~(std eq)~ and re-exported by the prelude:

#+BEGIN_SRC scheme
(def/trait (Eq %a)
  (: = (-> %a %a bool))
  (: eq-hash (-> %a int)))
#+END_SRC

Before this there were three unrelated equalities. ~=~ was typed ~(-> %a %a
bool)~ and emitted as C# ~==~, which does not compile at a type variable, does
not compile on ~Option~ or ~Result~, and silently means *reference* equality on
~List~ and ~Vec~. ~equal?~ was ~EqualityComparer<T>.Default.Equals~. ~eq?~ was
~ReferenceEquals~.

** What is guaranteed

- One equality. ~equal?~ is gone; it *is* ~=~ now. ~eq?~ is unchanged and still
  means object identity — for mutable cells, and silently structural on a value
  type.
- ~=~ at a type with no implementation is a type error naming the trait and the
  type, rather than a C# compile failure or a wrong answer.
- A container compares its elements through *their* ~Eq~ implementation, so
  ~(= (Some p) (Some q))~ reaches whatever ~p~'s type says equality is, at any
  depth. Implementations ship for ~List~, ~Vec~, ~Option~, ~Result~, ~Map~ and
  tuples of two, three and four elements.
- A generic function acquires ~(where (Eq %a))~ from its body. Nothing that
  compared two values has to be annotated.
- ~(= 1 2)~ still emits ~(1 == 2)~. A statically resolved call is spliced, so
  the primitive path costs no dictionary and no allocation — asserted against
  the generated C# in ~TestFiles/codegen/equality.bjo~, because no behavioural
  test can see it.
- ~eq-hash~ lives in the same trait as ~=~ rather than in one of its own,
  because it is derived from the same choice of fields. There are no default
  bodies: the only body a default could have is "ask .NET", which is wrong in
  exactly the case someone wrote an implementation for.
- ~double~ is reflexive on ~NaN~, deliberately: it uses ~Equals~ rather than
  ~==~, because a hash-based container cannot find a key that is not equal to
  itself. IEEE's answer is not available through ~=~.

** What is still open

- *A hand-written implementation and .NET disagree.* C# still synthesizes
  ~Equals~ and ~GetHashCode~ for a record or struct, so ~(def/impl (Eq Point)
  ...)~ governs every ~=~ in Bjolang while ~Map~, ~Set~, ~HashSet<Point>~,
  ~Distinct()~ and every other .NET consumer go on using the synthesized ones.
  Nothing in the language reaches them — every ~=~ is a trait call and the
  container implementations are Bjolang — but a ~Map~ keyed on a type with a
  hand-written implementation is keyed on a different equality from the one ~=~
  answers with.

  This closes when a record's ~Equals~ is emitted as a call to its ~Eq~
  implementation. It is deliberately not papered over by threading ~Eq~
  dictionaries into ~Map~ and ~Set~: that would fix two containers and leave
  interop broken, where emitting ~Equals~ fixes all of it in one place.

- *~=~ on a ~Map~ matches keys by lookup*, so key equality there is the trie's —
  .NET's — while values go through ~Eq~. The same fix closes it.

- *There is no ~derive~.* An implementation over a record's fields is written by
  hand.

- *Tuples reach ~Eq~ through a synthetic constructor key* (~Tuple2~, ~Tuple3~,
  ...); functions and other structural types have no head constructor and so
  cannot have an implementation at all.

** Incidental

- ~clr-eq~, ~clr-equals~ and ~clr-hash~ are builtins private to ~(std eq)~,
  refused by name anywhere else. They are what the primitive implementations are
  written in, and they are shut away against the day a type's ~Equals~ is its
  ~Eq~ implementation — at which point an implementation written with one of
  them calls itself forever.
- ~hash-combine~ is a builtin, for writing an ~eq-hash~ over several fields.
- A trait method's arguments are now all positional, keyword literals included.
  ~(= k #:foo)~ compares a keyword; it is not a call with a keyword argument,
  and no trait declares one.
- ~run_tests.sh~ grew a ~TestFiles/codegen~ stage: each ~;; EXPECT-CS:~ line in
  a fixture is a regex the generated C# has to match.
